一条SQL语句的执行流程是怎样的？
架构高频

Server层 + 存储引擎层

  1. 连接器：建立连接、权限验证。
  2. 查询缓存(8.0已废弃)：命中直接返回。
  3. 分析器：词法分析→语法分析，生成解析树。
  4. 优化器：选择索引、确定连接顺序，生成执行计划。
  5. 执行器：调用存储引擎API，逐行读取→判断→返回。
2
InnoDB 的索引数据结构是什么？为什么用 B+ 树？
索引高频

InnoDB使用B+树作为索引结构。

B+树优势：

  • 矮胖：高度低(3-4层)，IO次数少。
  • 叶子节点有序链表：支持范围查询，全表扫描快。
  • 非叶子节点只存key：一个节点可存更多key，减少IO。

对比：Hash索引只能等值查询；B树非叶子也存数据，节点容量小；跳表不如B+树磁盘友好。

什么是覆盖索引？索引最左前缀原则？
索引优化

覆盖索引：查询列全部在索引中，不需要回表。EXPLAIN中Extra显示Using index。

最左前缀原则：联合索引(a,b,c)时，查询条件必须从最左列开始匹配：

  • ✅ WHERE a=1 (使用索引)
  • ✅ WHERE a=1 AND b=2 (使用索引)
  • ❌ WHERE b=2 (不走索引，缺少a)
  • ✅ WHERE a=1 AND c=3 (部分使用，c不匹配但a匹配)
5
事务的四大特性（ACID）？
事务高频
  • 原子性(Atomicity)：事务要么全执行，要么全不执行。通过undo log实现。
  • 一致性(Consistency)：事务前后数据满足完整性约束。由其他三个特性共同保证。
  • 隔离性(Isolation)：并发事务之间互不影响。通过MVCC+锁实现。
  • 持久性(Durability)：事务提交后数据永久保存。通过redo log实现。

事务的隔离级别有哪些？解决了什么问题？
事务高频
隔离级别脏读不可重复读幻读
读未提交(READ UNCOMMITTED)❌❌❌
读已提交(READ COMMITTED)✅❌❌

💡 MySQL InnoDB默认RR，通过MVCC+Next-Key Lock解决了大部分幻读。

7
MVCC 的实现原理？
MVCC高频

MVCC(多版本并发控制)依赖三个隐藏字段+Read View：

  • DB_TRX_ID：最近修改该行的事务ID。
  • DB_ROLL_PTR：回滚指针，指向undo log中上一个版本。
  • DB_ROW_ID：行ID(无主键时使用)。

Read View判断可见性：通过比较事务ID，判断某版本数据是否对当前事务可见。

💡 RC级别每次快照读生成新Read View；RR级别仅在第一次快照读时生成。

MySQL 的锁有哪些类型？
锁高频

按粒度：

  • 表锁：锁整张表，MyISAM默认，InnoDB也可手动LOCK TABLE。
  • 行锁：InnoDB默认，锁索引记录。

行锁类型(InnoDB)：

  • Record Lock：锁单条索引记录。
  • Gap Lock：锁间隙，防止插入。
  • Next-Key Lock：Record + Gap，InnoDB RR级别默认，解决幻读。

按模式：共享锁(S)、排他锁(X)、意向锁(IS/IX)。

索引失效的场景有哪些？
索引优化
  • 联合索引不满足最左前缀。
  • 索引列使用函数/计算：WHERE YEAR(create_time)=2024
  • 模糊查询前置%：LIKE '%keyword'
  • 隐式类型转换：字符串列用数字查。
  • OR连接非索引列。
  • !=、NOT IN、IS NULL/IS NOT NULL(可能失效)。

💡 使用EXPLAIN查看执行计划，key列为NULL即未走索引。

EXPLAIN 的关键字段含义？
优化实战
  • id：查询序号，越大优先级越高。
  • select_type：SIMPLE/PRIMARY/SUBQUERY/DERIVED等。
  • type：访问类型，从好到差：system>const>eq_ref>ref>range>index>ALL
  • key：实际使用的索引。
  • rows：预估扫描行数。
  • Extra：Using index(覆盖索引)、Using filesort(文件排序-需优化)、Using temporary(临时表-需优化)。

SQL 优化有哪些思路？
优化实战
  1. 索引优化：合理建索引、覆盖索引、避免索引失效。
  2. SQL优化：避免SELECT *、避免大事务、用连接替代子查询。
  3. 表结构：字段选择合适类型、垂直拆分大字段、适当冗余。
  4. 架构：读写分离、分库分表、使用缓存(Redis)。
  5. 慢查询日志：开启slow_query_log，分析慢SQL。

分库分表的方案有哪些？
分库分表架构
  • 垂直分库：按业务拆分数据库(订单库、用户库)。
  • 垂直分表：大表按列拆分，主表存常用字段。
  • 水平分库：按规则(如用户ID)路由到不同库。
  • 水平分表：同一库内按规则分多张表。

分片策略：Hash取模(均匀但扩容难)、Range范围(扩容易但不均匀)、一致性Hash。

💡 中间件：ShardingSphere、MyCat。

MySQL 主从复制的原理？
主从架构

基于binlog的异步复制：

  1. Master：数据变更写入binlog。
  2. Slave I/O线程：连接Master，读取binlog→写入relay log。
  3. Slave SQL线程：读取relay log→重放SQL。

复制模式：STATEMENT(SQL语句)、ROW(行变更-推荐)、MIXED(混合)。

16
什么是SQL注入？如何防止？
安全基础

SQL注入：攻击者通过输入特殊字符篡改SQL语义，执行恶意操作。

防止方式：

  • PreparedStatement预编译（最有效）。
  • 输入校验和过滤。
  • 最小权限原则。
  • ORM框架自动防注入（MyBatis用#{}而非${}）。
17
MySQL 主从复制原理和流程？
主从复制高频

三个线程协作完成：

  1. Master Binlog Dump Thread：主库binlog变化→通知从库。
  2. Slave I/O Thread：连接主库，接收binlog→写入relay log。
  3. Slave SQL Thread：读取relay log→重放SQL→完成复制。

复制模式：STATEMENT（语句）、ROW（行）、MIXED（混合，默认）。ROW模式更安全，但日志量大。

18
主从延迟的原因和解决方案？
主从延迟高频

延迟原因：

  • 从库性能差/配置低。
  • 从库并发写入压力大（大事务、大量DML）。
  • 网络延迟。
  • 主库写并发高。

解决方案：

  • 并行复制（MySQL 5.7+）：slave_parallel_workers。
  • 分库分表降低单库压力。
  • 升级硬件和网络。
  • 读写分离时，核心写后读走主库。
  • 缓存层降低读压力。

MySQL 分库分表方案有哪些？
分库分表高频

垂直拆分：

  • 垂直分库：按业务（用户库、订单库）。
  • 垂直分表：按字段（常用字段和不常用字段分开）。

水平拆分：

  • 范围分片：按时间范围（按月分表）。
  • Hash分片：按key取模（userId%N）。
  • 一致性Hash：减少扩缩容时数据迁移。
  • 地理分片：按地区。

中间件：ShardingSphere（Sharding-JDBC/Proxy）、MyCat。

问题：跨库JOIN、分布式事务、全局ID、数据迁移。

分布式ID 生成方案有哪些？
分布式ID高频
  • UUID：简单但无序，索引性能差。
  • 数据库自增ID：单点瓶颈，适合小规模。
  • 数据库号段模式：一次取一段ID（如Leaf），减少DB访问。
  • Redis incr：性能高，需持久化。
  • Snowflake（雪花算法）：64位，1位符号+41位时间戳+10位机器ID+12位序列号。高性能、趋势递增。
  • 美团Leaf：号段+Snowflake双模式。
  • 百度UidGenerator：基于Snowflake改进。

SQL 执行慢如何排查和优化？
慢查询高频
  1. 开启慢查询日志：slow_query_log，long_query_time设置阈值。
  2. EXPLAIN分析：查看type（ALL最差→index→range→ref→const最好）、key（是否走索引）、rows（扫描行数）、Extra。
  3. 检查索引：是否缺失索引、是否索引失效（函数/类型转换/前导模糊查询）。
  4. SQL改写：避免SELECT *、避免大offset分页、子查询改JOIN。
  5. 表结构优化：字段类型合理、适当冗余减少JOIN。
  6. profiling：SHOW PROFILE查看SQL各阶段耗时。

MySQL 大表如何优化？
大表优化高频
  • 数据归档：历史数据迁移到归档表或冷存储。
  • 分库分表：水平拆分（Sharding）。
  • 读写分离：主库写、从库读。
  • 优化索引：避免冗余索引，使用覆盖索引。
  • 字段优化：IP用INT存（INET_ATON），用更小的数据类型。
  • 垂直拆分：不常用字段拆到扩展表。
  • 分区表：按时间RANGE分区（不过分区表维护成本高）。

深度分页问题如何解决？
分页优化

LIMIT 100000,20 会扫描10万条数据，越往后越慢。

解决方案：

  • 延迟关联：先用覆盖索引查主键，再关联原表。SELECT * FROM t INNER JOIN (SELECT id FROM t LIMIT 100000,20) AS tmp USING(id)
  • 游标分页：用上次查询的最大ID作为条件WHERE id > lastId LIMIT 20，配合索引。
  • ES等搜索引擎：搜索场景走ES。
  • 禁止跳页：只允许上一页/下一页。

MySQL 连接池参数如何配置？
连接池配置

以HikariCP为例：

  • maximumPoolSize：最大连接数，一般=(CPU核心数*2)+磁盘数。
  • minimumIdle：最小空闲连接（默认等于maximumPoolSize）。
  • connectionTimeout：获取连接超时（默认30s）。
  • idleTimeout：空闲超时（10min）。
  • maxLifetime：连接最大存活时间（30min，比数据库wait_timeout短）。
  • leakDetectionThreshold：连接泄漏检测。

💡 连接数公式：connections = ((core_count * 2) + effective_spindle_count)。

25
B+Tree 的插入和查询过程是怎样的？
B+Tree深入

查询：从根节点开始，每层二分查找确定下一层子节点，直到叶子节点。IO次数=树高度。千万级数据只需3-4层。

插入：

  • 找到叶子节点插入。
  • 若节点满（达到页大小/2），则分裂，将中间key提升到父节点。
  • 若父节点满，递归向上分裂。
  • 分裂可能导致树高度增加。

删除：删除后若节点元素少于阈值，从兄弟节点借调或合并。

MySQL 隐式类型转换的坑？
类型转换索引失效
  • 字符串与数字比较：字符串转为数字，索引失效。
  • 规则：字符串和数字→字符串转数字。一方是浮点→都转浮点。日期与数字→看作数字。
-- phone是varchar，有索引
SELECT * FROM t WHERE phone = 13800138000; -- 索引失效！
SELECT * FROM t WHERE phone = '13800138000'; -- 走索引

CHAR 和 VARCHAR 如何选择？TEXT 类型注意事项？
数据类型
  • CHAR：定长，适合固定长度（MD5、手机号、身份证）。查询速度快，不用计算长度。
  • VARCHAR：变长，适合长度波动大的（名字、描述）。节省空间但需存储长度信息。
  • TEXT：大文本，不能有默认值，不能全索引（需指定前缀长度）。
  • BLOB：二进制大对象（图片），建议只存路径。

💡 字段尽量NOT NULL，NULL值会额外占用空间且索引统计不准。

EXPLAIN 中 type 字段有哪些？如何判断效率？
EXPLAIN高频

type表示访问类型，从好到差：

  • const：主键/唯一索引等值查询（最优）。
  • eq_ref：联表查询时用主键/唯一索引关联。
  • ref：非唯一索引等值查询。
  • range：索引范围扫描（BETWEEN、>、<、IN）。
  • index：全索引扫描（比ALL好）。
  • ALL：全表扫描（最差，必须优化）。

Extra关键值：Using index（覆盖索引）→最好；Using filesort（额外排序）→需优化；Using temporary（临时表）→差。

MySQL redo log、undo log、binlog 的区别？
日志高频
日志层级作用格式
redo logInnoDB引擎层崩溃恢复，保证持久性物理日志(页修改)
undo logInnoDB引擎层回滚/MVCC，保证原子性逻辑日志(相反操作)
binlogServer层主从复制/数据恢复逻辑日志(SQL语句/行)

两阶段提交：保证redo log和binlog一致性。prepare→写binlog→commit。

索引下推（ICP）是什么？
索引优化ICP

Index Condition Pushdown（MySQL 5.6+）。将WHERE中部分条件下推到存储引擎层过滤，减少回表次数。

-- 联合索引 (name, age)
SELECT * FROM t WHERE name LIKE '张%' AND age = 25;
-- 没有ICP: 回表取所有name LIKE '张%'的行，再Server层过滤age
-- 有ICP: 存储引擎直接在索引中过滤age=25，减少回表

联合索引匹配原则和索引长度限制？
联合索引优化

索引长度限制：InnoDB单列索引最大767字节（某些字符集达3072字节）。前缀索引可减少长度。

联合索引设计：

  • 区分度高的在前（等值查询字段优先）。
  • 范围查询字段放最后（范围查询后的列不走索引）。
  • 常用查询字段覆盖。
  • ORDER BY / GROUP BY 字段可考虑加在联合索引中。

SQL 注入原理和防范？MyBatis 中 #{} 和 ${} 的区别？
SQL注入安全

SQL注入：拼接SQL时恶意输入如 ' OR 1=1 --。

防范：预编译（PreparedStatement）参数化查询、输入校验过滤、最小权限原则。

MyBatis中：

  • #{}：预编译占位符，安全。SELECT * FROM t WHERE name=#{name} WHERE name=?。
  • ${}：字符串直接替换，有注入风险。仅用于动态表名/列名/ORDER BY等无法预编译的场景，且需白名单校验。
33
子查询和 JOIN 哪个效率高？为什么？
SQL优化

大多数情况JOIN优于子查询，原因：

  • 子查询可能产生临时表和多次查询。
  • MySQL优化器对JOIN的优化更成熟（Nested Loop Join/Block Nested Loop）。
  • NOT IN子查询有NULL陷阱且性能差，应改写为NOT EXISTS或LEFT JOIN ... IS NULL。
  • MySQL 5.6+对子查询优化有所改善（半连接优化），但JOIN仍更可控。

💡 某些场景子查询更清晰（如EXISTS），优先可读性，再考虑性能。

34
分布式事务解决方案有哪些？
分布式事务高频

1. 2PC（两阶段提交）：协调者→prepare（预提交）→所有参与者yes→commit。XA协议，同步阻塞、单点故障。

2. TCC（Try-Confirm-Cancel）：业务层面补偿。Try预留资源→Confirm确认→失败则Cancel释放。Seata支持。

3. 本地消息表：本地事务+消息表+MQ+定时任务补偿。最终一致性。

4. 可靠消息最终一致性：RocketMQ事务消息。

5. 最大努力通知：重复通知+对账。

6. Saga：长事务分解为子事务，正向执行+反向补偿。

35
count(*)、count(1)、count(列名) 的区别？
高频聚合
  • count(*)：统计所有行数（包括NULL），MySQL优化器专门优化，效率最高。
  • count(1)：同count(*)，每行填充1再统计。
  • count(列名)：统计该列非NULL的行数。
  • count(distinct 列)：去重计数。

💡 MyISAM中count(*)没有WHERE条件时O(1)（行数存在表头），InnoDB必须全表/全索引扫描。推荐count(*)。

36
MVCC 读提交(RC)和可重复读(RR)下 ReadView 生成时机有何不同？
MVCC深入
  • RC：每次快照读都生成新的ReadView 能读到其他事务已提交的修改 不可重复读。
  • RR：事务中第一次快照读生成ReadView，后续复用 读到的数据始终一致 可重复读。

💡 这就是为什么RR能避免不可重复读的原因——ReadView复用了。

AUTO_INCREMENT 自增主键的坑？自增ID用完了怎么办？
自增主键
  • 自增ID不一定连续（回滚/删除后不回收）。
  • insert...select等批量插入可能导致ID分配不均。
  • 自增ID用完后INSERT会报主键冲突错误。

Int自增上限：有符号21.47亿，无符号42.94亿。单表日增百万，几年就用完。

解决方案：提前用BIGINT（9.22*10^18）、分库分表、业务主键替代自增。

38
MySQL 中 EXPLAIN 的 Extra 字段 Using filesort 和 Using temporary 是什么意思？
EXPLAIN优化
  • Using filesort：无法用索引排序，需要额外排序操作（内存sort_buffer或磁盘临时文件）。优化方向：让ORDER BY也走索引。
  • Using temporary：创建临时表处理查询（GROUP BY、DISTINCT、UNION）。优化方向：加索引避免临时表。
  • Using index：覆盖索引，无需回表（最好）。
  • Using where：Server层过滤（存储引擎返回后在Server层再过滤）。
  • Using index condition：使用了索引下推（ICP）。

什么是回表？如何避免回表？
回表优化

回表：通过二级索引找到主键→再到聚簇索引中查完整行数据的操作。

-- name有普通索引，非主键
SELECT * FROM t WHERE name='test'; -- 需要回表
SELECT id, name FROM t WHERE name='test'; -- 覆盖索引，无需回表

避免回表：

  • 覆盖索引：索引包含所有查询字段。
  • 减少SELECT *：只查需要的列。
  • 联合索引：把常用查询字段加入联合索引。
  • 索引下推(ICP)：减少不必要的回表。
