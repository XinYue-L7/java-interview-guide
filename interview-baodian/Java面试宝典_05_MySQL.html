数据库的三大范式是什么？
范式设计高频

一句话概括：
三大范式是设计关系型数据库表结构时的三层规范化准则，
用于消除数据冗余、避免插入/更新/删除异常，
依次为第一范式（1NF）、第二范式（2NF）、第三范式（3NF）。

一、三种范式的递进定义：

  1. 1NF（第一范式）—— 字段原子性：
    表中的每一列都不可再分，
    每个字段只能存一个值，不能存集合、数组或复合值。
    反例：字段存“爱好：篮球、足球”或“地址：北京市海淀区”，
    需要按城市维度查询，说明字段可再分，违反 1NF。
  2. 2NF（第二范式）—— 消除部分依赖：
    在满足 1NF 基础上，
    非主键列必须完全依赖主键，
    不能只依赖联合主键的一部分。
    反例：选课表（学号、课程号、课程名、成绩）中，
    课程名只依赖课程号、与学号无关，产生部分依赖，
    应拆出课程表。
  3. 3NF（第三范式）—— 消除传递依赖：
    在满足 2NF 基础上，
    非主键列只能直接依赖主键，
    不能通过其他非主键列间接依赖主键。
    反例：学生表（学号、班级、班主任）中班主任通过班级传递依赖学号，
    应拆成学生表与班级表。

二、作用：

  • 减少数据冗余，节省存储空间。
  • 避免插入异常：主键信息缺失时无法写入不完整数据。
  • 避免更新异常：同一信息只存一处，修改不会漏改或改错。
  • 避免删除异常：删除一条数据不会连带丢失其他有效信息。

三、示例：
把一张“学生选课大表”逐步拆分为学生表、课程表、选课关系表，
使每张表职责单一、只依赖自己的主键，
即完成 1NF → 2NF → 3NF 的规范化。

四、反范式化（反三大范式）—— 高频追问点：
反范式化不是"违背"范式，而是在完成 3NF 设计后，故意引入适度冗余，
用空间换时间、用冗余换 JOIN，让高频查询更快，
它是规范化的反向操作，核心目的是为"读"让路。

（1）为什么需要反范式：

  • 严格按 3NF 拆表后，一次查询常要关联 5~8 张表，
    大表 JOIN 慢、索引难命中，接口延迟高。
  • 互联网场景读多写少，热点数据（订单、商品、用户）被反复查询，
    每次都 JOIN 的成本远大于冗余几列的存储成本。
  • 存储越来越便宜，而 CPU、数据库连接数很贵，
    于是倾向"多存一点、少算一点"。

（2）常见反范式手段：

  • 冗余字段：订单表直接存"用户名、商品名、单价快照"，
    查询时免 JOIN 用户表/商品表，典型如电商订单。
  • 预计算列 / 汇总表：商品表冗余"销量、评论数"，
    或建统计表定时汇总，避免对大表实时 count()。
  • 适度合并表：把经常一起查的 1:1 关系表合并成一张，
    如用户主表与用户扩展资料表合并，减少一次 JOIN。
  • 缓存表 / 物化视图：把复杂报表结果提前算好落表，
    查询直接读结果（MySQL 无原生物化视图，可用定时任务刷新替代）。

（3）反范式的代价（面试主动说出更显全面）：

  • 更新异常回归：冗余字段存多份，修改时需同步多处，
    漏更即数据不一致，如改了用户名、历史订单快照仍是旧名。
  • 写放大与锁竞争：写入/更新成本上升，
    高并发更新同一冗余列时锁等待加剧。
  • 一致性依赖人工：通常靠"事务 + 应用层同步修改 + 对账/补偿任务"兜底。

（4）经验法则：
建模阶段先严格按 3NF 设计，保证数据一致、易维护；
遇到高频慢查询，再针对该场景定向反范式（冗余字段/汇总表），
并在代码与文档里注明冗余来源，方便后人维护。
一句话总结：范式保一致，反范式保性能——先规范、后优化、冗余要记账。

💡 注意事项：
范式越高拆的表越多、查询越要 JOIN，性能反而可能下降，
所以实际开发往往是"先 3NF 建模，再按需反范式"。
无论怎么反范式，都建议用事务或对账机制守住最终一致性。

💡 延伸（名词解释）：
BCNF 是 3NF 的加强版，要求所有决定因素都是候选键，
面试重点掌握 1NF ~ 3NF，加上反范式思想即可。

MySQL 的事务是什么？
事务高频

一句话概括：
事务是数据库执行的最小逻辑工作单元，
由一组 SQL 组成，要么全部成功提交，要么全部失败回滚，
通过 ACID 四大特性保证数据的一致与可靠。

一、事务的定义：
把多条 SQL 打包成一个整体执行，
用 BEGIN / START TRANSACTION 开启，
COMMIT 提交生效，ROLLBACK 回滚撤销。

二、ACID 四大特性：

  • 原子性（Atomicity）：
    事务内操作要么全成功要么全失败，
    由 undo log 实现，回滚时按日志还原数据。
  • 一致性（Consistency）：
    事务执行前后数据都满足业务约束，
    由原子性与隔离性共同保证。
  • 隔离性（Isolation）：
    并发事务之间互不干扰，
    由锁机制与 MVCC 实现。
  • 持久性（Durability）：
    事务提交后数据永久保存，
    由 redo log 实现崩溃恢复。

三、隔离级别（由低到高）：
读未提交（脏读）、读已提交（不可重复读）、
可重复读（幻读，InnoDB 默认）、串行化。

四、事务的实现原理：
undo log 支撑原子性与 MVCC 版本链，
redo log 通过 WAL（先写日志再落盘）保证持久性，
锁 + MVCC 实现不同隔离级别。

五、示例：
转账场景：扣 A 账户 100 元与给 B 账户加 100 元放同一事务，
任一步失败即 ROLLBACK，
不会出现钱已扣但未到账或凭空多钱的状态。

💡 注意事项：
避免大事务与长事务，否则锁占用、undo 膨胀会拖垮性能；
事务内不要包住远程调用、慢查询等无关操作；
详细展开可看本模块“事务的四大特性（ACID）”“事务的隔离级别”“MVCC 的实现原理”等题。

一条SQL语句的执行流程是怎样的？
架构高频

一条SQL的执行分为两层：Server层负责连接、解析、优化、执行，存储引擎层负责实际读写。

  1. 连接器：
    负责建立连接、校验用户名密码、获取并缓存权限信息。
    权限在连接建立时校验，后续操作直接复用。
  2. 查询缓存（8.0已废弃）：
    以SQL文本为key缓存结果集，命中直接返回。
    只要表有更新缓存就失效，命中率极低，8.0已彻底移除。
  3. 分析器：
    词法分析：识别SQL中的关键字、表名、列名。
    语法分析：校验SQL语法是否正确，生成解析树。
  4. 优化器：
    决定走哪个索引、多表连接顺序、是否做子查询改写。
    生成最优执行计划，是SQL快慢的关键环节。
  5. 执行器：
    调用存储引擎API逐行读取数据，Server层做条件判断过滤。
    将满足条件的行返回给客户端。

💡 口诀：连接器→查询缓存→分析器→优化器→执行器。
排查慢SQL时重点看优化器是否选错了索引。

InnoDB 的索引数据结构是什么？为什么用 B+ 树？
索引高频

一、基础概念先讲清楚（面试官追问时的铺垫）：

  • 索引结构：
    数据库为了加速查询而额外维护的"目录"数据。
    本质是以空间换时间，把无序数据变成可快速定位的有序结构。
    常见索引结构：B+ 树、Hash、跳表、倒排索引（全文搜索）。
  • InnoDB：
    MySQL 默认的存储引擎，负责数据的存储与读写。
    支持事务（ACID）、行级锁、外键、崩溃自动恢复；
    采用聚簇索引，表数据本身就是按主键组织的 B+ 树。
  • B+ 树：
    B 树的变体，一种多路平衡查找树，专为磁盘存储设计。
    非叶子节点只存 key 不存数据，一个 16KB 页能容纳上千个 key；
    叶子节点存放所有数据，并按 key 用双向链表串起来，天然有序。
  • 索引数据结构：
    索引底层具体采用哪种数据结构实现。
    B+ 树用于 InnoDB/MyISAM，Hash 用于等值快速查找，
    跳表用于 Redis，倒排索引用于 Elasticsearch 全文搜索。

二、直接结论：
InnoDB 使用 B+ 树作为索引结构，数据全部存放在叶子节点上。

三、为什么选 B+ 树（核心：从磁盘 IO 角度分析）：

  • 矮胖、层高低：
    非叶子节点只存 key 不存数据，一个 16KB 页能容纳上千个 key，扇出极大。
    千万级数据树高仅 3~4 层，查询只需 3~4 次磁盘 IO。
  • 叶子节点形成有序双向链表：
    天然支持范围查询（>、<、BETWEEN、ORDER BY），一次定位后沿链表顺序扫描即可。
    B 树范围查询需要中序遍历，效率低。
  • 叶子节点存数据、内部节点只做路由：
    数据集中连续存放，磁盘读取更高效。
    内部节点纯索引，一个页能放更多 key，树更矮。
  • 查询性能稳定：
    所有查询都必须走到叶子节点，IO 次数固定为树高，无波动。
    而 B 树部分数据在非叶子节点，存在"命中内部节点"和"命中叶子节点"的性能差异。

四、对比其他数据结构：

  • Hash 索引：
    只能等值查询（=、IN），无法支持范围查询、排序、前缀匹配。
    存在哈希冲突，且数据物理无序，无法利用顺序 IO。
  • B 树：
    非叶子节点也存数据，节点能容纳的 key 更少，树更高、IO 更多。
    叶子节点无链表，范围查询需要中序遍历，性能差。
  • 红黑树 / AVL：
    典型内存数据结构，树高约 log₂N，千万级数据需 20+ 层；
    节点在磁盘上分散，每次比较都可能触发 IO，对磁盘极不友好。
  • 跳表：
    Redis 用在内存场景；磁盘场景下指针冗余、空间浪费大，不如 B+ 树按页读取高效。

💡 补充：
主键索引（聚簇索引）的叶子节点存完整行数据，二级索引的叶子节点只存主键值，
因此二级索引查询通常需要回表。

事务的四大特性（ACID）？
事务高频

ACID 是事务的四大特性，InnoDB 分别用不同机制保证：

  • 原子性（Atomicity）：
    事务要么全部成功，要么全部回滚，不存在中间状态。
    通过 undo log 实现：记录反向操作，回滚时逆序执行，恢复到操作前状态。
  • 一致性（Consistency）：
    事务执行前后，数据都必须满足完整性约束（唯一约束、外键、业务规则）。
    一致性是最终目标，由原子性、隔离性、持久性共同保障。
  • 隔离性（Isolation）：
    多个事务并发执行时互不干扰，一个事务看不到其他事务未提交的数据。
    通过 MVCC（读）和锁（写）实现。
  • 持久性（Durability）：
    事务提交后数据永久保存，即使宕机也不丢失。
    通过 redo log 实现：先写日志，崩溃后按日志重放恢复。

💡 面试延伸：redo log 是物理日志解决崩溃恢复，undo log 是逻辑日志解决回滚和MVCC。

事务的隔离级别有哪些？解决了什么问题？
事务高频

一、三个并发问题先定义清楚：

  • 脏读：
    读到其他事务未提交的数据。
    事务A修改数据未提交，事务B读到了修改后的值，若A回滚则B读到的是脏数据。
  • 不可重复读：
    同一事务内两次读取同一行，结果不一致。
    因为两次读取之间，其他事务提交了对该行的修改。
  • 幻读：
    同一事务内两次范围查询，结果集行数不一致。
    因为其他事务插入了满足条件的行，多出来的行如同"幻影"。

二、四种隔离级别（✅表示已解决，❌表示未解决）：

隔离级别脏读不可重复读幻读
读未提交(READ UNCOMMITTED)❌❌❌
读已提交(READ COMMITTED)✅❌❌
可重复读(REPEATABLE READ)✅✅部分解决
串行化(SERIALIZABLE)✅✅✅

三、各隔离级别详解：

  • 读未提交：
    什么都不隔离，可读其他事务未提交的数据，存在脏读。
    并发最高、一致性最差，生产几乎不用。
  • 读已提交：
    只能读已提交的数据，解决脏读。
    两次查询之间其他事务提交了修改，结果可能不同（不可重复读）。
    Oracle / SQL Server 的默认级别。
  • 可重复读：
    同一事务内多次读取结果一致，解决不可重复读。
    标准定义下仍存在幻读，但 InnoDB 通过 MVCC + Next-Key Lock 解决了大部分幻读。
    MySQL InnoDB 的默认级别。
  • 串行化：
    事务完全串行执行，解决所有问题，但性能最差。
    通过强制加锁实现，生产几乎不用。

💡 InnoDB 为什么默认 RR：
历史原因（兼容早期 binlog Statement 格式的主从复制），
且已通过 MVCC + Next-Key Lock 消除大部分幻读，性能优于串行化。

MVCC 的实现原理？
MVCC高频

MVCC（多版本并发控制）核心思想：一份数据保留多个历史版本，读操作沿版本链选择可见版本，实现读不加锁、读写不互斥。

每行记录有三个隐藏字段：

  • DB_TRX_ID：
    最近一次修改该行的事务ID。
  • DB_ROLL_PTR：
    回滚指针，指向 undo log 中的上一个版本，形成版本链。
  • DB_ROW_ID：
    隐藏行ID，无主键时 InnoDB 用它生成聚簇索引。

Read View（读视图）由四部分组成：
m_ids（生成时活跃事务ID列表）、min_trx_id（最小活跃事务ID）、max_trx_id（最大事务ID+1）、creator_trx_id（当前事务ID）。

可见性判断规则：
版本事务ID < min_trx_id → 已提交，可见。
版本事务ID ≥ max_trx_id → 未来事务，不可见。
在 m_ids 中且≠自己 → 未提交，不可见。
在 m_ids 中且=自己 → 可见。

💡 生成时机差异：
RC：每次快照读都生成新的 ReadView，能读到其他事务已提交的修改（不可重复读）。
RR：只在第一次快照读时生成 ReadView 并复用，保证可重复读。

redo log、undo log、binlog 的区别？
日志高频
对比redo logundo logbinlog
层级InnoDB引擎层InnoDB引擎层Server层
作用保证持久性，崩溃恢复保证原子性，事务回滚+MVCC数据恢复、主从复制
记录内容物理日志：页修改逻辑日志：SQL逆操作逻辑日志：SQL语句
写入方式循环写，固定大小随机写追加写

二、redo log 深入：

  • WAL（预写日志）：
    先写日志、再改数据页，避免每次提交都把脏页刷到磁盘。
    崩溃时根据 redo log 重放，恢复已提交事务的数据，保证持久性（D）。
  • 记录内容：
    物理日志，记录"哪个页、哪个偏移量、被改成了什么"。
    只关心物理变更，不关心具体 SQL。
  • 循环写：
    固定大小（innodb_log_file_size），写满后从头部覆盖。
    被覆盖的日志前提是已通过 checkpoint 刷入数据文件。

三、undo log 深入：

  • 作用1：事务回滚。
    记录修改前的旧值，回滚时执行逆操作恢复，保证原子性（A）。
  • 作用2：MVCC 版本链。
    配合行记录的 DB_ROLL_PTR 找到历史版本，实现快照读不加锁。
  • 记录内容：
    逻辑日志，记录 SQL 的逆操作（INSERT→DELETE，UPDATE→反向 UPDATE）。

四、binlog 深入：

  • 作用：
    主从复制、基于时间点恢复数据。
  • 记录格式：
    Statement（SQL语句）、Row（行变更）、Mixed（混合）。
    Row 模式最安全可靠，生产推荐。
  • 追加写：
    文件写满滚动生成新文件，不会覆盖旧日志。

五、两阶段提交（保证 redo log 与 binlog 一致）：

1. 事务提交时先写 redo log，标记为 prepare 状态。
2. 再写 binlog。
3. 最后将 redo log 改为 commit 状态。

崩溃时判断：
redo log 为 prepare 且 binlog 完整 → 事务生效；
redo log 为 prepare 但 binlog 缺失 → 事务回滚。
避免出现"redo log 有、binlog 无"或反之，防止主从数据不一致。

六、前置概念（名词解释）：

  • redo log（重做日志）：
    InnoDB 引擎层的物理日志，记录数据页的物理修改（哪个页、哪个偏移量改成了什么），
    用于崩溃恢复、保证已提交事务的持久性（D），固定大小循环写。
  • undo log（回滚日志）：
    InnoDB 引擎层的逻辑日志，记录修改前的旧值（SQL 的逆操作），
    用于事务回滚保证原子性（A），并配合 DB_ROLL_PTR 形成 MVCC 版本链。
  • binlog（二进制日志）：
    MySQL Server 层的逻辑日志，记录 SQL 语句或行变更，
    用于主从复制和基于时间点的数据恢复，追加写、不覆盖。
  • WAL（Write-Ahead Logging，预写日志）：
    "先写日志、再改数据页"的原则，
    崩溃时用日志重放恢复，避免每次提交都把脏页刷盘。
  • 物理日志 vs 逻辑日志：
    物理日志记录"哪个页、哪个位置被改成了什么"，与具体 SQL 无关；
    逻辑日志记录操作语义（如 INSERT 的逆操作 DELETE），便于回滚和复制。
  • 两阶段提交（2PC）：
    一个协调者分 prepare（准备）和 commit（提交）两阶段统一提交多个参与者，
    在这里用于保证 redo log 与 binlog 的一致性。
  • MVCC（多版本并发控制）：
    通过 undo log 保存历史版本，配合隐藏列 DB_ROLL_PTR 串联成版本链，
    让读操作读快照不加锁、读写互不阻塞。
  • checkpoint（检查点）：
    把内存中已修改的脏页刷回磁盘并推进日志位点的机制，
    刷盘完成后 redo log 对应部分才允许被覆盖。
  • 主从复制：
    主库将 binlog 发送给从库并重放，
    使从库数据与主库一致，用于读写分离和高可用。
  • 原子性（A）/ 持久性（D）：
    原子性——事务内所有操作要么全部成功、要么全部回滚；
    持久性——事务提交后数据不因崩溃而丢失。

MySQL 的锁有哪些类型？
锁高频

一、分类总览（先总后分）：
MySQL 的锁主要按 4 个维度分类，共 12 种：

  • 按粒度分类（2 种）：
    表锁、行锁。
  • 按模式分类（3 种）：
    共享锁 S、排他锁 X、意向锁 IS/IX。
  • 行锁的具体类型（4 种）：
    Record Lock、Gap Lock、Next-Key Lock、插入意向锁。
  • 其他分类维度（3 种）：
    悲观/乐观锁、自增锁、元数据锁 MDL。

二、各分类详解：

  1. 按粒度分类（2 种）：
    • 表锁：
      锁整张表，开销小、并发低。
      MyISAM 默认使用；InnoDB 的 DDL 通过 MDL（元数据锁）保护表结构。
    • 行锁：
      InnoDB 默认，锁粒度最小、并发最高。
      行锁基于索引实现，若条件未走索引则可能退化为全表扫描加锁。
  2. 按模式分类（3 种）：
    • 共享锁 S：
      读锁，多个事务可同时持有，但阻止其他事务加 X 锁。
      SELECT ... LOCK IN SHARE MODE。
    • 排他锁 X：
      写锁，与任何锁都互斥。
      SELECT ... FOR UPDATE / UPDATE / DELETE。
    • 意向锁 IS/IX：
      表级标记，表示事务准备对表内行加锁，
      用于快速判断表锁与行锁是否冲突，无需逐行检查。
  3. 行锁的具体类型（InnoDB，4 种）：
    • Record Lock：
      记录锁，锁单条索引记录。
    • Gap Lock：
      间隙锁，锁索引记录之间的间隙，阻止其他事务在间隙插入。
    • Next-Key Lock：
      Record + Gap 组合，左开右闭区间。
      InnoDB RR 级别默认加锁方式，解决幻读。
    • 插入意向锁：
      插入前先获取，与 Gap Lock 互斥，控制插入位置。
  4. 其他分类维度（3 种）：
    • 悲观锁 / 乐观锁：
      悲观锁：SELECT ... FOR UPDATE，先锁后操作；
      乐观锁：版本号 / CAS，冲突时重试，适合读多写少。
    • 自增锁：
      控制自增列并发插入的连续性，innodb_autoinc_lock_mode 可配置。
    • 元数据锁 MDL：
      保护表结构定义，DDL 与 DML 之间互斥。

💡 快照读 vs 当前读：
快照读（普通 SELECT）不加锁，走 MVCC，并发高；
当前读（FOR UPDATE / UPDATE / DELETE）加行锁。
两个事务同时更新同一行会产生锁等待，甚至死锁。

索引失效的场景有哪些？
索引优化

一、最常见失效场景（面试必答）：

  • 不满足最左前缀：
    联合索引 (a,b,c)，跳过最左列直接查 b 或 c。
    例：WHERE b=1（a 未使用）。
  • 索引列使用函数或计算：
    例：WHERE YEAR(create_time)=2024、WHERE id+1=10。
    索引存的是原始值，无法匹配函数/计算后的结果。
  • 隐式类型转换：
    例：WHERE phone=13800138000（phone 是 varchar）。
    类型转换作用于索引列导致失效，建议改为 '13800138000'。
  • 模糊匹配前置 %：
    例：LIKE '%keyword'、LIKE '%key%'。
    只有 'keyword%'（前缀匹配）能走索引。
  • OR 连接非索引列：
    例：WHERE a=1 OR b=2（b 无索引）。
    MySQL 无法同时走索引，整体退化为全表扫描。

二、其他易踩坑场景：

  • 范围查询导致后续列失效：
    联合索引 (a,b)，WHERE a>10 AND b=1 时 b 列失效。
    设计时把范围查询列放最后。
  • !=、<>、NOT IN、NOT LIKE：
    MySQL 认为选择性低、范围大，一般走全表扫描。
  • IS NULL / IS NOT NULL：
    当非空值占比很大时，优化器可能放弃索引。
  • 关联列字符集不一致：
    JOIN 两表关联列字符集不同（utf8 vs utf8mb4），无法使用索引。
  • 优化器主动放弃：
    索引区分度太低（如性别列），优化器认为全表扫描更快而不用索引。

💡 排查方法：
EXPLAIN 看 key 列，为 NULL 即未走索引；
关注 type 字段，尽量达到 ref 或 range 级别。

EXPLAIN 的关键字段含义？
优化实战

核心字段逐一说明：

  • id：
    SELECT 的序号，id 越大优先级越高、越先执行；
    id 相同则按从上到下顺序执行。
  • select_type：
    查询类型：
    SIMPLE（简单查询）、PRIMARY（最外层）、SUBQUERY（子查询）、DERIVED（派生表）、UNION（联合查询）、UNION RESULT（联合结果）。
  • table：
    当前访问的表名（含别名）。
  • type：
    访问类型，从好到差：
    system > const > eq_ref > ref > range > index > ALL。
    const：主键/唯一键等值查询；eq_ref：连接时被驱动表用唯一索引；
    ref：普通索引等值；range：范围查询；index：扫全索引；
    ALL：全表扫描，需要优化。
  • possible_keys：
    优化器可能用到的索引。
  • key：
    实际使用的索引，为 NULL 表示未走索引。
  • key_len：
    索引使用的字节数，越小越好。
    可用于判断联合索引实际用到了几列。
  • ref：
    索引匹配的列或常量。
  • rows：
    预估扫描行数，越小越好。
  • Extra：
    额外信息：
    Using index：覆盖索引，最优；
    Using index condition：索引下推 ICP；
    Using filesort：需额外排序，应优化；
    Using temporary：使用临时表，应优化。

💡 实战排查口诀：
type 至少达到 range，最好 ref 及以上；
key 不能为 NULL；
Extra 避免出现 filesort 和 temporary。

SQL 优化有哪些思路？
优化实战

一、先定位慢 SQL：

  • 开启慢查询日志 slow_query_log，设置 long_query_time 阈值。
  • 对慢 SQL 用 EXPLAIN 分析执行计划，确认是否走索引。

二、索引层面：

  • 合理建索引：
    高频 WHERE、JOIN、ORDER BY 列建索引，区分度高的列优先。
  • 覆盖索引：
    查询列全部包含在索引中，避免回表（Extra 显示 Using index）。
  • 避免索引失效：
    函数/计算、隐式类型转换、前置 %、OR 连接非索引列等。
  • 联合索引注意列顺序：
    遵守最左前缀，范围查询列放最后。

三、SQL 写法层面：

  • 避免 SELECT *：
    只取需要的列，减少回表与网络传输。
  • 用 JOIN 替代子查询：
    子查询可能产生临时表，性能更差。
  • 大分页优化：
    LIMIT 100000,10 改为延迟关联（先查 id 再回表）
    或游标方式：WHERE id > 上次最大值 ORDER BY id LIMIT 10。
  • 避免大事务：
    分批处理，减少锁持有时间，降低死锁概率。
  • 批量操作：
    批量 insert / 批量 update，避免逐条提交。

四、表结构层面：

  • 字段选择合适类型，能用 int 不用 varchar，能用 varchar(20) 不用 varchar(200)。
  • 大字段 / 低频字段垂直拆分。
  • 适当冗余、反范式化，减少 JOIN。
  • 大表考虑分区或归档历史数据。

五、架构层面：

  • 读写分离：主库写、从库读。
  • 分库分表：单表数据量过大时拆分。
  • 引入缓存：热点数据放 Redis，扛住读压力。

💡 优化顺序建议：
先看 SQL 写法和索引（成本最低、收益最大），
再看表结构，最后才考虑读写分离 / 分库分表等架构手段。

分库分表的方案有哪些？
分库分表架构
  • 垂直分库：
    按业务域拆分数据库（订单库、用户库、商品库），解决单库容量与连接数瓶颈。
    缺点：跨库事务、跨库JOIN变复杂。
  • 垂直分表：
    把大表按列拆分，主表存高频字段，扩展表存大字段/低频字段。
    适合字段多、部分字段大且访问少的情况。
  • 水平分库：
    同一张表的数据按分片键路由到多个库，每个库存一部分。
    解决单库数据量过大、写入吞吐瓶颈。
  • 水平分表：
    同一库内按规则拆成多张结构相同的表。
    解决单表数据量过大导致的索引变深、查询变慢。

分片策略对比：

  • Hash取模：
    数据分布均匀，但扩容时取模基数变化需大量迁移数据（可用一致性Hash缓解）。
  • Range范围：
    按时间/ID区间分片，扩容简单，但热点集中在最新区间。
  • 一致性Hash：
    扩容时只影响少量数据迁移，适合节点增减频繁的场景。

💡 中间件：
ShardingSphere（推荐，功能全）、MyCat。
分库分表后还需处理：分布式ID、跨库查询、跨库事务、全局表/广播表。

MyISAM 和 InnoDB 的区别？
引擎基础

一、先定义清楚：

  • MyISAM：
    MySQL 早期（5.5 之前）默认存储引擎。
    使用表锁 + 非聚集索引，不支持事务、外键、崩溃恢复，
    但读取速度快、占用空间小，适合只读报表、日志类低并发场景。
  • InnoDB：
    MySQL 5.5+ 默认存储引擎。
    支持事务（ACID）、行级锁、外键、崩溃自动恢复，
    使用聚簇索引组织数据，适合高并发读写的事务型业务。

二、对比表格：

外键不支持支持

主键可无主键必须有，无则自动生成隐藏主键

三、关键差异展开讲：

  • 锁粒度：
    MyISAM 只支持表锁，写操作锁全表，并发写性能差；
    InnoDB 支持行锁，配合 MVCC 读写不互斥，高并发下性能好。
  • 索引结构：
    MyISAM 是非聚集索引，索引树叶子节点存数据行地址指针；
    InnoDB 是聚簇索引，主键索引叶子节点直接存整行数据，二级索引叶子节点存主键值。
  • 事务与外键：
    MyISAM 不支持事务和外键；
    InnoDB 支持 ACID 事务、外键约束，是业务系统的前提。
  • 崩溃恢复：
    MyISAM 崩溃后需要修复表（REPAIR TABLE），可能丢数据；
    InnoDB 通过 redo log 自动恢复，保证持久性。

💡 为什么 MySQL 默认用 InnoDB：
支持事务、行锁、外键、崩溃恢复，适合绝大多数业务场景。
MyISAM 仅适合只读报表、日志表、数据仓库等低并发场景，
MySQL 5.7 之后 MyISAM 已逐渐边缘化。

MySQL 主从复制的原理？
主从架构

一、什么是主从复制：
将主库（Master）的数据变更实时同步到一台或多台从库（Slave）的机制。
主库负责写，从库负责读，是读写分离和数据备份的基础。

二、为什么要主从复制（目的）：

  • 读写分离：
    主库写、从库读，分摊读压力，提升系统并发能力。
  • 高可用：
    主库宕机后从库可提升为新主库，减少业务中断。
  • 数据安全：
    从库作为实时备份，防止误操作或单点故障导致数据丢失。
  • 离线分析：
    报表、统计等重查询放到从库执行，不影响主库性能。

三、原理（基于 binlog，三个线程协作）：

  1. Master Binlog Dump 线程：
    主库数据变更写入 binlog 后，该线程将 binlog 事件推送给从库。
  2. Slave I/O 线程：
    连接到主库接收 binlog 事件，写入从库的 relay log（中继日志），并记录复制位点。
  3. Slave SQL 线程：
    读取 relay log，按顺序重放 SQL，将变更应用到从库。

四、复制模式（binlog 记录格式）：

  • STATEMENT（语句模式）：
    记录 SQL 语句，日志量小；
    但函数、存储过程等场景可能导致主从不一致。
  • ROW（行模式）：
    记录行级变更，最安全一致，生产推荐；
    缺点是日志量大。
  • MIXED（混合模式）：
    MySQL 默认，两种方式自动切换。

五、同步方式：

  • 异步复制：
    主库提交不等从库，延迟最低；
    但主库宕机时可能丢失已提交的数据。
  • 半同步复制（semi-sync）：
    至少一个从库收到并确认 binlog 后主库才提交，安全性提升。
  • 全同步复制：
    所有从库确认后才提交，最安全但性能最差。

六、注意事项：

  • 主从延迟是常态：
    写后立即读等强一致场景要走主库，或等待从库同步完成。
  • binlog 格式：
    推荐 ROW 模式，并设置 binlog_row_image=FULL 保证一致性。
  • 复制账号最小权限：
    只授予 REPLICATION SLAVE 权限，不用 root。
  • 每张表都要有主键：
    否则 ROW 模式复制效率极低，甚至无法正确同步。
  • 从库设置只读：
    read_only=1，避免从库被误写导致主从不一致。
  • 控制大事务：
    大事务会放大主从延迟，应拆分为小事务分批执行。
  • 监控延迟：
    通过 Seconds_Behind_Master 监控，延迟过大及时告警处理。

什么是SQL注入？如何防止？
安全基础

一、什么是 SQL 注入：

攻击者把恶意 SQL 片段拼进用户输入，改变原 SQL 的语义，执行未授权的操作。

经典示例：
登录校验：SELECT * FROM user WHERE name='xxx' AND pwd='123'；
输入 ' OR '1'='1 后拼成：
WHERE name='' OR '1'='1' AND pwd='123'，条件恒真，直接绕过登录。

二、危害：
拖库（读取全部数据）、篡改/删除数据、绕过认证、
甚至通过存储过程或 UDF 执行系统命令，拿到服务器权限。

三、防御手段（面试重点）：

  • PreparedStatement 预编译（最有效）：
    参数与 SQL 分离，SQL 先由数据库引擎编译，
    用户输入只作为参数值传递，无法改变 SQL 语义。
  • MyBatis 用 #{} 不用 ${}：
    #{} 是预编译占位符；${} 直接拼接字符串，存在注入风险。
    只有表名/列名等动态场景才用 ${}，且必须白名单校验。
  • 输入校验与过滤：
    白名单校验、长度限制、过滤特殊字符（'、"、;、--）。
  • 最小权限原则：
    应用账号只授予必要的库表权限，不用 root，
    即使被注入也无法造成更大破坏。
  • 隐藏错误信息：
    关闭详细 SQL 报错回显，避免攻击者利用报错判断注入点。
  • WAF / 数据库防火墙：
    拦截常见注入特征，作为纵深防御的最后一道防线。

💡 一句话总结：
核心是"参数与 SQL 分离"——预编译 + 参数化查询；
输入校验、权限控制、WAF 等都属于纵深防御。

MySQL 主从复制原理和流程？
主从复制高频

一、复制流程（三个线程协作）：

  1. Master Binlog Dump Thread：
    主库事务提交写 binlog 后，将 binlog 事件发送给从库。
  2. Slave I/O Thread：
    连接主库拉取 binlog，写入本机 relay log，并记录复制位点（file+pos）。
  3. Slave SQL Thread：
    顺序读取 relay log 并重放，将变更应用到从库，完成数据同步。

二、binlog 记录格式：

  • STATEMENT（语句模式）：
    记录 SQL 语句，日志量小；
    函数、存储过程等场景可能导致主从不一致。
  • ROW（行模式）：
    记录行级变更，最安全一致，生产推荐；
    缺点是日志量较大。
  • MIXED（混合模式）：
    MySQL 默认，两种方式自动切换。

三、复制架构：

  • 一主一从：
    基础架构，读写分离入门。
  • 一主多从：
    多个从库分摊读压力，提升读吞吐。
  • 级联复制：
    从库再挂从库，减轻主库推送压力；
    但链路越长延迟越大。
  • 双主互备：
    互为主从，配合 keepalived 实现高可用自动切换。

四、GTID 复制：
5.7+ 引入 GTID（全局事务标识），每个事务有全局唯一 ID；
主从切换时无需手动定位 binlog 位点，配置更简单可靠。

五、复制方式：
异步复制：延迟最低，但主库宕机可能丢数据；
半同步复制：至少一个从库确认 binlog 才提交；
全同步复制：所有从库确认才提交，性能最差。

💡 注意事项：
每张表要有主键，从库设置 read_only=1；
推荐 ROW 模式 + GTID，并通过 Seconds_Behind_Master 监控延迟。

主从延迟的原因和解决方案？
主从延迟高频

一、什么是主从延迟：
主库写完数据，从库没有及时跟上，从库数据落后于主库的现象。
产生窗口 = 主库写入完成到从库重放完成之间的时间差，
可通过 SHOW SLAVE STATUS 的 Seconds_Behind_Master 量化。

二、延迟产生的原因：

  • 从库单线程重放：
    历史版本从库只有一个 SQL 线程顺序重放 binlog，
    主库写入越快，从库越跟不上。
  • 大事务：
    主库一个大事务的 binlog 到从库后需整体重放，
    期间其他事务只能排队等待。
  • 从库锁竞争：
    从库自身的查询（如报表）占用锁，阻塞 SQL 线程。
  • 从库硬件差：
    磁盘、CPU、内存配置低于主库。
  • 网络延迟：
    主从跨机房/跨地域时，I/O 线程拉取 binlog 变慢。
  • 主库写并发过高：
    产生的 binlog 量超过从库消费能力。

三、解决方案：

  • 并行复制（5.7+）：
    配置 slave_parallel_workers，按库/按事务并行重放，提升从库吞吐。
  • 拆分大事务：
    大批量 DML 分批执行，减小单事务 binlog 体积。
  • 读写分离策略：
    核心写后读（强一致）走主库；
    从库只承担可容忍延迟的读。
  • 缓存降读：
    热点数据放 Redis，减少打到从库的读压力。
  • 架构优化：
    分库分表分散写入压力；
    从库提升硬件配置，使用 SSD。
  • 监控与告警：
    SHOW SLAVE STATUS 查看 Seconds_Behind_Master，延迟超标及时告警。

💡 完整业务案例（电商订单系统）：

场景：
订单系统采用主写从读架构，某天晚上运营在后台批量执行修改操作。

触发 SQL：
UPDATE orders SET status=5 WHERE status=2；
一次性更新 500 万行，事务耗时 15 分钟才提交，binlog 产生约 1GB。

现象：
主库一切正常，但前端订单列表（读从库）一直显示旧状态，用户投诉数据不刷新；
执行 SHOW SLAVE STATUS\G 查看：
Slave_IO_Running: Yes
Slave_SQL_Running: Yes
Seconds_Behind_Master: 900
SQL 线程正常但已落后主库 900 秒（15 分钟）。

原因分析：
1. 大事务 binlog 体积大，I/O 线程拉取耗时；
2. 从库 SQL 线程单线程重放 500 万行 UPDATE，耗时极长；
3. 期间主库新产生的事务全部在从库排队，延迟持续累积。

解决方案：
1. 避免一次性大事务：按 id 分批 UPDATE，每次 5 万行，提交后 sleep(1)；
2. 开启并行复制：slave_parallel_workers=4、slave_parallel_type=LOGICAL_CLOCK；
3. 强一致读取走主库：支付回调、下单结果等核心场景路由到主库；
4. 热点数据加 Redis 缓存，短期读到旧值也可接受。

最终结果：
从库延迟从 15 分钟降到 3 秒以内，业务恢复正常。

💡 判断延迟命令：
SHOW SLAVE STATUS 的 Seconds_Behind_Master 字段，
为 0 表示无延迟，数值越大表示延迟越严重。

MySQL 分库分表方案有哪些？
分库分表高频

一、什么是分库分表：
将原本存储在单库单表的数据拆分到多个数据库和表中，
解决单库性能瓶颈（连接数、磁盘 IO、CPU）和单表数据量过大（查询慢、索引膨胀）的问题。

二、为什么要分库分表：

  • 单库性能瓶颈：
    连接数上限（默认 151）、CPU 和磁盘 IO 达到上限，
    无法通过升级硬件线性扩展。
  • 单表数据量过大：
    超过千万级后查询变慢、索引维护成本高、DDL 锁表时间极长。
  • 高并发写入：
    单库写压力大，拆分到多库可分散写入。

三、拆分方式：

垂直拆分：

  • 垂直分库：
    按业务模块拆分，如用户库、订单库、商品库。
    不同业务独立部署，互不干扰。
  • 垂直分表：
    按字段拆分，把常用字段（id、name、status）和不常用字段（详情、图片、备注）分开。
    减少行宽度，提升缓存命中率。

水平拆分：

  • 范围分片：
    按时间范围拆分，如按月分表 orders_202401、orders_202402。
    优点：扩容简单，新月份直接建新表；
    缺点：数据分布不均，热点集中在新表。
  • Hash 分片：
    按分片键取模，如 userId % 4 分到 4 张表。
    优点：数据分布均匀；
    缺点：扩容需迁移大量数据。
  • 一致性 Hash：
    在 Hash 基础上引入虚拟节点，扩缩容时只影响相邻节点，
    减少数据迁移量，适合动态扩缩容场景。
  • 地理分片：
    按地区拆分，如华东库、华北库，
    适合按地域就近访问的业务。

四、分片键选择：
选择高频查询条件字段作为分片键，如用户表选 userId、订单表选 userId 或 orderId。
避免使用自增 ID 作为分片键（热点集中）。

五、中间件：

  • ShardingSphere：
    Java 生态主流，支持 Sharding-JDBC（应用层）和 Sharding-Proxy（代理层）两种模式。
  • MyCat：
    基于 MySQL 协议的数据库中间件，对应用透明。

六、带来的问题：

  • 跨库 JOIN：
    分库后无法直接 JOIN，需先查单库再聚合，或冗余字段到同库。
  • 分布式事务：
    跨库操作需引入 Seata、TCC、Saga 等分布式事务方案。
  • 全局 ID：
    自增 ID 不唯一，需改用雪花算法、号段模式等分布式 ID 方案。
  • 数据迁移：
    扩容或调整分片规则时，需双写 + 数据迁移 + 校验。
  • 排序分页：
    跨库 ORDER BY / LIMIT 需各库分别查询后内存归并，性能差。

💡 完整业务示例：

场景：
电商订单表 orders 数据量达 5000 万，单表查询慢，写入压力大。

方案：
1. 先垂直分表：把订单基本信息和订单详情拆成两张表；
2. 再水平分表：按 userId % 8 拆成 8 张表；
3. 分片键选 userId，因为 99% 查询都带 userId 条件；
4. 通过 Sharding-JDBC 配置分片规则，应用层无感知；
5. 订单 ID 改用雪花算法，保证全局唯一。

结果：
单表数据量降到 600 万左右，查询响应从 2 秒降到 50 毫秒。

分布式ID 生成方案有哪些？
分布式ID高频

一、什么是分布式 ID：
在分布式、分库分表场景下，需要一种全局唯一、高性能、趋势递增的 ID 生成方案。
数据库自增 ID 在分库后无法保证唯一，因此需要专门的分布式 ID 方案。

二、为什么需要分布式 ID：

  • 全局唯一：
    分库分表后各库独立自增，ID 必然重复。
  • 高性能：
    ID 生成不能成为系统瓶颈。
  • 趋势递增：
    有序 ID 有利于 B+ 树索引顺序写入，避免随机 IO 和页分裂。

三、主流方案对比表：

方案原理优点缺点
UUID全局唯一字符串无需依赖、绝对唯一无序、长度大、索引性能差
数据库自增AUTO_INCREMENT实现简单、有序单点瓶颈、分库后冲突
号段模式一次取一段，内存分配DB 压力小、性能高依赖 DB，号段用完需拉取
Redis incrRedis 原子自增性能高依赖 Redis 可用性和持久化
雪花算法时间戳+机器+序列高性能、趋势递增依赖时钟，回拨会重复
美团 Leaf号段+雪花双模式方案成熟、可降级需部署独立组件

四、各方案详解：

  • UUID：
    生成简单，全局绝对唯一；
    但 36 位字符串无序且长，作为主键会导致 B+ 树随机插入、页分裂严重，索引性能差。
  • 数据库自增 ID：
    实现最简单，天然有序；
    单库单点瓶颈，分库分表后 ID 冲突，仅适合小规模系统。
  • 数据库号段模式：
    每次从数据库取一段 ID（如 1000 个）缓存到内存，分配完再取；
    大幅减少数据库访问次数，性能好，美团 Leaf 号段模式即此原理。
  • Redis incr：
    利用 INCR / INCRBY 原子自增，性能高；
    但依赖 Redis 可用性，需要开启持久化防止 ID 丢失。
  • Snowflake（雪花算法）：
    64 位组成：1 位符号 + 41 位时间戳 + 10 位机器 ID + 12 位序列号；
    单机每秒可生成约 409.6 万个 ID，性能极高且趋势递增；
    缺点：依赖服务器时钟，时钟回拨会导致 ID 重复。
  • 美团 Leaf：
    号段 + 雪花双模式，可自动降级切换，
    并解决了雪花算法的时钟回拨问题。
  • 百度 UidGenerator：
    基于雪花算法改进，用 RingBuffer 预缓存 UID，性能更高。

💡 选择建议：
中小规模：数据库号段模式足够；
高并发大厂：Snowflake 或美团 Leaf；
可接受无序且追求绝对唯一：UUID（或 UUID 转 BIGINT）。

慢查询高频

  1. 开启慢查询日志：

    profiling=ON 后查看 SQL 各阶段耗时，

  • 表结构层面：

  • 架构层面：
    大表分库分表、读写分离、引入缓存。

💡 完整排查流程示例：
接口变慢 → 查慢查询日志找到 SQL → EXPLAIN 发现 type=ALL 全表扫描 →
确认缺索引 → 添加联合索引 → 响应时间从 3 秒降到 30 毫秒。

MySQL 大表如何优化？
大表优化高频

一、为什么大表需要优化：
单表数据量过大（如超千万级）会导致：
查询变慢、索引膨胀、DDL 锁表时间长、备份恢复慢、内存命中率下降。

二、优化手段：

  • 数据归档：
    历史数据迁移到归档表或冷存储，热表只保留近期数据。
    例：订单只保留近 3 个月，更早的按月归档。
  • 分库分表：
    水平拆分，把单表数据量控制在百万到千万级。
  • 读写分离：
    主库写、从库读，分摊读压力。
  • 优化索引：
    删除冗余索引、使用覆盖索引、避免无效索引。
  • 字段优化：
    IP 用 INT 存（INET_ATON/INET_NTOA）、
    使用更小的数据类型、字段尽量 NOT NULL。
  • 垂直拆分：
    不常用字段拆到扩展表，减少行宽度。
  • 分区表：
    按时间 RANGE 分区，注意分区表维护成本高、
    分区键必须出现在 WHERE 中才有效。

💡 优化顺序建议：
先做归档 + 索引 + 字段优化（成本最低），
再考虑垂直拆分，最后才分库分表（成本高、复杂度大）。

深度分页问题如何解决？
分页优化

一、问题本质：
LIMIT 100000,20 需要先扫描前 10 万条再丢弃，
偏移量越大，扫描的数据越多，查询越慢。

二、解决方案：

  • 延迟关联（核心）：
    先用覆盖索引查主键，再回原表取完整数据。
    SELECT * FROM t INNER JOIN (SELECT id FROM t ORDER BY id LIMIT 100000,20) AS tmp USING(id)
  • 游标分页：
    用上次查询的最大 ID 作为条件，配合索引。
    WHERE id > lastId ORDER BY id LIMIT 20
    翻页时带上游标，性能恒定，适合 App 场景。
  • 禁止跳页：
    只允许上一页/下一页（游标式），不允许随意跳页。
  • 搜索引擎：
    搜索类复杂场景走 ES，不直接查数据库。

💡 对比示例：
传统 LIMIT 100000,20：扫描 10 万行，耗时约 1.5 秒；
游标 WHERE id > 100000 LIMIT 20：仅扫描 20 行，耗时约 10 毫秒。

MySQL 连接池参数如何配置？
连接池配置

一、为什么要用连接池：
数据库连接创建/销毁开销大（TCP 握手 + 认证 + 资源分配），
连接池复用连接，显著降低开销并限制并发。

二、核心参数（以 HikariCP 为例）：

  • maximumPoolSize：
    最大连接数，常用公式：(CPU 核心数 * 2) + 磁盘数。
    过大会导致数据库端连接堆积，过小则请求排队等待。
  • minimumIdle：
    最小空闲连接数，默认等于 maximumPoolSize。
    适当调小可减少空闲资源占用。
  • connectionTimeout：
    获取连接的超时时间，默认 30s。
    过小会误杀慢请求，过大会拖慢故障发现。
  • idleTimeout：
    空闲连接存活时间，默认 10 分钟。
    仅当 minimumIdle 小于 maximumPoolSize 时生效。
  • maxLifetime：
    连接最大存活时间，默认 30 分钟。
    必须小于数据库 wait_timeout，防止连接被服务端回收后仍被复用。
  • leakDetectionThreshold：
    连接泄漏检测阈值，超过则打印告警日志，
    帮助定位未归还连接（程序 bug）。

三、配置建议：
maximumPoolSize 一般 10~50，根据并发和数据库配置调整；
maxLifetime 建议设 29 分钟（数据库 wait_timeout 为 30 分钟）；
禁止超过数据库 max_connections，否则应用启动即报连接耗尽。

B+Tree 的插入和查询过程是怎样的？
B+Tree深入

一、查询过程：

1. 从根节点出发，每层通过二分查找确定下一层子节点；
2. 逐层下探，直到叶子节点；
3. 在叶子节点中找到目标记录（聚簇索引）或指针。

IO 次数 = 树的高度，千万级数据树高仅 3~4 层，即 3~4 次磁盘 IO。

二、插入过程：

  1. 先定位到目标叶子节点，按 key 顺序插入记录。
  2. 若叶子节点已满，执行分裂：
    一半记录拆到新叶子节点，中间 key 提升到父节点。
  3. 若父节点也满，递归向上分裂，直到根节点。
  4. 分裂发生在根节点时，树高度 +1。

三、删除过程：

删除记录后，若节点元素数低于阈值（约半满），
先尝试从兄弟节点借调元素；
兄弟节点也不足时与兄弟节点合并，减少层数。

💡 完整示例：
查询 id=85：根节点 [50] → 右子树 [60,80] → 叶子节点 [85,90]，共 3 次磁盘 IO；
插入 id=95：先查找到对应叶子节点 → 未满直接插入 → 完成。

MySQL 隐式类型转换的坑？
类型转换索引失效

一、什么是隐式类型转换：
SQL 中字段类型与传入值类型不一致时，MySQL 会自动进行类型转换。
转换若作用于索引列，B+ 树无法按原值定位，只能全表扫描，索引失效。

二、转换规则：
字符串和数字比较 → 字符串转数字；
一方是浮点 → 双方转浮点；
日期与数字 → 按数字处理。

三、核心坑：
索引列参与类型转换或函数运算时，索引失效、退化为全表扫描。

-- phone是varchar，有索引
SELECT * FROM t WHERE phone = 13800138000; -- 数字 → phone被转成数字，索引失效！
SELECT * FROM t WHERE phone = '13800138000'; -- 加引号，正常走索引
SELECT * FROM t WHERE id = '1'; -- 主键是数字，字符串'1'转数字，仍可走索引

四、解决方法：
1. 显式转换：CAST(phone AS CHAR)；
2. 加引号，参数类型与字段类型保持一致；
3. 统一字符集与排序规则（utf8mb4），避免 JOIN 时转换。

💡 验证方法：
EXPLAIN 查看 type=ALL、key=NULL，即为隐式转换导致索引失效。

CHAR 和 VARCHAR 如何选择？TEXT 类型注意事项？
数据类型

一、CHAR vs VARCHAR：

  • CHAR(n)：
    定长存储，最大 255 字符。
    优点：无需额外字节记录长度，查询速度快；
    缺点：不足 n 个字符时补空格，浪费空间。
    适合：MD5、手机号、身份证号等固定长度字段。
  • VARCHAR(n)：
    变长存储，最大 65535 字节。
    优点：按实际内容存储，节省空间；
    缺点：需额外 1~2 字节记录长度，更新时可能触发行移动。
    适合：名字、描述等长度波动大的字段。

二、TEXT 注意事项：

  • 大文本，不能有默认值。
  • 不能全字段索引，建索引需指定前缀长度（INDEX(desc(100))）。
  • 排序/分组时可能使用磁盘临时表，性能差，应避免 SELECT * 取出大字段。

三、BLOB：
二进制大对象（图片、文件），建议只存路径，
文件本体放对象存储（OSS），不要直接存数据库。

💡 通用建议：
字段尽量 NOT NULL，NULL 值会额外占用空间且索引统计不准；
选择口诀：定长用 CHAR，变长用 VARCHAR，大文本上存储服务。

MySQL redo log、undo log、binlog 的区别？
日志高频

一、各日志定义：

  • redo log（重做日志）：
    InnoDB 存储引擎层独有的日志，记录的是"数据页被修改成了什么"（物理日志），
    用于崩溃后重放、恢复数据，保证事务的持久性（D）。
  • undo log（回滚日志）：
    InnoDB 存储引擎层独有的日志，记录的是"怎么把修改撤销回去"（反向操作，逻辑日志），
    用于事务回滚和 MVCC 快照读，保证事务的原子性（A）。
  • binlog（二进制日志）：
    MySQL Server 层日志，所有存储引擎通用，记录的是"数据变更的 SQL 或行结果"（逻辑日志），
    用于主从复制、数据恢复和审计。

二、三种日志对比表：

日志层级作用格式写入时机
redo logInnoDB引擎层崩溃恢复，保证持久性物理日志(页修改)数据页每次修改时
undo logInnoDB引擎层回滚/MVCC，保证原子性逻辑日志(相反操作)写操作开始时
binlogServer层主从复制/数据恢复逻辑日志(SQL/行变更)事务提交时

三、redo log 详解（WAL）：
Write-Ahead Logging：先写日志，再写数据页。
数据页修改后不会立即刷盘（随机 IO 慢），而是先顺序写入 redo log，
崩溃时用 redo log 重放恢复，保证持久性（D）。

  • 物理日志：
    记录"哪个页、哪个偏移位置、被改成了什么"，重放速度快。
  • 环形写入：
    文件大小固定（默认 2 个文件、各 48MB，可配置），
    写满后循环覆盖旧记录，不会无限膨胀。
  • 刷盘策略（innodb_flush_log_at_trx_commit）：
    0=每秒刷盘（性能最高，崩溃可能丢 1 秒数据）；
    1=每次事务提交都刷盘（最安全，默认）；
    2=先写 OS 缓存、每秒刷盘（性能与安全折中）。

四、undo log 详解：
逻辑日志，记录的是反向操作，保证原子性（A）。
例：INSERT 记录 DELETE 信息、UPDATE 记录修改前的旧值。

  • 事务回滚：
    事务执行失败时，按 undo log 逆向执行，恢复操作前状态。
  • MVCC 快照读：
    通过 undo log 构建版本链，配合 ReadView 实现无锁快照读。
  • 两种类型：
    insert undo log（回滚后即可清理）；
    update undo log（还要服务 MVCC，由后台 purge 线程延迟清理）。

五、binlog 详解：
Server 层日志，所有存储引擎通用，追加写、不覆盖。

  • 逻辑日志：
    记录 SQL 语句或行变更结果。
  • 三种格式：
    STATEMENT（记录原始 SQL，量小但不确定/不安全）；
    ROW（记录每行变更，最安全，MySQL 8.0 默认）；
    MIXED（根据语句自动选择）。
  • 用途：
    主从复制、基于时间点的数据恢复（误删恢复）、审计。
  • 刷盘策略（sync_binlog）：
    0=由 OS 决定刷盘；1=每次提交刷盘；N=每 N 次提交刷盘。

六、两阶段提交：
目的：保证 redo log 与 binlog 的一致性，防止主从数据不一致。

  1. 先写 redo log，标记 prepare 状态。
  2. 再写 binlog。
  3. 最后将 redo log 改为 commit 状态。

崩溃时判断：
redo log prepare 且 binlog 完整 → 事务生效（补 commit）；
redo log prepare 但 binlog 缺失 → 事务回滚。

七、redo log 为什么不能替代 binlog：
1. 层级不同：redo 在引擎层，binlog 在 Server 层；
2. 格式不同：redo 是物理日志，binlog 是逻辑日志；
3. 生命周期不同：redo 环形覆盖，binlog 追加保存；
4. 用途不同：redo 用于崩溃恢复，binlog 用于主从复制/数据恢复。

💡 高频追问：
安全最佳实践是双 1 配置：
innodb_flush_log_at_trx_commit=1 + sync_binlog=1，
每次提交都刷盘，数据最安全。

八、MySQL 架构分层（名词解释）：
MySQL 采用插件式存储引擎架构，分为两层：

  • Server 层（服务层）：
    负责 SQL 解析、优化、执行计划生成、通用功能（如 binlog、用户权限、连接管理等）。
    与存储引擎无关，所有存储引擎共享这一层。
  • 存储引擎层：
    负责数据的存储和读取，不同引擎实现不同的存储机制。
    MySQL 支持多种存储引擎（如 InnoDB、MyISAM、Memory 等），
    可通过 SHOW ENGINES 查看，创建表时可用 ENGINE=InnoDB 指定。
    InnoDB 是 MySQL 5.5+ 的默认引擎，支持事务、行锁、MVCC 等特性。

索引下推（ICP）是什么？
索引优化ICP

一、什么是索引下推（ICP）：
Index Condition Pushdown，MySQL 5.6+ 引入的查询优化。
把 WHERE 中能由索引列判断的条件（如 age=25）下推到存储引擎层，
在读取索引时提前过滤，减少回表次数和 Server 层传输的数据量。

-- 联合索引 (name, age)
SELECT * FROM t WHERE name LIKE '张%' AND age = 25;
-- 没有ICP: 先回表取出所有 name LIKE '张%' 的行，再到Server层过滤 age=25
-- 有ICP: 存储引擎在索引中直接过滤 age=25，只需回表符合条件的数据

二、核心原理：
没有 ICP：回表取回所有 name LIKE '张%' 的行，Server 层再过滤 age=25，回表次数多；
有 ICP：存储引擎在索引中直接过滤 age=25，只需回表符合条件的数据。

三、应用前提：
过滤条件基于索引列，且索引无法直接定位（如 LIKE 前缀匹配后的列）。

💡 如何确认启用：
EXPLAIN 的 Extra 出现 Using index condition 即表示启用了 ICP。

四、前置概念（名词解释）：

  • 存储引擎层：
    MySQL 分 Server 层和存储引擎层：
    Server 层负责 SQL 解析、优化、权限等通用功能；
    存储引擎层负责数据的存储和读取（如 InnoDB、MyISAM）。
    ICP 中的"下推"，就是把过滤操作下沉到存储引擎层执行。
  • 联合索引：
    由多个列组成的索引，如 (name, age)。
    遵循最左前缀原则：name 在前、age 在后，
    索引先按 name 排序，name 相同时再按 age 排序。
  • 聚簇索引（主键索引）：
    索引顺序与数据行的物理存储顺序一致，叶子节点直接存放完整行数据。
    InnoDB 中主键索引就是聚簇索引，一张表只有一个。
  • 非聚簇索引（二级索引/辅助索引）：
    叶子节点存放的是主键值（而非完整行数据）。
    一张表可有多个非聚簇索引（如普通索引、联合索引）。
    通过它查不到整行，需要拿主键再回聚簇索引查一次。
  • 回表：
    先通过非聚簇索引找到主键值，
    再根据主键到聚簇索引中查找完整行数据的操作。
    一次回表 = 额外一次随机 IO，回表次数越多性能越差。

联合索引匹配原则和索引长度限制？
联合索引优化

一、联合索引匹配原则（最左前缀）：

  • 必须从最左列开始使用：
    联合索引 (a,b,c)，WHERE a=1 AND c=3 只能用到列 a；
    WHERE b=1 完全不走索引。
  • 等值查询字段优先：
    区分度高的字段放前面。
  • 范围查询字段放最后：
    范围查询（>、<、BETWEEN）之后的列无法走索引。
  • ORDER BY / GROUP BY 字段可加入索引：
    避免 filesort，直接利用索引有序性。

二、索引长度限制：
InnoDB 单列索引最大 767 字节（utf8mb4 下约 191 个字符）；
开启 DYNAMIC/COMPRESSED 行格式 + 大前缀后可到 3072 字节。

三、解决方案：
1. 使用前缀索引：INDEX(name(20))，减少索引长度；
2. 字段尽量使用更小的类型（int 优于 varchar）；
3. TEXT/BLOB 建索引必须指定前缀长度。

💡 示例：
索引 (a,b,c)：
WHERE a=1 AND b=2 AND c=3 → 三列全用；
WHERE a=1 AND b>10 AND c=3 → 只用 a、b，c 失效；
WHERE b=2 AND c=3 → 完全失效。

四、前置概念（名词解释）：

  • 联合索引：
    由多个列组成的索引，如 (a, b, c)，
    先按第 1 列 a 排序，a 相同再按 b，b 相同再按 c。
  • 最左前缀原则：
    查询条件必须从联合索引的最左列开始连续匹配才能用到索引。
  • 前缀索引：
    只取列的前 N 个字符建立索引，如 INDEX(name(20))，
    缩短索引长度、减少磁盘占用和随机 IO。
  • 区分度：
    字段去重后的值所占比例，
    性别区分度低、身份证号区分度高，
    区分度高的字段放索引前面。

一、SQL 注入原理：
拼接 SQL 时，用户输入如 ' OR 1=1 -- 改变了原 SQL 语义，

  • 输入校验过滤：

  • 预编译（PreparedStatement）：
    先把 SQL 结构编译好，参数用占位符 ? 替代，
    之后只绑定参数值传入，SQL 结构与数据完全分离，
    用户输入永远只是"值"，无法改变 SQL 语义。
  • UDF：
    User Defined Function，用户自定义函数，
    攻击者注入后可通过 UDF 在数据库服务器上执行系统命令。
  • MyBatis：
    Java 持久层框架，支持 #{}（预编译占位符）和 ${}（字符串拼接）两种传参方式。

SQL优化

分布式事务解决方案有哪些？
分布式事务高频

一、解决方案有哪些（总览）：
分布式事务主流方案共 6 种，按一致性要求分为两类：

  • 强一致（1 种）：2PC（XA 两阶段提交）。
  • 最终一致（5 种）：TCC、本地消息表、可靠消息最终一致性（RocketMQ 事务消息）、最大努力通知、Saga。

二、逐一讲解每种方案：

  1. 2PC（两阶段提交）：
    协调者 → 所有参与者 prepare（预提交）→ 全部 yes → commit。
    基于 XA 协议，强一致；
    缺点：同步阻塞、协调者单点故障。
  2. TCC（Try-Confirm-Cancel）：
    业务层面补偿，侵入性强。
    Try 预留资源 → Confirm 确认 → 失败则 Cancel 释放。
    Seata 支持。
  3. 本地消息表：
    本地事务 + 消息表 + MQ + 定时任务补偿，
    最终一致性，实现简单但消息表与业务耦合。
  4. 可靠消息最终一致性：
    RocketMQ 事务消息（半消息 + 回查机制），
    主流方案，可靠性高。
  5. 最大努力通知：
    重复通知 + 对账补偿，
    适合跨平台支付回调等不要求强一致的场景。
  6. Saga：
    长事务分解为子事务，正向执行 + 反向补偿；
    适合长事务、无锁，但缺乏隔离性。

💡 选型建议：
强一致要求 → 2PC；
高并发、可接受最终一致 → TCC / 可靠消息；
长事务、低并发 → Saga。

三、前置概念（名词解释）：

  • 分布式事务：
    一次业务操作涉及多个数据库或微服务，
    需要保证这些跨节点操作要么全部成功、要么全部回滚。
  • XA 协议：
    数据库层面的分布式事务标准协议，
    由事务管理器统一协调各参与者的提交/回滚。
  • 2PC（两阶段提交）：
    由一个协调者统一管理多个参与者的提交，分两个阶段：
    ① 准备阶段（prepare）：协调者发 prepare 请求，参与者执行事务但不提交，回复 yes/no；
    ② 提交阶段（commit/abort）：全部 yes 则统一 commit，任一 no 则统一 rollback。
    基于 XA 协议实现，属于强一致方案。
  • TCC（补偿型分布式事务）：
    把一次业务拆成三个步骤，由业务代码实现，属于最终一致方案：
    ① Try（预留资源）：先检查并锁定资源，如冻结账户金额；
    ② Confirm（确认提交）：Try 全部成功才执行，真正扣款完成操作；
    ③ Cancel（补偿释放）：Confirm 失败则反向释放资源，如解冻金额。
  • MQ：
    消息队列，用于异步解耦，
    配合事务消息实现跨系统最终一致。
  • 最终一致性：
    不要求任何时刻强一致，
    只要经过一段时间后各节点数据最终相同。

count(*)、count(1)、count(列名) 的区别？
高频聚合

一、四种写法对比：

  • count(*)：
    统计所有行数（包括 NULL），
    MySQL 优化器专门优化，效率最高，推荐使用。
  • count(1)：
    同 count(*)，每行填充常量 1 再统计，性能基本相同。
  • count(列名)：
    统计该列非 NULL的行数；
    若该列大量为 NULL，结果会小于实际行数。
  • count(distinct 列)：
    去重后计数。

二、效率对比：
InnoDB 中 count(*) 与 count(1) 性能基本一致，都优于 count(列名)；
count(列名) 需要判断 NULL，且可能触发额外回表。

💡 注意：
MyISAM 中 count(*) 无 WHERE 条件时 O(1)（行数存于表头）；
InnoDB 必须全表/全索引扫描，因此统一推荐 count(*)。

三、前置概念（名词解释）：

  • count()：
    MySQL 聚合函数，用于统计记录行数。
  • NULL：
    表示"未知/没有值"，既不是 0 也不是空字符串，
    count(列名) 会跳过 NULL 值，参与运算结果也为 NULL。
  • InnoDB / MyISAM 计数差异：
    MyISAM 把表总行数存在表头，count(*) 无过滤条件时 O(1)；
    InnoDB 需按索引逐行扫描计数（受 MVCC/事务影响，不缓存总行数）。

MVCC 读提交(RC)和可重复读(RR)下 ReadView 生成时机有何不同？
MVCC深入

一、MVCC 回顾：
ReadView（读视图）记录生成时点活跃事务列表，
用于判断版本链中哪个版本对当前事务可见。

二、生成时机差异：

  • RC（读已提交）：
    每次快照读（普通 SELECT）都重新生成一个新的 ReadView。
    因此能读到其他事务已提交的最新修改，导致不可重复读。
  • RR（可重复读）：
    只在事务内第一次快照读时生成 ReadView，
    后续的快照读复用同一个。
    读到的数据始终是第一次快照时的状态，实现可重复读。

💡 根本原因：
这就是 RR 能避免不可重复读的原因——ReadView 只生成一次并复用。

注意：
当前读（SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE）
不依赖快照，始终读最新已提交数据，
RR 下通过 Next-Key Lock 解决幻读。

三、前置概念（名词解释）：

  • MVCC：
    Multi-Version Concurrency Control，多版本并发控制，
    同一行数据保存多个历史版本，读操作不加锁即可读到一致快照。
  • 版本链：
    每次修改基于 undo log 生成一个新版本，
    各版本按时间串联成链，供 MVCC 判断可见性。
  • ReadView（读视图）：
    记录生成时点还未提交的活跃事务 ID 列表，
    用来判断版本链中哪个版本对当前事务可见。
  • 快照读 vs 当前读：
    快照读（普通 SELECT）读历史版本、不加锁；
    当前读（UPDATE/DELETE/加锁 SELECT）读最新已提交数据、需加锁。
  • RC（读已提交，Read Committed）：
    事务只能读到其他事务已提交的数据；
    每次快照读都重新生成 ReadView，
    能读到别的事务最新提交的修改，
    因此同一事务内两次查询结果可能不同（不可重复读）。
  • RR（可重复读，Repeatable Read）：
    事务内多次读取结果保持一致；
    第一次快照读生成 ReadView 后复用，后续读到同一个快照，
    其他事务的修改对当前事务不可见。
    它是 MySQL InnoDB 的默认隔离级别。

  • 覆盖索引：

什么是回表？如何避免回表？
回表优化

一、什么是回表：
先通过二级索引（非聚簇索引）找到主键值，
再根据主键到聚簇索引（主键索引）中查找完整行数据的操作。

-- name有普通索引，非主键
SELECT * FROM t WHERE name='test'; -- 二级索引查到主键id → 再回聚簇索引查整行（回表）
SELECT id, name FROM t WHERE name='test'; -- 所需列都在索引中，覆盖索引，无需回表

二、为什么回表慢：
一次回表 = 额外一次随机 IO，
回表次数多时性能急剧下降。

三、如何避免回表：

  • 覆盖索引：
    索引中包含查询所需的全部字段，
    无需回表（Extra 显示 Using index）。
  • 减少 SELECT *：
    只查需要的列，提高覆盖索引命中概率。
  • 合理设计联合索引：
    把高频查询字段都放进索引。
  • 索引下推（ICP）：
    在索引层提前过滤，减少无谓回表。

四、前置概念（名词解释）：

  • 聚簇索引（主键索引）：
    叶子节点直接存放完整行数据，表数据物理顺序与索引顺序一致；
    InnoDB 主键索引即聚簇索引，一张表只有一个。
  • 二级索引（非聚簇索引）：
    叶子节点只存主键值，而非完整行数据；
    普通索引、联合索引都属于二级索引，一张表可有多个。
  • 覆盖索引：
    索引中已包含查询所需的全部字段，
    查询直接从索引取数，无需回表。
  • 随机 IO：
    每次按主键跳转到不同数据页读取，磁盘寻道开销大，
    性能远低于顺序 IO。

什么是索引？为什么要使用索引？索引有哪些优缺点？
索引基础

一句话概括：
索引是数据库为加速查询而额外维护的"目录"数据结构，
本质是以空间换时间，把无序数据变成可快速定位的有序结构；
它大幅提升查询速度，但会牺牲写入性能并占用额外空间。

一、什么是索引（定义、作用、原理）：

  • 定义：
    索引是一种用于快速查询和检索数据的数据结构，
    常见索引结构有 B 树、B+ 树和 Hash。
  • 作用：
    索引的作用相当于书的目录，
    没有目录时只能一页页翻找，有了目录直接定位页码即可。
  • 原理：
    索引对列的值排序后额外存储，并记录对应的物理位置，
    查询时先在索引中二分定位，再按位置读取数据，避免全表扫描。

二、为什么要使用索引（索引的优点）：

  • 保证数据唯一性：
    通过创建唯一性索引，可以保证数据库表中每一行数据的唯一性。
  • 大大加快检索速度：
    大幅减少检索的数据量，这是创建索引最主要的原因，
    毕竟大部分系统的读请求总是大于写请求的。
  • 帮助服务器避免排序和临时表：
    索引本身有序，可满足 ORDER BY、GROUP BY、DISTINCT 等操作，
    避免额外排序和建立临时表。
  • 将随机 IO 变为顺序 IO：
    按索引顺序读取数据，减少磁盘寻道开销，加速范围查询。
  • 加速表和表之间的连接：
    在经常用于连接的列（外键）上建索引，加快连接速度，
    在实现数据的参考完整性方面特别有意义。

三、索引的缺点（为什么不对每一列建索引）：

  • 降低增删改速度：
    当对表中的数据进行增、删、改时，索引也要动态维护，
    降低了数据的维护速度（如 InnoDB 的 B+ 树要重新调整）。
  • 占用物理空间：
    索引需要使用物理文件存储，每一个索引都要占一定的物理空间，
    如果要建立聚簇索引，需要的空间就会更大。
  • 耗费创建和维护时间：
    创建索引和维护索引要耗费时间，
    这种时间随着数据量的增加而增加。

四、前置概念（名词解释）：

  • 数据结构：
    数据在计算机中的组织方式，如 B 树、B+ 树、Hash、链表等，
    决定了数据的存取效率。
  • 全表扫描：
    从头到尾逐行遍历整张表查找数据，时间复杂度 O(n)，
    数据量大时性能极差。
  • 随机 IO / 顺序 IO：
    随机 IO 需要多次磁盘寻道，开销大；
    顺序 IO 连续读取，性能远高于随机 IO。
  • 聚簇索引：
    索引结构与数据一起存放的索引，如 InnoDB 的主键索引，
    叶子节点直接存放完整行数据。

B 树和 B+ 树的区别？
索引数据结构

一句话概括：
B 树所有节点都存 key 和数据、叶子节点相互独立；
B+ 树只有叶子节点存数据、叶子节点用链表串联、检索稳定，
因此 B+ 树更适合作数据库索引。

一、先讲两个概念（定义）：

  • B 树：
    多路平衡查找树，所有节点既存放键（key）也存放数据（data），
    树内节点都有实际数据，检索可能提前结束。
  • B+ 树：
    B 树的变体，只有叶子节点存放 key 和 data，
    其他内部节点只存放 key 作为路由，叶子节点用链表相连。

二、核心区别：

  • 数据存放位置不同：
    B 树所有节点既存 key 也存 data；
    B+ 树只有叶子节点存 key 和 data，内部节点只存 key。
  • 叶子节点结构不同：
    B 树的叶子节点都是独立的；
    B+ 树的叶子节点有一条引用链（双向链表）指向相邻叶子节点，天然有序。
  • 检索过程不同：
    B 树检索相当于对范围内每个节点的关键字做二分查找，
    可能还没到达叶子节点检索就结束了；
    B+ 树任何查找都是从根节点到叶子节点的过程，效率稳定，
    叶子节点支持顺序检索。
  • 磁盘 IO 不同：
    B+ 树内部节点只存 key，一个页能容纳更多 key，树更矮、IO 更少；
    B 树每个节点都存数据，key 容量小，树更高、IO 更多。

三、为什么数据库选 B+ 树：
叶子节点有序链表天然支持范围查询，
内部节点不存数据使树更矮，查询 IO 次数固定且稳定，
更契合磁盘顺序读写的特性。

四、前置概念（名词解释）：

  • 多路平衡查找树：
    每个节点可以有多个子节点的平衡树，
    相比二叉树更矮，可减少磁盘寻道次数。
  • 叶子节点：
    树的最底层节点，没有子节点，B+ 树中存放全部数据。
  • 内部节点：
    除叶子节点外的中间节点，B+ 树中只作索引路由使用。
  • 范围查询：
    检索某一区间内的数据，如 id BETWEEN 100 AND 200，
    B+ 树一次定位后沿链表顺序扫描即可。

Hash 索引和 B+ 树索引的优劣对比？
索引数据结构

一句话概括：
Hash 索引等值查询极快但不支持排序和范围查询；
B+ 树索引有序、支持范围查询和排序，是 MySQL 的主流选择。

一、Hash 索引（定义与特点）：

  • 定义：
    底层就是哈希表，通过 Hash 函数把 key 映射到存储位置。
  • 优点·定位快：
    最大的优点是能够在很短的时间内，根据 Hash 函数定位到数据所在的位置，
    这是 B+ 树所不能比的。
  • 缺点·Hash 冲突：
    多个 key 可能映射到同一位置，需要额外机制处理冲突，
    同 HashMap/Hashtable 一样存在 Hash 冲突问题。
  • 缺点·不支持顺序和范围查询（最大缺点）：
    B+ 树是有序的，范围查询直接遍历比某个值小的叶子节点即可；
    而 Hash 索引是根据 hash 算法定位的，
    范围查询需要把区间内每个数据都做一次 hash 计算来定位，性能极差。
    如 SELECT * FROM tb1 WHERE id < 500 这类查询 Hash 索引无法高效支持。

二、B+ 树索引（定义与特点）：

  • 定义：
    基于 B+ 树结构的有序索引，叶子节点按 key 排序并双向链接。
  • 优点·有序支持范围查询：
    范围查询时直接遍历比目标值小的叶子节点即可，优势非常大；
    同时天然支持 ORDER BY 排序。
  • 优点·支持前缀匹配：
    有序结构支持 LIKE 'abc%' 类型的前缀模糊查询。
  • 缺点·等值查询略慢：
    单条等值查询需要从根节点走到叶子节点，多次 IO，
    不如 Hash 索引直接定位快。

三、如何选择：
绝大多数需求为单条记录查询时可选择 Hash 索引（如 MEMORY 引擎）；
其余大部分场景建议选择 BTree（B+ 树）索引。

四、前置概念（名词解释）：

  • 哈希函数：
    把任意长度的 key 计算成固定长度存储地址的函数，
    是哈希表的定位依据。
  • 哈希冲突：
    不同 key 计算出相同地址的现象，
    需通过链地址法或开放寻址法解决。
  • 等值查询：
    WHERE 条件为精确值匹配（如 id = 5），
    Hash 索引只擅长此类查询。
  • MEMORY 引擎：
    MySQL 将数据保存在内存中的存储引擎，
    默认索引结构即 Hash 索引。

MySQL 索引有哪些类型？如何添加索引？
索引基础

一句话概括：
MySQL 索引按功能分为主键索引、唯一索引、普通索引、前缀索引、全文索引；
按列数分为单列索引和联合索引，
其中主键索引（聚簇索引）之外的都叫二级索引。

一、主键索引（Primary Key）：
数据表的主键列使用的就是主键索引。

  • 一张数据表只能有一个主键，且主键不能为 null、不能重复。
  • InnoDB 表中没有显式指定主键时，
    会先检查是否有唯一索引字段，若有则选其为默认主键，
    否则自动创建一个 6 Byte 的自增主键。
  • InnoDB 的主键索引即聚簇索引，叶子节点存完整行数据。

二、二级索引（辅助索引）：
二级索引的叶子节点存储的数据是主键，
通过二级索引可以定位主键的位置，再回表查询完整数据。
唯一索引、普通索引、前缀索引等都属于二级索引。

  • 唯一索引（Unique Key）：
    属性列不能出现重复数据，但允许数据为 NULL，
    一张表允许创建多个唯一索引；
    建立目的大部分时候是为了保证数据的唯一性，而非查询效率。
  • 普通索引（Index）：
    唯一作用就是快速查询数据，
    一张表允许创建多个，允许数据重复和 NULL。
  • 前缀索引（Prefix）：
    只适用于字符串类型的数据，对文本的前几个字符创建索引，
    相比普通索引占用空间更小，因为只取前几个字符。
  • 全文索引（Full Text）：
    主要为了检索大文本数据中的关键字信息，
    是搜索引擎数据库常用的一种技术；
    MySQL 5.6 之前只有 MyISAM 引擎支持，5.6 之后 InnoDB 也支持。

三、按列数分类：

  • 单列索引：
    即由一列属性组成的索引。
  • 联合索引（多列索引）：
    即由多列属性组成的索引，
    查询遵循最左前缀原则，尽量把查询最频繁的字段放最左。

四、如何为表字段添加索引（示例）：

-- 添加主键索引
ALTER TABLE `table_name` ADD PRIMARY KEY ( `column` );
-- 添加唯一索引
ALTER TABLE `table_name` ADD UNIQUE ( `column` );
-- 添加普通索引
ALTER TABLE `table_name` ADD INDEX index_name ( `column` );
-- 添加全文索引
ALTER TABLE `table_name` ADD FULLTEXT ( `column` );
-- 添加多列索引（联合索引）
ALTER TABLE `table_name` ADD INDEX index_name ( `column1`, `column2`, `column3` );

五、前置概念（名词解释）：

  • 聚簇索引：
    索引结构与数据一起存放的索引，InnoDB 主键索引即聚簇索引，
    一张表只能有一个。
  • 回表：
    先通过二级索引找到主键，再根据主键到聚簇索引查完整行数据的过程。
  • 索引组织表：
    InnoDB 中表数据按主键顺序组织存放，
    数据的存储顺序和索引顺序一致。
  • 最左前缀原则：
    联合索引必须从最左列开始连续匹配才能命中，
    如 (name,city) 索引，name=xx 可命中、city=xx 无法命中。

为什么索引能提高查询速度？
索引原理

一句话概括：
索引把无序的数据变成有序结构，
通过"目录 + 二分查找"将全表遍历的 O(n) 优化为 O(logn)，
底层实现就是 B+ 树。

一、先从 MySQL 的基本存储结构说起：

  • 页（Page）：
    MySQL 的基本存储结构，记录都存放在页里边，
    默认每页 16KB。
  • 双向链表：
    各个数据页可以组成一个双向链表，
    定位记录所在页需要遍历这个链表。
  • 单向链表：
    每个数据页中的记录又组成一个单向链表。
  • 页目录：
    每个数据页都会为存储在里边的记录生成一个页目录，
    通过主键查找时可在页目录中用二分法快速定位到对应的槽，
    再遍历该槽对应分组中的记录即可快速找到指定记录。

二、没有索引时的查找过程（为什么慢）：
以 select * from user where indexname = 'xxx' 为例：

  • 定位到记录所在的页：需要遍历双向链表，找到所在的页。
  • 从所在的页内查找记录：由于不是根据主键查询，
    只能遍历所在页的单链表。
  • 在数据量很大的情况下这样查找会很慢，
    时间复杂度为 O(n)。

三、使用索引之后（为什么快）：
索引做了些什么让我们查询加快速度呢？其实就是将无序的数据变成有序（相对）：

  • 没有索引时需要遍历双向链表来定位对应的页，
    通过"目录"（索引）就可以很快定位到对应的页。
  • 通过二分查找，时间复杂度近似为 O(logn)。
  • 底层结构就是 B+ 树，作为树的一种实现，
    能够让我们很快地查找出对应的记录。

四、选择索引和编写索引查询的 3 个原则：

  • 单行访问是很慢的：
    如果服务器从存储中读取一个数据块只是为了获取其中一行，
    就浪费了很多工作，最好读取的块中能包含尽可能多所需要的行。
  • 按顺序访问范围数据是很快的：
    顺序 IO 不需要多次磁盘寻道，所以比随机 IO 快很多；
    且不再需要额外的排序操作，GROUP BY 也无须再排序和聚合计算。
  • 索引覆盖查询是很快的：
    如果一个索引包含了查询需要的所有列，
    存储引擎就不需要再回表查找行，避免了大量的单行访问。

五、前置概念（名词解释）：

  • 二分查找：
    在有序序列中每次取中间值比较，排除一半数据，
    时间复杂度 O(logn)。
  • 页目录：
    数据页内部为记录建立的目录，
    记录被分成若干槽，支持二分定位。
  • 覆盖索引：
    索引包含查询所需的全部字段，无需回表，
    Extra 显示 Using index。
  • B+ 树：
    多路平衡查找树，内部节点只存 key、叶子节点存数据且有序，
    是 InnoDB/MyISAM 的默认索引结构。

使用索引的注意事项有哪些？
索引优化

一句话概括：
在经常搜索、WHERE 条件、排序、连接的列上建索引，
避免对索引列施加函数、避免 NULL、及时清理无用索引，
且索引并非越多越好、数据量小时收益有限。

一、使用索引的注意事项：

  • 在经常搜索的列上建索引：
    可以加快搜索的速度。
  • 在 WHERE 子句的列上建索引：
    加快条件的判断速度。
  • 在经常排序的列上建索引：
    索引已经有序，查询可以利用索引的排序，加快排序查询时间。
  • 中到大型表建索引有效：
    对于中到大型表索引非常有效，
    但特大型表维护开销会很大，不适合建索引。
  • 在经常连接的列（外键）上建索引：
    可以加快连接的速度。
  • 避免 where 子句中对字段施加函数：
    这会造成无法命中索引。
  • InnoDB 使用与业务无关的自增主键：
    即使用逻辑主键，而不要使用业务主键，
    避免主索引频繁分裂。
  • 索引列设置为 NOT NULL：
    否则将导致引擎放弃使用索引而进行全表扫描。
  • 删除长期未使用的索引：
    不用的索引存在会造成不必要的性能损耗；
    MySQL 5.7 可通过查询 sys 库的 schema_unused_indexes 视图
    查看哪些索引从未被使用。
  • limit offset 查询缓慢时借助索引：
    使用 LIMIT OFFSET 查询缓慢时，可以借助索引来提高性能。

二、使用索引一定能提高查询性能吗：

  • 大多数情况下，索引查询都比全表扫描要快。
  • 但如果数据库的数据量不大，
    使用索引也不一定能够带来很大提升。

三、前置概念（名词解释）：

  • 逻辑主键：
    与业务无关的自增主键，如 AUTO_INCREMENT 的 id，
    避免使用业务字段作主键导致索引频繁调整。
  • 全表扫描：
    不使用索引时逐行遍历整张表，复杂度 O(n)，
    引擎会在某些情况下（如索引列含 NULL）放弃索引。
  • LIMIT OFFSET：
    分页查询语法，OFFSET 越大扫描越深，性能越差，
    可用索引定位优化。
  • sys 库：
    MySQL 5.7 提供的性能诊断库，
    内含 schema_unused_indexes、schema_redundant_indexes 等视图。

索引的创建原则和注意点有哪些？
索引优化

一句话概括：
在不为 NULL、频繁查询、条件过滤、频繁连接的字段上建索引；
频繁更新、不常查询的字段慎建索引；
优先联合索引、避免冗余索引、字符串可用前缀索引。

一、选择合适的字段（适合建索引）：

  • 不为 NULL 的字段：
    索引字段的数据应该尽量不为 NULL，
    因为对于数据为 NULL 的字段，数据库较难优化；
    如果字段频繁被查询又避免不了 NULL，
    建议使用 0、1、true、false 等语义清晰的短值或短字符替代。
  • 被频繁查询的字段：
    创建索引的字段应该是查询操作非常频繁的字段。
  • 被作为 WHERE 条件查询的字段：
    被作为条件查询的字段，应该考虑建立索引。
  • 被经常用于连接的字段：
    经常用于连接的字段可能是一些外键列，
    对于频繁被连接查询的字段，可以考虑建立索引，提高多表连接查询的效率。

二、不合适创建索引的字段（慎建索引）：

  • 被频繁更新的字段：
    虽然索引能带来查询上的效率，但维护索引的成本也不小，
    一个字段不被经常查询反而被经常修改，就不应该建索引。
  • 不被经常查询的字段：
    没有查询价值的字段没有必要建立索引。

三、创建索引的注意点：

  • 尽可能考虑联合索引而不是单列索引：
    每个索引都对应一颗 B+ 树、占用磁盘空间，
    字段过多、索引过多会占很多空间且修改耗时；
    联合索引多个字段在一个索引上，节约磁盘空间、提升修改效率。
  • 遵守最左前缀原则：
    查询条件精确匹配索引左边连续一列或几列时才能命中；
    创建联合索引时字段顺序要考虑字段值去重后的个数，较多的放前面；
    ORDER BY 子句也遵循此规则。
  • 注意避免冗余索引：
    冗余索引指索引功能相同，能命中后者就肯定能命中前者，
    如 (name,city) 和 (name) 就是冗余索引；
    大多数情况下应该尽量扩展已有的索引而不是创建新索引；
    MySQL 5.7 后可通过 sys 库的 schema_redundant_indexes 表查看冗余索引。
  • 字符串类型优先考虑前缀索引：
    前缀索引只取字符串前几个字符建索引，
    相比普通索引占用更小空间，
    可考虑用前缀索引代替普通索引。

四、前置概念（名词解释）：

  • 联合索引：
    多个字段组成的索引，如 (name, city)，
    减少索引数量、提高查询效率。
  • 最左前缀原则：
    联合索引查询须从最左列开始连续匹配，
    如 (name,city) 索引下 city=xx 单独查询无法命中。
  • 冗余索引：
    功能重复的索引，浪费空间、拖慢写入性能。
  • 前缀索引：
    取字符串列前 N 个字符建立的索引，
    适合长字符串列，节省空间。

MySQL 数据库命名和基本设计规范有哪些？
设计规范规范

一句话概括：
命名要小写加下划线、见名识意、不使用保留字；
设计上统一 InnoDB + UTF8、加注释、控制数据量、分离冷热数据，
从源头保证规范性和可维护性。

一、数据库命令规范：

  • 所有数据库对象名称必须使用小写字母并用下划线分割。
  • 所有数据库对象名称禁止使用 MySQL 保留关键字，
    如果表名中包含关键字查询时，需要将其用单引号括起来。
  • 数据库对象的命名要能做到见名识意，
    并且最好不要超过 32 个字符。
  • 临时库表必须以 tmp 为前缀并以日期为后缀，
    备份表必须以 bak 为前缀并以日期（时间戳）为后缀。
  • 所有存储相同数据的列名和列类型必须一致（一般作为关联列），
    如果查询时关联列类型不一致会自动进行数据类型隐式转换，
    会造成列上的索引失效，导致查询效率降低。

二、数据库基本设计规范：

  • 所有表必须使用 InnoDB 存储引擎：
    没有特殊要求（如列存储、存储空间数据等）时，所有表使用 InnoDB；
    MySQL 5.5 之前默认 MyISAM，5.6 以后默认 InnoDB；
    InnoDB 支持事务、行级锁、更好的恢复性，高并发下性能更好。
  • 数据库和表字符集统一使用 UTF8：
    统一字符集可避免字符集转换产生的乱码和索引失效；
    如果有存储 emoji 表情的需要，字符集需采用 utf8mb4。
  • 所有表和字段都需要添加注释：
    使用 comment 从句添加表和列的备注，
    从一开始就进行数据字典的维护。
  • 尽量控制单表数据量在 500 万以内：
    500 万并不是 MySQL 数据库的限制，
    过大会造成修改表结构、备份、恢复困难；
    可用历史数据归档（日志数据）、分库分表（业务数据）控制数据量。
  • 谨慎使用 MySQL 分区表：
    分区表物理上表现为多个文件、逻辑上表现为一个表；
    谨慎选择分区键，跨分区查询效率可能更低；
    建议采用物理分表的方式管理大数据。
  • 尽量做到冷热数据分离、减小表的宽度：
    MySQL 限制每个表最多 4096 列，每行数据大小不能超过 65535 字节；
    减少磁盘 IO、保证热数据的内存缓存命中率；
    经常一起使用的列放到一个表中，避免更多的关联操作。
  • 禁止在表中建立预留字段：
    预留字段的命名很难做到见名识义；
    无法确认存储的数据类型，无法选择合适的类型；
    对预留字段类型的修改，会对表进行锁定。
  • 禁止存储图片、文件等大的二进制数据：
    文件很大时 IO 操作很耗时，且数据库读取会进行大量随机 IO；
    通常存储于文件服务器，数据库只存储文件地址信息。
  • 禁止在线上做数据库压力测试。
  • 禁止从开发环境、测试环境直接连接生产环境数据库。

三、前置概念（名词解释）：

  • 保留关键字：
    SQL 中保留特殊含义的单词，如 select、where、order 等，
    作表名/列名时需特殊处理或避免使用。
  • 隐式类型转换：
    比较时类型不一致自动转换类型，
    会导致索引失效、查询变慢。
  • 冷热数据：
    热数据访问频繁、冷数据访问很少，
    分离存储可提高缓存命中率。
  • 分区表：
    逻辑上一张表、物理上多个文件，
    按分区键把数据拆到不同分区文件。

MySQL 字段设计规范有哪些？
设计规范字段

一句话概括：
字段设计核心是"够用就好"：用最小的合适类型、避免 TEXT/BLOB 和 ENUM、
尽量 NOT NULL、时间用 TIMESTAMP/DATETIME、金额用 DECIMAL。

一、优先选择符合存储需要的最小的数据类型：

  • 原因：
    字段越大，建立索引时所需空间越大，
    一页中能存储的索引节点数量越少，
    遍历时所需 IO 次数越多，索引性能越差。
  • 方法 a·字符串转数字存储：
    如将 IP 地址转换成整型数据，
    inet_aton 把 ip 转为无符号整型（4~8 位），
    inet_ntoa 把整型的 ip 转为地址。
  • 方法 b·非负数据用无符号整型：
    如自增 ID、整型 IP 优先使用无符号整型，
    无符号相对于有符号可以多出一倍的存储空间。
  • 注意 VARCHAR(N) 的 N 是字符数：
    使用 UTF8 存储 255 个汉字 Varchar(255)=765 个字节，
    过大的长度会消耗更多的内存。

二、避免使用 TEXT、BLOB 数据类型：

  • 最常见的 TEXT 类型可以存储 64k 的数据。
  • MySQL 内存临时表不支持 TEXT、BLOB 这样的大数据类型，
    排序等操作时必须使用磁盘临时表，SQL 性能变差；
    且 MySQL 对这种数据要进行二次查询。
  • 如果一定要使用，建议把 BLOB 或 TEXT 列分离到单独的扩展表中，
    查询时不要用 select *，只取出必要的列，
    不需要 TEXT 列数据时不要对该列进行查询。
  • 由于 MySQL 对索引字段长度有限制，TEXT 或 BLOB 类型只能使用前缀索引，
    并且 TEXT 列上不能有默认值。

三、避免使用 ENUM 类型：

  • 修改 ENUM 值需要使用 ALTER 语句。
  • ENUM 类型的 ORDER BY 操作效率低，需要额外操作。
  • 禁止使用数值作为 ENUM 的枚举值。

四、尽可能把所有列定义为 NOT NULL：

  • 索引 NULL 列需要额外的空间来保存，所以要占用更多的空间。
  • 进行比较和计算时要对 NULL 值做特别处理。

五、使用 TIMESTAMP 或 DATETIME 类型存储时间：

  • TIMESTAMP：
    占用 4 个字节，范围 1970-01-01 00:00:01 ~ 2038-01-19 03:14:07，
    和 INT 相同但可读性高。
  • DATETIME：
    占用 8 个字节，超出 TIMESTAMP 取值范围时使用。
  • 不要用字符串存储日期：
    无法用日期函数进行计算和比较，且占用更多空间。

六、金额类数据必须使用 decimal 类型：

  • 非精准浮点：float、double，计算会丢失精度。
  • 精准浮点：decimal，计算时不会丢失精度；
    占用空间由定义宽度决定，每 4 个字节可存储 9 位数字，
    小数点占用一个字节，可存储比 bigint 更大的整型数据。

七、前置概念（名词解释）：

  • TEXT/BLOB：
    大文本/二进制类型，TEXT 存文本（最大 64KB），BLOB 存二进制，
    不适合索引、会降低排序性能。
  • ENUM：
    枚举类型，值从预定义集合中选取，
    修改枚举值成本高。
  • 前缀索引：
    对文本前几个字符建索引，TEXT 只能使用前缀索引。
  • 精度：
    浮点数计算的精确程度，DECIMAL 精准、FLOAT/DOUBLE 不精准。

MySQL 索引设计规范有哪些？
索引设计规范

一句话概括：
索引设计规范核心是：数量适中（≤5）、每个 InnoDB 表必有自增主键、
索引列选高区分度、避免冗余/重复索引、优先覆盖索引、少用外键。

一、限制每张表上的索引数量（建议不超过 5 个）：

  • 索引并不是越多越好，可以增加查询效率，同样可以降低效率。
  • 索引会降低插入和更新的效率。
  • MySQL 优化器生成执行计划时会对每个可用索引评估，
    索引过多会增加优化器生成执行计划的时间，同样降低查询性能。

二、禁止给表中的每一列都建立单独的索引：

  • 5.6 版本之前，一个 SQL 只能使用到一个表中的一个索引。
  • 5.6 以后虽然有了合并索引的优化方式，
    但还是远远没有使用一个联合索引的查询方式好。

三、每个 InnoDB 表必须有个主键：

  • InnoDB 是一种索引组织表，数据的存储逻辑顺序和索引顺序相同，
    按照主键索引的顺序组织表。
  • 不要使用更新频繁的列作为主键，不要使用多列主键（相当于联合索引）。
  • 不要使用 UUID、MD5、HASH、字符串列作为主键（无法保证数据的顺序增长）。
  • 主键建议使用自增 ID 值。

四、常见索引列建议：

  • 出现在 SELECT、UPDATE、DELETE 语句的 WHERE 从句中的列。
  • 包含在 ORDER BY、GROUP BY、DISTINCT 中的字段。
  • 不要将符合上面两点的字段都建立一个索引，
    通常将它们建立联合索引效果更好。
  • 多表 join 的关联列。

五、如何选择索引列的顺序：
建立索引的目的是减少随机 IO、增加查询性能，
索引能过滤出越少的数据，则从磁盘读入的数据也就越少。

  • 区分度最高的放在联合索引的最左侧
    （区分度 = 列中不同值的数量 / 列的总行数）。
  • 尽量把字段长度小的列放在联合索引的最左侧
    （字段长度越小，一页能存储的数据量越大，IO 性能越好）。
  • 使用最频繁的列放到联合索引的左侧（可以比较少的建立一些索引）。

六、避免建立冗余索引和重复索引：
冗余和重复索引会增加查询优化器生成执行计划的时间。

  • 重复索引示例：primary key(id)、index(id)、unique index(id)。
  • 冗余索引示例：index(a,b,c)、index(a,b)、index(a)。

七、对于频繁的查询优先考虑使用覆盖索引：
覆盖索引就是包含了所有查询字段（where、select、order by、group by 包含的字段）的索引。

  • 避免 InnoDB 表进行索引的二次查询：
    InnoDB 二级索引叶子节点存主键信息，
    用二级索引查询时要通过主键二次查询才能获取真实数据；
    覆盖索引的键值中可获取所有数据，避免二次查询、减少 IO。
  • 把随机 IO 变成顺序 IO：
    覆盖索引按键值顺序存储，
    对 IO 密集型的范围查找，对比随机从磁盘读取每一行数据 IO 少得多。

八、尽量避免使用外键约束：

  • 不建议使用外键约束（foreign key），
    但一定要在表与表之间的关联键上建立索引。
  • 外键可用于保证数据的参照完整性，但建议在业务端实现。
  • 外键会影响父表和子表的写操作从而降低性能。

九、前置概念（名词解释）：

  • 索引组织表：
    数据按主键索引顺序组织的表，InnoDB 即索引组织表。
  • 区分度：
    列中不同值数量与总行数的比值，
    区分度越高，索引过滤效果越好。
  • 冗余索引/重复索引：
    功能重复、浪费空间并拖慢写入的索引。
  • 覆盖索引：
    索引包含查询所需全部字段，无需回表。

MySQL SQL 开发规范有哪些？
SQL规范优化

一句话概括：
SQL 开发规范核心：预编译防注入、避免隐式转换和函数计算、
不用 select *、子查询转 join、限制 join 表数、拆大 SQL，
让每条 SQL 尽量命中索引且开销最小。

一、建议使用预编译语句进行数据库操作：

  • 预编译语句可以重复使用执行计划，减少 SQL 编译时间，
    还可以解决动态 SQL 所带来的 SQL 注入问题。
  • 只传参数，比传递 SQL 语句更高效；
    相同语句可以一次解析、多次使用，提高处理效率。

二、避免数据类型的隐式转换：
隐式转换会导致索引失效。

-- id 是整型，却用字符串查询，触发隐式转换、索引失效
select name, phone from customer where id = '111';

三、充分利用表上已经存在的索引：

  • 避免使用双 % 号的查询条件：
    a like '%123%' 无法用索引；
    只有后置 %（如 '123%'）可以用到列上的索引。
  • 一个 SQL 只能利用复合索引中的一列进行范围查询：
    如有 a、b、c 列的联合索引，a 列用范围查询时，
    b、c 列上的索引将不会被用到；
    若 a 列要范围查找，就把 a 列放到联合索引的右侧。
  • 使用 left join 或 not exists 来优化 not in 操作，
    因为 not in 也通常会使用索引失效。

四、数据库设计时考虑扩展、账号隔离：

  • 程序连接不同的数据库使用不同的账号，禁止跨库查询，
    为数据库迁移和分库分表留出余地、降低业务耦合度、避免权限过大。

五、禁止使用 SELECT *，必须使用 SELECT <字段列表>：

  • 消耗更多的 CPU、IO 以及网络带宽资源。
  • 无法使用覆盖索引。
  • 可减少表结构变更带来的影响。

六、禁止使用不含字段列表的 INSERT 语句：

-- 禁止
insert into values ('a','b','c');
-- 应使用
insert into t(c1,c2,c3) values ('a','b','c');

七、避免使用子查询，可以把子查询优化为 join 操作：

  • 子查询的结果集无法使用索引，通常会被存储到临时表中，
    临时表（内存或磁盘）都没有索引，查询性能受影响；
    子查询结果集越大，对查询性能影响越大。
  • 子查询会产生大量临时表且没有索引，
    消耗过多 CPU 和 IO 资源，产生大量慢查询。
  • 子查询为简单 SQL（不含 union、group by、order by、limit）时，
    才可以把子查询转化为关联查询进行优化。

八、避免使用 JOIN 关联太多的表：

  • MySQL 存在关联缓存，大小由 join_buffer_size 参数设置，
    同一个 SQL 每多关联一个表就多分配一个关联缓存，
    关联的表越多占用的内存越大，容易造成服务器内存溢出。
  • 关联操作会产生临时表操作，影响查询效率；
    MySQL 最多允许关联 61 个表，建议不超过 5 个。

九、减少同数据库的交互次数：
数据库更适合处理批量操作，合并多个相同的操作到一起，可以提高处理效率。

十、对同一列进行 or 判断时，使用 in 代替 or：

  • in 的值不要超过 500 个。
  • in 操作可以更有效地利用索引，or 大多数情况下很少能利用到索引。

十一、禁止使用 order by rand() 进行随机排序：

  • order by rand() 会把表中所有符合条件的数据装载到内存中，
    然后对所有数据根据随机生成的值排序，
    可能会对每一行都生成一个随机值，
    数据集大时消耗大量 CPU、IO 及内存资源。
  • 推荐在程序中获取一个随机值，
    然后从数据库中获取数据的方式。

十二、WHERE 从句中禁止对列进行函数转换和计算：
对列进行函数转换或计算时会导致无法使用索引。

-- 不推荐
where date(create_time) = '20190101'
-- 推荐
where create_time >= '20190101' and create_time < '20190102'

十三、在明显不会有重复值时使用 UNION ALL 而不是 UNION：

  • UNION 会把两个结果集的所有数据放到临时表中后再进行去重操作。
  • UNION ALL 不会再对结果集进行去重操作，性能更高。

十四、拆分复杂的大 SQL 为多个小 SQL：

  • 大 SQL 逻辑复杂，需要占用大量 CPU 进行计算。
  • MySQL 中一个 SQL 只能使用一个 CPU 进行计算，
    SQL 拆分后可以通过并行执行来提高处理效率。

十五、前置概念（名词解释）：

  • 预编译语句：
    先编译 SQL 骨架再传参执行的语句，
    防止注入、复用执行计划。
  • 隐式转换：
    比较时类型不一致自动转换，导致索引失效。
  • 子查询/临时表：
    嵌套查询的结果集放入临时表，无索引、开销大。
  • join_buffer_size：
    关联查询的缓存大小参数，关联表越多占用越大。

MySQL 数据库操作行为规范有哪些？
规范运维

一句话概括：
操作行为规范核心：大批量写操作分批执行、
大表用 pt-online-schema-change 改结构、
不给程序账号 super 权限、账号遵循权限最小原则。

一、超 100 万行的批量写操作（UPDATE、DELETE、INSERT）要分批多次进行操作：

  • 大批量操作可能造成严重的主从延迟：
    主从环境中，大批量写操作一般需要执行一定长的时间，
    只有当主库上执行完成后才会在其他从库上执行，
    会造成主库与从库长时间的延迟。
  • binlog 日志为 row 格式时会产生大量日志：
    row 格式会记录每一行数据的修改，
    一次修改的数据越多产生的日志量越大，
    日志的传输和恢复所需时间越长，这也是主从延迟的原因之一。
  • 避免产生大事务操作：
    大批量修改数据一定在一个事务中进行，
    会造成表中大批量数据被锁定、产生大量阻塞；
    长时间的阻塞会占满所有数据库可用连接，
    使生产环境中的其他应用无法连接数据库。

二、对于大表使用 pt-online-schema-change 修改表结构：

  • 避免大表修改产生的主从延迟。
  • 避免在对表字段进行修改时进行锁表，
    大表数据结构的修改会造成严重的锁表操作，
    尤其是生产环境，是不能容忍的。
  • 原理：
    首先建立一个与原表结构相同的新表，在新表上进行表结构修改；
    再把原表中的数据复制到新表中，并在原表中增加触发器，
    把原表新增的数据也同步复制到新表；
    所有数据复制完成之后，把新表命名成原表，并把原来的表删除掉；
    把原来一个 DDL 操作分解成多个小的批次进行。

三、禁止为程序使用的账号赋予 super 权限：

  • 当达到最大连接数限制时，还允许 1 个有 super 权限的用户连接。
  • super 权限只能留给 DBA 处理问题的账号使用。

四、对于程序连接数据库账号，遵循权限最小原则：

  • 程序使用数据库账号只能在一个 DB 下使用，不准跨库。
  • 程序使用的账号原则上不准有 drop 权限。

五、前置概念（名词解释）：

  • 主从延迟：
    从库复制主库 binlog 的滞后时间，
    大批量操作会加剧延迟。
  • binlog：
    MySQL 二进制日志，记录数据变更，
    用于主从复制和数据恢复。
  • pt-online-schema-change：
    Percona 提供的在线改表工具，
    通过触发器 + 分批复制避免锁表和主从延迟。
  • super 权限：
    MySQL 超级权限，可绕过最大连接数限制，
    仅限 DBA 使用。
