Elasticsearch 是什么？和 MySQL 有什么区别？
基础高频

一句话概括：Elasticsearch 是基于 Lucene 的分布式全文搜索引擎，用倒排索引实现秒级检索，定位与 MySQL 完全不同。

对比项ElasticsearchMySQL
定位分布式搜索引擎 / 分析引擎关系型数据库
索引结构倒排索引（全文检索）B+Tree（精确/范围查询）
写入近实时（秒级可见）事务 ACID，实时
强项全文搜索、相关度评分、聚合分析、海量日志强一致、复杂关联、事务
弱项事务弱、Join 能力弱模糊搜索性能差、海量数据扩展吃力
典型场景搜索、日志检索、监控分析业务核心数据存储

💡 常见组合：MySQL 存主数据，ES 同步做搜索（Binlog → MQ → ES），各取所长。

2
ES 的倒排索引（Inverted Index）原理？
核心原理高频

一句话概括：倒排索引是“词项 → 文档ID”的映射表：先对文档分词，再记录每个词出现在哪些文档，查询时直接查词找到文档，避免全表扫描。

  • 分词（Analyzer）：文档写入时按分析器切分成词项（token），如 “Elasticsearch 分布式搜索” → 分词后建表。
  • 结构：词项字典（Term Dictionary，有序）→ 倒排列表（Posting List，含文档ID、词频 TF、位置 Position、偏移）。
  • 查询过程：查询词 → 二分/跳表找词项 → 拿到倒排列表 → 合并（AND/OR）→ 按相关度打分排序。
  • 优化：词项字典用 FST 压缩（内存友好）、倒排列表用跳表 + Roaring Bitmap 加速合并。

💡 记忆点：正排是“文档→词”，倒排是“词→文档”，核心是空间换时间。

ES 为什么是近实时（Near Real Time）？写入流程是什么？
写入原理高频

一句话概括：数据先写入 内存 buffer + translog，默认每秒 refresh 一次生成可搜索的 segment，所以写入后约 1 秒才可被搜索到（近实时）。

  1. 写入内存 buffer：文档先写入分片的内存缓冲，此时不可搜索。
  2. 写 translog：同时追加写预写日志，用于崩溃恢复，防止数据丢失。
  3. refresh（默认 1s）：buffer 清空并生成内存中的 segment（OS 缓存），此后可被搜索。
  4. flush：translog 满（默认 512MB 或 30 分钟）时，把 segment fsync 落盘并删除旧 translog，生成 commit point。
  5. merge：后台合并小 segment 成大 segment，删除已删除文档，控制句柄与内存。

💡 调优：追求搜索实时性可调 refresh_interval；批量导入时可临时关闭 refresh，导入完再开启。

ES 的索引、分片（Shard）与副本（Replica）？
架构高频

一句话概括：索引（Index）是逻辑上的文档集合；物理上被拆成多个分片（Shard）分布在不同节点，每个分片可带副本（Replica）实现高可用与读扩展。

  • 主分片（Primary Shard）：写入必须走主分片，分片数在建索引时确定，之后不可修改。
  • 副本分片（Replica）：主分片的完整拷贝，用于容错与分摊读请求，可随时增减。
  • 路由：文档归属分片由 hash(routing) % 主分片数 决定，保证同一文档总落到同一分片。
  • 写入：请求到协调节点 → 路由到主分片 → 同步到副本 → 返回成功。
  • 分片数建议：单分片控制在 30–50GB 左右；集群规模按数据量与节点数规划，不宜过大。

💡 面试点：主分片数不可变，所以前期规划比后期扩容更重要；也可用 _reindex 重建索引调整分片数。

5
ES 集群的节点角色有哪些？
集群高频

一句话概括：节点按职责分为 Master、Data、Ingest、Coordinating 等角色，职责分离保证集群稳定与水平扩展。

  • Master 节点：负责集群元数据、索引创建/删除、分片分配，轻量不存数据；建议 node.master: true 且不参与数据。
  • Data 节点：真正存储分片、执行写入与查询，是集群的主力，可水平扩展。
  • Ingest 节点：负责写入前的预处理管道（如字段拆分、清洗）。
  • Coordinating 节点：只做请求路由、结果汇总（每个节点默认都是协调节点）。

💡 面试点：Master 最少 3 个候选（奇数）防止脑裂；数据节点多时查询汇总注意协调节点压力。

6
ES 中 query 和 filter 的区别？
查询高频

一句话概括：query 会计算相关度分数并影响排序，filter 只做过滤、不评分，且结果会被缓存，性能更好。

  • query：参与 _score 计算，适合全文检索、相关度排序（match、multi_match、match_phrase）。
  • filter：布尔过滤，结果二值化（命中/未命中），不评分不排序，走 filter cache 复用，性能高。
  • 组合：bool 查询中 must（评分） + filter（不评分） 搭配，既保证相关度又提升性能。
  • 示例：{"bool":{"must":[{"match":{"title":"手机"}}],"filter":[{"term":{"status":"1"}},{"range":{"price":{"gte":1000}}}]}}

💡 面试点：高频且不评分的条件（状态、时间范围）一律放 filter，利用缓存显著提速。

7
ES 的 keyword 和 text 字段有什么区别？
映射高频

一句话概括：text 会被分词用于全文检索，keyword 不分词整体存为单个词项，用于精确匹配、排序、聚合。

  • text：经分析器分词后建倒排索引，支持 match 全文搜索、模糊匹配；不支持直接做 term 精确匹配与聚合（除非开启 fielddata）。
  • keyword：整个字符串作为一个词项，适合 status、userId、订单号等；支持 term 精确匹配、range 范围、排序、聚合（bucket）。
  • 多字段（multi-fields）：常见做法 "title":{"type":"text","fields":{"keyword":{"type":"keyword"}}}，同字段兼顾搜索与聚合。
  • 长度限制：keyword 默认最长 256 字符（可配置），超长会被截断。

💡 面试点：需要“搜索用 text、精确/聚合用 keyword”，用 multi-fields 一个字段解决两种需求。

ES 深度分页问题与解决方案？
查询优化高频

一句话概括：from+size 越大，ES 需要把每个分片排序后的前 from+size 条全取回来再全局排序，内存开销爆炸，默认上限 index.max_result_window=10000。

  • 问题：深度分页（如第 10000 页）会让协调节点内存 OOM，性能急剧下降。
  • 方案一 search_after：基于上一页最后一条的 排序值游标继续翻页，适合“滚动加载”，无深翻页开销。{"search_after":[12.5,137224],"sort":[{"price":"desc"},{"_id":"asc"}]}
  • 方案二 scroll：服务端生成快照游标，适合导出、全量遍历（如数据迁移），不适合实时交互（有快照上下文开销）。
  • 方案三 PIT（Point In Time）：7.10+ 引入，search_after 配合 PIT 保证翻页期间数据一致。
  • 不适合：随机跳页仍用 from+size，但建议限制最大深度或改业务（如只允许前 1000 条）。

💡 记忆：交互翻页浅用 from+size，滚动加载用 search_after，全量导出用 scroll。

ES 的倒排索引和 MySQL 的 B+Tree 对比？为什么搜索用 ES？
核心原理

一句话概括：B+Tree 擅长精确/范围查询，倒排索引擅长分词后的全文检索，场景不同没有绝对优劣。

对比项倒排索引（ES）B+Tree（MySQL）
数据结构词项字典 + 倒排列表多路平衡树
检索方式词 → 文档（命中即得）二分查找叶子节点
全文检索强（分词、相关度打分）弱（LIKE %xx% 全表扫）
精确/范围一般（range 需专门优化）极快（索引有序）
模糊搜索支持（通配符，性能开销大）弱

为什么搜索用 ES：业务搜索本质是“按词找内容 + 相关度排序”，倒排索引天然匹配；MySQL 的 LIKE 无法利用索引且无法打分排序。

💡 面试点：强调两者互补——MySQL 管事务与精确查询，ES 管全文搜索与聚合分析。

ES 的聚合（Aggregation）是什么？常用类型？
聚合分析高频

一句话概括：聚合是 ES 的分析统计能力，类似 SQL 的 GROUP BY / 聚合函数，分桶聚合（Bucket）、指标聚合（Metric）、管道聚合（Pipeline）三类。

  • Bucket 桶聚合：把文档分组，如 terms（按字段分组）、date_histogram（按时间分桶，如按天统计）、range。
  • Metric 指标聚合：计算数值，如 avg、sum、min/max、cardinality（去重计数，近似）、percentiles（分位数）。
  • Pipeline 管道聚合：对前一个聚合结果再计算，如 bucket_script、avg_bucket。
  • 示例：按分类统计商品均价 —— {"aggs":{"by_cat":{"terms":{"field":"category.keyword"},"aggs":{"avg_price":{"avg":{"field":"price"}}}}}}
  • 注意：聚合字段需为 keyword 或 doc_values=true 的数值/日期字段。

💡 面试点：提到 ES 聚合常用于日志分析、销售报表、用户画像统计，替代部分 SQL 统计。

ES 集群的脑裂问题及解决方案？
集群高可用

一句话概括：脑裂指网络分区时集群被拆成多个“小集群”各自选举 Master，导致数据不一致；通过最小投票数与角色分离避免。

  • 现象：主节点与部分节点网络中断，另一部分节点因看不到主节点而重新选举出新 Master，出现两个 Master。
  • 方案一 discovery.zen.minimum_master_nodes（7.x 前）：设置为 候选主节点数/2 + 1，只有获得足够票数的节点才能成为 Master，保证同时只有一个。
  • 方案二（7.x+）：使用 cluster.initial_master_nodes 引导 + Zen2 选主（类似 Raft，需要多数派），并配置 discovery.seed_hosts。
  • 方案三 角色分离：Master 节点只当候选主节点（node.data: false），避免数据节点网络抖动影响选主。
  • 辅助：适当调大 discovery.zen.fd.ping_timeout，减少误判故障。

💡 面试点：脱口而出 “minimum_master_nodes = n/2 + 1”，并说明这是防脑裂的核心手段。

ES 的 refresh、flush、merge 分别是什么？
写入原理

一句话概括：三者是 segment 生命周期的关键动作：refresh 让数据可搜索，flush 让数据落盘，merge 合并小段提升查询与清理删除文档。

  • refresh（默认 1s）：内存 buffer → 生成 segment（在 OS 缓存中），可搜索但未持久化；可设 refresh_interval=-1 关闭（批量导入时）。
  • flush（默认 translog 512MB 或 30min）：segment fsync 落盘、清空 translog、写 commit point；是真正“持久化”的动作。
  • merge：后台把多个小 segment 合并成大 segment，减少 segment 数量（降低句柄/内存），并真正物理删除被标记删除的文档；会消耗 IO，可限速 indices.store.throttle。

💡 记忆口诀：refresh 可见、flush 落盘、merge 合并，三者构成 ES 写入链路的关键动作。

ES 的写入、更新、删除如何保证一致性？
一致性

一句话概括：ES 采用主分片写、副本同步 + translog 预写日志 + 版本号乐观并发控制，保证最终一致与崩溃不丢数据。

  • 写入一致性：写主分片成功并同步到副本（默认 wait_for_active_shards 可配置），协调节点返回成功。
  • 崩溃恢复：translog 记录所有写操作，宕机后重放 translog 恢复未 flush 的数据，不丢已确认写入。
  • 更新/删除：ES 文档不可变，更新=先删旧文档再写新文档；删除是标记删除，由 merge 真正清理。
  • 乐观锁：文档带 _version，更新时带上版本，版本不一致则失败（冲突可重试）。
  • 近实时限制：副本可见有延迟，可通过 _primary 强制读主分片但会牺牲性能。

💡 面试点：强调 ES 是最终一致，与数据库强一致不同，适合搜索场景。

ES 的 Analyzer 分词器有哪些？中文分词怎么配？
分词高频

一句话概括：分析器由 字符过滤器 + 分词器（Tokenizer）+ Token 过滤器 组成；中文默认不支持，需装 IK / 拼音 插件。

  • 内置分词器：standard（默认，按空格/标点切分）、keyword（不分词）、whitespace、simple、english（英文词干还原）。
  • 中文痛点：标准分词器对中文按单个字符切分，无法识别词语边界与语义。
  • 解决方案：安装 IK Analyzer（支持 ik_max_word 最细粒度 / ik_smart 智能切词），常见搭配 拼音分词器 做拼音搜索。
  • 自定义：PUT /index/_settings 配置分析器，字段映射里指定 "analyzer":"ik_max_word","search_analyzer":"ik_smart"。
  • 验证：POST /index/_analyze {"text":"中华人民共和国","analyzer":"ik_max_word"}。

💡 面试点：提到 索引用 ik_max_word（召回全）、搜索用 ik_smart（更精准） 的经典组合。

ES 生产环境如何优化与调优？
性能优化高频

一句话概括：调优围绕内存（堆）、磁盘（SSD）、索引设计、查询写法四个维度，核心是“减少不必要的开销”。

索引与映射：

  • 只索引需要的字段（"index":false）、合理设置分片数、避免字段过多；keyword 与 text 按需设计。
  • 日志类按时间滚动索引（ILM 索引生命周期管理），控制段数量。

查询优化：

  • 能 filter 不 query（走缓存）；避免 wildcard 开头通配符；控制 size；深分页用 search_after。
  • 聚合字段开启 doc_values；避免大结果集聚合。

节点与内存：

  • 堆内存建议 31GB（ES_JAVA_OPTS=-Xms31g -Xmx31g），留给 OS Page Cache 更多空间。
  • 关闭 swap；数据盘用 SSD；磁盘水位线监控（cluster.routing.allocation.disk.watermark）。
  • 批量写入用 _bulk（建议 5–15MB/批），必要时临时调大 refresh_interval 与 translog 参数。

💡 面试点：记住 “堆别超 31GB、SSD、filter 缓存、bulk 批量写” 四条硬核优化即可。
