Redis 的持久化机制？RDB 和 AOF 的区别？
持久化高频

定义：

持久化是把内存数据落盘保存，防止进程重启或宕机后数据丢失。

Redis 提供 RDB、AOF、混合持久化三种方式。

RDB（快照持久化）：

  • 原理：
    fork 子进程生成内存数据快照写入 dump.rdb；
    默认 save 900 1 / 300 10 / 60 10000 自动触发，也可手动 BGSAVE。
  • 优点：
    文件小、恢复快、适合冷备；
    子进程写文件不阻塞主线程。
  • 缺点：
    可能丢失最后一次快照之后的所有数据。

AOF（追加式持久化）：

  • 原理：
    把每条写命令追加到 appendonly.aof
  • fsync 策略可配 always / everysec / no，默认每秒一次。
  • 优点：
    数据安全，最多丢 1 秒数据（everysec）。
  • 缺点：
    文件大、恢复重放慢
  • 需 BGREWRITEAOF 压缩（合并历史命令）。

对比：

对比项RDBAOF
原理fork 子进程写快照追加写命令
恢复速度快慢（重放命令）
数据安全可能丢最后一次快照后数据最多丢 1 秒（可配置）
文件大小小（二进制压缩）大（文本）
rewrite不需要BGREWRITEAOF 压缩

混合持久化（Redis 4.0+）：

AOF rewrite 时用 RDB 二进制格式做文件头，之后增量命令以 AOF 格式追加，兼顾恢复快 + 丢数据少。

💡 面试点：

先分别说 RDB/AOF 原理与优缺点，再推荐「RDB 冷备 + AOF 保数据」混合方案，最后提 4.0 混合持久化。

如何用 Redis 实现分布式锁？
分布式锁高频

定义：

分布式锁用于多个服务实例之间互斥访问共享资源，保证同一时刻只有一个客户端能执行临界区代码。

核心命令：

SET key value NX PX timeout（Redis 2.6.12+ 一条命令原子完成加锁 + 过期）。

  • 加锁：
    SET lock_key uuid NX PX 30000——NX 保证互斥（key 不存在才设），PX 30 秒防死锁，uuid 是客户端唯一标识。
  • 解锁：
    用 Lua 脚本先判断 value(uuid) 是否是自己再 DEL，保证判断 + 删除原子执行，防止误删别人的锁。
  • 锁续期：
    Redisson 看门狗（Watch Dog）每 10 秒自动续期，防止业务未执行完锁就过期。

解锁 Lua 示例：

if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

可靠性提升：

RedLock 算法——向多个独立节点申请锁，过半数成功才算获取，缓解主从切换导致的锁丢失。

💡 面试点：

按「SET NX EX 加锁 + Lua 释放 + 看门狗续期」三要素回答；

展开误删、续期、主从不一致三大问题（详细见 Q14/Q15）。

Redis 的内存淘汰策略有哪些？
内存淘汰

定义：

当 Redis 内存达到 maxmemory 上限时，根据 maxmemory-policy 策略淘汰部分 key 以腾出空间。

8 种策略（按「数据范围 × 淘汰算法」记忆）：

策略说明适用场景
noeviction（默认）不淘汰，写操作报错不允许丢数据
allkeys-lru所有 key 中淘汰最近最少使用热点有明显冷热（最常用）
allkeys-lfu所有 key 中淘汰使用频率最低（4.0+）访问频率差异大
allkeys-random所有 key 中随机淘汰数据访问均匀
volatile-lru仅有过期时间的 key 中 LRU 淘汰部分 key 需永久保留
volatile-lfu仅有过期时间的 key 中 LFU 淘汰（4.0+）同上 + 频率差异
volatile-random仅有过期时间的 key 中随机淘汰同上 + 均匀访问
volatile-ttl淘汰 TTL 最短（即将过期）的尽快释放内存

LRU vs LFU：

LRU 看「多久没访问」（时间局部性）；

LFU 看「访问频率」（4.0+，避免偶发大流量把冷数据刷成热点）。

💡 面试点：

用「allkeys/volatile × lru/lfu/random/ttl + noeviction」矩阵记 8 种策略；

生产推荐 allkeys-lru 或 allkeys-lfu。

详细对比见 Q20。

Redis 主从复制的原理？
主从集群

定义：

主从复制让从节点实时同步主节点的数据，实现读写分离（主写从读）与数据冗余备份，是哨兵和集群高可用的基础。

全量复制（首次连接 / 断档重连）：

  1. 从节点执行 SLAVEOF host port（或配置 replicaof）发送 PSYNC 请求。
  2. 主节点执行 BGSAVE 生成 RDB 快照，同时把期间写命令缓存到复制缓冲区。
  3. 主节点发送 RDB 给从节点，从节点清空旧数据并加载。
  4. 主节点把缓冲区中的写命令继续发给从节点，完成追赶。

增量复制（实时同步）：

主节点将每个写命令实时推送给从节点，基于 replication backlog 缓冲区记录复制偏移量（offset）。

断线重连（PSYNC 2.0）：

从节点重连后携带 offset，主节点判断 offset 是否仍在 backlog 内：

在 → 增量同步；

不在 → 全量同步。

特点：

同步是异步的，主从存在短暂延迟；

从节点默认只读，防止写入不一致。

💡 面试点：

区分「首次全量 + 实时增量 + 断线续传」三阶段；

被问主从延迟：

强制主读、容忍短暂不一致、或者加延迟感知策略。

Redis 哨兵（Sentinel）机制？
哨兵高可用

定义：

哨兵（Sentinel）是 Redis 的高可用解决方案，在主节点故障时自动完成故障转移，无需人工干预。

三大功能：

  • 监控：
    每个哨兵每 1 秒 PING 主/从节点，判断是否存活；
    哨兵之间也互相通信。
  • 通知：
    节点故障时向管理员/客户端推送告警，并通知客户端新主节点地址。
  • 自动故障转移：
    主节点宕机后，从节点中选举出新主节点，其他从节点自动切换复制目标。

下线判定：

  • 主观下线（sdown）：
    单个哨兵判断主节点不可达。
  • 客观下线（odown）：
    超过 quorum 个哨兵都认为主节点不可达，才触发故障转移，防止误判。

选主过程：

哨兵间通过 Raft 共识选出 Leader → Leader 按「优先级 → 复制偏移量（数据最新）→ runid 最小」选择最优从节点 → 提升为新 Master。

💡 面试点：

Sentinel 至少 3 个实例（奇数）防脑裂；

按「监控 → 下线判定（sdown/odown）→ 故障转移」三步回答。

Redis Cluster（集群模式）原理？
集群分片

定义：

Redis Cluster 是去中心化的分布式集群方案，将数据按 16384 个哈希槽（hash slot）分片存储到多个主节点，支持水平扩展与自动故障转移。

分片方式：

slot = CRC16(key) % 16384，16384 个槽分配到不同节点，节点增减时只需迁移部分槽。

数据路由：

  • MOVED 重定向：
    key 的槽不在当前节点，返回「槽号 + 目标节点」，客户端缓存后直连。
  • ASK 重定向：
    槽正在迁移中，客户端临时去目标节点查询。

高可用：

每个主节点可配多个从节点，主节点挂掉由从节点自动接管（内部类似哨兵机制）。

去中心化：

节点间通过 Gossip 协议交换状态（心跳包），无中心代理，客户端可连任意节点。

限制：

不支持多 key 跨槽操作（可用 hash tag {user:1}:name 强制同槽）、Lua 脚本涉及 key 必须在同一节点、批量操作需客户端合并。

💡 面试点：

答「16384 槽 + CRC16 定位 + MOVED/ASK + Gossip」四个要点；

问为什么 16384：

槽 bitmap 心跳包约 2KB，平衡消息大小与槽粒度。

Redis 为什么这么快？
性能高频

概述：

Redis 单实例可达 10W+ QPS，核心原因是「纯内存 + 单线程 + IO 多路复用 + 高效数据结构」。

  1. 纯内存操作：
    数据全部在内存，读写为纳秒级，无磁盘寻址和随机 IO。
  2. 单线程模型：
    避免多线程上下文切换和锁竞争
  3. 命令天然原子，实现简单无死锁。
  4. IO 多路复用：
    用 epoll/kqueue 同时监听成千上万连接，事件就绪才处理，不空转等待。
  5. 高效数据结构：
    SDS（避免字符串拼接 O(n)）、跳表（O(logn) 有序）、quicklist、listpack 等针对场景定制。
  6. 其他优化：
    整数集合/压缩内存省内存提缓存命中；
    渐进式 rehash 避免大字典扩容卡顿。

为什么单线程反而快：

Redis 瓶颈在网络 IO 而非 CPU，单线程免锁、免上下文切换，性能反而更好

所以 Redis 6.0 只把网络 IO 多线程化，命令执行保持单线程。

💡 面试点：

强调「瓶颈在 IO 不在 CPU」是单线程成立的逻辑前提

6.0 多线程只负责网络读写，不碰命令执行。

Redis 过期键删除策略？
过期内存

定义：

Redis 对设置了过期时间的 key，采用惰性删除 + 定期删除组合策略清理，防止过期数据长期占用内存。

惰性删除（Lazy）：

  • 原理：
    每次访问 key 时先检查是否过期，过期则删除并返回 nil。
  • 优点：
    只在访问时才检查，CPU 开销最小。
  • 缺点：
    过期但长期不被访问的 key 会一直占用内存。

定期删除（Active）：

  • 原理：
    后台每 100ms 随机抽 20 个 key 检查，过期比例 >25% 则继续抽，直到比例 <25% 或耗时 >25ms。
  • 优点：
    均衡 CPU 与内存，弥补惰性删除的漏网。
  • 缺点：
    仍有残留；
    大量 key 同时过期会造成延迟毛刺。

为什么不用定时删除：

为每个 key 维护定时器成本极高，大量 key 同时到期会瞬间消耗 CPU、阻塞主线程。

示例：

过期命令 EXPIRE user:1001 300

可用 TTL key 查看剩余时间。

💡 面试点：

先答两种策略原理与优缺点，再区分「过期删除 ≠ 内存淘汰」——过期删除针对有过期时间的 key，内存淘汰针对内存满的场景（见 Q20）。

布隆过滤器（Bloom Filter）的原理和应用？
布隆过滤器高级

定义：

布隆过滤器是一种概率型数据结构，用极小的内存快速判断「元素是否可能存在」，常用于拦截无效查询。

原理：

  • 初始化一个 m 位的位数组，全部置 0。
  • 插入元素：
    用 k 个哈希函数计算 k 个位置，全部置 1。
  • 查询元素：
    k 个位置全部为 1 才认为可能存在；
    任一位置为 0 则一定不存在。

特性：

  • 「一定不存在」是准确的；
    「存在」可能有误判（哈希碰撞）。
  • 误判率可控制：
    位数组越大、哈希函数越多，误判率越低。
  • 不支持删除（置 0 会影响其他元素判断）。

应用：

防止缓存穿透、URL 去重、垃圾邮件过滤、黑名单拦截。

Redis 实现：

RedisBloom 模块（BF.ADD / BF.EXISTS），或基于 SETBIT / GETBIT 手动实现。

示例：

缓存穿透防护——查询前先 BF.EXISTS key，不存在直接返回，避免无效请求打到 DB。

💡 面试点：

讲清「位数组 + k 个哈希函数 + 误判率可控」；

能推出误判率公式 p ≈ (1−e^(−kn/m))^k 是加分项。

Redis 如何保证数据一致？（缓存和数据库一致性）
一致性实战

问题定义：

缓存与数据库是两份数据，写操作处理不当会产生脏读 / 数据不一致。

错误做法：

「先更新 DB 再更新缓存」或「先更新缓存再更新 DB」——并发写会导致旧值覆盖新值。

推荐方案：

Cache Aside（旁路缓存）

  • 读：
    先读缓存 → 命中返回 → 未命中读 DB → 回写缓存。
  • 写：
    先更新 DB → 再删除缓存（不是更新缓存）。

为什么删除而非更新：

并发写时「更新缓存」容易旧值覆盖新值；

删除缓存后下次读会重新加载，最安全。

延迟双删：

先删缓存 → 更新 DB → 延迟再删一次，解决「删除后、更新 DB 前」读请求回写旧数据的窗口期问题。

最终一致方案：

Canal 监听 MySQL binlog → MQ → 异步删除/更新缓存，应用解耦且删除失败可重试。

兜底：

缓存设置合理过期时间，用过期兜底，容忍秒级短暂不一致。

💡 面试点：

答「写 DB 删缓存 + 延迟双删 + Canal binlog 最终一致」三层方案；

强调大多数场景容忍秒级不一致。

Redis 的 pipeline 是什么？原理和注意事项？
Pipeline优化基础

Pipeline(管道)：

将多个命令打包成一批一次发送，一次性接收所有结果，减少 RTT（网络往返时间）。

原理：

客户端批量发送 → Redis 批量执行 → 批量返回结果，省去逐条命令的网络等待。

注意事项：

  • 不是原子操作：
    Pipeline 只是减少网络开销，命令之间可能插入其他客户端的命令
  • Pipeline 内某个命令失败，后续命令仍会执行，Redis 不会回滚。
  • 与事务(MULTI/EXEC)的区别：
    事务保证原子性，Pipeline 不保证；
    需要原子性用事务，需要批量性能用 Pipeline。


    两者可以结合使用（Pipeline 包裹 MULTI/EXEC）。
  • 数量控制：
    一次 Pipeline 命令不宜过多（占用客户端与服务端内存缓冲区），建议拆分为小批次（如每批 500~1000 条）。
  • Cluster 限制：
    Cluster 模式下 Pipeline 内的命令必须落在同一节点（同一 slot）
  • 跨 slot 需用 hash tag（如 {user}:123）强制路由到同一节点。
  • 不会阻塞 Redis：
    Pipeline 中的命令在 Redis 中仍是逐个串行执行，不会阻塞其他客户端
  • 但客户端需等待全部结果返回后才能继续。

💡 面试点：

先说原理（减少 RTT），再强调「Pipeline ≠ 事务、无回滚」，最后补充数量控制、Cluster 同 slot 限制与 hash tag 解决方案。

Redis 分布式锁如何实现？有哪些问题？
分布式锁高频

一句话概括：

Redis 分布式锁 = SET NX EX 获取锁 + Lua 脚本释放锁 + 看门狗续期，核心难点是防误删、防超时、防主从不一致。

1. 基础实现（SET NX EX）：

Redis 2.6 之前用 SETNX + EXPIRE 两条命令，存在非原子性（SETNX 后崩溃导致锁永不过期）。

Redis 2.6.12 起用一条命令原子解决：

SET lock_key unique_value NX EX 30
  • NX：
    只有当 key 不存在时才设置（互斥）。
  • EX 30：
    设置 30 秒过期时间（防死锁）。
  • unique_value：
    每个客户端生成唯一标识（如 UUID + 线程 ID），用于释放时校验「只能删自己的锁」。

2. 锁释放（Lua 脚本原子释放）：

不能用先 GET 再 DEL 的两步操作（中间可能被其他线程插入），必须用 Lua 脚本保证判断 + 删除原子执行：

if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

Java 调用示例（Jedis）：

3. Redisson 方案（生产首选）：

Redisson 封装了完整的分布式锁，核心机制：

  • 加锁：
    RLock lock = redisson.getLock("myLock"); lock.lock(); 底层也是 SET NX EX，但加入了看门狗（Watch Dog）自动续期。
  • 看门狗续期：
    默认锁过期 30 秒，看门狗每 10 秒（leaseTime / 3）自动续期到 30 秒；
    业务执行完手动 unlock() 后取消看门狗。
  • 可重入：
    同一线程可多次获取锁，内部用 Hash 结构记录重入次数。
RLock lock = redisson.getLock("order:123");
try {
    // 尝试加锁，最多等待 10 秒，锁持有 30 秒（看门狗自动续期）
    boolean locked = lock.tryLock(10, 30, TimeUnit.SECONDS);
    if (locked) {
        // 执行业务逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}

4. 核心问题与解决方案：

  • 锁误删（谁都能删）：
    没有 value 校验时，A 的锁过期后 B 获取锁，A 执行完仍 del 会把 B 的锁删掉。


    解决：
    释放锁前用 Lua 脚本校验 value 是否匹配。
  • 锁续期（业务超时）：
    业务执行时间超过锁过期时间，锁自动释放后其他线程获取锁，导致并发安全问题。


    解决：
    Redisson 看门狗自动续期；
    或自行启动后台线程定时续期。
  • 主从切换（锁丢失）：
    主节点写锁后宕机，锁数据未同步到从节点，从节点晋升为主节点后，其他线程可以再次获取锁。


    解决：
    RedLock 算法（向 N 个独立 Redis 实例申请锁，过半成功才算获取）；
    或直接用 Zookeeper/Etcd 等 CP 系统。
  • 不可重入：
    SET NX EX 本身不可重入，同一线程再次获取会失败。


    解决：
    Redisson 用 Hash 结构 + 重入计数实现可重入锁。

RedLock 算法的原理和争议？
RedLock深入

定义：

RedLock 是 Redis 作者 Antirez 提出的多主节点分布式锁算法，核心思想是：

向多个独立的 Redis 主节点申请锁，只有过半数节点成功才算真正获取锁。

目的是解决单节点 Redis 分布式锁的主从切换导致锁丢失问题。

为什么需要 RedLock：

单节点 Redis 锁（SET NX EX）的问题是——主节点写锁后若宕机，锁数据可能未同步到从节点，从节点晋升为主后其他客户端可以再次获取锁，导致同一时刻两个客户端同时持有锁。

RedLock 通过在多个独立节点上同时申请锁，降低单点故障带来的风险。

原理（5 个独立节点为例）：

  1. 获取当前时间戳 T1：
    记录开始申请锁的时间。
  2. 依次向 5 个独立 Redis 节点申请锁：
    对每个节点执行 SET resource_name random_value NX PX ttl（PX 单位毫秒）。


    每个节点申请都有独立的超时时间（如 10ms），超过则立即放弃该节点，避免阻塞。
  3. 计算获取锁耗时：
    获取当前时间戳 T2，耗时 = T2 - T1。
  4. 判断是否获取成功：
    若超过半数（≥3 个）节点成功加锁，且耗时 < 锁的 TTL，则获取锁成功。
  5. 计算锁的实际有效时间：
    锁剩余时间 = TTL - 获取锁耗时。


    例如 TTL=100ms，耗时 30ms，则实际有效时间只有 70ms。
  6. 失败则释放所有节点锁：
    向全部 5 个节点发送 Lua 脚本释放锁（不管该节点是否加锁成功，都要尝试释放，防止部分成功导致的残留）。

伪代码示例：

function redLock(lockKey, ttl, randomValue):
    nodes = [redis1, redis2, redis3, redis4, redis5]
    quorum = len(nodes) / 2 + 1  // 3
    lockedNodes = []
    start = currentTimeMillis()

    for node in nodes:
        try:
            // 每个节点申请锁，设置 10ms 超时，避免阻塞
            result = node.set(lockKey, randomValue, "NX", "PX", ttl, timeout=10ms)
            if result == "OK":
                lockedNodes.add(node)
        except Timeout:
            continue

    elapsed = currentTimeMillis() - start
    validTime = ttl - elapsed

    if len(lockedNodes) >= quorum and validTime > 0:
        // 获取锁成功，validTime 为实际可用时间
        return { success: true, validity: validTime }
    else:
        // 失败，向所有节点释放锁
        for node in nodes:
            node.eval(unlockScript, [lockKey], [randomValue])
        return { success: false }

争议（Martin Kleppmann vs Antirez）：

Martin Kleppmann（分布式系统专家、《DDIA》作者）认为 RedLock 存在根本性问题：

  • 时钟跳跃：
    若 Redis 节点发生 NTP 时间回拨，可能导致已发出的锁被认为未过期，而新的客户端又能获取锁。
  • GC pause / 网络延迟：
    客户端在申请锁后发生长时间 GC 或网络抖动，导致锁实际已过期但客户端不知情，继续执行业务，此时其他客户端已获取锁。
  • 锁续期难题：
    RedLock 没有自动续期机制，业务执行超过锁有效期会出问题。
  • 核心结论：
    RedLock 依赖系统时钟假设（时钟单调、网络延迟有界），但在分布式系统中这两个假设都不成立，因此不能提供严格的互斥保证。

Redis 作者 Antirez 的回应：

  • 承认上述问题在理论上存在，但认为实际生产环境中概率极低（需同时满足时钟跳跃 + GC pause + 网络延迟 + 过半节点异常）。
  • 强调 RedLock 是为了解决主从切换锁丢失这一特定问题，比单节点锁更安全。
  • 建议在高可靠性场景下，RedLock 配合fencing token（边界令牌）使用，业务执行前校验 token 是否匹配，进一步增强安全性。

实际选型建议：

  • 绝大多数业务：
    单节点 Redis + Redisson（看门狗续期 + Lua 释放），主从切换问题通过 Redis Sentinel/Cluster 高可用缓解。
  • 对一致性要求极高的金融场景：
    Zookeeper 或 Etcd（CP 系统，天然保证一致性，无需担心时钟问题）。
  • 折中方案：
    RedLock + fencing token，但实现复杂度高，需权衡收益。

💡 面试点：

先说定义和原理（N 个独立节点 + 过半数 + TTL 扣减耗时），再说伪代码流程，最后展开争议（时钟假设 vs 实际概率），给出选型建议。

Redis 哨兵（Sentinel）模式原理？
Sentinel高频

定义：

Sentinel 是 Redis 高可用方案，解决「主节点故障时系统不可用」的问题，实现监控 + 通知 + 自动故障转移。

架构：

Sentinel 是独立进程，通常部署 3~5 个（奇数）形成哨兵集群，共同监控主从节点。

工作流程：

  1. 监控：
    每 1 秒 PING 主/从节点判断存活，哨兵之间也互相通信交换状态。
  2. 下线判定：
    单个哨兵判定不可达 → 主观下线（sdown）；
    ≥quorum 个哨兵确认 → 客观下线（odown），触发故障转移。
  3. 选举 Leader：
    哨兵集群通过 Raft 共识选出一个 Leader 执行转移。
  4. 选新 Master：
    按「优先级（slave-priority）→ 复制偏移量（数据最新）→ runid 最小」选择。
  5. 切换：
    新 Master 上线，其他从节点切换复制目标，更新配置并通知客户端。

脑裂防护：

哨兵用多数派（quorum）确认，主节点失联需多数哨兵同意才转移，避免两个主节点并存。

💡 面试点：

答「sdown/odown 判定 + Raft 选主 + 最优从节点选举」即可；

与 Cluster 的故障转移机制对比记忆更牢固。

Redis Cluster 原理和槽位分配？
Cluster高频

定义：

Redis Cluster 是官方分布式集群方案，通过 16384 个哈希槽做数据分片，支持在线扩缩容与自动故障转移。

槽位分配原理：

  1. key 计算槽位：
    slot = CRC16(key) % 16384。
  2. 创建集群时把 16384 个槽按数量均分给各主节点（可用 redis-cli --cluster 工具调整）。
  3. 客户端只需连接任一节点，通过重定向找到数据所在节点。

路由机制：

  • MOVED 重定向：
    槽属于其他节点，返回目标节点地址，客户端应更新本地槽映射后重试。
  • ASK 重定向：
    槽正在迁移中，数据可能在目标节点，客户端带 ASKING 标记临时访问。

hash tag：

{user:1}:name 只对 {} 内做 CRC16，使相关 key 落在同槽，支持事务和 Lua。

为什么不选一致性哈希：

槽与节点映射可灵活迁移（按槽粒度），数据分布更均匀，扩缩容只需迁移部分槽。

💡 面试点：

重点答「CRC16 % 16384 + MOVED/ASK 区别 + hash tag 用途」；

问为什么 16384：

Gossip 心跳携带槽 bitmap 约 2KB，合理折中。

Redis 主从复制原理和过程？
主从复制高频

定义：

主从复制指从节点同步主节点数据，实现读写分离、数据备份、故障恢复基础。

全量同步（首次 / 断档）：

  1. 从节点发送 PSYNC 请求。
  2. 主节点执行 BGSAVE 生成 RDB，同时缓存期间新写命令。
  3. 主节点发送 RDB，从节点清空旧数据并加载。
  4. 主节点发送缓冲区中的写命令，追赶增量。

增量同步（实时）：

主节点将每个写命令实时推送给从节点，从节点记录复制偏移量（offset）。

断线续传（PSYNC 2.0）：

主节点维护 replication backlog 环形缓冲区（默认 1MB）。

从节点重连后发送 offset，若 offset 仍在 backlog 内 → 增量同步；

否则 → 全量同步。

特点：

同步异步，主从存在秒级以内延迟；

从节点默认只读。

主从延迟处理：

实时性要求高的读走主节点；

或用版本号/时间戳校验，过期数据降级重读。

💡 面试点：

答「全量 + 增量 + PSYNC 断线续传」三阶段；

问延迟怎么解决：

强制主读、容忍短暂不一致、延迟感知。

讲讲 Redis 4.0 混合持久化
持久化高频

一句话概括：

Redis 4.0 混合持久化 = RDB 快照 + AOF 增量日志，重启时先加载 RDB 恢复主体数据，再重放少量 AOF 命令补齐，兼顾恢复快与丢数据少。

为什么需要它？纯 RDB 恢复快但可能丢最后一次快照后的数据；

纯 AOF 丢数据少但文件大、恢复重放慢。

混合持久化取两者之长。

开启方式：

Redis 4.0+ 配置文件设置 aof-use-rdb-preamble yes（默认开启）。

工作原理：

AOF rewrite 时以 RDB 二进制格式作为 AOF 文件头写入主体快照，之后增量写命令以 AOF 格式追加到文件尾部

重启加载时先解析 RDB 部分快速恢复，再重放尾部少量 AOF 命令。

优点：

  • 加载快：
    主体数据由 RDB 恢复，无需重放全部命令。
  • 丢数据少：
    AOF 部分最多丢 1 秒/1 个命令。
  • 文件更小：
    比纯 AOF 显著减少。

注意事项：

AOF 追加部分仍会增长，需定期 rewrite；

Redis 4.0 之前版本无法识别混合格式 AOF 文件。

Redis 删除策略和内存淘汰策略？
过期删除内存淘汰

一句话概括：

过期删除策略解决「过期 key 怎么删」，内存淘汰策略解决「内存满了删谁」。

过期键删除策略（惰性删除 + 定期删除）：

  • 惰性删除（Lazy Expiration）：
    每次访问 key 时先检查是否过期，过期则立即删除并返回 nil。


    优点是只在使用时才检查，不额外消耗 CPU；
    缺点是过期但长期不被访问的 key 会一直占用内存，可能造成内存泄漏。
  • 定期删除（Active Expiration）：
    Redis 后台每 100ms（每秒约 10 次）执行一次过期清理，每次随机抽取 20 个 key 检查，如果过期比例 >25% 则继续循环抽取，直到比例低于 25% 或单次运行超过 25ms 为止。


    优点是平衡了 CPU 和内存；
    缺点是仍有残留，且如果同时大量 key 过期会触发循环清理，造成延迟毛刺。
  • 为什么不用定时删除：
    为每个 key 维护定时器成本极高，大量 key 同时过期会瞬间消耗大量 CPU，阻塞主线程。

内存淘汰策略（maxmemory-policy，当内存达到 maxmemory 时触发）：

8 种策略按「数据范围 + 淘汰算法」分类：

  • noeviction（默认）：
    不淘汰任何数据，写操作直接返回错误。


    生产环境通常需要显式改为其他策略。
  • allkeys-lru：
    在所有 key 中，淘汰最近最少使用的。


    最常用，适合热点数据有明显冷热之分。
  • allkeys-lfu（Redis 4.0+）：
    在所有 key 中，淘汰使用频率最少的。


    适合访问频率差异大的场景。
  • allkeys-random：
    在所有 key 中随机淘汰。


    简单但命中率低，一般不推荐。
  • volatile-lru：
    仅在设置了过期时间的 key 中，按 LRU 淘汰。


    适合部分数据需要持久保留、部分可淘汰的场景。
  • volatile-lfu（Redis 4.0+）：
    仅在设置了过期时间的 key 中，按 LFU 淘汰。
  • volatile-random：
    仅在设置了过期时间的 key 中随机淘汰。
  • volatile-ttl：
    仅在设置了过期时间的 key 中，淘汰TTL 最短（即将过期）的。


    适合希望尽快释放内存的场景。

LRU vs LFU 怎么选：

  • LRU 看「多久没访问」，适合数据访问有明显时间局部性的场景（如最近的新闻、会话缓存）。
  • LFU 看「访问频率高低」，适合数据价值与访问次数强相关的场景（如热门商品排行榜）。

生产建议：

通用场景推荐 allkeys-lru；

若数据冷热差异极大用 allkeys-lfu；

需保留部分 key 永不过期时用 volatile-lru。

同时配合 过期时间 + 随机偏移 避免雪崩。

💡 面试点：

先说「惰性+定期」两种过期删除策略的优缺点和触发时机，再说 8 种淘汰策略的分类逻辑（allkeys/volatile × lru/lfu/random/ttl + noeviction），最后给出 allkeys-lru 的选型理由。

Redis 单线程为什么还这么快？
性能高频

概述：

「Redis 单线程」指命令执行是单线程（6.0 起网络 IO 可多线程），却依然能支撑 10W+ QPS。

原因：

  1. 纯内存：
    数据在内存，读写纳秒级，CPU 不是瓶颈。
  2. 单线程免竞争：
    无锁、无上下文切换、无死锁
  3. 命令天然原子，实现简单。
  4. IO 多路复用：
    epoll 事件驱动，一个线程监听海量 socket，就绪才处理，空闲不占 CPU。
  5. 高效数据结构：
    SDS、跳表、quicklist、哈希表均针对内存场景优化。

为什么单线程比多线程快：

多线程加锁的成本 > 收益（Redis 是纯 CPU + 内存操作，无需等待 IO）

上下文切换破坏 CPU 缓存局部性。

真正的瓶颈是网络 IO，所以 6.0 把网络读写改成多线程，命令执行保持单线程。

示例：

10W QPS 场景下，单线程 epoll 每秒处理约 10 万事件循环，每个事件耗时极短，无需多核。

💡 面试点：

逻辑链：

内存快 → CPU 非瓶颈 → 单线程免竞争反而快 → 瓶颈在 IO → 6.0 多线程化网络 IO。

Lua 脚本在 Redis 中的使用和原子性？
Lua原子操作

定义：

Redis 内置 Lua 解释器，通过 EVAL / EVALSHA 执行脚本。

脚本整体原子执行（执行期间其他命令被阻塞），天然解决「多命令组合的原子性」问题。

使用场景：

  • 原子性校验 + 操作：
    如「先判断库存再扣减」。
  • 分布式锁释放：
    get 判断 + del 删除原子化。
  • 限流：
    固定窗口计数 + 过期。
  • 复杂逻辑合并，减少网络往返。

原子扣库存

if stock >= tonumber(ARGV[1]) then
    return redis.call("decrby", KEYS[1], ARGV[1])
else
    return -1
end

jedis.eval(script, keys, args)；

定义：

三个经典缓存问题本质都是大量请求绕过缓存打到数据库，但触发原因不同，需要区分解决。

问题原因现象解决方案
缓存穿透查询不存在的数据（恶意攻击 / 非法 id）缓存永远不命中，直接打 DB① 布隆过滤器前置拦截

如何保证缓存与数据库一致性？（Cache Aside）
缓存一致性超高频

定义：

Cache Aside（旁路缓存）是业界最常用的缓存读写模式，核心思想是应用主动管理缓存，缓存不参与强一致性。

读流程：

先读缓存 → 命中直接返回 → 未命中查 DB → 回写缓存 → 返回。

写流程：

先更新 DB → 再删除缓存（注意：

不是更新缓存）。

为什么写后删除而不是更新：

  • 并发写场景下「更新缓存」容易旧值覆盖新值（A 写新值、B 写旧值，B 后更新缓存导致脏数据）。
  • 删除缓存最安全：
    下次读 miss 时重新加载，保证读到最新 DB 数据。

遗留问题（读写并发窗口）：

读请求在「删缓存后、更新 DB 前」把旧 DB 值回写缓存 → 脏缓存。

解决：

延迟双删——先删缓存 → 更新 DB → 延迟（如 500ms）再删一次缓存，保证窗口期回写的旧数据被清掉。

最终一致性增强：

Canal 监听 binlog → 异步删除 / 更新缓存（MQ 消费），应用解耦，删除失败可重试。

💡 面试点：

答「写 DB 删缓存 + 延迟双删 + binlog 异步补偿」三层；

强调缓存设过期时间兜底，容忍秒级不一致。

Redis 的 Bitmap 和 HyperLogLog 应用场景？
高级结构

Bitmap（位图）：

基于 String 按位存储，1 个 bit 表示一个状态，内存极省（8 个状态仅占 1 字节）。

  • 原理：
    SETBIT / GETBIT 操作二进制位；
    BITCOUNT 统计置 1 个数；
    BITOP 位运算（AND/OR/XOR）。
  • 示例：
    签到——SETBIT sign:2024:10001 0 1（第 1 天签到）、BITCOUNT sign:2024:10001 统计 365 天签到天数
  • 连续签到用 BITOP AND 判断。
  • 应用：
    签到打卡、在线状态、用户活跃天数、布隆过滤器底层。

HyperLogLog（HLL）：

一种基数统计（去重计数）概率算法，固定 12KB 内存即可统计 2^64 规模数据，标准误差 0.81%。

  • 原理：
    基于伯努利实验——用元素哈希值末尾连续 0 的最大位数估算基数，不存储元素本身，因此极省内存。
  • 示例：
    UV 统计——PFADD uv:page:20240801 user1 user2 user3、PFCOUNT uv:page:20240801
  • PFMERGE 合并多天 UV。
  • 应用：
    UV / DAU / PV 去重统计等不需要精确计数的场景。

💡 面试点：

Bitmap「按位存状态」适合 0/1 统计；

HLL「概率去重」适合大基数近似统计；

精确去重用 Set 或 RedisBloom。

GEOHASH cities beijing                    -- 获取 geohash 字符串

Redis Stream 是什么？和传统MQ有什么区别？
Stream消息队列

定义：

Stream 是 Redis 5.0+ 引入的持久化消息队列，弥补 List/PubSub 做 MQ 的不足（消息丢失、不支持消费组），能力对齐 Kafka 消费组模型。

核心特性：

  • 消息 ID：
    格式「毫秒时间戳-序号」，支持按 ID 范围查询和历史消息回溯。
  • 消费者组：
    组内消费者分担消息（类似 Kafka 分区消费），消息只投递给组内一个消费者。
  • ACK / Pending：
    消费后显式 XACK 确认，未确认消息进入 Pending 列表，支持重新投递。
  • 持久化：
    消息随 RDB/AOF 持久化，不丢失。

常用命令：

XADD orders * user 1 amount 100   -- 追加消息
XREAD COUNT 10 STREAMS orders 0   -- 独立读取（可阻塞）
XGROUP CREATE orders g1 0         -- 创建消费者组
XREADGROUP GROUP g1 c1 COUNT 10 STREAMS orders >  -- 消费新消息
XACK orders g1 消息ID              -- 消费确认

vs Kafka：

  • Stream 轻量、部署简单，适合中小规模消息、任务队列。
  • Kafka 吞吐更高、分区扩展强、支持消息堆积和流处理生态，适合大数据。

💡 面试点：

答「消息 ID + 消费组 + ACK/Pending + 持久化」四个特性，再对比 Kafka 说明适用边界。

Redis 事务（MULTI/EXEC）的特点和局限性？
事务

定义：

Redis 事务通过 MULTI → 命令入队 → EXEC 执行，将多个命令打包，EXEC 时按序一次性执行，中间不插入其他客户端命令（隔离性）。

用法示例：

MULTI
INCR counter
INCR counter
EXEC        -- 一次性执行，返回两个结果

特性与局限性：

  • 顺序执行 + 隔离：
    EXEC 期间其他命令不会插入（类似串行化）。
  • 不支持回滚：
    入队时语法错误 → 整批不执行
  • 执行时运行时错误 → 只影响该命令，前面命令已生效，无法回滚。
  • 不保证 ACID 原子性：
    Redis 事务实际是「批量执行」，不是「要么全成功要么全失败」。
  • WATCH 乐观锁：
    WATCH 监听 key，EXEC 前若被其他客户端修改，则事务放弃执行（返回 nil），需重试。

WATCH 示例：

WATCH balance → 检查余额 → MULTI/EXEC 扣款

并发修改时事务失败，客户端重试。

💡 面试点：

强调「Redis 事务 ≠ ACID 事务」；

需要真正原子性用 Lua 脚本（原子执行，适合复杂逻辑）。

Redis 大Key问题如何排查和优化？
大Key高频

定义：

大 Key 指单个 key 的值过大：

String > 10KB，或集合类型元素 > 1 万个（或总大小 > 10KB）。

危害：

  • 阻塞操作：
    del / hgetall / keys 等命令处理大 key 耗时，阻塞主线程。
  • 网络瓶颈：
    单次大 value 读写占用大量带宽，拖慢其他请求。
  • 内存不均：
    大 key 集中在少数节点，集群数据倾斜。
  • 主从同步慢：
    RDB / 增量同步大 key 耗时增加，延迟加大。
  • 扩容困难：
    迁移大 key 耗时长，扩缩容不稳定。

排查：

redis-cli --bigkeys（建议从节点执行）、MEMORY USAGE key、scan + debug object。

优化：

  • String：
    压缩（GZIP）或拆分。
  • Hash：
    按 field 二次分片（hash:1~hash:N，field % N 取模）。
  • List：
    按时间 / ID 拆分为多个小 List。
  • Set / ZSet：
    SSCAN / ZSCAN 分批处理。
  • 删除：
    用 UNLINK 异步删除（4.0+），或渐进式删除（hscan/hdel、ltrim）。

💡 面试点：

先答「定义（10KB / 1 万元素）+ 危害（阻塞 / 网络 / 倾斜）」，再答「排查命令 + 分片优化 + UNLINK 异步删除」。

延时队列

什么是 Redis 多级缓存架构？
多级缓存架构

定义：

多级缓存把数据按「访问频率 × 访问速度」分层缓存，越靠近应用层速度越快、容量越小，逐层兜底降低单层压力。

架构（从近到远）：

  1. L1 本地缓存（Caffeine / Guava）：
    JVM 内，微秒级，容量小（几百 MB），适合高频热点。
  2. L2 分布式缓存（Redis）：
    毫秒级，容量大，集群可扩展，全局共享。
  3. L3 数据库（MySQL）：
    秒级，最终数据源。

更新策略：

  • 推模式：
    DB 更新 → Canal / binlog 或 MQ → 更新 Redis → 广播通知各应用更新本地缓存（实时性好，实现复杂）。
  • 拉模式：
    本地缓存设短 TTL（如 60s），过期后回源 Redis / DB（实现简单，有延迟）。

优缺点：

读多写少场景大幅降低 DB 压力；

但多级一致性维护复杂，需配合版本号 / 消息队列。

示例：

热点商品详情——本地 Caffeine（60s）→ Redis（10min）→ MySQL，90% 请求在 L1 命中。

💡 面试点：

答「L1 本地 + L2 Redis + L3 DB」结构 + 「推 / 拉两种更新策略」；

强调适合读多写少、容忍秒级一致性的场景。

Redis 字符串的 embstr 和 raw 编码有什么区别？SDS 如何优化内存？
Redis源码内存优化

String 三种内部编码：

int（纯整数）、embstr（短字符串）、raw（长字符串）。

embstr 与 raw 的区别：

  • embstr：
    value 长度 ≤ 44 字节（Redis 3.2 起，之前是 39 字节），redisObject 与 SDS 分配在同一块连续内存，一次 malloc 一次 free，CPU 缓存友好；
    字符串修改后长度超界会转为 raw。
  • raw：
    value 长度 > 44 字节，redisObject 与 SDS 分开两次分配，需要额外指针引用。

为什么是 44：

64 字节缓存行 − 16 字节 redisObject 头 − 3 字节 sdshdr8 头 − 1 字节结束符 = 44。

SDS 内存优化：

Redis 3.2 起 SDS 按字符串长度动态选择 header，共 sdshdr5/8/16/32/64 五种元数据结构，用最小可用的 header 记录长度，显著节省内存。

官方实验：

10 亿个 44 字节的 key，3.0.7 占约 177G，4.0.12 只占约 147G，省下约 30G。

💡 面试点：

答出「44 字节边界 + 一次分配 vs 两次分配 + SDS 5 种 header 动态选择」是高分答案，能说出 44 的构成公式更是加分项。

Redis 的 zset 为什么用跳跃表而不用红黑树？
Redis跳跃表高频

一句话：

跳跃表实现简单、区间查找高效、平衡代价低，完全满足 zset 的需求。

  • 实现简单：

    红黑树插入/删除要左旋右旋保持平衡，实现复杂。
  • 区间查找高效：
    zset 的 ZRANGEBYSCORE / ZREVRANGEBYSCORE 需要按 score 范围遍历，跳表天然是有序链表，找到起点后顺序遍历即可；
    红黑树范围查找需中序遍历，实现复杂且低效。
  • 平衡代价低：
    跳表用概率（每层 50% 晋升）近似平衡，写操作只影响局部节点；
    红黑树每次写操作都可能触发多次旋转调整整棵树。
  • 内存可控：
    跳表按概率分层，平均每节点约 2 层索引，无红黑节点标记等额外开销。

源码要点：

  • zskiplistNode 包含 score、member、backward 指针和 level 数组（每层存 forward 指针 + span 跨度）；
    zskiplist 记录头尾、长度和层数。
  • 最大层数 32（ZSKIPLIST_MAXLEVEL），随机层数按 50% 概率逐层晋升。
  • 同 score 时按 member 的字典序比较；
    元素少且成员较短时退化为 listpack（7.0+）紧凑存储。

💡 面试点：

从「实现复杂度、区间查找、平衡维护、内存」四个维度对比红黑树，再提一句 listpack 退化条件，基本就是满分回答。

为什么要用 Redis？和本地缓存（Map/Guava）有什么区别？
Redis缓存选型架构

为什么用 Redis：

高性能内存存储（单线程 + IO 多路复用，10W+ QPS）、丰富的数据类型（String/Hash/List/Set/ZSet）、持久化（RDB/AOF）、高可用（主从/哨兵/集群）、过期淘汰策略、Lua 原子脚本、发布订阅、分布式锁等。

本地缓存 vs Redis（分布式缓存）：

对比项本地缓存（Map/Guava/Caffeine）Redis
访问速度JVM 内直接读，最快（微秒级）需一次网络 RTT（毫秒级）
数据共享每实例一份，多节点不一致所有实例共享同一份，全局一致
容量受限于单机堆内存可集群横向扩展
持久化重启即丢失RDB/AOF 持久化，重启可恢复
治理能力无统一监控/淘汰过期、淘汰、监控、分布式锁等开箱即用

选型结论：

单机小项目用本地缓存即可；

分布式系统应使用 Redis，大型系统常用「本地 Caffeine + Redis + DB」的多级缓存架构。

💡 面试点：

核心是「共享 vs 不共享、网络开销 vs 一致性」，结合多级缓存架构作答更完整。

Redis 集群的数据分区方案有哪几种？各自优缺点是什么？
Redis集群数据分区

Redis 集群经历了三种数据分区方案的演进，核心矛盾是数据分布均匀性与扩缩容影响范围之间的平衡。

方案一：

哈希取余（Hash Mod）

  • 原理：
    计算 key 的 hash 值，对节点数量取余决定映射节点。
  • 优点：
    实现简单，数据分布均匀。
  • 缺点：
    节点增减时所有数据都要重新计算映射，引发大规模数据迁移，几乎无法在生产环境动态扩缩容。

方案二：

一致性哈希（Consistent Hashing）

  • 原理：
    将整个 hash 值空间组织成虚拟圆环 [0, 2³²−1]，每个节点映射到环上一个位置；
    key 的 hash 值沿顺时针找到第一个节点即为其映射节点。
  • 优点：
    增减节点时只影响相邻节点，不会导致全量数据迁移。
  • 缺点：
    节点数量较少时，增减单个节点可能造成该节点负载从 1/4 变为 1/2，数据严重不均衡。

方案三：

带虚拟节点的一致性哈希（Redis Cluster 采用的方案）

  • 原理：
    在一致性哈希基础上引入虚拟节点（槽 slot）作为数据和实际节点之间的抽象层。


    Redis Cluster 内置 16384 个槽，每个 key 通过 CRC16(key) % 16384 计算槽号，槽再映射到具体节点。
  • 优点：
    槽解耦了数据与实际节点，增删节点只需迁移部分槽，影响范围极小；
    16384 个槽粒度足够细，分布均匀。
  • 缺点：
    实现复杂度高于前两种，需要维护槽位映射表。

💡 面试点：

先说三种方案的演进关系，再强调 Redis Cluster 选 16384 个槽的原因（平衡心跳包大小与槽粒度），MOVED/ASK 重定向是衍生考点。

如何优雅地删除 Redis 大 Key？（渐进式删除方案）
Redisbigkey实战

为什么不能直接 del：

del 大 Key 会阻塞 Redis 单线程，导致大量请求超时。

对于 Hash/List/Set/ZSet，元素越多阻塞时间越长（百万级 ZSet 删除可达秒级）。

Redis 4.0+ 首选：

unlink（异步删除）

  • unlink 命令将 key 的内存回收交给后台 bio 线程，不会阻塞主线程，一条命令即可安全删除大 Key。

Redis 4.0 以前：

渐进式删除

  • String：
    value 本身是一个整体，del 通常不会阻塞（除非 value 极大），可直接 del。
  • Hash：
    用 hscan 每次扫描 100 个 field，再用 hdel 批量删除，最后 del 空 key；
    可配合 pipeline 加速。
  • List：
    Redis 没有 lscan，用 ltrim 每次从左侧截掉固定数量元素，循环截空后 del。
  • Set：
    用 sscan 每次扫描部分元素，再用 srem 批量删除，最后 del。
  • ZSet：
    用 zscan 扫描 + zrem 删除；
    或直接用 zremrangeByRank 按排名区间批量删除，效率更高。

最佳实践：

  • 优先开启 lazyfree 配置（lazyfree-lazy-expire yes / lazyfree-lazy-eviction yes），让过期和淘汰也走异步删除。
  • bigkey 检测：
    redis-cli --bigkeys（从节点执行）、scan + memory usage、客户端拦截阈值报警。
  • 业务层面预防：
    Hash 做二次分片（hash%100）、List 按时间或 ID 拆分、避免全量 hgetall。

💡 面试点：

先答 unlink（4.0+），再答各类型渐进式删除命令（hscan/ltrim/sscan/zremrangeByRank），最后提 lazyfree 配置和预防措施。

一个 Redis 实例存储多少 Key 比较合适？（dict/rehash/死键问题）
Redis源码内存优化

理论上限：

Redis 的键值对存储在全局 dict（哈希表）中，dict 的 size 是 unsigned long（4 字节），理论上可存 2³² ≈ 40 亿 个 key。

官方建议：

实测最佳实践是单实例存放 2.5 亿 个 key 左右，不建议超过千万级。

为什么不能太多？

  • rehash 内存突增：
    dict 扩容时新建一倍大小的哈希表，渐进式迁移。


    当 key 数达到 2ⁿ 临界点时，内存会瞬间突增（如 6710 万 key 时，dictEntry + expires 各需约 1GB，rehash 瞬间额外消耗 2GB）。


    如果此时超过 maxmemory，会触发大量淘汰甚至阻塞。
  • fork 阻塞：
    bgsave / bgrewriteaof 需要 fork 子进程，key 越多，fork 的页表拷贝时间越长，阻塞主线程风险越大。
  • 死键问题：
    过期键清理是单线程定时任务，key 数超过千万且大量设置过期时间时，过期清理要么频繁影响性能，要么不及时造成内存浪费。
  • 数据剔除抖动：
    key 过多时，一旦触发 maxmemory-policy，短时间内大量逐出操作会造成性能抖动。

单实例内存建议：

一般建议单实例 maxmemory 不超过 8GB，兼顾 fork 速度、RDB 生成/传输/加载时长和网络开销。

💡 面试点：

先说理论 40 亿、官方建议 2.5 亿，再展开 rehash 突增和死键问题（结合单线程特性），最后给出 8GB/千万级 key 的工程实践建议。

Redis 为什么选择单线程模型？事件循环是怎么工作的？
Redis单线程高频

为什么选单线程：

  • 避免多线程竞争：
    Redis 的核心是内存数据结构操作，多线程需要加锁保护共享数据，锁粒度控制不好会严重降低性能；
    单线程天然无竞争，所有操作串行执行，实现简单。
  • 减少上下文切换：
    多线程频繁切换会消耗 CPU 缓存命中率；
    单线程一直运行在同一 CPU 核心上，缓存亲和性最好。
  • 命令原子性：
    单线程保证每个命令的执行是原子的，客户端无需担心并发安全问题，大大简化了使用模型。
  • 瓶颈不在 CPU：
    Redis 操作的是内存，执行速度极快（纳秒~微秒级），真正的瓶颈是网络 I/O 和磁盘 I/O，而非 CPU 计算。

事件循环（Reactor 模型）工作流程：

  1. 监听连接：
    通过 epoll/kqueue/select 多路复用监听多个 socket 的可读/可写事件。
  2. 读取请求：
    客户端有数据到达时，从 socket 读取数据，解析为 Redis 命令。
  3. 执行命令：
    在单线程中串行执行命令，操作内存数据结构。
  4. 写回响应：
    将执行结果写入客户端 socket 的发送缓冲区。
  5. 继续监听：
    回到步骤 1，循环往复。

Redis 6.0 多线程演进：

  • 6.0 引入多线程网络 I/O（io-threads-do-reads / io-threads 配置），命令执行依然是单线程。
  • 多线程只负责协议解析和响应写回，不处理命令逻辑，既提升了高并发下的网络吞吐，又保留了单线程执行的原子性和简单性。

💡 面试点：

核心是「瓶颈在 IO 不在 CPU + 避免锁竞争 + 事件循环模型」

补充 6.0 多线程网络 I/O 是加分项，说明 Redis 并非排斥多线程，而是「命令执行单线程，网络 IO 多线程」。
