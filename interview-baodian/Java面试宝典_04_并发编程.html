synchronized 的实现原理？锁升级过程？
锁高频

底层实现：

基于对象头的Mark Word + Monitor（管程）。

锁升级过程（JDK1.6+优化）：

无锁 偏向锁 轻量级锁 重量级锁

  • 偏向锁：

    Mark Word记录线程ID，同一线程反复进入，CAS一次后不再CAS。
  • 轻量级锁：

    竞争时撤销偏向锁，CAS自旋获取，自旋失败升级。
  • 重量级锁：

    自旋失败后膨胀，线程阻塞进入等待队列，由操作系统调度。

💡 锁只能升级不能降级（偏向锁可被撤销）。

volatile 关键字的作用和原理？
volatile高频

两大作用：

  • 保证可见性：

    一个线程修改后立即写回主存，其他线程立即可见。

    通过内存屏障实现。
  • 禁止指令重排序：

    通过插入内存屏障阻止指令重排。

不保证原子性：

i++不是原子操作，volatile不能解决。

💡 经典应用：

DCL单例模式中的instance变量必须用volatile修饰。

AQS（AbstractQueuedSynchronizer）原理？
AQS高频

AQS是JUC锁框架的基础，核心三要素：

  • state(volatile int)：

    同步状态，CAS修改。
  • CLH队列(FIFO)：

    获取锁失败的线程加入队列等待。
  • 模板方法模式：

    子类实现tryAcquire/tryRelease等方法。

独占模式：

ReentrantLock。

state=0未锁定，state=1已锁定。

共享模式：

Semaphore、CountDownLatch。

state>0表示可用资源数。

💡 ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock等都基于AQS实现。

ReentrantLock 如何实现可重入？
Lock源码

通过AQS的state状态值实现：

  • 同一线程每次获取锁→state+1
  • 每次释放锁→state-1
  • state=0时锁完全释放

内部维护exclusiveOwnerThread记录当前持有锁的线程。

公平锁：

先检查等待队列是否有线程，有则排队。

非公平锁：

直接CAS尝试获取锁，失败再排队。

ThreadLocal 的原理和内存泄漏问题？
ThreadLocal高频

原理：

每个Thread内部有一个ThreadLocalMap，key是ThreadLocal的弱引用，value是存储的值。

内存泄漏原因：

  • ThreadLocal作为key是弱引用，GC时被回收→key=null。
  • 但value是强引用，且线程存活→value无法回收→内存泄漏。

💡 解决方案：

使用完毕后调用remove()方法。

阿里规约要求必须remove。

CAS 是什么？有什么问题？
CAS无锁

CAS(Compare And Swap)：

比较并交换，原子操作，CPU指令级支持。

需要3个操作数：

内存地址V、预期值A、新值B。

当V==A时更新为B。

三大问题：

  • ABA问题：

    A→B→A，CAS误判未变化。

    解决方案：

    AtomicStampedReference(版本号)。
  • 自旋开销：

    CAS失败后自旋重试，CPU消耗大。
  • 只能保证一个共享变量的原子操作：

    AtomicReference可包装多个变量。

死锁的4个必要条件？如何预防？
死锁经典

4个必要条件：

  1. 互斥：

    资源同一时间只能一个线程使用。
  2. 持有并等待：

    持有资源A，等待资源B。
  3. 不可剥夺：

    已获取资源不能被强制剥夺。

    形成资源等待环。

预防：

破坏任一条件即可——锁排序、超时放弃(tryLock)、一次性申请所有资源、使用无锁数据结构。

synchronized 锁升级过程是怎样的？
高频锁升级

synchronized锁升级是JDK6的优化：

无锁→偏向锁→轻量级锁→重量级锁，只能升级不能降级。

  1. 偏向锁：

    第一个获取锁的线程，CAS设置ThreadID，后续该线程无需同步操作直接进入。
  2. 轻量级锁（自旋锁）：

    有竞争时，撤销偏向锁。

    线程CAS尝试获取锁，失败则自旋等待（自适应自旋）。
  3. 重量级锁：

    自旋超限或竞争激烈，膨胀为重量级锁（monitor互斥），未获取锁的线程阻塞。

💡 偏向锁默认延迟4秒启动（可通过-XX:BiasedLockingStartupDelay=0关闭延迟）。

LockSupport.park() 和 unpark() 原理？
LockSupportAQS

LockSupport是最基本的线程阻塞原语，AQS的基石。

  • park()：

    阻塞当前线程，直到unpark()或中断。

    基于Unsafe.park()（C++的Parker::park）。
  • unpark(thread)：

    唤醒指定线程。

    即使unpark先于park执行，park也会立即返回（permit机制，最多1个）。

相比wait/notify的优势：

  • 不需要在synchronized块中。
  • unpark可以先于park调用。
  • 可以精确唤醒指定线程。

读写锁 ReentrantReadWriteLock 原理和锁降级？
读写锁高频

基于AQS，state高16位=读锁计数，低16位=写锁重入次数。

  • 读锁共享：

    多个线程可同时获取读锁。
  • 写锁互斥：

    写锁独占，读写互斥。
  • 锁降级：

    写锁→读锁（先获取读锁再释放写锁）。

锁降级场景：

写完后需要立即读，保证数据可见性。

rwLock.writeLock().lock();
// 写操作
rwLock.readLock().lock();   // 先获取读锁
rwLock.writeLock().unlock(); // 再释放写锁 = 降级为读锁

💡 不支持锁升级（读→写），会死锁。

JDK8引入StampedLock，支持乐观读。

Java 内存模型（JMM）是什么？
JMM高频

JMM（Java Memory Model）是规范，定义多线程下共享变量的访问规则：

  • 主内存：

    所有线程共享，存共享变量。
  • 工作内存：

    线程私有，存主内存中变量的副本。
  • 线程不能直接读写主内存，必须通过工作内存。

三大特性：

  • 原子性：

    synchronized、Lock、Atomic类。
  • 可见性：

    volatile、synchronized、final。
  • 有序性：

    volatile、synchronized、happens-before原则。

Happens-Before 规则有哪些？
JMM高频

Happens-Before规定操作间的偏序关系，保证前操作的结果对后操作可见：

  1. 程序次序：

    单线程中前面的操作hb后面的。

    （控制流而非程序顺序）。
  2. volatile：

    volatile写hb于后续读。
  3. 锁：

    unlock hb于后续lock。
  4. 传递性：

    A hb B, B hb C A hb C。
  5. start()：

    线程start() hb于线程内所有操作。
  6. join()：

    线程所有操作 hb于join()返回。
  7. 中断：

    interrupt() hb于被中断线程检测到中断。
  8. finalize：

    构造结束 hb于finalize()。

synchronized 底层的 monitorenter/monitorexit 是什么？
底层字节码

synchronized编译后在字节码中对应monitorenter和monitorexit指令。

  • monitorenter：

    尝试获取对象的monitor锁，计数器+1。
  • monitorexit：

    释放monitor锁，计数器-1，为0时释放。
  • 每个对象有一个monitor，基于ObjectMonitor（C++实现）。
  • 重入性：

    同一线程重复进入，计数器累加。

synchronized方法的区别：

方法标志位ACC_SYNCHRONIZED，不需要monitorenter/exit指令。

volatile 如何保证可见性和有序性？（内存屏障）
volatile底层

volatile通过内存屏障实现：

  • volatile写：

    前插StoreStore屏障，后插StoreLoad屏障→写完后立即刷回主内存并使其他CPU缓存行失效。
  • volatile读：

    前插LoadLoad屏障，后插LoadStore屏障→每次读都从主内存重新加载。
  • 禁止指令重排序：

    屏障确保volatile操作前后的指令不越界。

DCL单例为什么必须volatile：

防止指令重排序导致半初始化对象被其他线程读到。

不加volatile可能instance!=null但构造未完成。

29
Fork/Join 框架的 Work-Stealing 算法？
ForkJoin

Fork/Join是将大任务递归拆分为小任务并行执行的框架。

Work-Stealing（工作窃取）：

  • 每个工作线程有一个双端队列。
  • 自己产生的任务放入队列底部，自己从顶部取（LIFO）。
  • 自己队列空时，从其他队列尾部窃取（FIFO）。
  • 减少线程竞争，提高CPU利用率。

ForkJoinPool默认线程数=CPU核心数，适合CPU密集型任务。

线程的生命周期（6种状态）？
基础线程状态

Thread.State定义了6种状态：

  1. NEW：

    创建但未start()。
  2. RUNNABLE：

    运行中（包括就绪和运行，因为JVM不区分）。
  3. BLOCKED：

    等待synchronized锁。
  4. WAITING：

    wait()/join()/park()，等待其他线程通知。
  5. TIMED_WAITING：

    sleep(time)/wait(time)/join(time)。
  6. TERMINATED：

    执行完毕。

💡 操作系统层面的线程状态与Java不同（多了就绪状态）。

注意BLOCKED只是等synchronized锁，等Lock锁是WAITING状态。

如何实现一个生产者-消费者模型？
模式实战

实现方式（4种）：

  1. wait/notify：

    经典方式，需手动处理生产满/消费空的阻塞。
  2. BlockingQueue：

// 生产者: queue.put(task); // 满则阻塞
// 消费者: Task t = queue.take(); // 空则阻塞

线程池出现死锁如何排查？
排查死锁

线程池死锁常见原因：

  • 任务A等待任务B完成，任务B等待线程释放 互相等待。
  • 父子任务都提交到同一线程池 父任务占线程等子任务。

排查：

  1. jstack -l PID：

    查看线程状态，JVM会自动检测死锁（Found one Java-level deadlock）。
  2. 查看BLOCKED和WAITING的线程。
  3. Arthas：

    thread -b找死锁。

解决：

避免嵌套提交、用不同线程池执行父子任务、增加超时机制。

Future 和 CompletableFuture 对比？Future 的局限性？
异步对比

Future 局限性：

  • get()方法阻塞，不支持回调。
  • 不能手动完成任务。
  • 不能组合编排（A完成→B→聚合C和D）。
  • 异常处理不友好。

CompletableFuture 优势：

  • 支持回调（thenApply/thenAccept）。
  • 支持组合编排。
  • 支持异常恢复（exceptionally/handle）。
  • 可手动完成（complete）。
  • allOf/anyOf多任务聚合。

并行流 parallelStream 的陷阱？
Stream并发
  • 共用ForkJoinPool：

    默认用公共线程池，阻塞操作会耗尽线程→影响其他并行流。
  • 数据量小反而慢：

    拆分和合并有开销，数据量小时串行更快。
  • 线程不安全操作：

    并行流中的副作用操作可能导致数据错乱。
  • 顺序依赖：

    forEach不保证顺序，需用forEachOrdered。

安全使用：

无状态、无副作用、可拆分的大数据集才适合parallelStream。

InheritableThreadLocal 是什么？如何实现线程池上下文传递？
ThreadLocal上下文

InheritableThreadLocal：

子线程会继承父线程的ThreadLocal值（fork时拷贝）。

但线程池中线程复用后，不会重新复制。

线程池上下文传递方案：

  • 手动传递：

    Runnable包装，run()前设置上下文，finally清理。
  • 线程池Hook：

    beforeExecute设置，afterExecute清理。
  • Alibaba TransmittableThreadLocal(TTL)：

    完美解决线程池上下文传递。
  • Hystrix：

    HystrixRequestContext。
