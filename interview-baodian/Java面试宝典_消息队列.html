消息队列的作用？如何保证消息不丢失？
MQ高频

一、消息队列的核心作用

1. 异步解耦

系统间通过消息队列通信，调用方无需等待被调用方处理完成即可返回。
例如：
用户下单后，订单系统只需发送订单消息，积分系统、库存系统、物流系统各自异步消费处理，系统间松耦合，互不影响。

2. 削峰填谷

高并发场景下（如秒杀、大促），流量洪峰会被消息队列缓冲，后端服务按自身处理能力匀速消费，避免数据库被打挂。
生产者只管发消息，消费者按固定速率消费，流量被"削平"。

3. 最终一致性（分布式事务）

通过消息队列实现分布式事务的异步最终一致性，例如：
本地事务成功+发送消息，下游系统消费消息完成自身事务，失败可重试。

4. 广播与订阅

一条消息可被多个消费者组同时消费，实现一对多广播（如配置变更通知推送到多个服务实例）。

5. 日志采集与流式处理

大规模分布式系统中，各服务日志通过消息队列汇聚到分析系统（如 Kafka + Flink 实现实时数仓）。

二、如何保证消息不丢失（全链路视角）

消息从生产到消费经历三个阶段：Producer → Broker → Consumer，每个阶段都有丢失风险，需分别保证。

1. 生产端（Producer）不丢失

  • 同步发送 + 确认回调：
    等待 Broker 返回 ACK 后才认为发送成功，失败自动重试。
    Kafka 设置 acks=all，RocketMQ 使用同步发送 SendResult。
  • 异步发送 + 失败重试：
    指定回调函数处理发送失败，失败消息落入本地日志或死信队列，定时补偿重发。
  • 事务消息：
    本地事务与消息发送绑定，本地事务成功则消息一定发送成功。
    RocketMQ 提供 Half 消息 + 事务回查机制。
  • 消息落盘/落库：
    极端可靠场景下，发送前先将消息写入本地数据库/日志，发送成功后再删除，发送失败可定时扫描重发。

2. Broker 端不丢失

  • 同步刷盘（Sync Flush）：
    消息写入 PageCache 后强制刷入磁盘再返回 ACK，避免断电丢失。
    RocketMQ 支持同步/异步刷盘，高可靠场景选同步。
  • 多副本机制（Replication）：
    消息至少写入多个 Broker 副本才算成功。
    Kafka 设置 replication.factor ≥ 3，并配合 ISR 机制确保副本同步。
  • 多机房部署：
    跨可用区部署 Broker，单机房故障不丢数据。
  • Broker 持久化：
    RabbitMQ 将 Exchange、Queue、Message 全部持久化（durable=true, delivery_mode=2）。

3. 消费端（Consumer）不丢失

  • 手动 ACK / 手动提交 Offset：
    业务逻辑处理完成后，再向 Broker 确认消费成功。
    Kafka 设置 enable.auto.commit=false，RocketMQ 使用 CONSUME_SUCCESS 返回。
  • 先处理业务，再提交 Offset：
    如果先提交 Offset 再处理业务，处理失败时消息已标记为消费，无法再消费，造成丢失。
  • 消费异常处理：
    消费失败不直接 ACK，而是重试一定次数后转入死信队列（DLQ），人工介入处理。
  • 幂等消费：
    即使重复消费，也不会造成数据错误（见第 2 题）。

三、总结口诀

生产端：
同步发送 + 事务消息 + 失败重试；
Broker：
同步刷盘 + 多副本；
消费端：
手动 ACK + 先业务后 Offset。

如何保证消息不重复消费？
MQ幂等

核心认知：MQ 只能保证 At Least Once（至少一次）

消息队列为了保证消息不丢失，在网络抖动、Consumer 处理超时、Broker 重平衡等场景下会重复投递消息。去重必须由业务层实现，MQ 本身无法保证 Exactly Once（除 Kafka 事务在特定条件下可实现）。

一、幂等性设计方案

1. 数据库唯一索引（最常用）

  • 用消息的 唯一 ID（如 Kafka 的 offset+partition、RocketMQ 的 MessageID、业务唯一键如订单号）建立数据库唯一索引。
  • 消费时先 INSERT 一条消费记录，若唯一键冲突则直接丢弃，视为已消费。
  • 示例表结构：
CREATE TABLE idempotent_log ( msg_id VARCHAR(64) PRIMARY KEY, biz_key VARCHAR(64) NOT NULL, status TINYINT DEFAULT 0, create_time DATETIME DEFAULT CURRENT_TIMESTAMP );
  • 消费逻辑：
    先 INSERT IGNORE 或 ON DUPLICATE KEY UPDATE，成功则执行业务，冲突则跳过。
  • 优点：
    简单可靠，持久化去重记录。
    缺点：
    依赖数据库，高并发可能成为瓶颈（可配合缓存优化）。

2. Redis SETNX / 分布式锁

  • 消费前执行 SET msg_id "1" NX EX 86400（NX 表示仅当 key 不存在时才设置，EX 设置过期时间）。
  • 设置成功 → 首次消费，执行业务；
    设置失败 → 重复消息，直接返回。
  • Redis 性能高，适合高并发场景。
    注意：
    Redis 非强一致，极端情况下可能重复（主从切换），但概率极低。
  • 进阶：
    可结合 Redisson 分布式锁，保证集群环境下幂等。

3. 业务状态机幂等

  • 利用业务本身的有限状态机（FSM），只有特定状态才能流转到下一状态。
  • 示例：
    订单状态流转 待支付 → 已支付 → 已发货 → 已完成。
    收到支付消息时，只有"待支付"状态才能更新为"已支付"，重复消息因状态不匹配而忽略。
  • SQL 示例：UPDATE orders SET status='PAID' WHERE order_id=? AND status='PENDING'，影响行数为 0 则已处理过。
  • 优点：
    无需额外去重表，天然幂等。
    局限：
    仅适用于有明确状态流转的业务。

4. Token 机制（防重复提交场景）

  • 接口调用前先从服务端申请 Token，服务端将 Token 存入 Redis；
    调用时携带 Token，服务端校验并删除 Token。
  • 重复请求携带相同 Token，Redis 中已删除，校验失败拒绝处理。

5. Kafka Producer 端幂等（enable.idempotence）

  • Kafka 0.11+ 支持 Producer 幂等：
    通过 PID（Producer ID）+ Sequence Number 为每个消息编号，Broker 端去重。
  • 注意：
    仅解决生产端重复发送问题（网络超时导致重试），不解决消费端重复消费。

二、选型建议

方案适用场景优缺点
数据库唯一键通用场景，数据一致性要求高可靠持久；
DB 有压力
Redis SETNX高并发，允许极微小概率重复性能极高；
Redis 故障可能丢记录
状态机有明确状态流转的业务（订单、审批）无需额外存储；
局限性强
Token用户端防重复提交适合接口层面；
需前端配合

二、架构差异详解

1. Kafka：高吞吐日志型 MQ

  • 核心设计：
    将消息按 Topic 分多个 Partition，每个 Partition 是一个顺序写日志文件。
    Consumer 通过 offset 随机读取，支持"倒带"重放。
  • 为什么吞吐高：
    磁盘顺序写（比随机写快 3 个数量级）+ 零拷贝（sendfile）+ 批量压缩 + 页缓存。
  • 副本机制：
    Leader-Follower 模式，ISR（In-Sync Replicas）集合中副本同步后才算提交。
    依赖 ZooKeeper（3.x）或 KRaft（3.3+ 去 ZK）。
  • 局限：
    不支持延时消息；
    单 Topic 分区数过多时性能下降；
    消费失败不支持重试到特定队列。

2. RocketMQ：金融级业务型 MQ

  • 核心设计：
    Topic 逻辑队列 + CommitLog 物理存储。
    所有消息顺序写到一个 CommitLog，ConsumeQueue 存储偏移索引，读写分离。
  • 事务消息：
    Half 消息机制：
    先发 Half 消息（对消费者不可见）→ 执行本地事务 → 根据本地事务结果 Commit 或 Rollback → Broker 定时回查未决消息。
  • 顺序消息：
    支持全局顺序（单队列）和分区顺序（同 key 同队列），电商场景（如订单创建→支付→发货）非常实用。
  • 延时消息：
    内置 18 个延时级别（1s / 5s / 10s / 1m / 2m ... 2h），满足绝大部分定时任务需求。
  • NameServer：
    轻量级服务发现，无状态集群，运维比 ZooKeeper 简单得多。

3. RabbitMQ：通用型消息中间件

  • 核心设计：
    基于 AMQP 协议，Exchange（交换机）负责路由，Queue 负责存储，Binding 定义路由规则。
    灵活的路由能力（direct / topic / fanout / headers）。
  • 低延迟：
    Erlang 专为电信级高并发设计，消息在内存中流转时延迟极低（微秒级）。
  • 特性丰富：
    死信队列、TTL、延迟插件、优先级队列、消息追踪（Tracing）、 shovel 跨集群同步。
  • 局限：
    吞吐量相对低；
    Erlang 学习成本高；
    队列积压时性能急剧下降。

三、选型建议

  • 大数据 / 日志 / 实时流处理 → Kafka（吞吐最高，与 Flink/Spark 生态完美集成）
  • 电商 / 金融 / 需要分布式事务 → RocketMQ（事务消息、顺序消息、延时消息最完善）
  • 企业集成 / 复杂路由 / 低延迟任务调度 → RabbitMQ（AMQP 标准、路由灵活、功能丰富）

Kafka 如何保证消息不丢失？
Kafka消息队列

Kafka 消息从 Producer 到 Broker 到 Consumer，每个环节都有丢失风险，需分别配置保障。

一、Producer 端保证

  • acks=all（或 acks=-1）：
    Producer 收到 Leader + 所有 ISR 副本的确认后才算发送成功。
    若 acks=1 则只等 Leader，Leader 宕机且未同步到 Follower 时丢失；
    acks=0 则发完不管，最易丢。
  • retries > 0：
    发送失败自动重试次数，建议设为 3~5。
    注意：
    重试可能导致消息乱序，需配合 max.in.flight.requests.per.connection=1（Kafka < 2.5）或开启幂等。
  • enable.idempotence=true：
    开启 Producer 幂等，通过 PID + Sequence Number 防止因重试导致的消息重复发送。
  • 事务消息（可选）：
    多条消息原子性写入多个 Partition，配合 transactional.id 使用，适用于"恰好一次"语义场景。

Producer 配置示例：

props.put("acks", "all"); props.put("retries", 3); props.put("enable.idempotence", "true"); props.put("max.in.flight.requests.per.connection", 5); // Kafka 2.5+ 开启幂等后可大于 1 且保序

二、Broker 端保证

  • replication.factor ≥ 3：
    每个 Partition 至少 3 个副本，单机/单盘故障不丢数据。
  • min.insync.replicas ≥ 2：
    配合 acks=all，要求 ISR 中至少 2 个副本确认写入，才给 Producer 返回成功。
    避免 Leader 刚写入还未同步到 Follower 就宕机。
  • unclean.leader.election.enable=false：
    禁止非 ISR 副本当选为 Leader。
    若设为 true，未同步的副本成为 Leader 会导致已确认的消息丢失。
  • log.flush.interval.messages / log.flush.interval.ms：
    控制刷盘频率。
    默认依赖 OS 刷盘，高可靠场景可适当调小，但会影响吞吐。

Broker 配置示例：

# server.properties replication.factor=3 min.insync.replicas=2 unclean.leader.election.enable=false

三、Consumer 端保证

  • enable.auto.commit=false：
    关闭自动提交 Offset，改为业务处理完成后手动调用 consumer.commitSync()。
  • 先处理业务，再提交 Offset：
    如果先提交 Offset 再处理业务，处理过程中应用崩溃，消息已标记为消费成功，但实际未处理，造成丢失。
  • 消费异常处理：
    消费失败时捕获异常，不提交 Offset，消息会再次投递（可能重复，需业务幂等）。
  • 隔离级别（isolation.level）：
    如果 Producer 使用事务，Consumer 设置 isolation.level=read_committed，避免读取到事务未提交的消息（事务回滚后消息"消失"造成丢失感知）。

Kafka 如何保证消息不重复消费？
Kafka幂等

核心：Kafka 只能保证 At Least Once，消费端重复无法避免，必须业务层做幂等处理。

重复消费的典型场景：
Consumer 处理完业务后提交 Offset 前崩溃 → 重启后重新消费同一批消息；
或 Rebalance 导致分区重新分配，新 Consumer 从旧 Offset 开始消费。

一、Producer 端减少重复发送

  • enable.idempotence=true：
    通过 PID（Producer ID）+ Sequence Number 机制，Broker 端自动去重因网络超时导致的重试消息。
  • 事务消息：
    通过 transactional.id + initTransactions()，实现跨 Partition 的原子写入。
    事务保证了"要么全部成功要么全部失败"，配合 Consumer 的 isolation.level=read_committed 可实现端到端的 Exactly Once。

Producer 幂等示例：

props.put("enable.idempotence", "true"); props.put("acks", "all"); props.put("retries", Integer.MAX_VALUE); // 幂等开启后可安全设置大重试次数

二、Consumer 端幂等处理（核心）

Kafka 的事务和 Producer 幂等只能解决"生产端重复"，消费端重复只能靠业务层：

  • 唯一键去重（数据库唯一索引）：
    消息中携带业务唯一键（如订单号 + 事件类型），消费时先插入去重表，唯一键冲突则跳过。
  • Redis SETNX：SET msg_key "1" NX EX 86400，设置成功才消费。
    适合高并发场景。
  • 状态机/乐观锁：
    业务状态只能按固定方向流转，重复消息因状态条件不匹配被忽略。
    如 UPDATE orders SET status='PAID' WHERE id=? AND status='PENDING'。

三、Exactly Once 语义（端到端）

Kafka 在 0.11 版本后通过幂等 Producer + 事务 + read_committed Consumer实现了端到端 Exactly Once，但有限制：

  • Producer 必须开启幂等和事务。
  • Consumer 必须设置 isolation.level=read_committed。
  • Consumer 处理消息后若还要写入 Kafka（如 Stream 处理），需使用 Kafka Streams API 的事务支持，手动管理事务较复杂。
  • 如果 Consumer 消费后写入外部系统（如 MySQL、Redis），仍需要业务层幂等，因为 Kafka 无法跨系统保证 Exactly Once。

四、实际生产建议

  • Producer 开启 enable.idempotence=true，消除网络重试导致的重复。
  • Consumer 做好业务幂等（唯一键/状态机），这是最根本的保障。
  • 需要 Exactly Once 且消费后写入 Kafka 时，使用 Kafka Streams 的事务 API。
  • 消费后写入外部系统时，"两阶段提交"过于复杂，建议以业务幂等为主，接受极少量重复。

Kafka ISR 是什么？min.insync.replicas 的作用？
KafkaISR

一、ISR（In-Sync Replicas）详解

ISR 是与 Leader 保持同步的副本集合。
Kafka 的每个 Partition 有一个 Leader 和多个 Follower，ISR 包含 Leader 和所有"足够同步"的 Follower。

1. 副本同步条件

  • 副本在 replica.lag.time.max.ms（默认 10 秒）内向 Leader 发送过 Fetch 请求。
  • 副本的 LEO（Log End Offset）与 Leader 的 LEO 差距不超过 replica.lag.max.messages（已废弃，现仅看时间）。

若 Follower 因网络故障、GC 停顿等原因超过时间未同步，会被踢出 ISR，进入 OSR（Out-of-Sync Replicas）。

2. HW（High Watermark）与 LEO（Log End Offset）

  • LEO：
    副本日志的最后一个偏移量 + 1，即下一条待写入的位置。
    每个副本有自己的 LEO。
  • HW：
    ISR 中所有副本都已同步到的最大偏移量。Consumer 只能读取 HW 之前的消息（已同步确认的消息），HW 之后的数据即使 Leader 有，Consumer 也看不到。

HW 机制保证了：
Leader 宕机后，新选举的 Leader 所拥有的数据一定已被所有 ISR 副本确认，Consumer 不会读到"丢失"的数据。

3. Leader 选举

  • Leader 宕机后，Controller 从 ISR 中选举新 Leader（优先选数据最全的）。
  • 如果 unclean.leader.election.enable=false（推荐），ISR 为空时宁可不可用，也不选 OSR 副本为 Leader，避免数据丢失。
  • 如果设为 true，OSR 副本可能成为 Leader，导致已确认的消息丢失（它缺少部分数据）。

二、min.insync.replicas 详解

min.insync.replicas 是 Broker 端配置，表示当 acks=all 时，消息必须被 ISR 中至少这么多副本成功写入，Producer 才收到成功响应。

1. 与 acks=all 的配合

  • acks=all 表示 Producer 等待"所有 ISR 副本"确认。
  • min.insync.replicas 是"所有 ISR 副本"中的最低要求，是对 acks=all 的进一步约束。
  • 示例：
    replication.factor=3，min.insync.replicas=2，acks=all。
    Leader + 1 个 Follower 确认即可返回成功，不需要全部 3 个副本（只要 ISR 中确认数 ≥ 2）。

2. 数据安全保障

  • 若 ISR 中可用副本数 < min.insync.replicas，Producer 写入会收到 NOT_ENOUGH_REPLICAS 异常，拒绝写入 → 宁可不可用，也不丢数据。
  • 若 min.insync.replicas=1，则只要 Leader 确认即可返回成功，Leader 宕机未同步到 Follower 时数据丢失。

3. 推荐配置

replication.factor = 3 min.insync.replicas = 2 acks = all unclean.leader.election.enable = false

这组配置的含义：
每条消息至少写入 2 个副本（Leader + 1 Follower）才返回成功；
Leader 宕机时，新 Leader 一定拥有已确认的全部数据。

三、总结

  • ISR：
    动态维护的同步副本集合，保证 Leader 切换时数据不丢。
  • HW：
    消费者可见的最大偏移量，由 ISR 最小 LEO 决定。
  • min.insync.replicas：
    配合 acks=all 设置最低确认副本数，是 Kafka 不丢数据的核心安全参数。

RabbitMQ 如何保证消息不丢失？
RabbitMQ

RabbitMQ 消息流转路径：Producer → Exchange → Queue → Consumer，每个环节都可能丢失消息，需分别保障。

一、Producer → Exchange（消息到达交换机）

  • Publisher Confirm（发布确认）：
    Channel 开启 confirmSelect()，消息被 Exchange 成功接收后，Broker 异步返回 ack；
    失败返回 nack，Producer 可重试。
  • 与事务模式（txSelect）相比，Confirm 是异步的，性能高得多（事务同步阻塞，吞吐量下降 250 倍）。
channel.confirmSelect(); channel.basicPublish("exchange", "routingKey", props, msg.getBytes()); if (channel.waitForConfirms(5000)) { // 发送成功 } else { // 发送失败，补偿重试 }

二、Exchange → Queue（消息路由到队列）

  • mandatory=true：
    消息无法路由到任何 Queue 时（如路由键不匹配），Broker 将消息退回给 Producer，通过 ReturnListener 处理，而不是静默丢弃。
  • 备用 Exchange（Alternate Exchange）：
    为 Exchange 设置 AE，路由失败的消息自动转入 AE 绑定的队列，用于兜底。
// mandatory=true + ReturnCallback channel.addReturnListener((replyCode, replyText, exchange, routingKey, properties, body) -> { // 消息被退回，记录日志并补偿 }); channel.basicPublish("exchange", "rk", true, props, msg.getBytes());

三、Queue → 磁盘持久化

  • Exchange 持久化：
    声明时 durable=true，Broker 重启后 Exchange 不丢失。
  • Queue 持久化：
    声明时 durable=true，Broker 重启后队列元数据不丢失。
  • Message 持久化：
    发送消息时设置 deliveryMode=2（Persistent），消息会写入磁盘而非仅存在内存。
// 队列持久化 channel.queueDeclare("queue", true, false, false, null); // 消息持久化 AMQP.BasicProperties props = new AMQP.BasicProperties.Builder() .deliveryMode(2) // 1=非持久, 2=持久 .build(); channel.basicPublish("", "queue", props, msg.getBytes());

注意：
持久化会牺牲性能（磁盘 IO），非核心消息可不持久化。

四、Queue → Consumer（消费端不丢失）

  • 手动 ACK（acknowledge-mode: manual）：
    关闭自动确认，业务处理完成后调用 channel.basicAck()。
    若处理失败，调用 basicNack(requeue=true) 重试或 requeue=false 转入死信队列。
  • 先处理业务，再 ACK：
    和 Kafka 一样，如果先 ACK 再处理业务，处理失败时消息已删除，造成丢失。
// 手动 ACK DeliverCallback deliverCallback = (consumerTag, delivery) -> { try { processMessage(delivery.getBody()); channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false); } catch (Exception e) { channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, true); } }; channel.basicConsume("queue", false, deliverCallback, consumerTag -> {});

五、镜像队列（高可用，防止 Broker 宕机）

  • 普通队列只存在于一个节点，该节点宕机则队列不可用。
    镜像队列（Quorum Queue / Classic Mirrored Queue）将队列数据同步到多个节点。
  • RabbitMQ 3.8+ 推荐 Quorum Queues：
    基于 Raft 共识算法，自动故障转移，Leader 宕机自动选举新 Leader，数据不丢。

六、总结：RabbitMQ 不丢消息 checklist

环节措施
Producer → ExchangePublisher Confirm
Exchange → Queuemandatory=true + ReturnCallback / Alternate Exchange
Queue 持久化durable=true（Exchange + Queue + Message deliveryMode=2）
Consumer手动 ACK，先业务后 ACK
Broker 高可用镜像队列 / Quorum Queue

RabbitMQ 死信队列和延迟队列？
RabbitMQ

一、死信队列（DLX, Dead Letter Exchange）

死信队列是用来处理无法正常消费的消息的"兜底"机制。
消息成为"死信"后，会被转发到死信交换机（DLX），再路由到死信队列中，供后续分析、重试或人工处理。

1. 消息成为死信的三种条件

  • 消息被拒绝（Reject / NACK）且不重回队列：
    Consumer 调用 basicReject 或 basicNack(requeue=false)，消息进入死信队列。
  • 消息 TTL 过期：
    消息在队列中停留时间超过设定的 TTL（Time To Live），未被消费则过期成为死信。
  • 队列达到最大长度：
    队列满了（x-max-length 限制），新消息进来时，最早的消息被挤出成为死信。

2. 死信队列配置方式

  • 为普通队列设置两个参数：x-dead-letter-exchange（DLX 名称）和 x-dead-letter-routing-key（路由到 DLX 的路由键）。
  • 消息成为死信后，会被重新发送到 DLX，再根据 routing key 路由到死信队列。
// 声明死信交换机和队列 channel.exchangeDeclare("dlx.exchange", "direct"); channel.queueDeclare("dlx.queue", true, false, false, null); channel.queueBind("dlx.queue", "dlx.exchange", "dlx.routingKey"); // 声明普通队列，设置 DLX Map<String, Object> args = new HashMap<>(); args.put("x-dead-letter-exchange", "dlx.exchange"); args.put("x-dead-letter-routing-key", "dlx.routingKey"); args.put("x-message-ttl", 10000); // 消息 10s 过期 args.put("x-max-length", 1000); // 队列最大 1000 条 channel.queueDeclare("normal.queue", true, false, false, args);

3. 死信队列的应用场景

  • 异常消息兜底：
    消费失败的消息进入死信队列，避免无限重试阻塞正常消费。
  • 消息审计与追踪：
    收集所有死信，分析失败原因。
  • 延迟重试：
    死信队列配合 TTL 可实现"失败后等一段时间再重试"。

二、延迟队列（Delayed Queue）

延迟队列指消息发送到队列后，不会立即被消费，而是在指定延迟时间后才变为可消费状态。
典型场景：
订单 30 分钟未支付自动取消、秒杀结束后统一处理。

1. 方案一：TTL + 死信队列实现（最常用）

  • 创建延迟队列 A：
    不绑定 Consumer，只设置 x-message-ttl（如 30 分钟）和 x-dead-letter-exchange。
  • 消息发到队列 A → 30 分钟后 TTL 过期 → 消息变为死信 → 被转发到 DLX → 路由到实际消费队列 B → Consumer 消费。
// 延迟队列（不消费，只等过期） Map<String, Object> delayArgs = new HashMap<>(); delayArgs.put("x-message-ttl", 1800000); // 30 分钟 delayArgs.put("x-dead-letter-exchange", "order.dlx"); delayArgs.put("x-dead-letter-routing-key", "order.cancel"); channel.queueDeclare("order.delay.queue", true, false, false, delayArgs); // 死信转发的目标队列（真正消费） channel.queueDeclare("order.cancel.queue", true, false, false, null); channel.queueBind("order.cancel.queue", "order.dlx", "order.cancel");

2. 方案一的局限性：TTL 顺序问题

如果队列中有多条消息，TTL 各不相同（如第一条 30 分钟，第二条 10 分钟），RabbitMQ 只有队首消息过期后才会检查下一条。
队首是 30 分钟的消息时，即使第二条已过期，也必须等 30 分钟后才能被处理。

解决方案：

  • 每个 TTL 值创建一个独立的队列（队列数量膨胀）。
  • 使用延迟消息插件（推荐）。

3. 方案二：rabbitmq_delayed_message_exchange 插件（推荐）

  • 安装插件后声明 x-delayed-message 类型的 Exchange。
  • 发送消息时设置 x-delay 头（单位毫秒），消息在 Exchange 中延迟指定时间后才路由到队列。
  • 不同延迟时间的消息互不阻塞，解决了 TTL 队列的顺序问题。
// 声明延迟 Exchange Map<String, Object> args = new HashMap<>(); args.put("x-delayed-type", "direct"); channel.exchangeDeclare("delayed.exchange", "x-delayed-message", true, false, args); // 发送延迟消息 AMQP.BasicProperties props = new AMQP.BasicProperties.Builder() .headers(Collections.singletonMap("x-delay", 300000)) // 延迟 5 分钟 .build(); channel.basicPublish("delayed.exchange", "rk", props, msg.getBytes());

4. 方案对比

方案优点缺点
TTL + DLX无需插件，原生支持同队列不同 TTL 会阻塞；
需维护多个队列
延迟插件任意延迟时间，互不阻塞需安装插件；
消息在内存中堆积有压力

三、延迟队列的应用场景

  • 订单超时取消：
    下单后发送延迟消息，30 分钟后检查订单状态，未支付则自动取消。
  • 秒杀结束统一处理：
    秒杀开始后发延迟消息，15 分钟后统一汇总库存、生成报表。
  • 定时提醒：
    预约成功后发延迟消息，到达预约时间前 1 小时推送提醒。
  • 重试退避：
    消费失败后发延迟消息到 DLX，1 分钟/5 分钟/15 分钟阶梯重试。
