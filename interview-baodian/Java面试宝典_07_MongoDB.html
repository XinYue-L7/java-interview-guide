MongoDB 是什么？和关系型数据库（MySQL）有什么区别？
基础高频

一句话概括：

MongoDB 是面向文档（Document）的 NoSQL 数据库，数据以 BSON 文档存储，支持水平扩展，与 MySQL 的"表 + 行"关系模型完全不同。

对比项MongoDBMySQL
数据模型BSON 文档（Json 风格）表 + 行 + 列
Schema动态（字段可随时增减）固定（需 DDL 变更）
事务4.0+ 支持多文档事务强 ACID，天然支持
扩展方式分片（Sharding）水平扩展主从 / 分库分表，偏垂直
复杂关联查询弱（需 $lookup）强（JOIN 丰富）
典型场景海量数据、结构多变强一致、强事务业务

💡 选型：

结构多变、读写并发高、海量数据（用户画像/日志/商品）→ MongoDB；

强事务、复杂关联查询（订单/财务）→ MySQL。

💡 注意事项：

MongoDB 有 16MB 单文档上限，不适合存超大对象；

复杂 JOIN 需 $lookup，性能弱于 MySQL。

前置概念（名词解释）：

  • NoSQL：
    Not Only SQL，泛指非关系型数据库。
  • BSON：
    MongoDB 的二进制 JSON 存储格式。
  • 文档模型：
    数据以文档（类 JSON 对象）为单位存储。
  • Schema：
    数据结构的定义与约束。
  • 分片（Sharding）：
    把数据水平切分到多台机器的机制。
  • $lookup：
    聚合管道的跨集合关联操作，类似 JOIN。

MongoDB 的 BSON 和 JSON 有什么区别？
数据模型

一句话概括：

BSON 是 MongoDB 的二进制 JSON，比 JSON 支持更多数据类型、解析更快、空间利用更高效。

  • 数据类型更多：
    Date、ObjectId、BinData、Decimal128、正则、内嵌数组/文档等。
  • 二进制存储：
    带类型标记和长度，遍历/解析快，省去文本解析；
    空间上比纯 JSON 略大（字段名重复存储），存储层再通过压缩弥补。
  • 遍历更快：
    字段名旁直接带类型和长度，可直接跳读。
  • JSON：
    人可读的纯文本，跨语言通用，但类型弱（数字都是 number）。

💡 面试可说：

MongoDB 文档天然就是 BSON，内部存储、索引、复制均基于 BSON。

前置概念（名词解释）：

  • JSON：
    人可读的轻量级文本数据交换格式。
  • 二进制格式：
    以字节直接表示数据，无文本解析开销。
  • 类型标记：
    BSON 中标识字段数据类型的字节。
  • ObjectId / BinData / Decimal128：
    BSON 特有的扩展类型，JSON 不支持。

MongoDB 的 ObjectId 是怎么生成的？
数据模型

一句话概括：

ObjectId 是 12 字节的十六进制字符串，由 时间戳 + 机器标识 + 进程ID + 自增计数器四部分构成，无需中心自增即可全局唯一。

  • 4 字节：
    秒级时间戳（可按 _id 排序约等于按插入时间排序）。
  • 3 字节：
    机器标识（主机名 hash）。
  • 2 字节：
    进程 ID。
  • 3 字节：
    同一秒内的自增计数器（随机起点）。

优点：

客户端本地即可生成，天然支持分布式；

自带时间信息。

💡 对比：

MySQL 自增主键需要中心协调；

UUID 是 128 位更长、无序。

前置概念（名词解释）：

  • 时间戳：
    自 1970-01-01 起的秒数，决定 _id 前缀可排序。
  • 机器标识：
    标识生成文档的机器，保证跨机唯一。
  • 进程 ID：
    标识生成文档的进程。
  • 自增计数器：
    同一秒内的序号，保证同机同进程并发唯一。
  • UUID：
    128 位全局唯一标识，无序且更长。

MongoDB 的文档模型：范式化与反范式化如何选择？
建模高频

一句话概括：

范式化（引用）减少冗余但查询要多次；

反范式化（内嵌）一次查询出数据但要维护一致性。

内嵌（Embedded）：

  • 适合：
    一对一 / 一对少；
    子文档总是随主文档一起读；
    读多写少。
  • 例子：
    用户 + 收货地址、文章 + 评论。

引用（Reference）：

  • 适合：
    一对多 / 多对多；
    子文档独立变化；
    数据量大不宜内嵌。
  • 例子：
    用户 + 订单、商品 + 库存。

💡 实务：

混用——高频一起读的内嵌，低频或独立的用引用，必要时用 $lookup 关联。

💡 注意事项：

反范式化的冗余字段更新时要多处同步，容易不一致；

内嵌文档受 16MB 单文档上限约束。

前置概念（名词解释）：

  • 范式化：
    数据分文档存储，通过引用关联，冗余少。
  • 反范式化：
    把相关联数据冗余内嵌，查询快但冗余多。
  • 内嵌：
    子文档直接放在父文档内部。
  • 引用：
    文档中存另一个文档的 _id。
  • 一致性维护：
    反范式化后同一份数据多处存在，更新需同步多处。

MongoDB 有哪些索引类型？
索引高频

一句话概括：

MongoDB 索引底层用 B-Tree，类型丰富，覆盖单字段、复合、数组、全文、地理位置等场景。

  • 单字段索引：
    默认 _id 唯一索引；
    可对任意字段建升/降序。
  • 复合索引：
    多字段，遵循"最左前缀"原则（ESR：
    相等字段 → 排序 → 范围）。
  • 多键索引：
    对数组字段建索引，自动展开数组元素。
  • 文本索引：
    全文检索，支持中文分词（需指定语言）。
  • 地理空间索引：
    2dsphere，支持附近的人/距离查询。
  • TTL 索引：
    字段到期自动删除文档（如验证码、会话）。
  • 哈希索引：
    用于分片键均衡分布。
  • 唯一索引：
    保证字段唯一性。

💡 排查：

db.collection.getIndexes() 查看；

explain("executionStats") 判断是否走索引。

💡 注意事项：

索引不是越多越好；

每个索引都占用磁盘与内存，并拖慢写入（增删改需同步维护索引）。

前置概念（名词解释）：

  • B-Tree：
    多路平衡查找树，MongoDB 索引底层结构。
  • 复合索引：
    多个字段联合构建的索引，遵循最左前缀。
  • 多键索引：
    对数组字段的索引，自动展开数组元素。
  • 文本索引：
    支持全文检索的索引类型。
  • 2dsphere：
    地理空间索引，支持距离与区域查询。
  • TTL 索引：
    到期自动删除文档的索引。
  • 哈希索引：
    对字段取哈希的索引，用于分片键均衡分布。

MongoDB 的 WiredTiger 存储引擎有什么特点？
存储引擎

一句话概括：

WiredTiger 是 MongoDB 3.2+ 的默认存储引擎，基于 B-Tree，提供文档级锁 + 压缩 + 快照隔离（MVCC）+ 崩溃恢复。

  • 文档级并发控制：
    取代旧版 MMAPv1 的集合级锁，并发能力大幅提升。
  • 压缩：
    Snappy / Zlib 压缩数据和索引，显著节省磁盘。
  • 检查点 + Journal：
    定期 checkpoint + 预写日志（WAL），崩溃后快速恢复。
  • 内存缓存：
    默认使用 50% 内存（需显式配置，避免与 OS 冲突）。
  • 快照隔离：
    支持多版本并发控制，为事务提供基础。

💡 面试加分：

提到 MMAPv1 → WiredTiger 的演进，说明锁粒度从集合级到文档级。

💡 注意事项：

WiredTiger 默认缓存约为 (RAM - 1GB) / 2；

内存紧张时命中率下降，需监控 cache ratio 指标。

前置概念（名词解释）：

  • 存储引擎：
    数据库底层管理数据存取、索引和事务的组件。
  • 文档级锁：
    以单个文档为锁粒度，并发度高。
  • MVCC：
    多版本并发控制，读写互不阻塞。
  • checkpoint：
    定期把内存脏数据刷盘并更新日志位点。
  • Journal / WAL：
    预写日志，先写日志再改数据，崩溃可恢复。
  • Snappy / Zlib：
    WiredTiger 支持的压缩算法。

MongoDB 复制集（Replica Set）的原理和选举机制？
高可用高频

一句话概括：

复制集是一主多从的高可用架构：

主节点负责写，从节点通过复制 oplog 异步同步数据，主节点故障时自动选举出新主。

  • 写入：
    只写主节点，写入记录到 oplog（本地集合）。
  • 同步：
    从节点拉取并应用 oplog，默认异步复制。
  • 心跳：
    节点间每 2 秒心跳，超时（默认 10s）触发重新选举。
  • 选举：
    基于 Raft 算法；
    必须有大多数节点（n/2+1）在线才能选主，防止脑裂。
  • 优先级：
    priority 高的节点优先成为主；
    可配置隐藏节点、延迟节点（备份）。
  • 读写分离：
    secondaryPreferred 读从节点，但可能读到旧数据。

💡 典型规模：

3 节点（1 主 2 从）或 5 节点，最多可容忍 n/2 台故障。

示例：

rs.initiate() 初始化复制集；

rs.add("host:port") 添加从节点；

rs.conf() 查看复制集配置。

前置概念（名词解释）：

  • 复制集：
    一主多从、自动故障转移的高可用架构。
  • oplog：
    主节点的操作日志，从节点靠它同步。
  • Raft：
    分布式一致性算法，复制集选举的基础。
  • 心跳：
    节点间的保活信号，超时触发选举。
  • 脑裂：
    网络分区导致出现多个主节点；
    靠多数派投票机制避免。
  • 读写分离：
    读请求路由到从节点，分担主库压力。

MongoDB 的分片集群（Sharding）原理？
分片架构

一句话概括：

分片集群将集合按分片键水平切分到多个 shard，mongos 做路由，Config Server 保存元数据，数据按块（chunk）自动均衡。

  • 组件：
    mongos（路由）、Config Server（元数据副本集）、Shard（每个 shard 本身是副本集）。
  • 分片键选择：
    基数大、分布均匀、读写在它上面分散（避免热点）。
  • 数据分布方式：
    hashed（哈希取模，分布均匀）与 ranged（范围分片，利于范围查询）。
  • 均衡器：
    chunk 超过阈值自动迁移，动态扩缩容。

💡 什么时候分片：

数据量单机放不下、写入吞吐超单机、需要线性扩展；

分片键一旦选定不可修改，务必慎重。

示例：

sh.enableSharding("mydb") 开启分片；

sh.shardCollection("mydb.coll", {userId: "hashed"}) 按哈希分片。

前置概念（名词解释）：

  • mongos：
    分片集群的路由层，对应用透明。
  • Config Server：
    保存分片元数据的副本集。
  • Shard：
    真正存储数据的节点，本身是复制集。
  • 分片键：
    决定文档路由到哪个分片的字段。
  • chunk：
    分片数据的最小迁移单元，默认 64MB。
  • 均衡器：
    自动拆分与迁移 chunk 的后台进程。
  • hashed / ranged：
    哈希分片（分布均匀）与范围分片（利于范围查询）。

MongoDB 支持事务吗？如何实现？
事务高频

一句话概括：

MongoDB 4.0 起支持副本集多文档事务（ACID），4.2 起支持分片集群分布式事务。

  • 底层原理：
    基于 WiredTiger 的 快照隔离（MVCC） + Journal 日志，事务内读到一致快照。
  • 使用方式：
    session.startTransaction() → 多次操作 → commitTransaction() / abortTransaction()。
  • 限制：
    事务有时长限制（默认 60s）；
    事务内不能创建/删除集合；
    不能跨不同分片键的分布式事务做任意操作。
  • 注意：
    事务会放大锁冲突，谨慎控制事务内操作数量。

💡 面试点：

提到事务演进 2.6（单文档原子性）→ 4.0（多文档）→ 4.2（分布式事务）。

示例：

const s = db.getMongo().startSession();

s.startTransaction() → 执行多个增删改 → s.commitTransaction()；

出错时 s.abortTransaction() 回滚。

前置概念（名词解释）：

  • 事务：
    一组要么全部成功、要么全部回滚的操作。
  • ACID：
    原子性、一致性、隔离性、持久性。
  • MVCC / 快照隔离：
    事务读到一致快照，读写互不阻塞。
  • Journal：
    预写日志，保证崩溃后事务可恢复。
  • 分布式事务：
    跨多个分片 / 副本集的事务。

MongoDB 的聚合管道（Aggregation Pipeline）是什么？
聚合高频

一句话概括：

聚合管道类似 Linux 管道，把多个阶段（stage）依次作用于文档流，前一个阶段的输出作为下一阶段的输入。

  • 常用阶段：
    $match（过滤）→ $group（分组）→ $sort（排序）→ $project（投影）→ $unwind（展开数组）→ $lookup（跨集合关联，类似 JOIN）→ $limit/$skip（分页）。
  • 内存限制：
    单阶段默认内存上限 100MB，超出可用 allowDiskUse 落盘。
  • 优化：
    尽早 $match、$sort 尽量靠前（可复用索引），避免全量 $unwind。

💡 对比：

聚合管道比旧版 MapReduce 高效得多，是 Mongo 数据分析的主流方式。

示例：

db.orders.aggregate([{$match: {status: "PAID"}}, {$group: {_id: "$userId", total: {$sum: "$amount"}}}])

按用户统计已支付订单总额。

前置概念（名词解释）：

  • Stage（阶段）：
    聚合管道中一次独立的处理步骤。
  • $match：
    过滤文档，等价于查询条件。
  • $group：
    按字段分组并做聚合计算。
  • $lookup：
    跨集合关联，类似 SQL JOIN。
  • $unwind：
    把数组字段展开为多条文档。
  • allowDiskUse：
    允许大数据量聚合落盘，突破 100MB 内存限制。

MongoDB 的读写关注级别（Write Concern / Read Concern）？
一致性

一句话概括：

Write Concern 决定写多少节点确认才算成功；

Read Concern 决定读取哪种已提交状态的数据，两者共同平衡一致性与性能。

Write Concern：

  • w=1（默认）：
    主节点确认即返回，性能好。
  • w=majority：
    多数节点确认，数据不丢（选举后不丢写）。
  • j=true：
    journal 落盘后才确认。
  • wtimeout：
    等待超时上限，避免一直阻塞。

Read Concern：

  • local（默认）：
    读到本节点最新数据，可能未提交。
  • available：
    类似 local，分片场景可用。
  • majority：
    只读已提交到多数副本的数据（不读脏数据）。
  • linearizable：
    最强一致（结合 writeConcern majority 使用）。
  • snapshot：
    事务快照读。

💡 组合建议：

核心数据 w=majority + readConcern majority；

缓存类数据用默认级别换性能。

💡 注意事项：

readConcern majority 需配合副本集的 majority 提交机制；

w=majority 会等待复制，写延迟略高。

前置概念（名词解释）：

  • Write Concern：
    写操作需要多少节点确认才算成功。
  • Read Concern：
    读操作可读到哪种已提交状态的数据。
  • majority：
    多数副本确认 / 已提交的数据。
  • journal：
    预写日志，j=true 表示落盘才确认。
  • linearizable：
    线性一致读，最强一致性级别。
  • 脏读：
    读到其他事务未提交的数据。

MongoDB 和 Redis 有什么区别？如何选择？
对比高频

一句话概括：

MongoDB 是磁盘文档数据库（持久化核心数据），Redis 是内存 key-value 缓存（高并发热点数据）。

对比项MongoDBRedis
定位文档数据库（NoSQL）内存数据库 / 缓存
数据模型BSON 文档，复杂结构String / Hash / List / Set / ZSet
存储介质磁盘为主（WiredTiger）内存为主，持久化是补充
数据量海量（TB 级可分片）受内存限制（GB 级）
事务多文档 ACID（4.0+）Lua 脚本 / MULTI 弱事务
典型场景核心数据存储、查询分析缓存、计数器、排行榜、分布式锁

💡 常见组合：

Redis 扛高并发缓存 + MongoDB 存主数据，缓存击穿时回源 MongoDB。

💡 注意事项：

不要把 Redis 当唯一数据源存核心数据；

MongoDB 也常作为 Redis 的数据回源层。

前置概念（名词解释）：

  • 内存数据库：
    数据常驻内存、读写极快的数据库。
  • Key-Value：
    以键值对存取的数据模型。
  • 缓存击穿：
    热点 key 失效瞬间大量请求打到数据库；
    缓存穿透指查询不存在的数据绕过缓存。
  • 持久化：
    Redis 的 RDB / AOF 机制，把内存数据落盘。

MongoDB 的 GridFS 是什么？应用场景？
大文件

一句话概括：

GridFS 是 MongoDB 存储超过 16MB 大文件的规范：

文件拆成小块存入 chunks 集合，元数据存入 files 集合。

  • files 集合：
    存文件名、大小、上传时间、MD5 等元数据。
  • chunks 集合：
    存二进制分块（默认每块 255KB），带 files_id 关联。
  • 优点：
    随 MongoDB 分片/副本集扩展；
    支持断点续传；
    免搭建文件服务器。
  • 缺点：
    查询性能不如专业对象存储（OSS/S3）；
    不支持文件内随机修改（需整块重写）。

💡 场景：

中小规模的文件存储（头像、日志归档、内部资料）；

大规模场景优先 OSS/S3。

💡 注意事项：

小文件（几百 KB 内）直接存文档更合适，没必要用 GridFS。

前置概念（名词解释）：

  • chunks 集合：
    存储文件二进制分块（默认 255KB/块）。
  • files 集合：
    存储文件元数据（名称、大小、MD5 等）。
  • 16MB：
    MongoDB 单个文档的大小上限。
  • 断点续传：
    按块读取，可从中断处继续传输。
  • 对象存储（OSS/S3）：
    专业的大文件云存储服务，性能与扩展性更强。

MongoDB 慢查询如何排查和优化？
性能优化高频

一句话概括：

开启 Profiler 记录慢操作 → 用 explain 分析执行计划 → 对症下药（建索引/改查询/调分页）。

  1. 开启慢查询日志：
    db.setProfilingLevel(1, {slowms: 100})，慢操作写入 system.profile 集合。
  2. 分析执行计划：
    db.collection.find(...).explain("executionStats")，关注 COLLSCAN（全表扫描）→ 应改为 IXSCAN。
  3. 建索引：
    针对查询条件、排序字段建复合索引（遵循 ESR 顺序）。
  4. 限制返回：
    只查需要的字段（$project），避免大文档全量传输。
  5. 分页优化：
    深分页用 skip 很慢，改用键集分页（_id > 上次值）或 find().sort().limit() 游标式。
  6. 监控：
    db.serverStatus()、mongostat 观察内存、连接数、队列。

💡 注意事项：

线上开启 Profiler 会带来一定开销；

建议只记录慢操作（level=1 + slowms），不要全量记录。

前置概念（名词解释）：

  • Profiler：
    慢查询分析器，结果写入 system.profile。
  • explain：
    查看执行计划的命令。
  • COLLSCAN：
    全表扫描，慢查询的元凶。
  • IXSCAN：
    索引扫描，理想的执行方式。
  • 执行计划：
    优化器选定的查询执行路径。
  • 键集分页：
    用 _id > 上次值 代替 skip 的深分页优化。
  • mongostat：
    实时监控 MongoDB 状态的命令行工具。

MongoDB 与 Elasticsearch 的区别？
对比

一句话概括：

MongoDB 是文档数据库（负责存储、事务、查询），Elasticsearch 是搜索引擎（负责全文检索、分析聚合），二者定位不同常配合使用。

对比项MongoDBElasticsearch
定位文档数据库（NoSQL）分布式搜索引擎
索引结构B-Tree（字段索引）倒排索引（全文检索）
写入一致性事务 ACID近实时（秒级可见）
强项存储、查询、事务全文搜索、相关度评分、聚合分析
弱项全文检索能力弱不适合强一致业务存储

💡 常见组合：

MongoDB 存业务数据，ES 同步数据做全文搜索（如商品搜索、日志检索）。

💡 注意事项：

ES 适合"搜索 + 分析"，不适合作为唯一数据源；

一致性要求高的写操作仍应走 MongoDB。

前置概念（名词解释）：

  • 搜索引擎：
    以全文检索为核心能力的分布式系统。
  • 倒排索引：
    由词指向文档的索引，支撑快速全文检索。
  • 全文检索：
    对文本内容分词后按相关性检索。
  • 近实时：
    写入后秒级可查，而非立即可见。
  • 相关度评分：
    ES 按 TF-IDF / BM25 计算文档与查询的匹配度。

NoSQL 是什么？和关系型数据库（RDBMS）有什么区别？非关系型数据库有哪些？
基础高频

一句话概括：

NoSQL（Not Only SQL）是非关系型数据库的总称；
用键值、文档、列、图等非表格模型存储数据；
牺牲部分事务一致性，换取水平扩展与灵活 Schema。

与 RDBMS 的区别：

  • 数据模型：
    关系型用表 + 行 + 列；
    NoSQL 用文档 / 键值 / 列 / 图。
  • Schema：
    关系型固定（需 DDL 变更）；
    NoSQL 动态（字段随时增减）。
  • 事务：
    关系型强 ACID；
    NoSQL 偏弱，多为最终一致。
  • 扩展：
    关系型偏垂直扩展；
    NoSQL 天然支持水平扩展。
  • 查询：
    关系型 SQL 强大、支持 JOIN；
    NoSQL 各自方言、关联能力弱。

非关系型数据库有哪些：

  • 文档型：
    MongoDB、Elasticsearch。
  • 键值型：
    Redis。
  • 列族型：
    HBase、Cassandra。
  • 图型：
    Neo4j。

什么时候用 / 不用：

  • 适合用：
    非结构化 / 半结构化大数据；
    字段动态变化；
    需要水平扩展、海量写入。
  • 不适合用：
    强事务业务（订单、金融）；
    复杂关联查询；
    BI 分析（周边设施不完善）。

💡 选型提示：

信息表（商品、用户画像）适合 NoSQL 的灵活类型；

交易表、财务对账必须用关系型数据库。

前置概念（名词解释）：

  • NoSQL：
    Not Only SQL，泛指非关系型数据库。
  • RDBMS：
    关系型数据库管理系统，如 MySQL、Oracle。
  • Schema：
    数据结构的定义与约束。
  • 水平扩展：
    增加机器分担数据与压力；
    垂直扩展指升级单机硬件。
  • 最终一致：
    允许短暂不一致，最终收敛一致。

MongoDB 支持哪些数据类型？
数据模型

一句话概括：

MongoDB 文档以 BSON 存储；
支持 String、Integer、Double、Boolean、Object、ObjectId、Array、Date、Code、正则、Decimal128、BinData、Min/Max Key 等类型。

  • 基础类型：
    String（字符串）、Integer / Double / Decimal128（数值）、Boolean、Date（时间）。
  • 结构类型：
    Object（内嵌文档）、Array（数组）。
  • 标识类型：
    ObjectId，默认文档主键 _id。
  • 特殊类型：
    Code（JavaScript 代码）、Regular Expression（正则）、BinData（二进制）、Min / Max Key（比较哨兵）。
  • ObjectId：
    12 字节：时间戳 4 + 机器标识 3 + 进程 ID 2 + 自增计数器 3；
    客户端本地即可生成，天然支持分布式。
  • Decimal128：
    高精度十进制，适合金额计算；
    避免 Double 的浮点精度误差。
  • Code / RegExp：
    在文档中存 JS 代码和正则表达式；
    绝大多数业务场景用不到。

💡 面试加分：

金额字段用 Decimal128 而不是 Double；

分布式环境用 ObjectId 代替自增主键。

前置概念（名词解释）：

  • BSON：
    MongoDB 的二进制 JSON 存储格式。
  • ObjectId：
    MongoDB 的分布式主键类型，12 字节。
  • Decimal128：
    128 位高精度十进制类型。
  • 浮点误差：
    二进制无法精确表示部分十进制小数（如 0.1）。
  • BinData：
    二进制数据，用于存图片、文件块等。

MongoDB 支持存储过程吗？如何用？
高级

一句话概括：

MongoDB 支持存储过程；
它是用 JavaScript 编写的，保存在 db.system.js 集合中；
和 MySQL 一样，生产场景下基本不会使用。

定义与作用：

存储过程是把一段可复用的业务逻辑预先存到服务端；

调用时在数据库端执行，减少网络往返。

使用示例：

  • 保存：
    db.system.js.save({_id: "add", value: function(x, y) { return x + y; }})
  • 调用：
    db.eval("add(1, 2)")

注意事项：

  • 性能差：
    db.eval 会持有全局写锁，阻塞其他操作。
  • 有安全风险：
    JavaScript 注入、权限管理复杂。
  • 难维护：
    逻辑散落在数据库中，版本管理困难。
  • 兼容性：
    MongoDB 4.2 起已移除 db.eval。

前置概念（名词解释）：

  • 存储过程：
    预编译、存储在数据库端的可复用逻辑。
  • db.eval：
    在服务端执行 JS 表达式的命令；
    新版已移除，改用聚合等替代。

MongoDB 为什么选择 B-Tree 而不是 B+Tree 做索引？
索引原理

一句话概括：

MongoDB 是聚合型文档数据库，用 B-Tree（所有节点都带数据）；
MySQL 是关系型数据库，用 B+Tree（数据全在叶子节点）；
两者侧重点不同，选择也不同。

两者的区别：

  • B-Tree：
    内节点也存 data 域；
    查找命中中间节点即可返回，时间复杂度不固定（最好 O(1)）。
  • B+Tree：
    内节点只存 key，数据全部在叶子节点；
    每次查询必须走到叶子，时间复杂度固定 log(n)；
    叶子节点链表有序，适合范围扫描。

MongoDB 为什么选 B-Tree：

  • 定位不同：
    MongoDB 以 JSON/BSON 文档存储，目的就是高性能、高可用、易扩展；
    单文档精确查询（如按 _id）是主要访问模式。
  • 减少磁盘 IO：
    key 和 data 聚合在一起，命中内节点就直接拿到数据；
    单次查询平均比 B+Tree 少访问一层。
  • MySQL 为什么用 B+Tree：
    关系型查询大量是范围查询、排序、JOIN；
    B+Tree 叶子链表有序，范围扫描性能更好。

💡 注意事项：

MongoDB 的复合索引同样遵循最左前缀原则；

该问题存在争议，重点记住"MongoDB 不用 B+Tree，而是 B-Tree"。

前置概念（名词解释）：

  • B-Tree：
    多路平衡查找树，每个节点同时存键和数据。
  • B+Tree：
    B-Tree 变体，数据只在叶子节点，叶子间有链表。
  • 磁盘 IO：
    读写磁盘一次的开销，是数据库性能的主要瓶颈。
  • 范围查询：
    如 age > 20 AND age < 30 的区间扫描。

MongoDB 复合索引：查询 {B,C} 和 {C,B} 都会走索引吗？
索引高频

一句话概括：

MongoDB 的复合索引查询和 MySQL 的 B+Tree 基本一致，遵循最左前缀原则；
查询 {B,C} 可完整走索引；
查询 {C,B} 若跳过最左字段，只能部分使用索引。

原理：

复合索引按建索引时的字段顺序构建键值；

只有从最左字段开始连续匹配，才能利用完整索引。

示例：

  • 索引：
    db.user.createIndex({portal_id: 1, created: -1})
  • 查询 portal_id + created：
    两个字段连续命中，完整走索引。
  • 只查 created：
    缺少最左字段 portal_id，不走索引（COLLSCAN）。
  • 只查 portal_id：
    走索引前缀，但无法利用 created 部分。

💡 注意事项：

等值查询的条件顺序不要求与索引一致（优化器可重排）；

关键是字段是否从最左开始连续出现。

前置概念（名词解释）：

  • 复合索引：
    由多个字段组合构建的索引。
  • 最左前缀原则：
    查询条件必须从索引最左字段开始连续匹配才能走索引。
  • 覆盖索引：
    查询所需字段全部在索引中，无需回表读文档。

MongoDB 有哪些存储引擎？如何选择？
存储引擎

一句话概括：

MongoDB 有 3 种存储引擎：
WiredTiger（默认）、In-Memory（内存型）、MMAPv1（4.0 起已废弃）；
生产环境基本都使用 WiredTiger。

  • WiredTiger（默认）：
    文档级锁、压缩、快照隔离（MVCC）、checkpoint + journal 崩溃恢复；
    各方面性能均优于 MMAPv1。
  • In-Memory：
    数据全部驻留内存，读写极快；
    重启数据丢失，仅适合缓存类场景；
    真要内存型，直接选 Redis 更合适。
  • MMAPv1：
    基于内存映射文件；
    集合级锁、无压缩，并发能力差；
    MongoDB 4.0 起废弃。

💡 面试加分：

存储引擎负责数据落盘、索引、锁、事务的实现；

提到 WiredTiger 的演进（MMAPv1 → WiredTiger）体现了解版本差异。

前置概念（名词解释）：

  • 存储引擎：
    数据库底层管理数据存取、索引和事务的组件。
  • MVCC：
    多版本并发控制，读写互不阻塞。
  • checkpoint：
    定期将内存数据刷盘并更新日志位点。
  • WAL：
    预写日志，先写日志再改数据。

MongoDB 的延迟节点（Delayed Node）是什么？有什么用？
高可用

一句话概括：

延迟节点是一种特殊的 Secondary；
它故意延迟同步 oplog（如延迟 1 小时）；
相当于一台"时间机器"，用于误删 / 误更新后的数据回滚。

作用：

  • 误操作回滚：
    主库误删、误更新后，延迟节点还未同步该操作，可恢复数据。
  • 备份：
    不对外提供服务，适合在其上做全量备份，减轻主库压力。

原理：

同样通过复制 oplog 同步数据；

只是节点配置 secondaryDelaySecs 主动延迟应用。

注意事项：

  • 不参与选举：
    priority 设为 0。
  • 隐藏：
    hidden 设为 true，不作为读写分离的目标节点。
  • 延迟有限：
    超过延迟时间后，误操作同样会被同步。

前置概念（名词解释）：

  • Secondary：
    复制集中的从节点，负责同步主节点数据。
  • oplog：
    复制集本地的操作日志，从节点靠它同步数据。
  • 隐藏节点：
    不参与客户端读的从节点，用于备份和延迟复制。

MongoDB 如何做备份与恢复？journal 和 fsync 机制是什么？
运维

一句话概括：

MongoDB 备份分全量备份与增量备份；
全量用 mongodump 或文件快照；
增量靠备份 oplog；
journal 保证崩溃恢复，写入默认延迟落盘（fsync）。

备份方式：

  • 全量备份：
    逻辑备份：mongodump / mongorestore；
    物理备份：文件系统快照（需 journal 开启）。
  • 增量备份：
    定期备份 oplog，可恢复到任意时间点。
  • 最佳实践：
    优先在隐藏节点 / 延迟节点上做备份，避免影响主库。

journal 机制：

journal 是预写日志（WAL）；

每组写操作作为一个整体，不完整就不回放；

崩溃恢复时只重放完整组，不会出现半截数据。

fsync 机制：

  • 延迟落盘：
    更新默认不会立即 fsync 到磁盘；
    mongod 先写 journal 再写内存，间歇性 flush。
  • 间隔：
    默认 syncPeriodSecs = 60 秒，可配置，不建议修改。
  • 举例：
    一秒内收到一千次对同一对象的递增操作，只刷一次盘。

前置概念（名词解释）：

  • mongodump：
    MongoDB 的逻辑备份工具。
  • oplog：
    操作日志，增量备份与复制的数据源。
  • journal：
    预写日志，保证崩溃后数据不丢。
  • fsync：
    把内存中的数据强制刷到磁盘的系统调用。
  • 快照：
    某一时刻数据的一致副本。
24
MongoDB 分片集群的常见问题？（chunk 分布、迁移、故障、moveChunk）
分片

一句话概括：

分片数据按 chunk（默认 64MB）分布；
只有存在多个 chunk 才会分散到多个分片；
chunk 迁移期间写旧块、moveChunk 失败自动重试。

① 数据什么时候扩展到多个分片：

  • 集合数据先集中在一个 chunk；
  • chunk 超过默认 64MB 才会触发拆分与迁移；
  • 因此至少 64MB 数据才可能实施迁移。

② 更新正在被迁移的 chunk 上的文档：

  • 更新立即发生在旧 chunk 上；
  • 所有权转移前，更改会复制到新分片。

③ 分片停止或响应很慢时发起查询：

  • 分片停止：查询返回错误，除非设置了 Partial 选项；
  • 分片变慢：MongoDB 会等待它的响应。

④ moveChunk 目录里的旧文件能否删除：

  • 是均衡操作产生的临时文件；
  • 操作完成后可以删除，但目前清理需手动。

⑤ moveChunk 失败需要手动清理吗：

  • 不需要；
  • 移动操作一致且确定性，失败会不断重试；
  • 成功后数据只会出现在新分片。

前置概念（名词解释）：

  • 分片键：
    决定文档路由到哪个分片的字段。
  • chunk：
    分片数据的最小迁移单元，默认 64MB。
  • 均衡器：
    负责拆分与迁移 chunk 的后台进程。
  • moveChunk：
    把一个 chunk 从旧分片迁移到新分片。

MongoDB 的数据文件为什么越来越大？如何回收空间？
运维

一句话概括：

MongoDB 会积极预分配数据文件来防止文件系统碎片；
删除、更新产生的空间不会立即释放；
所以磁盘占用大不等于实际数据多。

原理：

  • 预分配：
    提前申请文件空间，避免频繁扩容产生碎片。
  • 存储空洞：
    删除文档、更新变长字段后，旧空间被保留待复用；
    空闲列表会优先分配给新写入。

如何回收：

  • compact：
    db.runCommand({compact: "collection"}) 压缩集合；
    需额外磁盘空间，4.4 前会阻塞读写。
  • 重建副本：
    从备份重同步该成员，重新生成紧凑的数据文件。
  • drop：
    删除整个集合可释放文件（数据不可恢复）。

前置概念（名词解释）：

  • 预分配：
    提前为数据文件预留空间。
  • 存储空洞：
    已删除数据占用的可复用空间。
  • compact：
    压缩整理集合、回收空洞的命令。

MongoDB 连接数耗尽（too many open connections）如何排查和处理？
性能优化实战

一句话概括：

MongoDB 默认最大连接数是 819；
连接数打满后新请求无法建立连接；
典型表现为服务时好时坏、报 no reachable servers。

原因：

  • 请求量突增，连接创建速度超过释放速度；
  • 应用连接池未复用连接、无上限；
  • 存在连接泄漏或超时设置不合理。

排查步骤：

  1. 看应用日志：
    出现 no reachable servers。
  2. 看数据库日志：
    出现 too many open connections: 819。
  3. 查当前连接数：
    db.serverStatus().connections。
  4. 查网络状态：
    netstat -anp | grep ESTABLISHED 确认连接是否堆积。

处理方案：

  • 调大服务端上限：
    maxConns=20000（最大 20000）；
    避免再次触碰连接上限，是治标。
  • 限制应用连接池：
    如 mgo 设置 Session.SetPoolLimit(200)；
    让连接尽量复用，是治本。
  • 排查泄漏：
    检查连接释放、超时和重试逻辑。

💡 注意事项：

连接数不是越大越好，每个连接都会占用内存；

核心是连接池复用，而不是无限加连接。

前置概念（名词解释）：

  • 连接池：
    预先创建并复用的数据库连接集合。
  • maxConns：
    MongoDB 实例的最大连接数配置。
  • mongostat：
    监控 MongoDB 实时状态的命令行工具。

MongoDB 查询缓慢的真实案例：45 万数据未建索引导致服务告警，如何排查？
性能优化实战

一句话概括：

真实案例：配置中心服务时好时坏、CPU 高达 96%；
最终定位是 user_config 集合 45 万条数据未建索引；
每次查询全表加载到内存导致慢查询；
补上 portal_id 索引后服务恢复。

① 排查链路：

  1. 看应用日志：
    大量 no reachable servers，先怀疑数据库。
  2. 看数据库日志：
    发现 too many open connections: 819，先调连接数：
    maxConns=20000 + 应用 SetPoolLimit(200)。
  3. 问题反复：
    mongostat、连接数、IO 都正常，排除连接与 IO 瓶颈。
  4. 开启慢查询：
    db.setProfilingLevel(1, 200)；
    从 system.profile 发现 user_config 大量慢查询（COLLSCAN）。
  5. 补索引：
    db.user_config.ensureIndex({"portal_id": 1})；
    代码里再 EnsureIndex 兜底，防止遗漏。

② 根因分析：

  • MongoDB 查询不加索引时，需要把数据全部加载到内存；
  • 数据量达到几十万甚至百万级时，加载过程冲击系统、拖垮其他请求；
  • 建立索引后查询只加载索引数据，速度大幅提升。

💡 注意事项：

上线前评估查询字段是否建索引，是这条案例的教训；

慢查询监控（Profiler）应常态化开启。

前置概念（名词解释）：

  • COLLSCAN：
    全表扫描，查询不走索引时逐条扫描集合。
  • Profiler：
    慢查询分析器，结果写入 system.profile。
  • ensureIndex：
    确保索引存在的命令，不存在则创建。
