Spring IOC 的实现原理？
Spring高频

IOC(Inversion of Control)控制反转：

将对象创建和依赖关系的管理交给Spring容器。

核心：

BeanFactory + 反射

  1. 资源定位：

    加载XML/注解配置。
  2. BeanDefinition解析：

    将配置解析为BeanDefinition。
  3. Bean注册：

    注册到BeanDefinitionRegistry(Map)。
  4. Bean创建(DI)：

    反射创建实例→填充属性→初始化。

💡 ApplicationContext是BeanFactory的子接口，功能更丰富(国际化、事件发布等)。

Spring AOP 的实现原理？
Spring高频

AOP(Aspect Oriented Programming)面向切面编程：

将横切关注点(日志/事务/权限)与业务逻辑分离。

两种实现：

  • JDK动态代理：

    基于接口，Proxy+InvocationHandler。

    目标类必须实现接口。
  • CGLIB代理：

    基于继承，ASM字节码生成子类。

    不能代理final类/方法。

💡 Spring默认：

有接口用JDK代理，无接口用CGLIB。

SpringBoot 2.0+默认使用CGLIB。

Spring 事务的实现原理和传播行为？
Spring事务

原理：

AOP代理 + ThreadLocal

7种传播行为：

  • REQUIRED：

    有事务则加入，无则新建（默认）。
  • REQUIRES_NEW：

    总是新建事务，挂起当前事务。
  • SUPPORTS：

    有事务则加入，无则以非事务运行。
  • NOT_SUPPORTED：

    非事务运行，挂起当前事务。
  • MANDATORY：

    必须在事务中，无则抛异常。
  • NEVER：

    必须非事务，有则抛异常。
  • NESTED：

    嵌套事务，有savepoint可部分回滚。

Spring 事务失效的场景有哪些？
Spring实战

事务失效本质：

@Transactional基于AOP动态代理，只要请求没经过代理或异常没被正确传播，事务就会失效。

  1. 同类自调用：

    类A无事务方法调本类有事务方法B，走的是this调用绕过代理 → 失效。

    解决：

    AopContext.currentProxy()或注入自身。
  2. 方法非public：

    默认代理只能拦截public方法。
  3. 异常被吞：

    try-catch后未重新抛出，Spring感知不到异常 → 不回滚。
  4. 异常类型不匹配：

    默认只回滚RuntimeException和Error，受检异常(如IOException)需@Transactional(rollbackFor = Exception.class)。
  5. 数据库引擎不支持：

    MyISAM不支持事务，需InnoDB。
  6. 类未被容器管理：

    没加@Component/@Service，或new出来的对象，无代理。
  7. 多线程：

    新线程不在同一事务上下文，事务不回滚。
  8. 切面顺序错误：

    事务切面与自定义切面顺序不当，异常被其他切面拦截。
  9. 父子容器问题：

    事务方法被非本容器的Bean调用（多容器环境）。
  10. synchronized锁失效：

    分布式环境下本地锁无法保证并发事务一致。

💡 核心口诀：

内部调用绕过代理、异常没抛出/类型不对、类/方法/引擎不支持、多线程/切面/容器出问题。

Spring 中 @Autowired 和 @Resource 的区别？
Spring注解
对比@Autowired@Resource
来源Spring（org.springframework）JDK 标准（JSR-250，javax.annotation）
注入方式默认 byType（找不到再按name回退）默认 byName（找不到再按type回退）
指定名称+@Qualifier 指定 Bean 名称name 属性直接指定
支持位置字段 / setter / 构造器字段 / setter（不支持构造器）
required支持（默认 true，找不到报错）不支持
兼容性仅 Spring 框架可用JSR 标准，脱离 Spring 也可用

查找逻辑补充：

  • @Autowired：

    先按类型找，多个同类型Bean时若只有一个@Primary或主Bean则注入它，否则需@Qualifier指定，再不行抛NoUniqueBeanDefinitionException。
  • @Resource：

    先按字段名找Bean，找不到再按类型找，都找不到抛异常。

    它是字段名与Bean名一致时的首选。

💡 推荐：

团队约定优先用构造器注入（配合@Autowired），避免字段注入导致的循环依赖和难以测试问题；

如用@Resource，字段名尽量与Bean名一致以命中byName。

Spring 的循环依赖是如何解决的？
Spring高频

三级缓存解决单例Bean的循环依赖：

  • 一级缓存 singletonObjects：

    完全初始化好的Bean。
  • 二级缓存 earlySingletonObjects：

    早期暴露的半成品Bean（已实例化但未注入属性）。
  • 三级缓存 singletonFactories：

    ObjectFactory，可生成Bean的早期引用（支持代理对象）。

流程：

A创建→实例化→放入三级缓存→填充属性发现需要B→触发B创建→B填充属性需要A→从三级缓存获取A的早期引用→B完成→A完成。

💡 限制：

只能解决单例setter注入的循环依赖，构造器注入不行（实例化阶段就需要依赖）。

Prototype作用域也不支持。

Spring 事务传播行为有哪些？
事务高频

7种传播行为（Propagation）：

  1. REQUIRED（默认）：

    有则加入，无则新建。

    最常用。
  2. REQUIRES_NEW：

    挂起当前，新建事务。

    内部和外部事务独立。
  3. SUPPORTS：

    有则加入，无则非事务运行。
  4. NOT_SUPPORTED：

    非事务运行，挂起当前事务。
  5. MANDATORY：

    必须有事务，无则抛异常。
  6. NEVER：

    必须非事务，有则抛异常。
  7. NESTED：

    嵌套事务，内部事务依赖外部事务（savepoint回滚）。

💡 REQUIRES_NEW完全独立，外部回滚不影响内部；

NESTED外部回滚会回滚内部。

Spring AOP 的原理？JDK代理和CGLIB代理的区别？
AOP高频

AOP基于动态代理，在BeanPostProcessor.postProcessAfterInitialization中创建代理。

JDK动态代理：

  • 目标类必须实现接口。
  • 基于反射+接口，生成Proxy$类。
  • 性能略低（反射调用）。

CGLIB代理：

  • 基于ASM字节码，生成子类。
  • 不需要接口，但不能代理final类/方法。
  • 性能略高（直接方法调用）。

💡 Spring Boot 2.x默认使用CGLIB。

@EnableAspectJAutoProxy(proxyTargetClass=true)强制CGLIB。

@Configuration 和 @Component 的区别？full模式和lite模式？
SpringBean

@Configuration（full模式）：

通过CGLIB增强，确保@Bean方法内部调用仍然走容器（单例）。

@Component（lite模式）：

不走CGLIB代理，内部调用@Bean方法会创建新实例。

@Configuration // full模式
public class Config {
    @Bean A a() { return new A(b()); } // b()走代理，同一实例
    @Bean B b() { return new B(); }
}
@Component // lite模式
// a()中b()不会走代理，new新B()

什么是 Spring 框架？有哪些核心模块？
Spring框架基础

一句话概括：

Spring 是 Java 生态最流行的轻量级开源框架，核心是 IoC（控制反转）和 AOP（面向切面编程），目的是降低组件之间的耦合、简化企业级 Java 开发。

定义：

  • Spring 是一个分层的一站式（Full-Stack）框架，2002 年由 Rod Johnson 提出，2004 年发布 1.0。
  • IoC 容器：

    把对象的创建和依赖关系交给容器管理，开发者不再手动 new，实现解耦。
  • AOP：

    把日志、事务、权限等横切逻辑与业务逻辑分离，通过动态代理织入。
  • 本身不重复造轮子，而是整合主流框架（MyBatis、JPA、Quartz 等），降低集成成本。

核心模块（按分层记忆）：

模块作用
Spring Core（Beans / Core / Context / SpEL）IoC 容器核心，Bean 管理与依赖注入
Spring AOP / Aspects面向切面编程，方法拦截与增强
Spring JDBC / Tx数据访问抽象与声明式事务管理
Spring ORM集成 Hibernate / JPA / MyBatis 等 ORM 框架
Spring Web / WebMVCWeb 应用开发，MVC 分层与 REST 支持
Spring JMS / Messaging消息队列集成（ActiveMQ / Kafka 等）
Spring Test单元测试与集成测试支持

核心特征：

  • 轻量：

    框架本身不强制依赖其他组件，核心仅需少量 jar。
  • 低侵入：

    业务代码不强制继承 Spring 类，通过注解/配置解耦。
  • 容器化：

    统一管理 Bean 生命周期与依赖。
  • 声明式事务：

    一个 @Transactional 即可完成事务控制。

💡 面试点：

牢记 Spring 两大核心是 IoC 与 AOP；

模块记忆口诀：

Core 容器 → AOP 切面 → JDBC/ORM 数据 → Web/MVC 展示。

@Controller 和 @RestController 的区别？
SpringWeb注解

一句话概括：

@RestController 是 @Controller + @ResponseBody 的组合注解，专门用于 REST 接口直接返回 JSON/XML。

区别对比：

对比项@Controller@RestController
组成独立的控制层注解组合了 @Controller + @ResponseBody
返回值处理返回视图名（ModelAndView）返回数据对象，序列化为 JSON/XML 写入响应体
视图渲染需要 ViewResolver 解析（JSP/Thymeleaf）跳过视图，直接用 HttpMessageConverter 序列化
@ResponseBody每个方法需要单独加默认所有方法都有
典型场景服务端渲染页面（老项目 JSP）前后端分离的 REST API

原理：

@RestController 是一个元注解，内部组合了 @Controller 和 @ResponseBody，因此类中所有方法默认都带 @ResponseBody 语义。

示例：

@Controller
public class PageController {
    @GetMapping("/user")
    public String user() { return "userDetail"; } // 返回视图名，ViewResolver 找 userDetail.jsp
}

@RestController
public class ApiController {
    @GetMapping("/api/user")
    public User user() { return new User("tom"); } // 返回 JSON：{"name":"tom"}
}

💡 面试点：

REST 接口用 @RestController；

需要页面跳转的场景用 @Controller（方法上加 @ResponseBody 也能返回 JSON）。

Spring AOP 和 AspectJ AOP 的区别？
AOPAspectJ

一句话概括：

Spring AOP 是运行时基于动态代理的轻量级 AOP；

AspectJ 是编译期/加载期织入字节码的完整 AOP 框架。

两者本质区别是织入时机不同。

区别对比：

对比项Spring AOPAspectJ AOP
织入方式运行时动态代理（JDK / CGLIB）编译期（AJC）或加载期（LTW）织入字节码
依赖Bean 必须由 Spring 容器管理不依赖 Spring，可独立使用
性能相对较低（代理 + 方法调用拦截）相对较高（字节码直接增强）
切点支持仅支持方法级切点，且是 Spring Bean 的 public 方法支持方法、字段、构造器、异常等完整切点
内部自调用this 调用本类方法无法拦截可以拦截
使用场景Spring 项目内的事务/日志/权限等复杂切面、非 Spring 项目、需要静态织入

关系：

Spring 2.0 以后借用了 AspectJ 的注解语法（@Aspect / @Before / @Around / @Pointcut）来表达切面，但底层织入仍然是 Spring AOP 的动态代理机制；

也可以额外集成 AspectJ 的加载期织入（LTW）获得完整能力。

💡 面试点：

高频回答模板——"Spring AOP 用 AspectJ 的注解语法，但织入方式是运行时动态代理；

真正的 AspectJ 是编译期织入，性能更高、支持字段/构造器切点"。

Spring 单例 Bean 存在线程安全问题吗？如何解决？
Spring线程安全高频

一句话概括：

Spring 容器只保证 Bean 是单例，不保证线程安全。

单例 Bean 是否线程安全，取决于它是否持有可变的成员变量。

分析：

  • 无状态 Bean（推荐）：

    只有方法、没有可变成员变量 → 天然线程安全。
  • 有状态 Bean：

    存在可变成员变量（如 SimpleDateFormat、Map、计数器、ArrayList）→ 线程不安全，多线程共享同一实例会互相干扰。
  • 典型事故：

    成员变量 SimpleDateFormat 在并发解析日期时抛出 NumberFormatException 或解析结果错乱。

解决方案：

方案说明
无状态化不定义可变成员变量，用局部变量/方法参数传递
ThreadLocal每个线程持有自己的副本，如 ThreadLocal<SimpleDateFormat>
prototype 作用域@Scope("prototype") 每次获取都 new 新实例
加锁synchronized / ReentrantLock（影响性能，慎用）
线程安全容器用 ConcurrentHashMap / CopyOnWriteArrayList 替代普通集合

示例：

// 不安全：成员变量被多线程共享
@Service
public class DateService {
    private SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");
}

// 安全：ThreadLocal 每个线程一份
private static ThreadLocal<SimpleDateFormat> SDF =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

💡 面试点：

先答结论——"无状态安全、有状态不安全"；

再答治理手段，ThreadLocal 与无状态化是最高频答案。

@Component 和 @Bean 的区别？
SpringBean注解

一句话概括：

@Component 标注在类上，由组件扫描自动注册；

@Bean 标注在 @Configuration 类的方法上，由方法返回对象手动注册。

区别对比：

对比项@Component@Bean
标注位置类上方法上
注册方式组件扫描（@ComponentScan）自动发现显式调用 @Bean 方法，把返回值注册为 Bean
适用对象自己写的类（Controller / Service / DAO）第三方类（无法加注解的 SDK）、复杂初始化逻辑的对象
灵活性固定：一个类对应一个 Bean方法内可写任意逻辑：可 new、可条件判断、可多次注册
依赖注入通过 @Autowired 注入@Bean 方法参数会自动从容器注入

示例：

// 方式一：组件扫描，适用于自己写的类
@Component
public class MyService { ... }

// 方式二：@Bean 手动注册，适用于第三方类
@Configuration
public class WebConfig {
    @Bean
    public RestTemplate restTemplate() {
        return new RestTemplate(); // 可在这里做复杂初始化
    }
}

💡 面试点：

记忆要点——自己写的类用 @Component（扫描），第三方的类用 @Bean（手动）；

@Bean 方法参数自动注入是加分细节。

将一个类声明为 Spring Bean 的注解有哪些？
SpringBean注解

一句话概括：

最核心的是 @Component 及其四个衍生注解（@Service / @Repository / @Controller / @RestController），外加 @Configuration 和 @Bean。

注解清单：

注解语义 / 适用层
@Component通用组件，最基础的 Bean 注解
@Service业务逻辑层（Service）
@Repository数据访问层（DAO），并转换持久层异常
@Controller控制层（MVC 控制器）
@RestControllerREST 接口（= @Controller + @ResponseBody）
@Configuration配置类（full 模式，CGLIB 代理）
@Bean标注在 @Configuration 类的方法上，注册第三方对象
@Import导入其他配置类或普通类
@Mapper（MyBatis）等第三方框架提供的注册注解

原理：

@Service、@Repository、@Controller、@RestController 都是 @Component 的衍生（元注解组合），被 @ComponentScan 扫描时统一按组件注册；

区分它们主要是为了语义分层和便于 AOP 精确切分（如对 @Repository 统一转换异常）。

💡 面试点：

答出"四大分层注解都是 @Component 的衍生"就是亮点；

再补一句 @Bean 注册第三方、@Configuration 是配置类。

Spring 管理事务的方式有几种？
Spring事务

一句话概括：

Spring 管理事务有两种方式：

编程式事务（TransactionTemplate / PlatformTransactionManager）和 声明式事务（@Transactional），实际开发推荐声明式事务。

两种方式对比：

对比项编程式事务声明式事务
实现TransactionTemplate / PlatformTransactionManager 手动 begin / commit / rollback@Transactional 注解或 XML aop:tx，基于 AOP 代理
侵入性业务代码中混入事务代码，侵入性强注解声明，零侵入
粒度精细（可以控制循环内每次提交）粗粒度（方法级）
可维护性重复代码多，易出错简洁清晰，声明即可
使用场景循环内部分提交、事务边界动态控制等特殊场景绝大多数常规业务

示例：

// 声明式：最简单
@Transactional
public void transfer() { ... }

// 编程式：细粒度控制
public void batchSave() {
    transactionTemplate.execute(status -> {
        for (Item item : list) {
            dao.save(item);
            if (item.isBad()) throw new RuntimeException("bad item"); // 触发回滚
        }
        return null;
    });
}

💡 面试点：

首选回答"两种方式：

编程式 + 声明式，推荐声明式"；

TransactionTemplate 处理"循环内部分提交"是最常追问的场景。

@Transactional(rollbackFor = Exception.class) 注解了解吗？
Spring事务高频

一句话概括：

@Transactional(rollbackFor = Exception.class) 指定出现 Exception（包括受检异常）时事务回滚，解决"受检异常默认不回滚"的问题。

为什么需要它：

  • Spring 默认规则：

    只有 RuntimeException 和 Error 才触发回滚。
  • 受检异常（如 IOException、SQLException）默认提交不回滚。
  • 原因：

    Spring 约定受检异常通常代表可预期、可恢复的业务异常，不应中断事务。
  • 但如果业务要求"受检异常也必须回滚"，就必须显式加 rollbackFor = Exception.class。

原理：

@Transactional 基于 AOP 代理。

方法抛出异常后，TransactionInterceptor 会调用 rollbackOn(exception) 判断该异常是否符合回滚规则——匹配则标记事务回滚，否则提交。

rollbackFor 就是扩展了"回滚异常白名单"。

相关属性：

  • rollbackFor：

    指定哪些异常触发回滚。
  • noRollbackFor：

    指定哪些异常不触发回滚（即使默认该回滚）。
  • propagation / isolation / timeout / readOnly：

    传播行为、隔离级别、超时、只读。

示例：

@Transactional(rollbackFor = Exception.class)
public void importFile() throws IOException {
    dao.insert(order);
    fileService.write(file); // 抛 IOException：受检异常
    // 不加 rollbackFor 时：IOException 导致提交不回滚（脏数据！）
    // 加了 rollbackFor：事务整体回滚
}

💡 面试点：

这是事务失效的经典场景之一（呼应"异常类型不匹配导致失效"）；

回答要点——默认只回滚 RuntimeException，受检异常要显式 rollbackFor。

如何使用 JPA 在数据库中忽略某个字段（不持久化）？
JPAHibernate注解

一句话概括：

在实体类的字段上加 @Transient 注解，JPA 就不会为该字段创建数据库列、也不会持久化。

实现方式：

  • @Transient（JPA 标准注解，推荐）：

    字段不映射数据库列，用于"只在内存中计算、不需要入库"的字段。
  • transient 关键字：

    影响的是 Java 序列化（原生序列化 / 部分 JSON 序列化），与 JPA 无关，两者不要混用。

示例：

@Entity
@Table(name = "user")
public class User {
    @Id
    private Long id;
    private String name;

    @Transient
    private String tempAge; // 不生成列，不持久化

    // 不持久化的计算属性（getter 上也可以加）
    @Transient
    public String getDisplayName() {
        return "用户：" + name;
    }
}

易混淆点：

机制作用场景
@TransientJPA 不持久化（不建列）实体类中仅内存使用的字段
transient 关键字Java 序列化忽略序列化时排除字段（如密码）
@JsonIgnore（Jackson）JSON 序列化/反序列化忽略返回给前端时隐藏字段

💡 面试点：

能区分 @Transient（JPA） vs transient（序列化） vs @JsonIgnore（JSON）三者，就是加分的完整回答。
