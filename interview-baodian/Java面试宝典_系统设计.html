如何设计一个秒杀系统？
系统设计实战

一句话概括

秒杀系统的核心挑战是：

短时间内海量用户抢少量商品。

设计目标是保证不超卖、保证高可用、尽量公平，同时不能让抢购流量冲垮整个电商网站。

整体架构分层

层级核心策略具体手段
前端层能挡则挡，减少无效请求打到后端商品详情页静态化+CDN；按钮防重复点击（点完变灰）；验证码/答题削峰；倒计时误导（随机提前或延后）
网关层限流+过滤，保护后端服务Sentinel/令牌桶限流；IP 黑名单；用户频率限制；Nginx 直接返回静态"已售罄"页面
业务层库存扣减要快、要准Redis 预减库存（Lua 脚本原子扣减）→ 扣减成功才放行到下单；消息队列异步处理订单（RocketMQ/Kafka）
数据层最终一致性，防超卖DB 用乐观锁（version 字段 / 条件 update）兜底；库存和订单最终一致性由 MQ 保证

防超卖的三种手段

  • Redis 原子扣减：
    用 Lua 脚本把"查库存→减库存"做成原子操作，避免并发竞争。
  • DB 乐观锁：
    UPDATE stock SET count=count-1 WHERE count>0，利用数据库的行锁保证最终不超卖。
  • Token 令牌：
    提前在 Redis 里生成和商品数量相等的 Token，抢到 Token 才有资格下单，没 Token 的直接拒绝。

消息队列的作用

  • 异步下单：
    用户点击"立即抢购"，Redis 扣库存成功后就返回"抢购成功"，真正的创建订单、写数据库交给 MQ 异步处理。
  • 削峰填谷：
    秒杀那一瞬间的流量峰值被 MQ 缓存住，后端消费者按自己的速度慢慢处理，DB 不会被冲垮。
  • 最终一致性：
    如果 MQ 消费失败，可以重试；
    极端情况下用对账补偿机制保证库存和订单一致。

面试常问的细节

  • Redis 挂了怎么办？降级为直接查数据库+限流，或者使用 Redis Cluster 高可用。
  • 消息队列消费慢了怎么办？增加消费者实例，或者设置消费超时自动退款。
  • 如何保证公平？按请求到达网关的时间排队，而不是按用户手速（防脚本刷）。
  • 库存预热：
    秒杀开始前把库存数据加载到 Redis 里，避免秒杀开始瞬间大量请求穿透到 DB。

举例讲解

场景：

10000 人抢 100 台 iPhone

  1. 秒杀开始前 5 分钟，运营后台把库存 100 写入 Redis，同时生成 100 个 Token 放到 Redis 队列里。
  2. 用户打开页面，看到 CDN 加速的静态页面，点击按钮时先验证验证码（挡住一部分机器人）。
  3. 请求打到网关，Sentinel 限流每秒最多 5000 个请求，超出的直接返回"活动太火爆"。
  4. 请求到达业务层，先从 Redis 队列里抢一个 Token，抢到了才有资格继续。
  5. 抢到 Token 后，Lua 脚本原子扣减 Redis 库存，扣减成功返回"抢购成功，正在生成订单"。
  6. 订单创建任务丢进 MQ，消费者慢慢写数据库、扣真实库存、发优惠券。
  7. 100 个 Token 抢完后，后续请求直接返回"已售罄"，Nginx 直接返回静态页面，不再打到业务层。

限流算法有哪些？
限流算法

一句话概括

限流就是控制系统的请求流量，防止突发流量把服务打垮。

就像高速公路的收费站，车太多时让车辆排队或劝返，而不是一股脑全涌进主路造成拥堵。

四种限流算法对比

算法核心思想优点缺点类比
计数器固定窗口固定时间窗口内计数，超过阈值就拒绝实现简单，内存占用小边界突刺：窗口交界处的请求可能翻倍通过像"每小时限流100人"，11:59和12:01各来100人，中间只隔2分钟却通过了200人
计数器滑动窗口把大窗口分成多个小格子，每次滑动一小格统计解决边界突刺问题，精度更高实现稍复杂，内存占用随格子数增加像"每10分钟限流100人"，但每1分钟检查一次过去10分钟的总数
漏桶算法请求像水一样流入桶，桶以恒定速率漏出处理，桶满则溢出丢弃流量绝对平滑，后端不会被突发冲垮无法应对突发，即使后端此时有空闲也不允许突发通过像医院挂号，每小时固定放10个号，来得再急也得排队
令牌桶算法以恒定速率生成令牌，请求来时要拿到令牌才能通过，桶满则令牌丢弃允许一定程度的突发（桶里攒的令牌可以一次性用完），同时保证长期平均速率实现稍复杂像游乐园发快速通行证，每小时发10张，攒了3小时就有30张，可以一次性放30人进去

面试常问：选哪个算法

  • 一般 API 接口限流：
    令牌桶（Guava RateLimiter、Sentinel），允许突发，用户体验好。
  • 严格平滑流量（如支付接口）：
    漏桶，绝对平滑，不给后端任何压力波动。
  • 简单统计（如接口调用次数）：
    滑动窗口计数器，精度够用，实现简单。
  • 固定窗口：
    不推荐生产环境，仅适合简单的统计类场景。

Sentinel 的限流策略

  • 快速失败：
    超过阈值直接拒绝，抛异常或返回固定提示。
  • Warm Up（预热）：
    系统刚启动时慢慢放开流量，防止冷启动被冲垮。
  • 匀速排队：
    漏桶思想，请求排队匀速通过，适合脉冲流量。
  • 关联限流：
    当 A 接口压力大时，限制 B 接口的流量（如读压力大时限制写）。

举例讲解

场景：

电商大促期间，商品详情页接口限流

  1. 平时每秒 100 个请求，系统扛得住，用令牌桶限流每秒 150 个，允许偶尔突发到 200 个。
  2. 大促开始瞬间，流量飙到每秒 10000 个，令牌桶的 150 个令牌瞬间被抢完，后续请求直接返回"系统繁忙，请稍后"。
  3. 秒杀结束后，流量回落到每秒 50 个，令牌桶慢慢攒令牌，下次突发时还能应付。
  4. 对于下单接口（更严格），用漏桶算法，每秒固定处理 50 单，绝对不超，保证数据库稳定。

Linux 常用命令有哪些？（排查问题相关）
Linux运维

一句话概括

线上出问题时，Linux 命令是排查定位的"手术刀"。

常见的排查路线是：

先看系统整体状况 → 再看具体进程 → 查日志定位问题 → 看网络和磁盘IO排除外部因素。

按排查场景分类速查

排查场景常用命令用法说明
系统整体负载top / htop / uptime看 CPU、内存、负载均衡。load average 三个数分别代表1/5/15分钟平均负载，超过 CPU 核数说明有压力。
内存使用情况free -h / vmstat 1free -h 看总内存/已用/空闲；vmstat 1 每秒刷新看内存换页（si/so 高说明内存不够在 swap）。
磁盘空间和IOdf -h / du -sh / iostat -x 1df -h 看各分区使用率；du -sh 目录 看某个目录多大；iostat 看磁盘读写是否打满。
进程排查ps -ef / jps / lsof -p PIDps -ef | grep java 找 Java 进程；jps -lvm 看 Java 进程详情；lsof -p PID 看某个进程打开了哪些文件/端口。
端口和网络netstat -tlnp / ss -tlnp / curl / telnetnetstat/ss 看端口监听状态；curl 测接口；telnet IP 端口 测连通性。
日志排查tail -f / less / grep / awk / sedtail -f app.log 实时看日志；grep 'ERROR' app.log | tail -50 找最近50条报错；awk 按列提取数据；sed 替换文本。
文件操作find / chmod / chown / ls -lafind / -name '*.log' 找文件；chmod/chown 改权限和归属。

高频组合命令（面试加分项）

  • 查最耗 CPU 的线程：
    top -H -p PID → 找到线程 TID → printf '%x\n' TID 转十六进制 → jstack PID | grep 十六进制 定位到具体代码。
  • 查 GC 情况：
    jstat -gcutil PID 1000 每秒看一次 GC 统计，如果老年代（O）一直涨不下降，可能是内存泄漏。
  • 导出线程/内存快照：
    jstack PID > thread.dump（分析死锁）、jmap -dump:format=b,file=heap.hprof PID（分析内存泄漏，配合 MAT）。
  • 统计接口耗时：
    grep '接口名' access.log | awk '{print $10}' | sort -n | tail -10 看最慢的10次请求耗时。

面试常问

  • CPU 100% 怎么排查？top 找 PID → top -H 找 TID → jstack 定位代码 → 看是否有死循环、频繁创建对象、正则回溯等。
  • 内存溢出（OOM）怎么排查？先看日志确认 OOM 类型（堆/元空间/直接内存）→ jmap 导出堆 dump → MAT 分析大对象引用链 → 定位泄漏代码。
  • 磁盘满了怎么排查？df -h 看哪个分区满了 → du -sh 逐层定位大目录 → 清理日志或扩容。

举例讲解

场景：

线上服务突然卡顿，用户反馈页面加载慢

  1. 看系统整体：
    top 发现 Java 进程 CPU 占用 98%，负载 15（8 核机器）。
  2. 定位线程：
    top -H -p PID 发现线程 12345 占 CPU 最高。
  3. 转十六进制：
    printf '%x\n' 12345 得到 0x3039。
  4. 堆栈定位：
    jstack PID | grep -A 20 3039 发现卡在 OrderService.calculatePrice() 的一个死循环里。
  5. 看 GC：
    jstat -gcutil PID 1000 发现 Full GC 每秒都在发生，因为死循环创建了大量临时对象。
  6. 修复：
    修复死循环代码，重启服务，问题解决。

OAuth 2.0 和 SSO 单点登录原理？
认证OAuth2

一句话概括

  • OAuth 2.0：
    是一种授权协议，解决的是"A 应用想访问 B 应用上用户的资源，但不想让 A 知道用户的密码"。
    典型场景：
    微信扫码登录第三方网站。
  • SSO（单点登录）：
    是一种登录体验，解决的是"用户登录一次，就能访问多个互相信任的系统，不需要重复输入密码"。
    典型场景：
    企业 OA、邮箱、HR 系统统一登录。

OAuth 2.0 四种授权模式

模式流程适用场景安全性
授权码模式第三方请求授权 → 用户同意 → 授权服务器返回授权码 → 第三方用授权码+客户端密钥换 AccessToken有后端的 Web 应用（最安全、最常用）高（Token 不经过用户浏览器）
隐式模式直接返回 Token（跳过授权码步骤）纯前端应用（如 SPA）低（Token 暴露在浏览器 URL 中）
密码模式用户直接把用户名密码给第三方，第三方去换 Token内部系统、第一方应用（如自家 APP 登录自家服务）中（只有极度信任的第三方才能用）
客户端凭证模式没有用户参与，客户端直接用 client_id + client_secret 换 Token服务器间调用（如微服务之间）中

OAuth 2.0 核心角色

  • 资源所有者（Resource Owner）：
    用户本人，数据的拥有者。
  • 客户端（Client）：
    第三方应用，想要访问用户数据的那个应用。
  • 授权服务器（Authorization Server）：
    负责验证用户身份、发放 Token（如微信授权服务器）。
  • 资源服务器（Resource Server）：
    存用户数据的服务器，用 Token 来校验是否允许访问（如微信用户信息服务）。

SSO 单点登录原理

核心思路是把登录状态交给一个独立的"认证中心"来管，其他系统不再各自维护登录态。

  1. 首次登录（A 系统）：
    用户访问 A 系统 → A 发现没登录 → 重定向到认证中心 → 用户输入用户名密码 → 认证中心验证通过 → 写 Cookie（认证中心域下）→ 发一个Ticket/Token给 A → A 用这个 Ticket 向认证中心确认 → A 建立本地 Session → 用户登录成功。
  2. 访问 B 系统：
    用户再访问 B 系统 → B 发现没登录 → 重定向到认证中心 → 认证中心发现已经有 Cookie（之前登录过）→ 直接发 Ticket 给 B → B 确认 → 用户免密登录 B。
  3. 关键：
    认证中心的 Cookie 是跨系统共享的基石，Ticket 是一次性凭证，防止被截获后重复使用。

OAuth 2.0 vs SSO 的区别

对比项OAuth 2.0SSO
核心目的授权——让第三方有限地访问用户资源登录——让用户只登录一次就能访问多个系统
典型场景微信扫码登录美团、GitHub 授权登录第三方应用企业 OA、邮箱、HR、财务系统统一登录
用户是否在场用户必须在场确认授权用户在场登录一次，之后系统自动处理
Token 含义授权凭证，表示"用户同意我访问他的数据"登录凭证，表示"这个用户已经认证过了"
常用协议OAuth 2.0 + OpenID ConnectCAS、SAML、OAuth 2.0（也可用于 SSO）

举例讲解

场景：

用微信扫码登录某外卖网站（OAuth 2.0 授权码模式）

  1. 你在外卖网站点"微信登录"，外卖网站把浏览器重定向到微信授权页面，带上自己的 client_id 和回调地址。
  2. 你扫码确认授权，微信服务器收到你的同意后，生成一个授权码，通过回调地址返回给外卖网站。
  3. 外卖网站拿到授权码后，在服务器后台用授权码 + client_secret 向微信换 AccessToken。
  4. 外卖网站用 AccessToken 调微信接口，获取你的头像、昵称（你授权的范围）。
  5. 你成功登录外卖网站，整个过程中外卖网站从未拿到你的微信密码。

场景：

登录公司内网后自动进入 OA、邮箱、HR 系统（SSO）

  1. 早上你打开公司门户，输入一次用户名密码。
  2. 认证中心验证通过，在你的浏览器里种下一个 Cookie（sso.company.com 域下）。
  3. 你点击"进入 OA"，OA 系统发现你没登录，把你带到认证中心。
  4. 认证中心看到你已经有 Cookie，直接给你发一个 Ticket，OA 验证 Ticket 后让你进。
  5. 你再点击"进入邮箱"，同样的流程，但你不用再输密码，认证中心直接放行。

Git 常用操作和常见问题？
Git工具

高频命令速查

场景常用命令一句话说明
初始化/克隆git init / clone新建仓库或从远程拉一份完整的代码到本地
日常开发add / commit / status / diff改完代码 → git add 加入暂存区 → git commit 提交到本地仓库
分支操作branch / checkout / switch / merge / rebase创建/切换分支，把分支代码合并到当前分支
远程协作push / pull / fetchpush 把本地提交推上去；pull = fetch + merge，拉最新代码并合并
临时保存stash代码写到一半要切分支，先 stash 存起来，之后 pop 恢复
挑拣提交cherry-pick把另一个分支上的某一次提交"复制"到当前分支
撤销回退revert / reset / checkoutrevert 安全回滚（新建提交）；reset 重置指针（会丢历史，慎用 --hard）

合并冲突处理

多人改了同一文件的同一处，Git 无法自动合并，会标出冲突。

处理流程：

  1. 定位冲突：
    git status 看哪些文件冲突了，文件里会有 <<<<<<< 标记。
  2. 手动解决：
    打开文件，找到冲突标记，保留想要的代码，删掉标记。
  3. 标记已解决：
    git add 文件名 告诉 Git 这个文件的冲突处理完了。
  4. 继续合并：
    如果是 merge 冲突 → git merge --continue；
    如果是 rebase 冲突 → git rebase --continue。

代码回滚对比

命令作用是否安全适用场景
git revert新建一个"反向提交"来撤销某次提交的改动安全，不删历史已推送到远程的提交，需要保留完整提交历史
git reset把 HEAD 指针移到指定提交，可选 --soft/--mixed/--hard--hard 会丢工作区改动，危险仅本地未推送的提交，想重写历史
git checkout切换到指定文件/提交的版本，不修改历史安全（未提交改动会丢失）想临时看旧版本，或恢复单个文件

merge vs rebase 怎么选

  • merge：
    把两个分支的终点连起来，形成一个新的合并提交。
    优点：
    保留完整历史，谁什么时候合的看得清清楚楚；
    缺点：
    历史图会有分叉，比较复杂。
  • rebase：
    把当前分支的提交"挪"到目标分支最新提交的后面，形成一条直线。
    优点：
    历史干净、线性，好看；
    缺点：
    会改写提交历史，如果已经 push 到远程，rebase 后别人拉代码会出问题。
  • 面试金句：
    "本地开发用 rebase 保持提交记录干净，合并到主分支时用 merge 保留完整历史。
    " 铁律：
    已经 push 到远程的提交，绝不用 rebase。

分支策略对比

策略分支结构适用场景特点
Git Flowmain + develop + feature + release + hotfix大型项目、版本发布周期明确分工明确，但分支多、流程重
GitHub Flowmain + feature 分支中小型项目、持续部署简单轻量，PR 合并后直接上线
Trunk-Based只有一个主分支（trunk）敏捷团队、高频发布极致简化，要求频繁提交 + 特性开关

举例讲解

场景：

你正在开发一个登录功能，突然线上报了一个紧急 Bug。

  1. 你正在 feature/login 分支写了一半，还没提交。
    先用 git stash 把改动存起来。
  2. 切回 main 分支：
    git checkout main，拉最新代码：
    git pull。
  3. 新建修复分支：
    git checkout -b hotfix/bug-123，改完 Bug 后 git add . && git commit -m "fix: 修复XXBug"。
  4. 推送到远程：
    git push origin hotfix/bug-123，提 PR 合并到 main。
  5. 切回 feature/login：
    git checkout feature/login，恢复之前的代码：
    git stash pop。
  6. feature/login 开发完了，先 git rebase main 把 main 最新代码接过来（本地保持线性），再提 PR merge 到 main。

💡 这个流程里用到了 stash、checkout、branch、commit、push、rebase、merge、PR，几乎覆盖了日常 Git 的核心操作。

DDD 领域驱动设计核心概念？
DDD架构

一句话概括

DDD（Domain-Driven Design，领域驱动设计）是一种以业务领域为核心来设计软件的方法论。

它的核心思想是：

先深入理解业务，把业务知识提炼成"领域模型"，再用模型来指导代码结构，让代码和业务保持同步。

为什么要用 DDD

  • 传统开发是数据库驱动：
    先建表，再写代码，业务逻辑散在 Service 层，时间一长就变成"面条代码"。
  • DDD 是领域驱动：
    先和业务专家一起梳理业务规则，把核心业务逻辑封装到"领域对象"里，代码结构天然反映业务结构。
  • 特别适合复杂业务系统（如电商、金融、物流），业务规则多、变化快，需要代码能跟上业务节奏。

七大核心概念速查

概念一句话说明类比
实体（Entity）有唯一标识（ID），属性可变，同一 ID 始终代表同一个对象像你的身份证，换发型改名了，身份证号不变
值对象（Value Object）没有唯一标识，属性相同就是同一个对象，通常不可变像地址"北京市朝阳区"，内容一样就是同一个地址
聚合（Aggregate）一组相关对象的逻辑整体，对外只有一个入口（聚合根）像一台电脑，CPU/内存/硬盘是零件，但你只买"整台电脑"
聚合根（Aggregate Root）聚合的对外代表，外部只能通过它操作聚合内部对象像电脑的"电源键"，你按电源键开机，不需要直接拨弄主板
仓储（Repository）领域对象的持久化接口，让领域层不用关心"怎么存数据库"像仓库管理员，你告诉他"我要取 5 号订单"，他去库里拿给你
领域服务（Domain Service）不适合放在单个实体/值对象里的跨对象业务逻辑像"转账"涉及两个账户，不能归给 A 账户或 B 账户，单独一个"转账服务"处理
领域事件（Domain Event）领域内发生的有意义的事情，用于解耦不同模块像"订单已支付"事件，库存模块、物流模块各自订阅处理
限界上下文（Bounded Context）领域模型的边界，同一个名词在不同上下文里含义不同像"用户"在"会员系统"是顾客，在"CRM"是线索，在"权限系统"是账号

分层架构

DDD 通常配合四层架构使用：

  • 用户接口层（UI/API）：
    接收请求、参数校验、返回结果。
  • 应用层（Application）：
    编排业务流程，如"下单"需要调用订单聚合、库存聚合、支付聚合，但不写业务规则。
  • 领域层（Domain）：
    核心业务逻辑所在地，包含实体、值对象、聚合、领域服务、领域事件。
    最核心、最稳定。
  • 基础设施层（Infrastructure）：
    数据库、缓存、消息队列、第三方接口等具体实现。

💡 依赖方向：

领域层不依赖其他任何层，其他层都依赖领域层。

这样业务逻辑最纯粹，不受技术框架变化影响。

DDD 与微服务的关系

  • DDD 的限界上下文是微服务拆分的最佳依据——一个限界上下文对应一个微服务。
  • 同一个名词在不同上下文中含义不同，拆分后就避免了"一个大而全的用户表"的尴尬。
  • DDD 给出拆分的业务理由，微服务给出拆分的落地方式，两者结合天衣无缝。

举例讲解

场景：

电商系统中的"订单"

  • 实体：
    订单（Order）有唯一订单号，状态可以从"待付款"变成"已发货"。
  • 值对象：
    收货地址（Address）由省市区和详细地址组成，只要内容一样就是同一个地址，没有 ID。
  • 聚合/聚合根：
    订单是一个聚合，包含订单项（OrderItem）、收货地址、支付信息。
    外部只能通过"订单"这个聚合根来操作，不能直接改订单项。
  • 领域服务：
    "计算订单总价"不能放在单个订单项里（需要遍历所有项），放在 OrderDomainService 里。
  • 领域事件：
    订单支付成功后发出"OrderPaidEvent"，库存模块扣库存、物流模块创建发货单、营销模块发优惠券，各自订阅处理，互不影响。
  • 限界上下文：
    "订单"在"订单上下文"里是交易单据，在"物流上下文"里是"待发货任务"，在"财务上下文"里是"应收凭证"——同一个"订单"，三个系统各管各的。

Maven 依赖传递和冲突解决？
Maven构建

什么是依赖传递

你在 pom.xml 里声明了依赖 A，而 A 内部又依赖了 B 和 C，Maven 会自动把 B 和 C 也引入到你的项目里，这就是依赖传递。

好处是省事，坏处是可能带来版本冲突。

scope 对传递的影响

scope是否传递说明
compile是默认 scope，会传递，A 依赖 B，你的项目也会拿到 B
provided否运行时容器提供（如 servlet-api），不传递
runtime是编译不需要，运行需要（如 JDBC 驱动），会传递
test否只在测试代码里用，不会传递到主代码
system否本地 jar，不推荐使用

依赖冲突是怎么发生的

假设你的项目引入了 A 和 B，A 依赖 C-1.0，B 依赖 C-2.0。

Maven 最终只能选一个版本的 C 放在 classpath 里，这时候就产生了依赖冲突。

冲突解决的两大原则

  • 最短路径优先：
    哪个版本的依赖路径更短，就用哪个。

    例：
    你的项目 → A → C(1.0)（路径长度2）；
    你的项目 → B → D → C(2.0)（路径长度3）。
    选 C-1.0。
  • 第一声明优先：
    如果路径长度相同，pom.xml 里先声明的那个依赖所带的版本优先。

    例：
    先声明 A（带 C-1.0），后声明 B（带 C-2.0），且路径长度都是2。
    选 C-1.0。

面试常问的解决手段

手段用法适用场景
手动排除<exclusions><exclusion>...某个传递依赖根本用不到，或已知会引发冲突
dependencyManagement在父 POM 中统一声明版本号多模块项目统一管理依赖版本，子模块只写 groupId 和 artifactId
直接声明在自己的 pom 中直接引入想要的版本明确知道自己需要哪个版本，覆盖传递过来的版本
mvn dependency:tree命令行查看依赖树排查冲突时定位"到底是谁带进来的这个版本"

举例讲解

场景：

Spring Boot 项目里 Jackson 版本冲突

  1. 你的项目依赖 spring-boot-starter-web，它传递了 jackson-databind-2.15.0。
  2. 你又引入了一个第三方 SDK，它传递了 jackson-databind-2.10.0。
  3. 两个版本冲突了！运行时报 NoSuchMethodError 或序列化异常。
  4. 排查：
    运行 mvn dependency:tree | findstr jackson，发现两个版本的存在。
  5. 解决：
    在父 POM 的 <dependencyManagement> 里统一指定 jackson-databind-2.15.0，或者在自己的 pom 里直接引入 jackson-databind-2.15.0 覆盖旧版本。

💡 面试金句：

"遇到依赖冲突，先用 mvn dependency:tree 定位是谁带进来的，然后用 dependencyManagement 统一版本或手动排除。

"
