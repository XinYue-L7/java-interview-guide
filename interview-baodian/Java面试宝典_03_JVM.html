JVM 内存区域是如何划分的？
内存模型高频

线程私有：

  • 程序计数器：
    记录当前线程执行字节码的行号，唯一无OOM的区域。
  • 虚拟机栈：
    存储栈帧(局部变量表、操作数栈等)，方法调用入栈/返回出栈。
    StackOverflowError / OOM。
  • 本地方法栈：
    为Native方法服务，HotSpot中与虚拟机栈合二为一。

线程共享：

  • 堆：
    存放对象实例，GC主要区域。
    OOM。
  • 方法区/元空间(JDK8+)：
    存储类信息、常量、静态变量。
    OOM。
  • 运行时常量池：
    方法区的一部分，存放编译期生成的字面量和符号引用。

💡 JDK8用元空间(Metaspace)替代永久代(PermGen)，使用本地内存，不再有-XX:MaxPermSize。

堆内存的结构是怎样的？
堆分代

分代模型（JDK8）：

  • 新生代(Young Gen)：
    1/3堆空间
    • Eden区(8/10) + Survivor0(1/10) + Survivor1(1/10)
    • 对象先在Eden分配，Minor GC后存活→S0→S1，每GC一次年龄+1
  • 老年代(Old Gen)：
    2/3堆空间，年龄达到15(可配置)或大对象直接进入

💡 字符串常量池在JDK7后移到堆中。

如何判断对象是否已死？（GC Roots）
GC高频

一句话概括：

JVM 通过可达性分析算法，从 GC Roots 出发遍历引用链，不可达的对象判定为可回收；

引用计数法因无法解决循环引用，Java 未采用。

两种判定算法对比：

  • 引用计数法：
    每个对象维护引用计数器，引用+1、失效-1，为零时回收。
    缺点：
    无法处理循环引用（A 引用 B，B 引用 A，但两者均不被外部引用），Java 未采用。
  • 可达性分析（JVM 采用）：
    从一组称为 GC Roots 的对象出发，沿引用链向下搜索，不可达的对象标记为可回收。

GC Roots 包括：

  • 虚拟机栈中局部变量表引用的对象（正在执行的方法参数、局部变量）。
  • 方法区中静态属性引用的对象。
  • 方法区中常量引用的对象。
  • 本地方法栈中 JNI（Native 方法）引用的对象。
  • JVM 内部的引用（如基本数据类型对应的 Class 对象、系统类加载器、异常对象）。
  • 所有被 synchronized 持有的对象。
  • 反映 Java 虚拟机内部情况的 JMXBean、JVMTI 中注册的回调、本地代码缓存等。

两次标记过程：

  1. 第一次标记：
    可达性分析发现对象不可达，标记并放入队列。
  2. 筛选：
    检查是否覆盖 finalize() 且未执行过；
    若有则放入 F-Queue 等待执行。
  3. 第二次标记：
    finalize() 执行后若对象仍无引用链关联，则最终判定为死亡，等待回收。

💡 面试点：

记住可达性分析的根节点集合，尤其是栈帧局部变量 + 静态属性 + 常量 + JNI + synchronized 持有对象这五类最常见。

强引用、软引用、弱引用、虚引用的区别？
引用GC

一句话概括：

四种引用强度依次递减：

强引用 > 软引用 > 弱引用 > 虚引用，GC 对待它们的回收策略不同，适用于不同场景。

定义：

  • 强引用 StrongReference：
    最常见的引用，如 Object o = new Object()。
    只要强引用存在，对象就永远不会被 GC 回收。
    即使内存不足，JVM 宁愿抛出 OOM 也不会回收强引用对象。
  • 软引用 SoftReference：
    通过 SoftReference<T> 包装对象。
    内存充足时不回收；
    当 JVM 即将 OOM 时，会优先回收软引用对象以释放内存。
    适合实现内存敏感的缓存。
  • 弱引用 WeakReference：
    通过 WeakReference<T> 包装对象。
    无论内存是否充足，下次 GC 时必定回收。
    弱引用对象只能存活到下一次垃圾回收之前。
  • 虚引用 PhantomReference：
    通过 PhantomReference<T> 包装对象，必须配合 ReferenceQueue 使用。
    虚引用本身不影响对象生命周期，对象随时可能被回收；
    get() 始终返回 null，唯一作用是在对象被回收时收到通知，用于跟踪对象回收或清理堆外内存等资源。
类型回收时机获取对象典型场景
强引用 StrongReference永不回收，除非引用置 null直接获取普通对象 Object o = new Object()
软引用 SoftReference内存不足时（即将 OOM 前）回收get() 可能返回 null内存敏感型缓存、图片缓存
弱引用 WeakReference下次 GC 时必定回收get() 可能返回 nullWeakHashMap、ThreadLocal
虚引用 PhantomReference随时可能被回收，不影响生命周期get() 始终返回 null对象回收跟踪、堆外内存清理（配合 ReferenceQueue）

ReferenceQueue 配合：

软/弱/虚引用都可以关联一个 ReferenceQueue，当引用对象被回收时，JVM 会把引用本身放入队列，用于监听对象回收事件或清理资源。

ThreadLocal 经典问题：

ThreadLocal 的 Key 是弱引用（ThreadLocal 对象），而 Value 是强引用。

如果 ThreadLocal 外部强引用被置 null，Key 会在下次 GC 被回收，但 Value 仍被线程的 ThreadLocalMap 强引用，导致内存泄漏。

使用完必须调用 remove()。

💡 面试点：

四类引用的回收时机排序是必考点；

ThreadLocal 内存泄漏的根因是 Key 弱引用 + Value 强引用 + 未 remove()。

垃圾回收算法有哪些？
GC算法高频
  • 标记-清除(Mark-Sweep)：
    标记存活→清除未标记。
    简单但产生碎片。
  • 标记-复制(Mark-Copy)：
    标记存活→复制到新空间→清理原空间。
    无碎片但浪费一半内存。
    新生代使用。
  • 标记-整理(Mark-Compact)：
    标记存活→移动到一端→清理边界外。
    无碎片但耗时。
    老年代使用。
  • 分代收集：
    新生代用复制，老年代用标记-清除/整理。

Minor GC、Major GC、Full GC 的区别？
GC基础
  • Minor GC(Young GC)：
    仅回收新生代，频繁，速度快(复制算法)。
  • Major GC：
    回收老年代，通常伴随Minor GC，比Minor GC慢10倍+。
    CMS中特指老年代GC。
  • Full GC：
    回收整个堆+方法区，最慢，STW最长。
    应尽量避免。

Full GC触发条件：

老年代满、元空间满、System.gc()、大对象分配失败。

    栈→句柄池(两个指针：

什么情况下会出现 StackOverflowError？
异常栈
  • 无限递归：
    方法不断调用自身，栈帧不断入栈超过栈深度。
  • 大量局部变量：
    每个栈帧中的局部变量表太大。

解决方法：

  • 检查递归终止条件
  • 增大栈大小：
    -Xss参数
  • 改用迭代

💡 与OOM的区别：

StackOverflow是栈深度超限，OOM是堆/元空间内存不足。

CMS 收集器的流程和优缺点？
CMSGC

CMS（Concurrent Mark Sweep）是老年代并发收集器，目标：

最短停顿时间。

流程4步：

  1. 初始标记(STW)：
    标记GC Roots直接关联对象，快。
  2. 并发标记：
    GC Roots Tracing，耗时长但并发。
  3. 重新标记(STW)：
    修正并发标记变化，比初始标记长。
  4. 并发清除：
    清理垃圾，并发。

缺点：

产生浮动垃圾（并发标记中产生的新垃圾）、标记-清除算法有碎片、对CPU敏感、预留空间不足时退化为Serial Old。

G1 收集器的核心特点和原理？
G1高频

G1（Garbage First）是JDK9+默认收集器，面向服务端大堆内存。

设计思想：

将堆分为2048个Region，各Region可动态扮演Eden、Survivor、Old、Humongous。

混合回收(Mixed GC)：

不光回收新生代，还回收部分老年代Region（垃圾最多的Region优先→Garbage First）。

核心特点：

  • 可预测停顿：
    通过-XX:MaxGCPauseMillis设置目标。
  • 标记-整理+复制算法，无内存碎片。
  • Remembered Set解决跨Region引用。
  • SATB(Snapshot-At-The-Beginning)解决并发标记问题。

ZGC 和 Shenandoah 的特点？
ZGC低延迟

ZGC：

JDK11引入，JDK15生产可用。

目标：

亚毫秒级停顿，支持TB级堆。

  • 基于染色指针（Colored Pointers）和读屏障。
  • 并发标记、并发整理（Compacting时短暂停顿）。
  • 停顿时间< 1ms，且不随堆大小增加。

Shenandoah：

JDK12引入，类似G1但并发整理（移动对象与用户线程并发）。

  • 用Brooks Pointer转发指针实现并发整理。
  • 回收阶段几乎全并发。

类加载器的双亲委派模型是什么？为什么破坏它？
类加载高频

三层类加载器：

  • Bootstrap ClassLoader（C++，加载rt.jar）Extension ClassLoader（加载ext）Application ClassLoader（加载classpath）。

双亲委派流程：

加载→先委托父加载器→父找不到才自己加载。

保证核心类安全（如自定义String不会覆盖核心String）。

破坏场景：

  • JDBC：
    Bootstrap加载的类需调用SPI实现类（Application加载），通过线程上下文类加载器绕开。
  • Tomcat：
    WebApp类加载器优先加载应用自己的类，打破委派。
  • OSGi：
    网状类加载器结构。

Tomcat 为什么要打破双亲委派？
类加载Tomcat

Tomcat的WebappClassLoader优先加载应用自己的类，原因：

  1. 隔离性：
    不同Web应用各自类加载器，同名类互不干扰。
  2. 灵活性：
    应用可加载自己的Spring版本覆盖Tomcat提供的。
  3. 热部署：
    单独卸载某个WebappClassLoader即可重载应用。

加载顺序：

先查本地缓存→避免JVM核心类→先自己加载→自己找不到才委托父加载器。

对象分配内存的过程是怎样的？
内存分配高频

优先TLAB（线程本地分配缓冲区）：

  1. 先在栈上分配（逃逸分析+标量替换），分配在栈上。
  2. 栈上不行→尝试TLAB（Eden区的线程私有区域），CAS分配。
  3. TLAB不够→Eden区CAS分配。
  4. Eden不够→触发Minor GC。
  5. 大对象（如长数组）→直接进老年代。
  6. 年龄够了→晋升老年代。

栈上分配条件：

逃逸分析判定对象不会逃出方法+可以被标量替换。

-XX:+DoEscapeAnalysis默认开启。

对象晋升老年代的几种情况？
GC晋升
  1. 年龄达标：
    默认15岁（-XX:MaxTenuringThreshold）。
  2. 动态年龄判断：
    Survivor区中同龄对象总大小 > Survivor空间的50%→直接晋升。
  3. 大对象：
    超过-XX:PretenureSizeThreshold直接进老年代。
  4. 空间担保：
    Minor GC时Survivor放不下→通过空间分配担保进老年代。

OOM 有哪些类型？如何排查？
OOM高频

常见OOM类型：

  • Java heap space：
    堆溢出，大对象或内存泄漏。
  • GC overhead limit exceeded：
    GC时间超过98%但只回收<2%堆。
  • Metaspace：
    加载过多类或类加载器泄漏。
  • Direct buffer memory：
    堆外内存溢出(NIO)。
  • unable to create new native thread：
    线程数达到上限。

排查步骤：

  1. 留现场：
    -XX:+HeapDumpOnOutOfMemoryError
  2. 分析dump：
    MAT/JProfiler查看大对象和GC Root链。
  3. 查日志：
    GC日志分析频率和效果。
  4. 监控：
    jstat查看各区域使用情况。

full GC 频繁如何排查和优化？
调优高频

排查方向：

  1. 内存泄漏：
    jmap dump后MAT分析大对象引用链。
  2. 堆太小：
    增大-Xmx。
  3. 晋升过快：
    增大新生代(Xmn)或调整晋升阈值。
  4. System.gc()：
    使用-XX:+DisableExplicitGC禁用手动GC。
  5. 元空间不足：
    增大-XX:MaxMetaspaceSize。
  6. 大对象多：
    调整PretenureSizeThreshold。

优化手段：

扩大堆内存、换G1收集器、调整Region大小、减少对象创建。

类的生命周期（加载过程）是怎样的？
类加载高频

类从加载到卸载共7个阶段：

  1. 加载：
    通过全限定名获取二进制字节流→方法区生成Class对象。
  2. 验证：
    文件格式、元数据、字节码、符号引用验证。
  3. 准备：
    为static变量分配内存并赋零值（final static赋实际值）。
  4. 解析：
    符号引用→直接引用（可延迟到初始化后）。
  5. 初始化：
    执行类构造器<clinit>()（static块+static变量赋值）。
  6. 使用。

什么是直接内存？和堆内存有什么区别？
直接内存NIO

一句话概括：

直接内存（Direct Memory）是堆外内存，不属于 JVM 运行时数据区，通过 ByteBuffer.allocateDirect() 或 Unsafe.allocateMemory() 分配，主要用于 NIO 零拷贝场景。

什么是堆内存？

  • 堆内存（Java Heap）是 JVM 运行时数据区中最大的一块内存，由 JVM 启动时创建，所有线程共享。
  • 作用：
    存放对象实例与数组（new 出来的对象都分配在堆上），是 GC（垃圾回收）的主要区域。
  • 结构划分：
    新生代（Eden + 两个 Survivor）与老年代；
    大小通过 -Xms（初始）与 -Xmx（最大）控制。
  • 特点：
    由 GC 自动管理，分配快（TLAB），但对象跨 JVM 与 OS 传输时需要从堆拷贝到 Native 缓冲区。

什么是直接内存？

  • 直接内存（Direct Memory）是 JVM 进程向操作系统直接申请的本地内存（Native Memory），位于 JVM 堆之外，不属于运行时数据区。
  • 作用：
    主要用于 NIO 的缓冲区（Buffer），数据可以直接读写，避免在 Java 堆与 Native 内存之间来回拷贝（零拷贝）。
  • 分配方式：
    ByteBuffer.allocateDirect()（推荐）或 Unsafe.allocateMemory()（底层）。
  • 大小限制：
    不受 -Xmx 控制，但受物理内存和 -XX:MaxDirectMemorySize 参数限制（默认约等于 -Xmx）。

与堆内存的区别：

对比项直接内存（堆外）堆内存
归属操作系统 Native 内存JVM 运行时数据区
分配方式ByteBuffer.allocateDirect()new Object()
GC 管理不直接管理，需手动释放或 Cleaner自动 GC 回收
内存拷贝零拷贝，可直接写入通道需从堆拷贝到 Native 缓冲区
分配/回收成本高（系统调用 malloc/free）低（TLAB 快速分配）
大小限制受物理内存 + MaxDirectMemorySize受 -Xmx 限制
典型场景NIO 网络/文件 IO、Netty ByteBuf普通对象存储

特点：

  • 零拷贝性能高：
    直接内存的地址可被操作系统直接访问，NIO 读写时无需在 Java 堆和 Native 堆之间来回拷贝数据，大幅提升 IO 性能。
  • 不受堆大小限制：
    适合分配大缓冲区（如 1GB 以上的网络包），不受 -Xmx 约束。
  • 分配回收成本高：
    每次分配需系统调用，回收依赖 Cleaner 或手动 free，不能像堆对象一样被 GC 自动管理。
  • 可能 OOM：
    直接内存耗尽时抛出 OutOfMemoryError: Direct buffer memory。

原理（分配与回收）：

  1. 分配：
    ByteBuffer.allocateDirect(size) → 在堆中创建一个 DirectByteBuffer 对象（很小）→ 通过 Unsafe.allocateMemory() 向 OS 申请 Native 内存 → 返回指向 Native 内存的地址。
  2. 回收机制：
    DirectByteBuffer 内部持有 Cleaner（继承自 PhantomReference），当堆中的 DirectByteBuffer 对象被 GC 回收时，Cleaner 的 clean() 方法被触发，调用 Unsafe.freeMemory() 释放 Native 内存。
    注意：
    如果 DirectByteBuffer 对象一直存活（如被强引用持有），Native 内存不会释放，可能导致物理内存泄漏。
  3. 显式释放：
    Netty 等框架使用 ((DirectBuffer) buf).cleaner().clean() 主动释放，避免等待 GC。

💡 面试点：

直接内存的零拷贝优势是 NIO 高性能的核心；

Cleaner + PhantomReference 是其回收的关键机制；

生产环境务必设置 -XX:MaxDirectMemorySize 防止耗尽物理内存。

Class 文件（.class 文件）的结构是怎样的？
字节码类文件

一句话概括：
Class 文件是 JVM 执行的标准格式文件，
以魔数开头、按固定顺序排列各种表结构，
存放常量池、访问标志、类/父类/接口索引、字段表、方法表和属性表，
让任何语言编译后的字节码都能在 JVM 上跨平台运行。

一、什么是 Class 文件（定义、作用、原理）：

  • 定义：
    Class 文件是一组以 8 位字节为基础单位的二进制流，
    各个数据项目严格按照顺序紧凑地排列在文件中，
    中间没有任何分隔符。
  • 作用：
    作为 JVM 的执行输入，Java、Groovy、Kotlin、Scala 等
    编译后都生成 Class 文件，JVM 只认 Class 文件格式，
    这是 Java 实现跨平台（一次编写处处运行）的关键。
  • 原理：
    Class 文件采用类似 C 语言结构体的伪结构存储，
    有两种数据类型：无符号数和表；
    无符号数描述数字、索引引用、数量值、字符串值；
    表由多个无符号数或其他表构成。

二、ClassFile 结构总览：

ClassFile {
    u4             magic;                 // 魔数
    u2             minor_version;         // 次版本号
    u2             major_version;         // 主版本号
    u2             constant_pool_count;   // 常量池计数器
    cp_info        constant_pool[];       // 常量池
    u2             access_flags;          // 访问标志
    u2             this_class;            // 类索引
    u2             super_class;           // 父类索引
    u2             interfaces_count;      // 接口计数器
    u2             interfaces[];          // 接口索引集合
    u2             fields_count;          // 字段表计数器
    field_info     fields[];              // 字段表
    u2             methods_count;         // 方法表计数器
    method_info    methods[];             // 方法表
    u2             attributes_count;      // 属性表计数器
    attribute_info attributes[];          // 属性表
}

三、核心组件详解：

  • 魔数（magic）：
    每个 Class 文件的头 4 个字节称为魔数，值为 0xCAFEBABE，
    唯一作用是确定这个文件是否为一个能被虚拟机接受的 Class 文件。
  • 版本号：
    第 5、6 字节是次版本号，第 7、8 字节是主版本号；
    高版本 JVM 能向下兼容运行低版本 Class 文件，反之不行。
  • 常量池（constant_pool）：
    是 Class 文件中的资源仓库，
    存放两大类常量：字面量（Literal）和符号引用（Symbolic References）；
    计数器从 1 开始，0 表示不引用任何常量池项。
    详见下一题。
  • 访问标志（access_flags）：
    2 字节，用于识别一些类或接口层次的访问信息，
    如这个 Class 是类还是接口、是否为 public、是否 abstract、是否 final 等。
  • 类索引、父类索引、接口索引集合：
    类索引（this_class）和父类索引（super_class）是一个 u2 类型数据，
    指向常量池中的 CONSTANT_Class_info 常量，
    分别确定这个类或接口的全限定名和父类；
    接口索引集合描述实现了哪些接口，按 implements 顺序排列。
  • 字段表集合（field_info）：
    描述类或接口中声明的变量（不含方法内部局部变量），
    包括 access_flags、name_index（简单名称）、descriptor_index（描述符）、attributes（额外信息）。
  • 方法表集合（method_info）：
    描述类或接口中声明的方法，结构几乎和字段表一样，
    由访问标志、名称索引、描述符索引、属性表集合构成；
    方法里的代码保存在属性表的 Code 属性中。
  • 属性表集合（attribute_info）：
    在 Class 文件、字段表、方法表都可以携带属性表集合，
    用于描述某些场景的专有信息，如 Code、LineNumberTable、Exceptions 等。

四、前置概念（名词解释）：

  • 字节码：
    JVM 能直接执行的一串指令，编译后的 .class 文件即字节码文件。
  • 全限定名：
    把类名中的"."替换为"/"的名称，如 java/lang/Object。
  • 描述符：
    描述字段数据类型和方法参数、返回值的字符串，
    如 Ljava/lang/String;、()V 表示无参 void 方法。
  • 魔数：
    文件开头用于标识文件类型的固定字节，
    Java 的 Class 文件魔数为 0xCAFEBABE。

Class 文件中的常量池是什么？存放了哪些内容？
字节码常量池

一句话概括：
常量池是 Class 文件中的"资源仓库"，
存放字面量和符号引用两大类常量，共 14 种常量类型，
供类索引、字段表、方法表等各处通过索引引用。

一、什么是常量池（定义、作用）：

  • 定义：
    常量池（constant_pool）位于 Class 文件的魔数和版本号之后，
    是 Class 文件中与其他项目关联最多的数据。
  • 作用：
    存放编译期生成的各种字面量和符号引用，
    Class 文件中几乎所有结构都会引用到常量池中的常量，
    是连接代码与数据的重要桥梁。

二、常量池存放的两大类常量：

  • 字面量（Literal）：
    如文本字符串、被声明为 final 的常量值等，
    如 "hello"、100 这样的具体值。
  • 符号引用（Symbolic References）：
    编译阶段不保存目标内存地址，只保存符号引用，
    包括以下三类：
    类或接口的全限定名；
    字段的名称和描述符；
    方法的名称和描述符。

三、为什么需要符号引用：
Class 文件在编译期不保存各个方法、字段的最终内存布局信息，
因为 JVM 内存布局要到类加载阶段才确定，
因此编译期只能以符号引用来替代，
在类加载的解析阶段再转换为直接引用（真实内存地址）。

四、常量池的 14 种常量类型：

类型                                    标志  含义
CONSTANT_Utf8_info                       1     UTF-8编码字符串
CONSTANT_Integer_info                    3     整型字面量
CONSTANT_Float_info                      4     浮点型字面量
CONSTANT_Long_info                       5     长整型字面量
CONSTANT_Double_info                     6     双精度字面量
CONSTANT_Class_info                      7     类或接口的符号引用
CONSTANT_String_info                     8     字符串类型字面量
CONSTANT_Fieldref_info                   9     字段符号引用
CONSTANT_Methodref_info                  10    类中方法符号引用
CONSTANT_InterfaceMethodref_info         11    接口中方法符号引用
CONSTANT_NameAndType_info                12    字段或方法的部分符号引用
CONSTANT_MethodType_info                 16    方法类型
CONSTANT_MethodHandle_info               15    方法句柄
CONSTANT_InvokeDynamic_info              18    动态方法调用点

五、如何查看常量池：

javap -v 类名   # 查看常量池、字段、方法等详细信息
javap -c 类名   # 查看字节码指令

六、前置概念（名词解释）：

  • 字面量：
    源代码中的常量值，如字符串、数字，编译后进入常量池。
  • 符号引用：
    以一组符号描述引用目标，不含真实内存地址，
    解析阶段才转换为直接引用。
  • 直接引用：
    指向目标的内存地址或方法表偏移量。
  • javap：
    JDK 自带的字节码反汇编工具，可查看 Class 文件结构。

类加载过程中加载、验证、准备、解析阶段分别做了什么？
类加载原理

一句话概括：
类加载的四个连接阶段各有分工：
加载负责"读入字节流生成 Class 对象"，
验证负责"检查字节码合法性"，
准备负责"给静态变量分配内存赋零值"，
解析负责"把符号引用换成直接引用"。

一、加载（Loading）：

  • 三件事：
    1、通过一个类的全限定名获取定义此类的二进制字节流；
    2、将这个字节流所代表的静态存储结构转化为方法区的运行时数据结构；
    3、在内存中生成一个代表这个类的 java.lang.Class 对象，
    作为方法区这个类的各种数据的访问入口。
  • 加载的来源：
    二进制字节流可以从 ZIP 包（JAR）、网络、运行时计算生成（动态代理）、
    其他文件生成（JSP）、数据库读取等多种途径获取。
  • 可控性最强：
    加载阶段是开发阶段可控性最强的阶段，
    因为既可以使用系统提供的类加载器完成加载，
    也可以使用自定义的类加载器来控制字节流的获取方式。
  • 数组的特殊性：
    对于非数组类，通过类加载器加载并明确创建过程；
    对于数组类，数组类本身不通过类加载器创建，
    而是由 JVM 直接在内存中动态构造。
  • 与连接交叉进行：
    加载阶段尚未完成，连接阶段可能已经开始，
    这两个阶段的开始时间有先后，但交叉进行，
    加载完成后，验证、准备、解析等阶段才能开始。

二、验证（Verification）：
确保 Class 文件的字节流中包含的信息符合 JVM 规范要求，
如果验证失败，JVM 会抛出 VerifyError。
分为 4 个校验动作：

  • 文件格式验证：
    验证字节流是否符合 Class 文件格式规范，
    如是否以 0xCAFEBABE 开头、版本号是否受支持等。
  • 元数据验证：
    对字节码描述的信息进行语义分析，
    如类是否有父类、是否继承了被 final 修饰的类等。
  • 字节码验证：
    对类的方法体进行校验分析，
    确保方法在运行时不会做出危害 JVM 安全的行为，
    是整个验证过程中最复杂的部分。
  • 符号引用验证：
    对常量池中的各种符号引用进行匹配性校验，
    如通过字符串描述的全限定名能否找到对应的类。

三、准备（Preparation）：
正式为类变量（static 修饰的变量）分配内存并设置类变量初始值（零值）。

  • 分配位置：
    这些变量所使用的内存都将在方法区中进行分配（JDK7 前），
    JDK8 中静态变量和字符串常量池移至堆中。
  • 零值：
    如 int 为 0、boolean 为 false、引用类型为 null，
    例如 static int value = 123，
    准备阶段后 value 的值为 0 而不是 123。
  • 例外情况：
    如果类字段的字段属性表中存在 ConstantValue 属性（即被 static final 修饰），
    那么在准备阶段 value 就会被初始化为 ConstantValue 指定的值，
    如 static final int value = 123，准备阶段 value 直接为 123。

四、解析（Resolution）：

  • 定义：
    把常量池内的符号引用替换为直接引用的过程。
  • 直接引用：
    直接指向目标的指针、相对偏移量或一个能间接定位到目标的句柄，
    如方法表中的偏移量就是直接引用。
  • 解析的对象：
    针对类或接口、字段、类方法、接口方法、方法类型、方法句柄、调用点限定符
    共 7 类符号引用进行。

五、前置概念（名词解释）：

  • 全限定名：
    类的完整名称，如 java/lang/String，
    加载时据此获取二进制字节流。
  • 类变量：
    被 static 修饰的变量，属于类而不属于某个实例。
  • ConstantValue 属性：
    被 final 修饰的静态变量的属性，
    使准备阶段直接赋指定值。
  • 符号引用 / 直接引用：
    编译期的符号描述 vs 解析后的真实内存地址。

方法区、永久代、元空间有什么区别？为什么用元空间替换永久代？
内存区域方法区

一句话概括：
方法区是 JVM 规范定义的"逻辑区域"，
永久代和元空间是它的两种实现：
JDK8 之前用永久代实现（在堆内）、JDK8 之后用元空间实现（在本地内存），
元空间不再受 JVM 内存上限约束，彻底解决了永久代的 OOM 问题。

一、方法区（定义、作用）：

  • 定义：
    方法区（Method Area）是 JVM 规范中定义的一块逻辑内存区域，
    与堆一样是各个线程共享的内存区域。
  • 作用：
    存储已被虚拟机加载的类型信息、常量、静态变量、
    即时编译器编译后的代码缓存等数据。
  • 注意：
    方法区只是 JVM 规范中的概念，不同 JVM 可以有不同的实现，
    HotSpot 虚拟机用永久代（JDK8 前）和元空间（JDK8 起）来实现方法区。

二、永久代与元空间（区别）：

  • 永久代（PermGen）：
    JDK8 之前 HotSpot 对方法区的实现，
    位于 JVM 堆内，受 -XX:MaxPermSize 限制。
  • 元空间（Metaspace）：
    JDK8 之后对方法区的实现，
    位于本地内存（直接内存），默认不受上限限制，
    只受操作系统可用内存限制，可通过 -XX:MaxMetaspaceSize 设置上限。
  • JDK7 到 JDK8 的迁移：
    JDK7 已把字符串常量池、静态变量从永久代移到堆中，
    JDK8 彻底移除永久代，把类元数据移到元空间。

三、为什么用元空间替换永久代（3 个原因）：

  • 1、字符串存在大量重复、永久代容易 OOM：
    永久代空间有限，大量字符串（JDK7 前）和动态生成的类
    容易导致 java.lang.OutOfMemoryError: PermGen space；
    移入元空间后由操作系统管理，极大降低了 OOM 概率。
  • 2、类及方法元数据大小难以预估：
    动态代理、大量反射、热部署会生成大量类，
    永久代固定上限很难定得合理，
    元空间直接使用本地内存，类元数据不再受 JVM 内存上限约束。
  • 3、为合并 JRockit 铺路：
    Oracle 收购 BEA 后要将 HotSpot 与 JRockit 融合，
    而 JRockit 没有永久代的概念，
    移除永久代便于两个 JVM 整合。

四、相关参数对比：

  • 永久代：
    -XX:PermSize（初始大小）、-XX:MaxPermSize（最大大小）。
  • 元空间：
    -XX:MetaspaceSize（初始大小）、-XX:MaxMetaspaceSize（最大大小，默认无限）。

五、前置概念（名词解释）：

  • 方法区：
    JVM 规范中的逻辑区域，存类元数据、常量、静态变量。
  • 永久代：
    方法区在 JDK8 前的 HotSpot 实现，位于堆内，上限受限。
  • 元空间：
    方法区在 JDK8 后的实现，位于本地内存，
    默认无上限、不易 OOM。
  • 本地内存：
    不归 JVM 堆管理的内存，
    由操作系统分配，又称直接内存。

对象在内存中的布局是怎样的？
对象内存布局

一句话概括：
HotSpot 中对象在堆内存中由三部分组成：
对象头（Mark Word + 类型指针）、实例数据和对齐填充，
其中对象头记录哈希码、GC 分代年龄、锁状态等关键运行时信息。

一、对象头（Object Header）：
对象头是对象最重要的部分，又分为两块：

  • Mark Word（运行时数据）：
    用于存储对象自身的运行时数据，如哈希码（HashCode）、
    GC 分代年龄、锁状态标志、线程持有的锁、偏向线程 ID 等，
    这部分数据长度在 32 位和 64 位的 JVM 中分别占 32bit 和 64bit，
    官方称它为"Mark Word"。
  • 类型指针（Klass Pointer）：
    对象指向它的类元数据的指针，JVM 通过这个指针来确定该对象是哪个类的实例；
    并不是所有的虚拟机实现都必须在对象数据上保留类型指针，
    即对象的元数据信息不一定要经过对象本身就能确定。
  • 特殊情况：
    如果对象是一个 Java 数组，那么对象头中还必须有一块
    用于记录数组长度的数据，因为 JVM 可以通过普通 Java 对象的元数据
    确定 Java 对象的大小，但从数组的元数据中却无法确定数组的大小。

二、实例数据（Instance Data）：
对象真正存储的有效信息，即代码中定义的各种类型的字段内容，
无论是从父类继承下来的，还是在子类中定义的，都需要记录起来；
字段的存储顺序受到分配策略参数和字段在源码中定义顺序的影响，
相同宽度的字段总是被分配到一起，
这样做的目的是减少填充造成的空间浪费。

三、对齐填充（Padding）：
并不是必然存在的，也没有特别的含义，
它仅仅起着占位符的作用；
由于 HotSpot VM 的自动内存管理系统要求对象起始地址必须是 8 字节的整数倍，
也就是说任何对象的大小都必须是 8 字节的整数倍，
而对象头部分正好是 8 字节的倍数（32 位或 64 位），
因此当对象实例数据部分没有对齐时，
就需要通过对齐填充来补全。

四、举例说明：

一个空的 Object 对象（64 位 JVM，开启指针压缩）：
Mark Word(8字节) + Klass Pointer(4字节) + 对齐填充(4字节) = 16 字节

五、前置概念（名词解释）：

  • Mark Word：
    对象头中存运行时数据的部分，
    记录哈希码、分代年龄、锁状态等，内容随锁状态变化而复用。
  • 类型指针：
    指向类元数据的指针，用于确定对象所属的类。
  • 哈希码：
    Object.hashCode() 的默认实现基于对象内存地址生成，
    存储在 Mark Word 中。
  • 分代年龄：
    对象在 Minor GC 中存活的次数，默认 15 岁晋升老年代，
    记录在 Mark Word 中。

String 和常量池的关系？String.intern() 的作用？
String常量池

一句话概括：
String 对象有两种创建方式，直接赋值走常量池、new 走堆；
intern() 方法可以把运行期字符串加入常量池并返回池中引用，
避免重复创建相同内容的字符串，节省内存。

一、String 的两种创建方式（区别）：

  • 直接赋值（走常量池）：
    String s1 = "abc";
    先在常量池中查找是否有"abc"，有则直接返回池中的引用，
    没有则先在常量池中创建再返回引用，
    因此 s1 指向的是常量池中的对象。
  • new 创建（走堆）：
    String s2 = new String("abc");
    会在堆中创建对象，如果常量池中还没有"abc"，
    也会在常量池中创建一个"abc"字符串对象，
    s2 指向堆中对象。

二、String.intern() 方法（作用、原理）：

  • 作用：
    当一个 String 实例调用 intern() 方法时，
    JVM 会查找常量池中是否已有相同内容的字符串，
    如果有则直接返回常量池中的引用；
    如果没有，则在常量池中创建并返回引用。
  • JDK1.7 前后的差异：
    JDK1.6 及以前：常量池在永久代，
    字符串不存在时直接复制一份放入常量池，返回永久代的引用；
    JDK1.7 及以后：常量池在堆中，
    字符串不存在时只把堆中的引用放入常量池（不复制对象），
    因此 intern() 返回的引用可能与堆中的对象是同一个。
  • 示例：
    String s = new String("1") + new String("1");
    s.intern();
    // JDK1.7+ 之后，s 和 intern() 返回的是同一个对象
    // 因为"11"第一次出现，常量池只存了堆中"11"的引用

三、字符串拼接：

  • 常量折叠：
    "a" + "b" 编译期直接优化为 "ab"，仍然走常量池。
  • 变量拼接：
    String s = "a"; s + "b";
    编译后等价于 new StringBuilder().append("a").append("b").toString()，
    在堆中产生新对象，不走常量池。

四、new String("abc") 创建了几个对象：
创建 1 个或 2 个对象：
如果常量池中已有"abc"，则只在堆中创建 1 个对象；
如果常量池中没有"abc"，则在常量池创建 1 个、堆中创建 1 个，共 2 个对象。

五、注意事项：
频繁使用字符串拼接会产生大量中间对象，
循环拼接应显式使用 StringBuilder 或 StringBuffer；
intern() 使用不当会撑大常量池，
且 JDK7 前大量 intern() 可能导致永久代 OOM。

六、前置概念（名词解释）：

  • 字符串常量池：
    JVM 中专门存放字符串常量的池，JDK7 起位于堆中，
    避免重复创建相同内容的字符串。
  • intern()：
    String 的本地方法，返回常量池中该字符串的引用。
  • 常量折叠：
    编译期对常量表达式求值的优化，
    "a"+"b" 编译后直接成为 "ab"。
  • StringBuilder：
    可变字符串类，用于高效拼接字符串，
    非线程安全，线程安全用 StringBuffer。

8 种基本类型的包装类和常量池的关系？
包装类常量池

一句话概括：
除 Float 和 Double 外，其余 6 种包装类都有缓存机制：
Byte、Short、Integer、Long 缓存 -128~127，
Character 缓存 0~127，Boolean 缓存 TRUE/FALSE，
自动装箱（valueOf）时优先返回缓存的常量池对象。

一、什么是包装类（定义、作用）：
包装类是 8 种基本类型对应的类：
Integer、Long、Byte、Short、Character、Boolean、Float、Double，
作用是把基本类型包装成对象，
以便参与泛型、集合等面向对象操作，并提供了类型转换等工具方法。

二、哪些包装类有缓存（原理）：

  • Integer：
    缓存 -128~127，
    超出该范围时每次 valueOf 都会 new 一个新对象。
  • Byte、Short、Long：
    缓存 -128~127，范围与 Integer 相同。
  • Character：
    缓存 0~127，即 ASCII 码范围。
  • Boolean：
    缓存 true 和 false 两个常量对象。
  • Float、Double：
    没有缓存机制，因为浮点数范围太大，没有缓存的必要。

三、valueOf 源码逻辑（以 Integer 为例）：

public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}

四、验证示例（自动装箱）：

Integer i1 = 100;   // 自动装箱 → valueOf(100)，命中缓存
Integer i2 = 100;
System.out.println(i1 == i2); // true，是同一个缓存对象

Integer i3 = 200;   // 超出缓存范围，new 新对象
Integer i4 = 200;
System.out.println(i3 == i4); // false，两个不同对象

// 注意：比较数值应使用 equals() 而非 ==

五、注意事项：

  • 自动装箱底层调用 valueOf()，自动拆箱调用 intValue() 等。
  • 包装类对象比较数值必须用 equals()，== 比较的是引用。
  • 缓存范围 -128~127 是性能与资源的权衡，
    该范围是使用最频繁的小整数，缓存可避免频繁创建对象。

六、前置概念（名词解释）：

  • 自动装箱/拆箱：
    基本类型与包装类之间的自动转换，
    装箱调 valueOf()、拆箱调 xxxValue()。
  • IntegerCache：
    Integer 内部的静态缓存类，加载时预创建 -128~127 的对象。
  • equals()：
    Object 中用于比较对象内容的方法，
    包装类已重写为比较数值。
  • ASCII 码：
    0~127 的字符编码范围，Character 只缓存这个区间。

类加载器有哪些？如何自定义类加载器？
类加载器双亲委派

一句话概括：
JVM 内置三层类加载器：启动类加载器（Bootstrap）、扩展类加载器（Extension）、
应用类加载器（Application），父子关系通过组合实现双亲委派；
自定义类加载器只需继承 ClassLoader 并重写 findClass() 方法即可。

一、三大类加载器（定义、职责）：

  • 启动类加载器（Bootstrap ClassLoader）：
    负责加载存放在 <JAVA_HOME>/lib 目录中的类，
    或者被 -Xbootclasspath 参数指定路径中的类，
    如 JDK 核心类库 rt.jar；
    它由 C++ 实现，是 JVM 的一部分，
    并不继承 java.lang.ClassLoader。
  • 扩展类加载器（Extension ClassLoader）：
    负责加载 <JAVA_HOME>/lib/ext 目录中的类，
    或者被 java.ext.dirs 系统变量指定的路径中的类，
    由 Java 实现，是 ClassLoader 的子类。
  • 应用类加载器（Application ClassLoader）：
    负责加载用户类路径（classpath）上的类，
    一般情况下程序中的类都由它加载，
    是 ClassLoader 的子类，ClassLoader.getSystemClassLoader() 返回它。

二、双亲委派模型（简述）：
类加载请求先委派给父类加载器，逐级向上，
父类加载不了才由自己加载，
这样保证核心类只被加载一次、不被篡改。
详细机制与破坏场景见 Q18。

三、loadClass() 源码逻辑：
ClassLoader 的 loadClass() 方法实现了双亲委派：

protected Class<?> loadClass(String name) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1、先检查类是否已被加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 2、父加载器不为空则委派给父加载器
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    // 父加载器为空则使用启动类加载器
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器无法加载
            }
            if (c == null) {
                // 3、父加载器加载不了，才调用 findClass 自己加载
                c = findClass(name);
            }
        }
        return c;
    }
}

四、如何自定义类加载器：
推荐做法是继承 ClassLoader，重写 findClass() 方法：

public class MyClassLoader extends ClassLoader {
    private String path; // 自定义加载路径

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // 1、读取 class 文件的字节数组
        byte[] data = loadClassData(name);
        // 2、把字节数组转换为 Class 对象
        return defineClass(name, data, 0, data.length);
    }
}

// 使用
ClassLoader loader = new MyClassLoader();
Class<?> clazz = loader.loadClass("com.demo.Hello");
  • findClass() vs loadClass()：
    只重写 findClass() 会保留双亲委派，
    父加载器加载不到时才会走自定义逻辑；
    如果重写 loadClass() 则可能破坏双亲委派，
    需根据业务需求（如热部署、Web 容器隔离）选择。
  • defineClass()：
    ClassLoader 提供的模板方法，
    把字节数组转换为 Class 对象，是加载的核心。

五、前置概念（名词解释）：

  • 类加载器：
    负责把 Class 文件加载到 JVM 中生成 Class 对象的组件，
    也是加载阶段获取二进制字节流的入口。
  • 双亲委派：
    类加载请求先委派父加载器，
    父加载不了才自己加载的机制，详见 Q18。
  • findClass()：
    ClassLoader 的受保护方法，
    自定义类加载器重写它来定义加载逻辑。
  • defineClass()：
    把字节数组转换成 Class 对象的方法，
    自定义加载器的最后一步。

如何判断一个常量是废弃常量？运行时常量池如何回收废弃常量？
常量池垃圾回收

一句话概括：
运行时常量池中的常量（字面量/符号引用）不再被任何对象引用时即为废弃常量，
会在发生内存回收且有必要时被清理出常量池。

一、运行时常量池存什么：

  • 字面量（Literal）：
    如字符串 "abc"、final 常量值等，
    是编译期可确定的具体值。
  • 符号引用（Symbolic Reference）：
    类和接口的全限定名、字段的名称和描述符、方法的名称和描述符，
    在类加载解析阶段可能转换为直接引用。

二、如何判断常量是否废弃：
以字符串字面量为例：假设字符串常量池中存在 "abc"，
如果当前没有任何 String 对象引用 "abc"（即没有任何地方使用它），
那么 "abc" 就是一个废弃常量。
符号引用的判定则与类是否被卸载相关（详见 Q33）。

三、回收时机：
发生内存回收（如 Full GC）且确有回收必要时，
JVM 会把废弃常量清理出常量池释放内存。
与废弃常量的回收相比，无用类的回收条件更苛刻。

💡 判断"废弃常量"只需判断"无人引用"；
而判断"无用类"还需满足：所有实例已回收、ClassLoader 已回收、
对应的 Class 对象未被反射引用（见 Q33），所以类的回收比常量更难。

虚拟机栈的栈帧结构是怎样的？什么是局部变量表 Slot 复用？
虚拟机栈栈帧

一句话概括：
每个方法被调用时都会创建一个栈帧（入栈），方法结束即出栈，栈帧先进后出（LIFO）；
栈帧由局部变量表、操作数栈、动态链接、方法出口组成，
其中局部变量表以 Slot 为最小单位，Slot 可以被复用。

一、栈帧的四部分：

  • 局部变量表：
    存放方法参数和局部变量，以 Slot（变量槽）为最小单位，
    是栈帧中空间占用最大的部分，直接影响栈的深度。
  • 操作数栈：
    存放计算过程的中间结果，
    如执行 i+j 时先把 i、j 压入操作数栈再执行加法。
  • 动态链接：
    指向运行时常量池中该方法的引用，
    用于支持方法调用时把符号引用解析为直接引用。
  • 方法出口（返回地址）：
    记录调用该方法的位置，
    方法正常/异常返回后能回到调用处继续执行。

二、局部变量表 Slot 复用：

  • Slot 大小：
    32 位以内的类型（int、short、byte、char、float、引用）占 1 个 Slot，
    64 位的 long、double 占 2 个 Slot。
  • 复用规则：
    方法体内变量的作用域结束后（如 for 循环结束后），
    它占用的 Slot 可以分配给后续声明的变量使用，
    这就是"局部变量表不是方法结束才释放、而是离开作用域即释放"的原因。
  • Slot 复用对 GC 的影响：
    一个较大的局部变量离开作用域后若被复用，
    堆中的对象失去引用，就能被 GC 正常回收；
    如果变量离开作用域但未被复用，且仍持有堆对象引用，
    会阻碍该对象回收——可在不再使用时手动置 null 帮助 GC。

💡 栈帧对应一次方法调用；递归过深时栈帧无限入栈，最终抛 StackOverflowError。
