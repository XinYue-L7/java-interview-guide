TCP 三次握手和四次挥手？
网络基础

定义

TCP（传输控制协议）是面向连接的、可靠的、基于字节流的传输层协议。

三次握手是建立连接的过程，四次挥手是断开连接的过程，两者是保证 TCP 可靠传输的基础。

作用

  • 三次握手：
    在传数据之前，先确认双方"都能发、都能收"，确保连接可靠建立，防止历史请求干扰。
  • 四次挥手：
    数据传完后，让双方各自确认"我这边没有要发的数据了、你也都收到了"，确保数据完整传输后再干净地断开。

原理

TCP 用 SYN（请求建立）、ACK（确认收到）、FIN（请求关闭）三种标志位来沟通状态。

三次握手按"SYN → SYN+ACK → ACK"两两确认；

四次挥手因为 TCP 是全双工的，双方要各自用一次 FIN + ACK 关闭自己方向的发送通道，最后再等 2MSL 兜底。

举例讲解

三次握手（建立连接）—— 像打电话确认信号：

  1. 客户端发一个请求：
    "喂，服务器，你能听到我说话吗？"
  2. 服务器回复：
    "我能听到你。
    那你能听到我说话吗？"
  3. 客户端回复：
    "我也能听到你，那咱们开始聊吧！"

为什么要握三次？

  • 两次不够：
    服务器不知道客户端能不能收到自己的消息。
  • 三次才能确认：
    双方都能发、也都能收，连接才算可靠建立。
  • 还能防止"历史连接"捣乱——万一网络里有之前延迟到达的旧请求，三次握手能识别出来并丢弃。

四次挥手（断开连接）—— 像挂电话，双方都要说再见：

  1. 客户端：
    "我说完了，我要挂电话了。
    "（发 FIN）
  2. 服务器：
    "知道了，你先别挂，我话还没说完。
    "（回 ACK）
  3. 服务器：
    "好了，我也说完了，我也挂了。
    "（发 FIN）
  4. 客户端：
    "好的，知道了，你挂吧。
    "（回 ACK）

为什么要挥四次？

  • TCP 是全双工的，两边可以同时收发。
    关闭时两边要各自独立关闭自己的发送通道。
  • 客户端发完 FIN 只代表它不发数据了，但服务器可能还有数据要发，所以不能一起关闭，必须分两次。

TIME_WAIT（2MSL）是干嘛的？

  • 客户端发完最后一个 ACK 后，不会立刻关闭，而是等待一段时间（2MSL，通常是 2~4 分钟）。
  • 原因：
    怕最后一个 ACK 丢了，服务器没收到就会一直重发 FIN。
  • 客户端等这段时间，就能兜底处理服务器重发的 FIN，再回一个 ACK，确保双方都能干净地关闭连接。

HTTP 和 HTTPS 的区别？HTTPS 握手流程？
网络HTTPS

定义

HTTP 是超文本传输协议，明文传输，客户端和服务器之间直接传数据，中间任何人都能看到。

HTTPS 是在 HTTP 下面加了一层 SSL/TLS安全协议，给数据加密后再传，防止中间人偷看或篡改。

作用

  • HTTP：
    适合传输公开信息，速度快、开销小，但不安全，容易被窃听、篡改、冒充。
  • HTTPS：
    保护敏感数据（密码、银行卡、个人信息），确保数据加密、身份可信、内容完整，是银行、电商、登录页面的标配。

原理

HTTPS 在 HTTP 和 TCP 之间插入了一个 TLS/SSL 安全层。

握手阶段用非对称加密（公钥/私钥）交换密钥并验证身份，确认安全后切换到对称加密传数据，兼顾安全和性能。

整个过程靠 CA 数字证书来证明"你访问的网站真的是它说的那个网站"。

HTTP 和 HTTPS 的区别

对比项HTTPHTTPS
加密明文传输，内容可被窃听加密传输，内容不可被偷看
端口80443
证书不需要需要向 CA 机构申请数字证书
安全性易被窃听、篡改、冒充保证加密、身份可信、内容完整
性能无握手开销，速度快握手多几轮交互，首次连接稍慢
URLhttp://https://

HTTPS 握手流程（TLS 1.2）

  1. Client Hello：
    客户端发"我支持这些加密方式"+ 一个随机数 A。
  2. Server Hello：
    服务器选一种加密方式 + 自己的随机数 B + 发送 CA 证书。
  3. 验证证书：
    客户端用 CA 公钥验证证书真伪，确认服务器身份可信。
  4. 发送预主密钥：
    客户端生成一个预主密钥，用服务器的公钥加密后发给服务器。
  5. 生成会话密钥：
    双方用"随机数 A + 随机数 B + 预主密钥"各自算出同一把会话密钥。
  6. Finished：
    双方互发确认消息，之后都用这把会话密钥（对称加密）传数据。

经典6步流程图

1
服务器办证
服务器把"域名 + 服务器公钥"等信息交给 CA，CA 用自己的私钥签名，签发数字证书（内含服务器公钥、域名、有效期、签名）。
↓
2
浏览器敲门
输入网址 → DNS 解析 IP → TCP 三次握手 → 发现是 https，发起 TLS 握手，向服务器要证书。
↓
3
服务器亮证
服务器把数字证书发给浏览器，证书里包含服务器公钥、域名、有效期、CA 签名。
↓
4
浏览器验证证书
用系统内置的 CA 公钥"验签"，检查证书是否过期、域名是否匹配，确认证书没被篡改、确实是可信 CA 签发（注意是验签，不是解密证书）。
↓
5
确认身份
验签通过后，浏览器信任证书中的服务器公钥，认可"这个公钥属于这个网站"。
↓
6
密钥交换
浏览器用服务器公钥加密"会话密钥"发给服务器；服务器用私钥解开，双方拿到同一把对称密钥，之后数据传输都用它加密（速度快）。

举例讲解

HTTP vs HTTPS —— 像寄明信片 vs 寄信封：

  • HTTP 就像寄明信片：
    邮递员、路人都能随手看到上面写了什么，内容完全公开。
  • HTTPS 就像寄上锁的信封：
    信封上了锁，只有收件人有钥匙能打开，路上谁也看不到里面写了什么。

HTTPS 握手 —— 像双方交换密码本：

  1. 浏览器说：
    "你好，我支持这几种加密方式，这是我的随机数 A。
    "
  2. 服务器回复：
    "我选这种加密方式，这是我的随机数 B，还有我的身份证明（CA 证书）。
    "
  3. 浏览器验证证书是真的，然后生成一个预主密钥，用服务器的公钥加密后发过去。
  4. 双方各自用三个随机数（A + B + 预主密钥）算出同一把会话密钥，之后的数据都用这把密钥加密传输。
  5. 双方互相确认：
    "密钥算好了，开始安全通信！"

为什么要先非对称、后对称？

  • 非对称加密（公钥/私钥）很安全，但太慢，不适合传大量数据。
  • 对称加密（同一把密钥）很快，但密钥如果直接传出去会被截获。
  • 所以 HTTPS 很聪明：
    先用非对称加密安全地把对称密钥送过去，之后全程用对称加密传数据，又快又安全。

TLS 1.3 升级：

把握手从 2-RTT 优化到 1-RTT，更快更安全，还支持 0-RTT 会话恢复。

Cookie、Session、Token（JWT）的区别？
认证高频

定义

  • Cookie：
    浏览器提供的一种客户端本地存储机制，服务器通过 Set-Cookie 响应头把一小段数据写给浏览器，浏览器之后每次访问该网站都会自动带上这段数据。
  • Session：
    服务器端维护的会话状态，用户登录后服务器在内存/数据库里存一份用户信息，并生成一个唯一的 SessionID 通过 Cookie 交给浏览器，后续浏览器凭这个 SessionID 来"认领"自己的会话。
  • Token（JWT）：
    一种无状态的认证凭证，服务器把用户信息（如用户ID、角色、过期时间）用签名算法打包成一个字符串，交给客户端保存；
    客户端每次请求时把这个字符串放在请求头里带过来，服务器验签即可知道你是谁，不需要在服务端存任何会话数据。

作用

  • Cookie：
    让浏览器"记住"一些服务器给的小信息（如登录状态标识、用户偏好设置），实现有状态的 HTTP 请求。
  • Session：
    在服务端安全地保存用户的登录状态、购物车、权限等敏感信息，数据不暴露给客户端，安全性高。
  • Token（JWT）：
    让服务器"不用记"用户状态，认证信息全由客户端自己保管和携带，天然适合分布式系统、微服务、移动端、跨域场景。

原理

  • Cookie：
    服务器 → Set-Cookie → 浏览器本地存储 → 后续请求自动 Cookie: xxx 带上。
    受同源策略限制，默认只能发给同域名，有 4KB 大小限制。
  • Session：
    用户登录 → 服务器创建 Session 对象（存内存/Redis）→ 生成 SessionID → 通过 Cookie 发给浏览器 → 后续请求浏览器带 SessionID → 服务器查 Session 表确认身份。
    多台服务器时需共享 Session 存储（如 Redis）。
  • Token（JWT）：
    用户登录 → 服务器用私钥签名生成 JWT（Header.Payload.Signature）→ 发给客户端 → 客户端存 localStorage 或内存 → 后续请求放在 Authorization: Bearer xxx 头里 → 服务器用公钥验签即可解析出用户信息，无需查库。

Cookie、Session、Token 的区别

对比项CookieSessionToken（JWT）
存储位置客户端浏览器服务端（内存/Redis/数据库）客户端（localStorage/header）
数据内容通常是 SessionID 或偏好设置完整的用户会话数据用户ID、角色、过期时间等
安全性较低，可被篡改/窃取（需配合 HttpOnly/Secure）较高，敏感数据不暴露给客户端中等，Payload 只是 Base64 不加密，需 HTTPS + 合理过期
跨域支持默认受限，需设置 Domain/Path依赖 Cookie 传递 SessionID，同样受限天然支持，放在请求头里不受 Cookie 跨域限制
服务端压力无，纯客户端存储有，需维护 Session 存储，分布式需共享无，服务端只验签不存状态
适用场景传统 Web 网站、保持登录态需要服务端控制会话、随时强制下线的场景分布式系统、微服务、移动端、API 接口、单页应用

举例讲解

Cookie —— 像你的"会员卡"：

  • 你去健身房办了一张会员卡，前台把卡号写在小纸条上给你（Set-Cookie）。
  • 之后每次去健身房，你出示这张小纸条，前台就知道你是谁（自动带上 Cookie）。
  • 小纸条只能在这家健身房用（同源限制），而且纸条很小，写不了太多字（4KB 限制）。

Session —— 像健身房的"会员档案柜"：

  • 健身房前台有一个档案柜，里面存着每个会员的详细资料（Session 存服务端）。
  • 你每次出示会员卡号（SessionID），前台去档案柜里找到你的资料，确认身份。
  • 资料都在柜子里，很安全，但如果健身房开了分店，档案柜也要同步（分布式共享 Session）。

Token（JWT）—— 像你的"电子身份证"：

  • 你去办了一张带数字签名的电子身份证（JWT），里面写好了你的名字、会员等级、有效期。
  • 之后去任何一家连锁店，你出示这张电子身份证，店员用公钥验证签名是真的，就知道你是谁，不需要查档案柜。
  • 身份证在你自己手里，适合去不同的店（跨域/分布式），但要注意身份证别丢了，而且上面的信息是公开的（Base64 不加密），所以敏感信息不能写上去。

JWT 使用注意事项：

  • Payload 不加密：
    JWT 的 Payload 只是 Base64 编码，任何人都能解码看到内容，不要放密码、身份证号等敏感信息。
  • 设置合理过期时间：
    JWT 一旦签发，在过期前一直有效，服务端无法提前"作废"，所以要设置较短的过期时间（如 15 分钟）。
  • 配合 Refresh Token：
    短效的 Access Token + 长效的 Refresh Token，既保证安全又避免频繁登录。
  • 必须用 HTTPS：
    防止 Token 在传输过程中被截获。
  • 退出登录处理：
    服务端维护一个"黑名单"（如 Redis），把要作废的 Token 加进去，验签时先查黑名单。
