Spring IOC 的实现原理？
Spring高频

IOC(Inversion of Control)控制反转：将对象创建和依赖关系的管理交给Spring容器。

核心：BeanFactory + 反射

  1. 资源定位：加载XML/注解配置。
  2. BeanDefinition解析：将配置解析为BeanDefinition。
  3. Bean注册：注册到BeanDefinitionRegistry(Map)。
  4. Bean创建(DI)：反射创建实例→填充属性→初始化。

💡 ApplicationContext是BeanFactory的子接口，功能更丰富(国际化、事件发布等)。

Spring AOP 的实现原理？
Spring高频

AOP(Aspect Oriented Programming)面向切面编程：将横切关注点(日志/事务/权限)与业务逻辑分离。

两种实现：

  • JDK动态代理：基于接口，Proxy+InvocationHandler。目标类必须实现接口。
  • CGLIB代理：基于继承，ASM字节码生成子类。不能代理final类/方法。

💡 Spring默认：有接口用JDK代理，无接口用CGLIB。SpringBoot 2.0+默认使用CGLIB。

Spring 事务的实现原理和传播行为？
Spring事务

原理：AOP代理 + ThreadLocal

7种传播行为：

  • REQUIRED：有事务则加入，无则新建（默认）。
  • REQUIRES_NEW：总是新建事务，挂起当前事务。
  • SUPPORTS：有事务则加入，无则以非事务运行。
  • NOT_SUPPORTED：非事务运行，挂起当前事务。
  • MANDATORY：必须在事务中，无则抛异常。
  • NEVER：必须非事务，有则抛异常。
  • NESTED：嵌套事务，有savepoint可部分回滚。

Spring 事务失效的场景有哪些？
Spring实战
  • 数据库引擎不支持事务(MyISAM)。
  • 方法非public（AOP代理只能拦截public方法）。
  • 类内部调用(this.method())，绕过了代理对象。
  • 异常被try-catch吞掉，没有抛出。
  • rollbackFor设置错误(默认只回滚RuntimeException和Error)。
  • 多线程中调用事务方法。

💡 解决内部调用：注入自身或使用AopContext.currentProxy()。

MyBatis 的一级缓存和二级缓存？
MyBatis缓存
  • 一级缓存(SqlSession级别)：默认开启，同一SqlSession内相同查询只查一次DB。执行增删改/commit/close会清空。
  • 二级缓存(Namespace级别)：默认关闭，需手动开启。多个SqlSession共享。适合不常变更的数据。

💡 生产环境通常不用MyBatis二级缓存，用Redis等分布式缓存替代。

Dubbo 的工作流程和核心组件？
DubboRPC

核心组件：Provider(服务提供者)、Consumer(消费者)、Registry(注册中心)、Monitor(监控中心)。

调用流程：

  1. Provider向Registry注册服务。
  2. Consumer向Registry订阅服务。
  3. Registry通知Consumer服务列表。
  4. Consumer通过负载均衡选择Provider，直连调用(RPC)。
  5. Monitor统计调用数据。

💡 注册中心可用Zookeeper/Nacos/Redis等。

核心：树形节点(ZNode) + Watch机制 + ZAB协议

应用场景：

  • 服务注册与发现(Dubbo)。

Spring 的循环依赖是如何解决的？
Spring高频

三级缓存解决单例Bean的循环依赖：

  • 一级缓存(singletonObjects)：完全初始化好的Bean。
  • 二级缓存(earlySingletonObjects)：早期暴露的Bean(已实例化但未注入属性)。
  • 三级缓存(singletonFactories)：Bean工厂，可生成代理对象。

流程：A创建→提前暴露到三级缓存→A填充B→触发B创建→B填充A→从三级缓存获取A的早期引用→B完成→A完成。

💡 限制：只能解决单例setter注入的循环依赖，构造器注入不行。

Spring 循环依赖是如何解决的？
循环依赖高频

Spring通过三级缓存解决单例setter注入的循环依赖：

  • singletonObjects（一级）：完全初始化好的Bean。
  • earlySingletonObjects（二级）：早期暴露的半成品Bean。
  • singletonFactories（三级）：ObjectFactory，可生成Bean的早期引用。

💡 不能解决构造器注入的循环依赖（因为实例化阶段就需要依赖）。Prototype作用域也不支持。

Spring 事务传播行为有哪些？
事务高频

7种传播行为（Propagation）：

  1. REQUIRED（默认）：有则加入，无则新建。最常用。
  2. REQUIRES_NEW：挂起当前，新建事务。内部和外部事务独立。
  3. SUPPORTS：有则加入，无则非事务运行。
  4. NOT_SUPPORTED：非事务运行，挂起当前事务。
  5. MANDATORY：必须有事务，无则抛异常。
  6. NEVER：必须非事务，有则抛异常。
  7. NESTED：嵌套事务，内部事务依赖外部事务（savepoint回滚）。

💡 REQUIRES_NEW完全独立，外部回滚不影响内部；NESTED外部回滚会回滚内部。

Spring 事务失效的常见场景？
事务超高频
  • 自调用：同类中方法A（无事务）调方法B（有事务），B的事务不生效→因为是this调用不走代理。解决：AopContext.currentProxy()或注入自己。
  • 非public方法：默认CGLIB/JDK只能代理public方法。
  • 异常被吞：catch后未抛出，事务不回滚。
  • 非RuntimeException：默认只回滚RuntimeException和Error，受检异常需@Transactional(rollbackFor = Exception.class)。
  • 数据库引擎不支持：MyISAM不支持事务。
  • 多线程：不同线程不在同一事务上下文。

MyBatis 的 #{} 和 ${} 区别？底层原理？
MyBatis高频
  • #{}：预编译占位符?，底层是PreparedStatement 参数化查询 防SQL注入。类型处理器(TypeHandler)做参数映射。
  • ${}：字符串拼接，直接替换到SQL中 有注入风险。仅用于动态表名、列名、ORDER BY等无法预编译场景。

💡 #{}替换为?由JDBC驱动最终处理，${}直接由MyBatis替换。

Dubbo 的核心原理和调用流程？
DubboRPC

Dubbo是高性能RPC框架，核心流程：

  1. 注册：Provider向Registry注册服务。
  2. 订阅：Consumer从Registry订阅服务（拉取+监听变更）。
  3. 调用：Consumer通过动态代理（Proxy）发起远程调用→经过Filter链→负载均衡选择Provider→Netty网络传输→Provider反序列化→执行→返回。
  4. 监控：Monitor统计调用次数和耗时。

注册中心：ZooKeeper（默认）、Nacos、Redis、Consul。

Dubbo 负载均衡策略有哪些？
Dubbo负载均衡
  • Random（默认）：加权随机，按权重随机。
  • RoundRobin：加权轮询。
  • LeastActive：最少活跃调用数（处理快的节点分配更多）。
  • ConsistentHash：一致性Hash，相同参数的请求始终发到同一Provider。
  • ShortestResponse：最短响应时间（Dubbo 2.7+）。

Dubbo 的集群容错策略有哪些？
Dubbo容错
  • Failfast：快速失败，立即抛异常。适合非幂等写操作。
  • Failsafe：失败安全，忽略异常。适合写入日志。
  • Failover（默认）：失败自动切换重试（默认2次+本机1次=3次）。适合幂等读操作。
  • Failback：失败自动恢复，后台定时重发。
  • Forking：并行调用多个Provider，一个成功即返回。
  • Broadcast：广播调用所有Provider，一个失败即失败。

Netty 的线程模型和零拷贝？
Netty高频

Reactor主从模型：

  • Boss Group（1个NioEventLoop）：接收连接，注册Channel到Worker。
  • Worker Group（CPU*2个NioEventLoop）：处理读写IO和业务逻辑。
  • 每个NioEventLoop绑定一个Selector和一条线程。

零拷贝（Zero Copy）：

  • FileRegion：transferTo()操作系统级零拷贝（DMA拷贝）。
  • CompositeByteBuf：逻辑组合多个ByteBuf，无物理拷贝。
  • Unpooled.wrappedBuffer：包装字节数组，不拷贝。

Spring AOP 的原理？JDK代理和CGLIB代理的区别？
AOP高频

AOP基于动态代理，在BeanPostProcessor.postProcessAfterInitialization中创建代理。

JDK动态代理：

  • 目标类必须实现接口。
  • 基于反射+接口，生成Proxy$类。
  • 性能略低（反射调用）。

CGLIB代理：

  • 基于ASM字节码，生成子类。
  • 不需要接口，但不能代理final类/方法。
  • 性能略高（直接方法调用）。

💡 Spring Boot 2.x默认使用CGLIB。@EnableAspectJAutoProxy(proxyTargetClass=true)强制CGLIB。

@Configuration 和 @Component 的区别？full模式和lite模式？
SpringBean

@Configuration（full模式）：通过CGLIB增强，确保@Bean方法内部调用仍然走容器（单例）。

@Component（lite模式）：不走CGLIB代理，内部调用@Bean方法会创建新实例。

@Configuration // full模式
public class Config {
    @Bean A a() { return new A(b()); } // b()走代理，同一实例
    @Bean B b() { return new B(); }
}
@Component // lite模式
// a()中b()不会走代理，new新B()
