1
Spring Cloud 核心组件有哪些？分别负责什么？
微服务高频

一、定义：
Spring Cloud 是一套基于 Spring Boot 的微服务解决方案集合，
把注册中心、配置中心、网关、负载均衡等组件打包整合，
让开发者快速搭建分布式系统。

二、作用：
统一解决微服务架构中的服务治理、服务调用、流量控制、配置管理等共性问题，
避免每个项目重复造轮子。

三、核心组件（先讲定义、再讲作用）：

  • 服务注册中心（Eureka / Nacos）：
    定义：管理所有服务地址的"通讯录"。
    作用：服务启动时注册自己的地址，
    服务调用时从注册中心拉取目标地址。
  • 负载均衡（Ribbon / LoadBalancer）：
    定义：把请求按策略分发到多个服务实例的组件。
    作用：分散压力，提升系统吞吐量。
  • 服务调用（OpenFeign）：
    定义：声明式 HTTP 客户端。
    作用：像调用本地方法一样调用远程服务，
    内部自动完成 HTTP 封装和负载均衡。
  • 服务熔断降级（Hystrix / Sentinel）：
    定义：防止单个服务故障拖垮整个系统的保护组件。
    作用：熔断、降级、限流，实现快速失败。
  • 网关（Gateway / Zuul）：
    定义：所有请求的统一入口。
    作用：路由转发、鉴权、限流、日志。
  • 配置中心（Config / Nacos Config）：
    定义：统一管理各服务配置的组件。
    作用：配置修改实时生效，无需重启服务。
  • 链路追踪（Sleuth + Zipkin）：
    定义：记录一次请求跨多个服务的完整调用链的组件。
    作用：快速定位慢请求、排查故障。

四、示例：
用户点击下单，
请求先进入 Gateway → 经 Ribbon 负载均衡 → Feign 调用订单服务 → 订单服务再调用库存服务，
整个过程由 Sleuth 记录链路，由 Sentinel 保护。

五、注意事项：
1. 组件版本需与 Spring Boot 版本匹配，
否则启动报错；
2. 国内主流用 Spring Cloud Alibaba 全家桶（Nacos + Sentinel + Seata），
原 Netflix 组件部分已停止维护。

六、前置概念：
微服务：把一个大型应用拆成多个独立部署的小服务，
每个服务只负责一个业务模块，
服务之间通过网络通信。

Eureka 注册中心的工作原理？
Eureka注册中心

一、定义：
Eureka 是 Netflix 开源的注册中心组件，
采用"客户端-服务端"模式管理微服务地址。

二、作用：
实现服务的注册、发现与健康检查，
让服务之间无需硬编码地址即可互相调用。

三、工作原理：
核心角色有两个：Eureka Server 和 Eureka Client，
工作流程分四步。

  • 1. 服务注册：
    服务提供者启动时，
    向 Eureka Server 发送注册请求，
    携带服务名和实例地址。
  • 2. 心跳续约：
    服务提供者每隔 30 秒发送一次心跳（Renew），
    告诉 Server 自己还活着，
    默认 90 秒收不到心跳则剔除该实例。
  • 3. 服务发现：
    服务消费者启动时，
    从 Server 拉取服务实例列表并缓存在本地，
    之后调用时直接走本地缓存。
  • 4. 自我保护机制：
    当短时间内大量心跳丢失（如网络分区），
    Eureka 不会立刻剔除实例，
    而是进入自我保护模式，
    宁可保留可能已挂的实例，也不误删健康实例。

四、示例：
订单服务（provider）注册到 Eureka，
用户服务（consumer）通过服务名"order-service"找到订单服务地址并调用，
订单服务下线后 90 秒内被剔除。

五、注意事项：
1. 自我保护模式下可能调用到已宕机的实例，
需配合重试机制；
2. Eureka 是 AP 模型，
保证可用性但不保证强一致，
读到的实例列表可能短暂不一致。

六、前置概念：
注册中心：微服务架构中的"服务通讯录"，
记录所有服务的名称与地址，
是服务治理的基础设施。

Ribbon 负载均衡的原理和策略？
Ribbon负载均衡

一、定义：
Ribbon 是 Netflix 开源的客户端负载均衡器，
运行在服务消费方，
从注册中心拿到实例列表后在本地选择目标实例。

二、作用：
在多个服务实例之间智能分发请求，
避免单个实例过载，
提升系统整体可用性。

三、工作原理：
Ribbon 采用"客户端负载均衡"模式，
核心分三步。

  • 1. 获取服务列表：
    与注册中心（Eureka/Nacos）整合，
    定时拉取并缓存服务实例列表。
  • 2. 负载均衡算法选实例：
    根据配置的策略（如轮询、随机），
    从实例列表中选出一个目标地址。
  • 3. 发起 HTTP 请求：
    由 RestTemplate 或 Feign 发起真实调用，
    并支持失败重试到下一个实例。

四、负载均衡策略：

  • 轮询（RoundRobinRule）：
    按顺序轮流选择实例，
    默认策略。
  • 随机（RandomRule）：
    随机选择一个实例。
  • 权重（WeightedResponseTimeRule）：
    响应时间越短权重越大，
    选中的概率越高。
  • 重试（RetryRule）：
    选中实例失败后自动重试其他实例。
  • 可用性过滤（AvailabilityFilteringRule）：
    先过滤掉熔断、高并发的实例，
    再从剩余实例中轮询。

五、示例：
订单服务有 3 个实例（order-1、order-2、order-3），
用户服务用 Ribbon 轮询调用，
第 1 次请求 → order-1，第 2 次 → order-2，第 3 次 → order-3，循环往复。

六、注意事项：
1. 客户端负载均衡要求消费方本地缓存实例列表，
列表更新有延迟；
2. 服务端负载均衡（如 Nginx）在网关层做，
客户端负载均衡在调用方做，
两者可同时存在。

七、前置概念：
负载均衡：把请求均匀分发到多个服务实例的技术，
目的是提高吞吐量和可用性，
分为客户端负载均衡和服务端负载均衡两种。

OpenFeign 的实现原理？
Feign服务调用

一、定义：
OpenFeign 是一个声明式 HTTP 客户端，
只需定义接口并加注解，
就能像调用本地方法一样调用远程服务。

二、作用：
简化服务间调用代码，
自动集成负载均衡和熔断，
提高开发效率。

三、工作原理：
核心机制是"动态代理 + 接口解析"，
分四步。

  • 1. 扫描注解：
    启动时扫描 @FeignClient 注解的接口，
    为每个接口生成一个 JDK 动态代理对象。
  • 2. 生成请求模板：
    解析接口方法上的注解（@GetMapping 等），
    生成包含 URL、请求方式、参数的 RequestTemplate。
  • 3. 负载均衡：
    调用时交给 Ribbon/LoadBalancer，
    根据服务名解析出真实实例地址。
  • 4. 发送请求：
    通过 HttpURLConnection / HttpClient 发送请求，
    把响应结果反序列化为接口返回值，
    完成一次"本地方法调用"。

四、示例：
定义接口：
@FeignClient("order-service")
public interface OrderClient {
  @GetMapping("/order/{id}")
  Order getOrder(@PathVariable("id") Long id);
}
调用 OrderClient.getOrder(1L)，
实际是向 order-service 的 /order/1 发起了 HTTP GET 请求。

五、注意事项：
1. 接口上的 @PathVariable 必须显式指定 value，
否则报错；
2. 超时时间默认 1 秒，
需要按业务调整；
3. 开启熔断需引入 sentinel/hystrix 依赖并配置。

六、前置概念：
动态代理：运行时为接口生成代理对象的技术，
调用方法时先经过代理逻辑，
再转发到真实实现，
是 Feign、MyBatis Mapper 等框架的共同底层原理。

Spring Cloud Gateway 的核心原理？
网关高频

一、定义：
Spring Cloud Gateway 是基于 WebFlux 的响应式 API 网关，
是 Spring Cloud 官方推荐的网关组件。

二、作用：
作为所有请求的统一入口，
负责路由转发、鉴权认证、限流熔断、日志监控。

三、工作原理：
核心由三部分组成：Route（路由）、Predicate（断言）、Filter（过滤器），
处理流程分三步。

  • 1. 路由匹配（Predicate）：
    请求到达网关后，
    按配置的断言规则（路径、请求头、参数等）判断该请求匹配哪个路由。
  • 2. 过滤器链（Filter）：
    匹配成功后进入过滤器链，
    分为全局过滤器和网关过滤器，
    先执行 pre 逻辑（鉴权、限流、改请求头），
    再转发到下游服务，
    最后执行 post 逻辑（记录日志、改响应）。
  • 3. 负载均衡转发：
    使用 lb://服务名 协议转发，
    结合 LoadBalancer 把请求分发到具体实例。

四、示例：
配置路由：
spring.cloud.gateway.routes[0]
  id: order-route
  uri: lb://order-service
  predicates: Path=/api/order/**
当请求 /api/order/1 到达网关时，
命中 order-route，
转发到 order-service 的 /1。

五、注意事项：
1. 基于 WebFlux 非阻塞模型，
不支持 Servlet 相关依赖（如 spring-boot-starter-web）；
2. 网关是流量入口，
必须做限流，
防止被刷；
3. 网关层尽量保持轻量，
避免放业务逻辑。

六、前置概念：
响应式编程（WebFlux）：基于事件驱动和非阻塞 IO 的编程模型，
用少量线程支撑高并发请求，
底层依赖 Netty。

Nacos 作为注册中心的原理？
Nacos注册中心

一、定义：
Nacos 是阿里巴巴开源的一站式服务治理平台，
同时具备注册中心和配置中心两大能力。

二、作用：
实现服务注册、发现、配置管理和动态下发，
是 Spring Cloud Alibaba 生态的核心组件。

三、工作原理：
Nacos 支持临时实例和持久化实例两种模型，
机制不同。

  • 1. 临时实例（默认）：
    采用 Distro 协议，AP 模型，
    客户端每 5 秒发送心跳，
    服务端超过 15 秒未收到心跳则标记不健康，
    超过 30 秒剔除实例。
  • 2. 持久化实例：
    采用 Raft 协议，CP 模型，
    实例数据持久化到磁盘，
    通过 Raft 选举保证强一致。
  • 3. 服务发现：
    消费者通过服务名拉取实例列表，
    并支持 UDP 推送变更通知，
    比 Eureka 的定时拉取更实时。
  • 4. 健康检查：
    客户端主动上报心跳 + 服务端主动探测（TCP/HTTP），
    双保险保障实例状态准确。

四、示例：
订单服务启动后注册到 Nacos（临时实例），
注册成功后每 5 秒发心跳；
订单服务宕机，
30 秒内被 Nacos 剔除，
消费者通过推送通知立刻感知，
不再把请求发到宕机实例。

五、注意事项：
1. 集群部署建议 3 台以上，
并配置 MySQL 存储持久化数据；
2. 临时实例模式是 AP，
可能出现短暂不一致；
3. 与 Eureka 相比，
Nacos 支持服务端主动推送，
变更感知更快。

六、前置概念：
CAP 理论：分布式系统只能同时满足一致性（C）、可用性（A）、分区容错性（P）中的两个，
Nacos 临时实例选 AP，
持久化实例选 CP。

Sentinel 限流、熔断、降级的工作原理？
Sentinel高可用

一、定义：
Sentinel 是阿里巴巴开源的流量控制与高可用保护组件，
主要提供限流、熔断、降级三大能力。

二、作用：
保护系统在高并发或依赖故障时不被拖垮，
保证核心业务的可用性。

三、工作原理：
核心思路是"资源 + 规则"，
所有被保护的方法都视为资源，
规则决定保护策略，
处理流程分三步。

  • 1. 资源定义：
    通过 @SentinelResource 注解或代码块标记受保护的资源，
    每次请求进入资源时触发规则检查。
  • 2. 限流（FlowRule）：
    支持 QPS 限流和并发线程数限流，
    超过阈值直接拒绝或排队等待，
    可选基于调用关系的关联限流、链路限流。
  • 3. 熔断降级（DegradeRule）：
    三种策略：
    慢调用比例：响应时间超阈值且比例达标 → 熔断；
    异常比例：异常占比超阈值 → 熔断；
    异常数：单位时间内异常数超阈值 → 熔断。
    熔断后进入降级逻辑（返回兜底值），
    熔断窗口结束后自动恢复探测。

四、示例：
接口 QPS 限流 100，
第 101 个请求直接被拒绝；
下游服务 1 秒内异常数超过 20，
触发熔断 10 秒，
期间直接返回兜底数据"系统繁忙，请稍后再试"。

五、注意事项：
1. 规则支持推模式（控制台 → Nacos → Sentinel），
实现动态下发、实时生效；
2. 限流阈值要基于压测数据设定，
避免误伤正常流量；
3. 降级兜底方法要与业务隔离，
保证快速返回。

六、前置概念：
熔断：连续失败达到阈值后主动"断电"，
快速失败保护系统，
类似家用电器的保险丝，
一段时间后自动恢复尝试。

分布式配置中心的作用和实现原理？
配置中心Nacos Config

一、定义：
分布式配置中心是一个统一管理所有微服务配置的服务端组件，
常见实现有 Nacos Config、Spring Cloud Config + Bus。

二、作用：
把配置从代码中剥离出来集中管理，
支持多环境隔离、配置热更新、版本回滚，
修改配置无需重启服务。

三、工作原理：
核心角色有三个：配置服务端、客户端、变更通知，
流程分四步。

  • 1. 配置存储：
    配置保存在配置中心（Nacos 存于 MySQL，Config 存于 Git 仓库），
    按 DataId、Group、Namespace 三级隔离。
  • 2. 客户端拉取：
    服务启动时从配置中心拉取配置，
    本地会缓存一份，
    防止配置中心宕机时服务无法启动。
  • 3. 动态刷新：
    Nacos 客户端每 10 秒轮询 + 服务端 UDP 推送，
    感知配置变更后更新本地缓存，
    通过 @RefreshScope 重新注入 Bean。
  • 4. 广播通知（Config + Bus）：
    Spring Cloud Bus 基于消息队列广播"配置已变更"事件，
    所有实例同时刷新配置。

四、示例：
把数据库连接池大小配置放到 Nacos，
线上想调整连接数，
直接在控制台修改并发布，
所有服务 10 秒内自动生效，
无需逐个重启。

五、注意事项：
1. 配置中心是高危依赖，
必须做高可用集群部署；
2. 敏感配置（密码、密钥）需加密存储；
3. 配置变更要有变更记录和版本回滚能力。

六、前置概念：
配置热更新：运行时动态修改配置并立即生效的能力，
本质是"配置变更 → 监听通知 → Bean 重建"的过程。

链路追踪（Sleuth + Zipkin）的原理？
链路追踪排障

一、定义：
链路追踪是记录一次请求从入口到出口、跨越所有服务调用过程的技术，
Sleuth 负责生成和传递追踪信息，
Zipkin 负责收集和可视化展示。

二、作用：
在微服务架构中快速定位"请求到底卡在哪个服务"，
排查慢请求、分析依赖关系、统计各服务耗时。

三、工作原理：
核心模型有两个：Trace（追踪）和 Span（跨度），
流程分三步。

  • 1. 生成 TraceId / SpanId：
    请求进入系统时生成全局唯一的 TraceId，
    每次跨服务调用生成新的 SpanId，
    并记录父 SpanId 形成树状调用链。
  • 2. 透传上下文：
    TraceId 和 SpanId 通过 HTTP 请求头（如 X-B3-TraceId）传递给下游服务，
    保证整条链路使用同一个 TraceId。
  • 3. 收集上报：
    每个服务把 Span 数据（开始时间、耗时、标签）异步上报给 Zipkin，
    Zipkin 汇总后按 TraceId 串联成完整调用链，
    在 Web UI 上可视化展示。

四、示例：
一次下单请求 TraceId=abc123，
经过 Gateway（耗时 10ms）→ 订单服务（耗时 200ms）→ 库存服务（耗时 1500ms），
在 Zipkin 界面能看到库存服务耗时最长，
立刻定位到性能瓶颈。

五、注意事项：
1. 采样率默认 10%，
生产环境按需调整，
全量采样会带来额外开销；
2. 异步线程、消息队列场景需手动传递 TraceId，
否则链路会断裂。

六、前置概念：
Trace 与 Span：Trace 是一条完整请求链路，
Span 是链路上的每一次调用，
多个 Span 通过父子关系组成一条 Trace，
类似一棵树。

Spring Cloud 和 Dubbo 有什么区别？
对比高频

一、定义：
Spring Cloud 是一整套微服务解决方案全家桶，
Dubbo 是阿里巴巴开源的 RPC 服务调用框架。

二、作用：
两者都用于解决服务之间的调用与治理，
但侧重点不同：
Spring Cloud 覆盖注册、配置、网关、追踪全链路，
Dubbo 专注高性能服务调用。

三、核心区别：

  • 通信协议：
    Dubbo：RPC，二进制传输（Hessian2 序列化），
    性能高、传输体积小。
    Spring Cloud：HTTP + JSON（RESTful），
    通用性好、跨语言。
  • 负载均衡：
    Dubbo：客户端负载均衡，
    支持随机、轮询、一致性哈希等。
    Spring Cloud：Ribbon/LoadBalancer 客户端负载均衡。
  • 生态能力：
    Spring Cloud：注册中心、配置中心、网关、链路追踪全家桶。
    Dubbo：需配合 Zookeeper/Nacos 做注册，
    与 Spring Cloud Alibaba 组合后能力补齐。
  • 性能：
    Dubbo 底层 TCP 长连接 + NIO，
    性能更高；
    Spring Cloud 每次 HTTP 短连接，
    性能略低但开发简单。
  • 跨语言：
    Spring Cloud 的 HTTP 协议天然跨语言；
    Dubbo 主要面向 Java 生态。

四、选型建议：
1. 对性能要求高、内部 Java 服务 → 选 Dubbo；
2. 追求生态完整、需要网关/配置/追踪 → 选 Spring Cloud；
3. 国内很多公司用 Dubbo + Nacos + Sentinel 组合，
兼顾性能与治理能力。

五、注意事项：
1. Dubbo 3.x 已支持应用级注册和 Triple 协议，
可与 Spring Cloud 融合；
2. 面试重点不是"谁更好"，
而是结合场景说清各自优劣。

六、前置概念：
RPC（远程过程调用）：像调用本地方法一样调用远程服务的技术，
屏蔽网络通信细节，
与 HTTP 相比性能更高，
但通常要求同语言生态。
