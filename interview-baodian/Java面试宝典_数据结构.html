什么是 Cuckoo Filter（布谷鸟过滤器）？
概率型数据结构哈希

1. 定义：

Cuckoo Filter（布谷鸟过滤器）是一种概率型数据结构，由 Fan 等人在 2014 年提出，常被视作 Bloom Filter 的替代方案。它最突出的特点是原生支持删除操作，同时能在较低的误判率下保持不错的空间效率。

2. 工作原理：

🐦 Cuckoo Filter 基于"布谷鸟哈希"（Cuckoo Hashing）设计，可以把它想象成一个特殊的哈希表，里面存的不是原始数据，而是数据的指纹（一个短哈希值）。

  • 两个候选位置：
    每个元素通过哈希计算，会得到两个可能的桶位置。
  • 指纹存储：
    元素本身不存进去，只存一个短小的"指纹"（比如 8 位或 16 位）。
  • 踢出机制：
    插入时如果两个桶都满了，它会随机踢走一个已有的指纹，让这个指纹去它自己的另一个位置。这个过程就像布谷鸟把别的鸟蛋踢出巢一样，可能连锁触发，直到找到空位。

3. Redis 中的 Cuckoo Filter（RedisBloom 模块）：

命令以 CF. 开头：

  • 添加：
    CF.ADD key item 或 CF.INSERT key [CAPACITY cap] ITEMS item...。
  • 查询：
    CF.EXISTS key item 或批量 CF.MEXISTS key item...。返回 1 表示可能存在，0 表示一定不存在。
  • 删除：
    CF.DEL key item，这是它区别于 Bloom Filter 的关键操作。

4. ⚠️ 需要注意的"坑"：

虽然设计上 Cuckoo Filter 号称没有假阴性（即已插入的元素一定查得到），但实际的工程实现中，在高负载或特定哈希冲突下，可能会出现假阴性。有研究指出，在过滤器接近满载时，部分实现会因踢出机制和哈希截断的相互作用，导致本该存在的元素查不到。所以，如果业务上不允许漏判，使用前最好针对具体实现做测试验证。

什么是布隆过滤器（Bloom Filter）？
概率型数据结构高频

1. 定义：

布隆过滤器（Bloom Filter）是 1970 年由 Burton Howard Bloom 提出的一种概率型数据结构，由一个很长的位数组和若干个哈希函数组成，用来判断一个元素是否在集合中。

它的判断结果是"概率性"的：

  • 说不存在，就一定不存在（无假阴性）。
  • 说存在，只是可能存在（有假阳性，即误判率）。

2. 工作原理：

布隆过滤器由一个长度为 m 的位数组（初始全 0）和 k 个相互独立的哈希函数组成，每个哈希函数都能把元素映射到 [0, m-1] 范围内的某个下标。

  • 插入流程：
    将元素 x 依次经过 k 个哈希函数，得到 k 个下标 h1(x)、h2(x)、…、hk(x)，把位数组中这 k 个位置全部置为 1。如果某个位置原本就是 1，保持不变（位只能从 0 变 1，不能变回 0）。
  • 查询流程：
    同样计算 k 个下标并检查对应位：
    只要任意一位为 0 → 一定不存在（若元素插入过，这些位必然都已是 1）；
    如果全部为 1 → 可能存在，因为这些位可能是其它元素各自"凑"出来的，这就是假阳性（误判）的来源。
  • 误判率与参数关系：
    位数组越大（m 越大）、哈希函数个数 k 选取合适，误判率越低；插入元素越多（n 越大），位数组越"满"，误判率越高。近似公式：误判率 p ≈ (1 - e^(-kn/m))^k。
    工程上通常按预期元素量 n 和目标误判率 p 反推出所需的 m 和 k（如 m = -n·lnp / (ln2)²，最优 k ≈ (m/n)·ln2）。
  • 为什么用多个哈希函数：
    单个哈希函数冲突率高；多个独立哈希函数要求所有位同时"撞车"才误判，概率大幅降低。工程上常用双重哈希（Double Hashing）模拟 k 个函数：hi(x) = h1(x) + i·h2(x)，只算两次哈希即可。

3. 核心特点：

  • 空间效率极高：
    不存储元素本身，只存比特位，比 HashMap 等结构节省几十倍空间。
  • 查询时间恒定：
    O(k)，k 为哈希函数个数（通常个位数），与数据量无关。
  • 不支持删除：
    位数组的一个位可能被多个元素共享，直接置 0 会影响其它元素。想支持删除需用计数布隆过滤器（Counting Bloom Filter）或改用 Cuckoo Filter。
  • 存在误判率：
    由位数组大小 m、哈希函数个数 k、已插入元素数 n 共同决定；装载越满误判率越高。

4. 使用示例（Redis RedisBloom 模块）：

  • 添加：
    BF.ADD key item 或批量 BF.MADD。
  • 查询：
    BF.EXISTS key item，返回 1 表示可能存在，0 表示一定不存在。
  • 创建时指定参数：
    BF.RESERVE key 0.001 1000000（误判率 0.1%、预计 100 万元素）。

Java 侧可用 Guava 的 BloomFilter：

// Guava 示例 BloomFilter<String> filter = BloomFilter.create( Funnels.unencodedCharsFunnel(), 1000000, 0.001); filter.put("hello"); filter.mightContain("hello"); // true（可能存在）

5. 典型应用场景：

  • 缓存穿透防护：
    请求先过布隆过滤器，不存在的 Key 直接拦截，不打到数据库。
  • 爬虫 URL 去重、垃圾邮件/黑名单过滤、推荐系统已读去重。

6. ⚠️ 注意事项：

  • 误判率需提前评估并预留足够空间，接近满载时误判率急剧上升，应重建或扩容。
  • 不支持删除，元素过期场景要考虑定期重建或改用 Cuckoo Filter。
  • 哈希函数需相互独立且分布均匀（工程上常用双重哈希模拟 k 个函数）。
  • 它只能做"存在性判断"，不能取出原始元素，不能遍历。

什么是堆？什么情况下要用堆？
堆高频

一、什么是堆

堆（Heap）是一种特殊的树形数据结构：它首先是一棵完全二叉树，其次树上任意节点都要满足「堆序性质」——父节点的值与子节点的值有固定的大小关系。按关系方向分两种：

  • 大顶堆（Max-Heap）：每个节点的值 ≥ 其子节点的值 → 沿着任意路径从上往下值递减 → 堆顶（根节点）就是全局最大值
  • 小顶堆（Min-Heap）：每个节点的值 ≤ 其子节点的值 → 堆顶就是全局最小值

注意两个关键点：

  • 堆序只约束「父 vs 子」，不约束左右兄弟之间的大小——左子树和右子树谁大谁小完全无序，所以堆无法按顺序遍历，也不能高效查找任意元素
  • 堆的有序性是「局部」的（只保证堆顶是极值），不像二叉搜索树那样「全局有序」

存储实现：用数组，不用指针。因为完全二叉树的节点是连续排列的，可以用下标直接算出父子关系，不需要 left/right 指针：

  • 下标 i 的左子 = 2i+1，右子 = 2i+2，父节点 = (i-1)/2
  • 好处：内存紧凑、缓存友好、省掉每个节点两个指针的开销；Java 的 PriorityQueue 内部就是一个 Object[]

两个核心动作（维持堆序性质的手段，面试常追问）：

  • 上浮 siftUp：新元素放到数组末尾，若比父节点大（大顶堆）就和父节点交换，一路向上直到合法 → 插入用
  • 下沉 siftDown：堆顶被取走后，把末尾元素搬到堆顶，与较大的子节点交换，一路向下直到合法 → 删堆顶用
操作复杂度说明
取最值O(1)直接读堆顶，这是堆存在的唯一意义
插入O(log n)放末尾后「上浮」siftUp
删除堆顶O(log n)末尾元素换到堆顶后「下沉」siftDown
建堆O(n)从最后一个非叶子节点向前依次下沉
查找任意元素O(n)堆只保证堆顶有序，其余无序

二、什么情况下要用堆：需要「动态、反复地取最值」

关键词是动态——数据一直在增删，而你要不断拿当前的最大/最小值。如果数据是静态的，直接排序一次更快。

  • 优先队列：Java PriorityQueue 就是小顶堆；任务按优先级出队
  • TopK 问题：求最大的 K 个 → 维护大小为 K 的小顶堆，新元素比堆顶大就替换，时间 O(n log K)
  • 数据流中位数：一个大顶堆放左半、一个小顶堆放右半，两边平衡
  • 堆排序：O(n log n)，原地、最坏也是 O(n log n)（对比快排最坏 O(n²)）
  • 图算法优化：Dijkstra、Prim 用堆取当前最短/最小边
  • 定时任务：DelayQueue 按到期时间排堆；海量定时任务则升级为时间轮

三、为什么不用别的结构（选型对比）

方案取最值插入问题
有序数组O(1)O(n)每次插入都要搬元素
无序数组O(n)O(1)取最值要全扫
平衡树O(log n)O(log n)功能过剩、常数大、有旋转开销
堆O(1)O(log n)只关心最值时的最优解

四、局限

堆只保证堆顶有序，无法按顺序遍历全部元素（要排序得反复弹出，O(n log n)）；也不能随机查找、删除中间元素（O(n)）。需要有序遍历就用 TreeMap。

五、补充：什么是完全二叉树

完全二叉树（Complete Binary Tree）的定义：除最后一层外，每一层的节点都填满；最后一层的节点必须从左到右连续排列，不允许出现空洞。

  • 满二叉树（Full/Perfect）：每一层都填满，是完美形态；满二叉树一定是完全二叉树，反之不成立
  • 完全二叉树：只要求最后一层"靠左对齐"，可以缺右边几个节点
  • 反例：最后一层跳过左边空位、先填了右边 → 不是完全二叉树

堆为什么非要选完全二叉树？

  • 能用数组存：节点连续排列，父子关系可以用下标公式（2i+1 / 2i+2 / (i-1)/2）算出来，不需要指针，也不浪费数组空间——如果有空洞，数组中间就得留空位
  • 高度必然是 O(log n)：n 个节点的完全二叉树高度就是 ⌊log₂n⌋，不会退化，这直接保证了插入、删除的 O(log n)
  • 对比普通二叉树：如果插入顺序不巧，普通二叉树可以退化成一条链（高度 n），堆序性质就白设了

所以「完全二叉树 + 堆序性质」两者缺一不可：前者保证了数组存储和 O(log n) 高度，后者保证了堆顶是极值。

什么是红黑树？为什么 TreeMap、HashMap 要用它？
红黑树高频

一、什么是红黑树

红黑树是一种自平衡的二叉搜索树：每个节点带红/黑颜色，靠颜色规则 + 旋转把树高度维持在 O(log n)。

五条性质（必须背）：

  • ① 节点非红即黑
  • ② 根节点是黑色
  • ③ 所有 NIL 叶子节点是黑色
  • ④ 红色节点的两个子节点必须是黑色（不能有连续的红色）
  • ⑤ 任一节点到其所有后代叶子的路径上，黑节点数量相同

性质 ④ + ⑤ 组合出的结论：最长路径 ≤ 2 × 最短路径 → 树高被压到 O(log n)，不会退化成链表。

失衡时通过变色 + 左旋 / 右旋修复，插入最多 2 次旋转，删除最多 3 次。

二、为什么 TreeMap 用它

  • TreeMap 要求 Key 有序（支持 firstKey/lastKey/subMap/范围查询），哈希表做不到
  • 普通二叉搜索树在有序插入时会退化成链表（O(n)），红黑树保证 O(log n)
  • 相比 AVL 树：AVL 平衡更严格、查询略快，但插入删除旋转更多；TreeMap 是读写混合场景，红黑树综合更优（这也是 JDK 选它的原因）

三、为什么 HashMap 也要用它

  • 哈希冲突严重时，同一个桶内的链表会退化成 O(n) 查找（极端情况可被构造为拒绝服务攻击）
  • JDK 8 起：链表长度 ≥ 8 且容量 ≥ 64 时转成红黑树，查找从 O(n) 降到 O(log n)；缩回 6 时转回链表
  • 用树而不用 AVL：桶内节点数通常很少，红黑树「旋转少、调整代价低」更适合频繁增删
  • 注意：HashMap 里的树节点按 hash 值排序，仍然不保证整体有序，只是把桶内查找变快

什么是 BitMap（位图）？有什么用？
BitMap海量数据

一、什么是 BitMap

用一个 bit（0/1）表示「某个数字是否存在」，而不是用 int/long 存这个数字本身。一个 long 是 64 bit，就能标记 64 个数字。

实现：底层是 long[]，对数字 num：

  • 定位在第几个 long：num >>> 6（等价于 num / 64）
  • 定位 long 内的第几位：num & 63（等价于 num % 64）
  • 置位 |=、清位 &= ~、判断 &，全部是 O(1)

二、有什么用：海量整数的「判重 / 排序 / 统计」

场景用法
海量数据去重40 亿个 int 去重判重，遍历时置位，已置位即为重复
O(n) 排序全部置位后按 bit 顺序扫描输出，天然有序（值域小时比快排快）
用户签到 / 活跃统计Redis SETBIT/BITCOUNT，一年 365 天只需 46 字节
布隆过滤器底座布隆过滤器本质就是「多个哈希函数 + 一个 BitMap」
文件/块去重、权限位Linux 文件权限、磁盘块位图

三、为什么用它：空间碾压其他方案

方案40 亿个整数占用说明
int 数组约 16 GB每个数 4 字节，还得去重
HashSet更大（含哈希表开销）单条 Entry 几十字节
BitMap约 500 MB40 亿 bit，1 bit/数，压缩 32 倍

四、局限与替代

  • 只能表示非负整数；负数要先偏移映射
  • 值域必须有限且不能过大（值域 100 亿就是 1.25 GB）
  • 稀疏数据浪费严重（只有 3 个数但值域 1 亿）→ 换 RoaringBitmap（分块压缩）或布隆过滤器
  • 不支持取出原始元素，只能判断存在性

什么是跳表（SkipList）？为什么 Redis 的 zset 用它不用红黑树？
跳表高频

一、什么是跳表

跳表 = 有序链表 + 多层索引。底层是一条存全部元素的有序链表，上面每层都是下一层的「抽样索引」，越往上越稀疏，形成「地铁快线 + 慢线」的效果。

查找过程：从最高层出发，能往右就往右；右边比目标大就下沉一层继续，直到最底层命中。类似二分，平均 O(log n)。

  • 节点层数随机生成（通常 1/2 概率升层），不需要任何平衡计算
  • 插入 = 先查找到位置 → 改指针 → 随机决定要不要向上建索引
  • 删除 = 查到后改指针，层层摘除

二、为什么 Redis zset 用跳表而不用红黑树

维度跳表红黑树
实现复杂度简单，核心就是链表 + 随机层数复杂，插入删除要处理多种旋转/变色情形
范围查询（zset 核心）找到起点后沿底层链表顺序遍历，天然高效需要中序遍历 + 回溯，实现繁琐
并发/局部修改只改动局部指针，锁范围小旋转可能波及全局结构
代码可维护性无旋转，不易出 bug边界情况多，易错
内存略多（索引层）每个节点 2 指针 + 颜色位

一句话：zset 最高频的操作是 ZRANGE 范围查询和 ZRANK 排名，跳表在「有序 + 范围遍历」上比红黑树更简单直接，Redis 作者 antirez 也明确说过这是为「实现简单、范围查询方便」而做的取舍。

三、为什么不用哈希表 / 数组

  • 哈希表：无法按 score 排序、无法范围查询（zset 要 ZRANGEBYSCORE）
  • 数组：插入删除 O(n)，zset 高频增删不可接受
  • zset 实际是双结构：dict（member→score，O(1) 查分数）+ skiplist（按 score 有序，范围查询）

什么是时间轮？为什么 Kafka、Netty、Dubbo 都用它？
时间轮中间件

一、什么是时间轮

时间轮是一个环形数组 + 循环指针构成的定时器数据结构：把时间切成固定刻度（如 1 秒一格），指针每格走一次，走到哪个格子就执行那个格子里的任务。

  • 槽（slot）：数组每个元素是一个时间刻度，槽内用双向链表挂同一时刻到期的任务
  • 指针（tick）：每个最小时间单位前进一格，取模回到起点
  • 圈数（round）：任务延迟超过一整圈的，记录需要多转几圈；指针经过时圈数减 1，减到 0 才执行
  • 多层时间轮（Kafka）：秒轮、分轮、时轮分层，类似钟表时针分针，用少量格子表达很长的时间范围

二、为什么用它：O(1) 代替 O(log n)

每任务一个线程 TimerO(1)难-线程爆炸，资源不可控

海量定时任务场景（几十万连接的心跳检测、请求超时、订单关单），时间轮的优势是增删任务都 O(1)、且没有堆的锁竞争，指针推进只处理当前格子的任务。

三、为什么 Kafka、Netty、Dubbo 都用它

  • Netty：HashedWheelTimer 管理连接空闲检测、读写超时，单线程推进指针，几十万连接也只是一次链表遍历
  • Dubbo：失败重试、请求超时用时间轮调度（默认 HashedWheelTimer）
  • Kafka：分层时间轮（TimingWheel）处理延迟生产、延迟拉取、会话超时，可表达任意长度延迟
  • Linux 内核：定时器也采用时间轮思想

四、局限

  • 精度取决于最小刻度（如 100ms），不适合毫秒级精确调度
  • 单层轮的延迟范围受格子数限制 → 需要多层轮或圈数机制
  • 任务执行时长会阻塞指针推进 → 耗时任务要丢到业务线程池执行
  • 一般定时场景（任务量小）用 DelayQueue 反而更简单
