Netty 的线程模型和零拷贝？
Netty高频

一句话概括

Netty 采用Reactor 主从模型管理线程，用零拷贝减少数据在内核态与用户态之间的搬运次数，这两点共同撑起了它的高性能。

定义

Reactor 主从模型：

一种事件驱动 + IO 多路复用的网络编程模型。

Boss 线程专职接收连接，Worker 线程专职处理已连接通道的读写事件。

零拷贝（Zero Copy）：

在数据传输过程中，减少甚至消除数据在内核缓冲区与用户缓冲区之间的来回拷贝，让数据尽可能"直达"目的地。

作用

  • 主从模型：
    用极少量线程支撑海量并发连接，避免"一个连接一个线程"带来的内存和上下文切换开销。
  • 零拷贝：
    降低 CPU 占用、减少内存带宽消耗、提升文件/网络传输吞吐量。

原理

线程模型——Reactor 主从多线程

  • Boss Group：
    通常只配 1 个 NioEventLoop，专门做 Accept（监听端口、接收新连接），然后把新 Channel 注册到 Worker Group 的某个 EventLoop 上。
  • Worker Group：
    通常配 CPU 核心数 × 2 个 NioEventLoop，每个 EventLoop 绑定一个 Selector + 一条线程，负责这条线程上所有 Channel 的读写事件。
  • 关键约束：
    一个 Channel 生命周期内只绑定在一个 NioEventLoop 上，所以 Channel 的读写操作天然是单线程的，不需要额外加锁。

零拷贝三种实现

  • FileRegion.transferTo()：
    操作系统级 DMA 拷贝，数据从磁盘直接到网卡缓冲区，不经过用户空间。
  • CompositeByteBuf：
    逻辑上将多个 ByteBuf"拼"在一起，物理上数据不需要拷贝到新数组。
  • Unpooled.wrappedBuffer()：
    包装已有字节数组，只是换了个"壳"，不产生新的内存拷贝。

举例讲解

把 Netty 比作一家高级餐厅：

  • Boss Group 是迎宾员，只站在门口迎接客人（接收连接），然后带客人入座，把客人交给负责该区域的服务员。
  • Worker Group 是服务员，每人负责一片区域的多张桌子（一个线程管理多个 Channel）。
    一张桌子自始至终只由一个服务员服务（Channel 绑定在一个 EventLoop 上），所以不会出现两个服务员同时给同一桌点菜的情况（线程安全）。
  • 零拷贝 就像餐厅用了"智能传送带"，后厨炒好菜后，菜盘不经过服务员的手推车（用户空间），而是直接通过传送带从厨房窗口送到客人桌上（内核 DMA 直达网卡），省掉了服务员来回搬运的中间环节，上菜速度自然快得多。

面试速记口诀

"一主多从、一个 Channel 一个 EventLoop；

零拷贝三种套路——transferTo 直接传、Composite 拼着用、wrapped 包个壳。

"

Netty 解决 TCP 粘包/拆包方案？
Netty粘包

一句话概括

TCP 是面向流的协议，本身没有消息边界，所以发送方多次写入的数据可能被接收方一次性读完（粘包），也可能一个大消息被分多次才读完（拆包）。

Netty 提供了多种解码器（Decoder）在 ChannelPipeline 里自动识别消息边界。

定义

粘包：

发送方连续发送多条小消息，TCP 协议栈为了提升效率会把它们合并到一个 TCP 报文中发出，接收方一次 read 就读到了多条消息的内容。

拆包：

发送方发送了一条大消息，但 TCP 报文有大小限制（MSS），这条消息被拆成多个报文发送，接收方需要多次 read 才能拼出完整消息。

作用

如果不对粘包/拆包做处理，接收方拿到的字节流是"糊成一团"的，无法区分哪里是一条完整消息的结束、下一条消息的开始。

解码器的作用就是在字节流到达业务 Handler 之前，先把"散装"的字节流切成一条条完整的消息帧。

原理与方案对比

解码器核心原理适用场景生活类比
FixedLengthFrameDecoder按固定字节长度切分消息长度固定，如心跳包每页纸刚好印 100 个字，读到 100 字就是一页
LineBasedFrameDecoder按换行符 \n 或 \r\n 切分文本协议，如 Redis 协议、SMTP一句话一行，看到回车就知道这句讲完了
DelimiterBasedFrameDecoder按自定义分隔符切分消息以特定字符结尾，如 CSV逗号分隔表格，看到逗号就知道一个单元格结束
LengthFieldBasedFrameDecoder消息头包含"长度字段"，先读长度再按长度读数据二进制协议，企业级最常用快递单上写了包裹尺寸，先看清尺寸再拆开
自定义协议魔数 + 版本号 + 长度 + 数据 + 校验和RPC 框架、游戏服务器信封格式统一：特殊暗号 + 页数 + 正文 + 防伪码

举例讲解

想象两个人隔着一根长长的透明水管传纸条：

  • 粘包：
    第一个人连续扔了 3 张纸条进水口，第二个人在水管出口一次捞上来 3 张粘在一起的纸条，分不清哪句话是谁的、从哪里断句。
  • 拆包：
    第一个人写了一张很长的纸条（比如 1000 字），但水管一次只能传 200 字，第二个人分 5 次才捞完，前 4 次都是"没说完的半句话"。

解决办法就是在纸条上做标记：

  • 如果每句话都裁成固定 50 字，捞够 50 字就是一条完整消息 → FixedLengthFrameDecoder。
  • 如果每句话末尾都画一条横线（换行），看到横线就知道这句完了 → LineBasedFrameDecoder。
  • 如果纸条开头写了"本消息共 300 字"，对方先读长度，再按 300 字精确截取 → LengthFieldBasedFrameDecoder（最靠谱，也是 Dubbo、RocketMQ 等框架的首选）。

面试速记口诀

"TCP 粘包拆包是天生缺陷，Netty 五种解码器来补刀——定长、换行、分隔符、长度字段最常用，复杂场景自定义协议。

生产环境首选 LengthFieldBasedFrameDecoder，简单文本用换行，固定长度心跳包用定长。

"
