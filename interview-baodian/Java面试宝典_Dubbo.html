Dubbo 的工作流程和核心组件？
DubboRPC

核心组件：

Provider(服务提供者)、Consumer(消费者)、Registry(注册中心)、Monitor(监控中心)。

调用流程：

  1. Provider向Registry注册服务。
  2. Consumer向Registry订阅服务。
  3. Registry通知Consumer服务列表。
  4. Consumer通过负载均衡选择Provider，直连调用(RPC)。
  5. Monitor统计调用数据。

💡 注册中心可用Zookeeper/Nacos/Redis等。

2
Dubbo 的核心原理和调用流程？
DubboRPC

Dubbo是高性能RPC框架，核心流程：

  1. 注册：

    Provider向Registry注册服务。
  2. 订阅：

    Consumer从Registry订阅服务（拉取+监听变更）。
  3. 调用：

    Consumer通过动态代理（Proxy）发起远程调用→经过Filter链→负载均衡选择Provider→Netty网络传输→Provider反序列化→执行→返回。
  4. 监控：

    Monitor统计调用次数和耗时。

注册中心：

ZooKeeper（默认）、Nacos、Redis、Consul。

Dubbo 负载均衡策略有哪些？
Dubbo负载均衡
  • Random（默认）：

    加权随机，按权重随机。
  • RoundRobin：

    加权轮询。
  • LeastActive：

    最少活跃调用数（处理快的节点分配更多）。
  • ConsistentHash：

    一致性Hash，相同参数的请求始终发到同一Provider。
  • ShortestResponse：

    最短响应时间（Dubbo 2.7+）。

Dubbo 的集群容错策略有哪些？
Dubbo容错
  • Failfast：

    快速失败，立即抛异常。

    适合非幂等写操作。
  • Failsafe：

    失败安全，忽略异常。

    适合写入日志。
  • Failover（默认）：

    失败自动切换重试（默认2次+本机1次=3次）。

    适合幂等读操作。
  • Failback：

    失败自动恢复，后台定时重发。
  • Forking：

    并行调用多个Provider，一个成功即返回。
  • Broadcast：

    广播调用所有Provider，一个失败即失败。

Dubbo 服务暴露和服务引入流程？
Dubbo深入

服务暴露：

  1. Spring容器刷新→ServiceBean.onApplicationEvent→export()。
  2. 服务配置转URL→适配协议(dubbo/http等)→开启Netty服务器监听端口。
  3. 注册到注册中心(ZooKeeper/Nacos)。

服务引入：

  1. ReferenceBean.getObject()→init()。
  2. 连接注册中心→订阅服务→获取Provider列表。
  3. 动态代理生成接口实现类（InvokerInvocationHandler）。

Dubbo 是如何动态感知服务下线的？
注册中心

一句话概括

依赖 Zookeeper 的心跳检测 + Watch 事件通知机制，服务下线后消费端被实时推送通知并剔除本地缓存地址。

流程

  • 服务地址以树形结构维护在 Zookeeper 的 /providers 节点下，每个提供者启动时创建临时节点注册。
  • Zookeeper 通过心跳检测提供端状态，提供者宕机 → 会话过期 → 临时节点自动删除。
  • 消费端启动时用 Watch 机制监听 /providers，子节点变化立即收到事件通知。
  • 消费端收到通知后删除本地缓存的该服务地址，后续请求不再发往故障节点（负载均衡自然将其排除）。

💡 若用 Nacos 注册中心则走客户端心跳上报 + 服务端主动探测（AP 模型），机制不同但效果一致。

Dubbo 的 SPI 和 Java 的 SPI 有什么区别？
SPI高频
对比Java SPIDubbo SPI
加载方式遍历配置文件，全部实现类一次性实例化按名称获取、延迟加载，一次只加载所需实现
资源浪费加载全部实现，耗时浪费按需加载
IOC/AOP不支持扩展点可通过 setter 注入其他扩展点（IOC）、支持包装类增强（AOP）
第三方容器无支持与 Spring Bean 集成
扩展标注无@Adaptive 自适应扩展（按 URL 参数适配）、@Activate 激活扩展

💡 Java SPI 配置在 META-INF/services/，Dubbo SPI 配置在 META-INF/dubbo/，格式为 名称=实现类全限定名，支持键值对按名取实现。

Dubbo 的整体分层是怎样的？
架构

三大层次（官方 10 层的归并）

  • Business 业务层：使用者提供接口、实现与配置，Dubbo 不关心业务内容。
  • RPC 层（核心）：封装远程调用全过程 —— 代理（Proxy）、注册发现（Registry）、路由、负载均衡（Cluster）、协议（Protocol）、交换（Exchange）。
  • Remoting 层：封装网络传输（Netty）与数据转换（序列化）。

10 层细分：Service、Config 两层属 API 层面向使用者；其余各层属 SPI 层，供扩展者二次开发。分层让"业务无关的 RPC 能力"与"业务本身"彻底解耦，各层都可被 SPI 替换实现。

怎么设计一个 RPC 框架？
设计题高频

核心模块清单

  • 注册中心：管理消费者与提供者的节点信息，双方注册/订阅，地址变更推送（ZK/Nacos）。
  • 代理层：让调用方像调本地方法一样发起远程调用（JDK 动态代理/CGLIB）。
  • 负载均衡 + 路由：provider 集群时选节点（随机/轮询/一致性 Hash），支持自定义路由规则（灰度、机房就近）。
  • 通信 + 序列化：网络传输模块（Netty NIO）+ 协议设计（消息头含请求 ID 支持异步收发）+ 序列化（Hessian/Protobuf/Kryo）。
  • 集群容错：失败重试、快速失败、降级兜底。
  • 治理增强：监控上报、超时控制、泛化调用、配置管理等。

💡 面试时按"调用链路"讲：动态代理拦截 → 服务发现选节点 → 负载均衡 → 序列化 → Netty 发送 → 服务端反序列化 → 反射调用 → 结果回传。
