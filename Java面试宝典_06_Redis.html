Redis 有哪些数据类型？各自使用场景？
数据类型高频
  • String：缓存、计数器、分布式锁、Session共享。
  • Hash：存储对象(如用户信息)、购物车。
  • List：消息队列(左进右出)、最新列表(朋友圈时间线)。
  • Set：标签、共同好友、随机抽奖(srandmember)。
  • Sorted Set(ZSet)：排行榜、延时队列、带权重的集合。
  • 高级：Bitmap(签到统计)、HyperLogLog(UV统计)、GEO(附近的人)、Stream(消息队列)。

3
缓存穿透、缓存击穿、缓存雪崩是什么？如何解决？
缓存问题高频
  • 缓存穿透：查不存在的数据，缓存和DB都没有→直接打DB。
    解决：布隆过滤器、缓存空值(短过期)、参数校验。
  • 缓存击穿：热点key过期瞬间，大量请求打到DB。
    解决：互斥锁、逻辑过期+异步刷新、永不过期。
  • 缓存雪崩：大量key同时过期或Redis宕机。
    解决：过期时间加随机值、多级缓存、限流降级、Redis集群高可用。
4
如何用 Redis 实现分布式锁？
分布式锁高频

核心命令：SET key value NX PX timeout

  • 加锁：SET lock_key uuid NX PX 30000（原子操作）。
  • 解锁：Lua脚本先判断value(uuid)是否是自己，是则DEL（保证原子性+防误删）。
  • 锁续期：看门狗机制(Redisson)，定时续期。

💡 RedLock算法：多个独立Redis节点，过半加锁成功才算成功，提高可靠性。

5
Redis 的内存淘汰策略有哪些？
内存淘汰
  • noeviction：不淘汰，内存满时写操作报错（默认）。
  • allkeys-lru：所有key中淘汰最近最少使用的。
  • volatile-lru：有过期时间的key中淘汰LRU。
  • allkeys-lfu：所有key中淘汰最不经常使用的(Redis 4.0+)。
  • volatile-lfu：有过期时间的key中淘汰LFU。
  • allkeys-random / volatile-random / volatile-ttl

💡 一般推荐allkeys-lru或allkeys-lfu。

6
Redis 主从复制的原理？
主从集群
  1. 全量复制：Slave首次连接→Master fork子进程生成RDB→发送RDB→Slave加载→发送缓冲区命令。
  2. 增量复制：Master的写命令实时同步到Slave(基于replication backlog缓冲区)。
  3. 断线重连：Redis 2.8+支持PSYNC，通过replication offset判断是否需要全量复制。
7
Redis 哨兵（Sentinel）机制？
哨兵高可用

Sentinel是高可用方案，负责：

  • 监控：定期PING Master/Slave，判断是否存活。
  • 自动故障转移：Master挂了，选举新Master(投票机制)。
  • 通知：将新Master信息通知客户端和Slave。

💡 Sentinel至少3个实例（奇数），防止脑裂。主观下线→客观下线(quorum个哨兵确认)。

8
Redis Cluster（集群模式）原理？
集群分片
  • 分片方式：16384个哈希槽(hash slot)，CRC16(key) % 16384定位槽→槽分配到不同节点。
  • 高可用：每个主节点可配多个从节点，主挂掉从接管。
  • 去中心化：节点间Gossip协议通信，无中心代理。
  • 限制：不支持多key跨槽操作(除非用HashTag)、批量操作需在客户端合并。
9
Redis 为什么这么快？
性能高频
  1. 纯内存操作：数据都在内存，纳秒级访问。
  2. 单线程模型：避免上下文切换和锁竞争(6.0引入多线程IO但执行命令仍单线程)。
  3. IO多路复用：epoll监听多个连接，单线程处理大量并发。
  4. 高效数据结构：SDS简单动态字符串、跳表、压缩列表等。

💡 Redis 6.0的多线程只用于网络IO读写，命令执行仍是单线程。

10
Redis 过期键删除策略？
过期内存

惰性删除 + 定期删除

  • 惰性删除：访问key时检查是否过期，过期则删除。节省CPU但浪费内存。
  • 定期删除：每100ms随机抽取部分key检查并删除。平衡CPU和内存。

💡 过期+内存淘汰策略共同保证内存不会无限增长。

布隆过滤器（Bloom Filter）的原理和应用？
布隆过滤器高级

原理：位数组 + 多个Hash函数。元素加入时，多个Hash位置置1；查询时所有位置为1则可能存在。

  • 特性：不存在一定准确，存在可能有误判。
  • 应用：防止缓存穿透、垃圾邮件过滤、URL去重。
  • Redis实现：RedisBloom模块 或 基于bitmap+多个hash函数。

Redis 如何保证数据一致？（缓存和数据库一致性）
一致性实战
  • 先删缓存再更新DB → 并发下可能读到旧数据。
  • 先更新DB再删缓存 → 推荐，但需处理删除失败(重试/订阅binlog)。
  • 延迟双删：先删缓存→更新DB→延迟再删一次。
  • Canal监听binlog → 异步更新缓存，最终一致性。

💡 大多数场景容忍短暂不一致，用过期时间兜底。

14
Redis 的 pipeline 是什么？
优化基础

Pipeline(管道)：将多个命令打包发送，一次性接收所有结果，减少RTT(网络往返时间)。

  • 不是原子操作，命令之间可能插入其他客户端的命令。
  • 适合批量操作但不需要事务的场景。
  • 与事务(MULTI/EXEC)的区别：事务保证原子性，pipeline只减少网络开销。
15
Redis 分布式锁如何实现？有哪些问题？
分布式锁高频

SETNX + EXPIRE：原子设置锁和过期时间。SET lock_key value NX EX 30。

Redisson方案（RedLock）：自动续期看门狗（watch dog），每10s续期到30s。

核心问题：

  • 锁释放：只能释放自己的锁（value用UUID校验，Lua脚本原子释放）。
  • 锁续期：业务执行超时，锁被自动释放→其他线程获取锁→并发问题。
  • 主从切换：主宕机，锁数据未同步到从→新主上有两个线程持有锁。RedLock方案缓解。
16
RedLock 算法的原理和争议？
RedLock深入

RedLock（Redis官方分布式锁算法）：

  1. 客户端向N个独立Redis节点（通常5个）依次请求加锁。
  2. 若在超时时间内超过半数(N/2+1)节点成功→获取锁。
  3. 锁有效时间 = 初始TTL - 获取锁耗时。
  4. 失败则向所有节点发起释放。

争议（Martin Kleppmann）：GC pause、时钟跳跃、网络延迟可能导致两个客户端同时认为持有锁。Redis作者Antirez回应：实际场景中极低概率。

17
Redis 哨兵（Sentinel）模式原理？
Sentinel高频

Sentinel是Redis高可用方案，监控+通知+自动故障转移。

功能：

  • 监控：持续检查Master和Slave是否正常（PING）。
  • 通知：节点故障时告警。
  • 自动故障转移：Master宕机→选出新Master→其他Slave切换复制新Master→通知客户端。

选主过程：多个Sentinel选举一个Leader（Raft共识）→Leader选择最优Slave（优先级→复制偏移量→runid）→提升为Master。

18
Redis Cluster 原理和槽位分配？
Cluster高频

Redis Cluster是去中心化的分布式方案，16384个哈希槽。

  • 槽位分配：CRC16(key)%16384 → 映射到对应节点的槽位。
  • 去中心化：节点间Gossip协议互通状态。
  • MOVED重定向：key不在当前节点，返回目标节点地址，客户端请求新节点。
  • ASK重定向：槽正在迁移中，临时重定向。
  • hash_tag：{user:1}:name，只计算{}内的CRC16，实现多key同槽。

限制：不支持多key跨槽操作、Lua脚本涉及key必须在同一节点。

19
Redis 主从复制原理和过程？
主从复制高频

全量同步（SYNC/PSYNC）：

  1. 从节点发送PSYNC。
  2. 主节点执行BGSAVE生成RDB，同时缓存写命令。
  3. 主节点发送RDB给从节点。
  4. 从节点载入RDB。
  5. 主节点发送缓冲区中的写命令。

增量同步：主节点维护replication backlog缓冲区，从节点断开重连后根据offset增量同步。若offset不在backlog中，则全量同步。

💡 主从同步过程是异步的。

21
Redis 删除策略和内存淘汰策略？
过期删除内存淘汰

过期键删除策略（惰性+定期）：

  • 惰性删除：访问key时检查是否过期，过期则删除。
  • 定期删除：每秒10次，随机抽20个key检查，过期>25%则继续清理。

内存淘汰策略（maxmemory-policy）：

  • noeviction：不淘汰，写报错（默认）。
  • allkeys-lru/lfu：所有key中LRU/LFU淘汰。
  • volatile-lru/lfu：仅过期key中淘汰。
  • allkeys-random：随机。
  • volatile-ttl：淘汰TTL最短的。
22
Redis 单线程为什么还这么快？
性能高频
  • 纯内存操作：数据都在内存，读写速度极快。
  • 单线程避免上下文切换：无锁竞争，无死锁。
  • IO多路复用：epoll/kqueue模型，一个线程处理多个连接。
  • 高效数据结构：SDS（简单动态字符串）、ziplist(7.0已移除)、quicklist等。

💡 Redis 6.0+引入多线程IO（只是网络读写多线程，命令执行仍单线程），进一步提升性能。

23
Redis Pipeline 原理和注意事项？
Pipeline

Pipeline将多个命令打包一次发送，减少RTT（往返时间）。

原理：客户端批量发送→Redis批量执行→批量返回结果。

注意事项：

  • Pipeline中命令不保证原子性（不是事务）。
  • 一次Pipeline命令不宜过多（内存压力），建议拆分为小批次。
  • Cluster模式下，Pipeline命令必须同一节点。
24
Lua 脚本在 Redis 中的使用和原子性？
Lua原子操作

Redis通过EVAL/EVALSHA执行Lua脚本，脚本执行期间其他命令被阻塞→原子性。

使用场景：

  • 原子性校验+操作（如库存扣减）。
  • 分布式锁释放（get+del原子化）。
  • 复杂计算避免多次网络往返。

注意事项：

  • 脚本不要执行太久（阻塞），建议拆分。
  • Cluster模式下脚本涉及的key必须在同一节点（用hash_tag）。
  • 脚本中写操作会引起主从复制。
25
缓存穿透、缓存击穿、缓存雪崩是什么？如何解决？
缓存问题超高频

缓存穿透：查询不存在的数据→缓存无→直接打到DB。

  • 方案：布隆过滤器过滤、缓存空值（短TTL）、接口层校验。

缓存击穿：热点key过期→大量请求同时打到DB。

  • 方案：互斥锁（一个线程查DB更新缓存）、永不过期（逻辑过期+异步更新）。

缓存雪崩：大量key同时过期或Redis宕机→DB压力激增。

  • 方案：过期时间加随机值、限流降级、Redis高可用（集群/哨兵）、多级缓存。
26
如何保证缓存与数据库一致性？（Cache Aside）
缓存一致性超高频

Cache Aside Pattern（旁路缓存）：

  • 读：先读缓存→缓存有则返回→无则读DB→写缓存。
  • 写：先更新DB→再删除缓存（不是更新缓存！）。

为什么不更新缓存而是删除？并发写可能导致缓存和DB不一致，删除缓存最安全。

延迟双删：先删缓存→更新DB→延迟再删缓存。应对读写并发问题。

兜底方案：Canal监听binlog→异步同步缓存。

Redis 的 Bitmap 和 HyperLogLog 应用场景？
高级结构

Bitmap（位图）：按位存储，极省内存。

  • 签到打卡：SETBIT sign:2024:uid 1→SETBIT sign:2024:uid 356 1。
  • 统计在线用户、活跃用户。
  • 布隆过滤器底层。

HyperLogLog：基数统计（去重计数），标准误差0.81%，12KB固定内存。

  • UV统计：PFADD uv:page user_id → PFCOUNT uv:page。
  • 日/月活统计。

💡 数据量大且对精度要求不高时用HyperLogLog，精确去重用Set或Bitmap。

GEO 地理位置的应用原理？
GEO

Redis GEO基于Sorted Set（ZSet）+ GeoHash实现。

  • 经纬度→GeoHash编码（字符串）→作为ZSet的score。
  • GEOADD cities 116.40 39.90 beijing 添加地理位置。
  • GEORADIUS 指定半径内查询。
  • GEODIST 计算两点距离。

应用：附近的人、附近的商家、配送范围计算。

Redis Stream 是什么？和传统MQ有什么区别？
Stream消息队列

Redis 5.0+引入的持久化消息队列，类似Kafka。

特点：

  • 支持消费者组（Consumer Group），类似Kafka的消费组。
  • 消息持久化（AOF/RDB）。
  • 支持ACK和Pending List（确认机制）。
  • 支持范围查询和历史消息回溯。

vs Kafka：

  • Redis Stream更轻量，适合小规模消息。
  • Kafka吞吐量更高、分区机制更强、适合大数据流。
30
Redis 事务（MULTI/EXEC）的特点和局限性？
事务

Redis事务（MULTI→命令队列→EXEC）：

  • 命令顺序执行，中间不插入其他命令（隔离性）。
  • 不支持回滚：某条命令语法错误则不执行，运行时错误只影响该命令。
  • 不支持ACID中的原子性和持久性保证。
  • WATCH实现乐观锁（CAS版本号校验）。

💡 需要真正原子性操作用Lua脚本，或分布式锁+业务逻辑。

31
Redis 热点Key问题如何解决？
热点Key高频

发现：客户端统计、Redis --hotkeys命令、Proxy层统计。

解决方案：

  • 读写分离：热点Key分散到多个从节点读取。
  • 本地缓存：热点数据缓存到JVM本地（Caffeine/Guava）+推模式更新。
  • Key拆分（二级缓存）：hotkey_1→hotkey_1_1, hotkey_1_2...随机读取，分摊压力。
  • 业务降级：限流+熔断+兜底数据。
32
Redis 大Key问题如何排查和优化？
大Key高频

大Key定义：String>10KB，集合元素>1万个。

危害：网络阻塞、慢查询、内存不均、主从同步慢、扩容迁移困难。

排查：redis-cli --bigkeys、MEMORY USAGE key、scan+debug object。

优化：

  • String：压缩（GZIP）或拆分。
  • Hash：拆分多个小Hash，按field取模。
  • List：拆分为多个小List。
  • 大Set/ZSet：用SSCAN/ZSCAN分批处理。
  • 删除时用UNLINK异步删除（Redis 4.0+）。

Redis 6.0/7.0 有哪些重要新特性？
新版本

Redis 6.0：

  • 多线程IO（网络读写多线程）。
  • ACL（访问控制列表），精细化权限管理。
  • RESP3协议，支持更丰富的数据类型返回。
  • SSL/TLS加密通信。
  • 客户端缓存（tracking）。

Redis 7.0：

  • Redis Functions（Lua脚本替代，函数式管理）。
  • ACL改进（key/command权限粒度更细）。
  • Sharded Pub/Sub（分片发布订阅，Cluster下真正分布式）。
  • AOF改进（多部分AOF，RDB时间戳更精确）。
  • MP-MP（多线程分流）改进。

Redis 延时队列如何实现？
延时队列

1. ZSet方式：score=执行时间戳，定时任务ZRANGEBYSCORE获取到期任务。

  • 优点：简单可靠。
  • 缺点：定时轮询有时间间隔。

2. Keyspace Notifications + 过期键：监听key过期事件。

  • 限制：过期事件不一定准时触发（惰性删除+定期删除）。

3. Redisson DelayedQueue：基于ZSet+订阅通知，封装完善的延时队列。

💡 真正的消息延时推荐RocketMQ（支持18个延迟级别）或RabbitMQ DLX。

35
什么是 Redis 多级缓存架构？
多级缓存架构

多级缓存架构从近到远：

  1. L1 本地缓存：Caffeine/Guava Cache，毫秒级，JVM内。
  2. L2 分布式缓存：Redis，毫秒~微秒级。
  3. L3 数据库：MySQL，毫秒~秒级。

更新策略：推模式（DB更新→MQ/Canal→更新Redis→通知应用更新本地缓存）或拉模式（TTL过期后重新加载）。

💡 适合读多写少的场景，写操作多反而增加复杂度。
