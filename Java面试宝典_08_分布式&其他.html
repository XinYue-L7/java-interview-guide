CAP 理论是什么？BASE 理论呢？
分布式高频

CAP：三者最多满足两个

  • C(Consistency)：一致性，所有节点同一时刻数据相同。
  • A(Availability)：可用性，非故障节点正常响应。
  • P(Partition Tolerance)：分区容错性，网络分区时系统仍可工作。

P必须保证，所以实际是CP或AP的选择。Zookeeper→CP，Eureka→AP。

BASE：AP方案的补充

  • BA(Basically Available)：基本可用。
  • S(Soft State)：软状态，允许中间状态。
  • E(Eventually Consistent)：最终一致性。

什么是分布式事务？解决方案有哪些？
分布式事务

分布式事务是指事务的参与者、资源服务器、事务管理器分别位于不同分布式节点上。简单说，一个业务操作需要跨多个服务/数据库完成，且要保证数据一致性。例如：下单（订单服务）→ 扣库存（库存服务）→ 扣余额（账户服务），三步要么全成功、要么全回滚。

与单机事务的核心区别：单机事务靠数据库的 ACID 机制保证；分布式事务中网络不可靠、各节点独立，无法简单套用 ACID，需要额外的协调协议。

常见解决方案：

  • 2PC(两阶段提交)：准备阶段→提交阶段。强一致但性能差、协调者单点。
  • TCC(Try-Confirm-Cancel)：Try预留→Confirm确认→Cancel回滚。最终一致。
  • 本地消息表：本地事务+消息表，定时重试。最终一致。
  • RocketMQ事务消息：半消息+本地事务+回查。最终一致。
  • Seata：阿里分布式事务中间件，支持AT/TCC/Saga模式。

💡 大部分场景用最终一致性方案即可，强一致代价太高。

设计模式高频

TCP 三次握手和四次挥手？
网络高频

三次握手：

  1. Client → Server：SYN=1, seq=x
  2. Server → Client：SYN=1, ACK=1, seq=y, ack=x+1
  3. Client → Server：ACK=1, seq=x+1, ack=y+1

💡 为什么三次？防止旧连接请求到达服务端、确认双方收发能力。

四次挥手：

  1. Client → Server：FIN=1
  2. Server → Client：ACK（Server可能还有数据要发）
  3. Server → Client：FIN=1
  4. Client → Server：ACK → Client等待2MSL

HTTP 和 HTTPS 的区别？HTTPS 加密过程？
网络安全

区别：HTTPS = HTTP + SSL/TLS。端口80→443。HTTP明文，HTTPS加密。

HTTPS加密过程：

  1. Client Hello(支持的加密套件+随机数1)。
  2. Server Hello(选加密套件+随机数2+证书含公钥)。
  3. Client验证证书→生成随机数3→公钥加密→发送。
  4. 双方根据三个随机数生成对称密钥→后续用对称加密通信。

💡 非对称加密(握手)+对称加密(数据传输)，兼顾安全与性能。

限流算法有哪些？
限流算法
  • 计数器固定窗口：固定时间窗口内计数，边界突刺问题。
  • 计数器滑动窗口：将窗口细分，解决边界问题。
  • 漏桶(Leaky Bucket)：恒定速率处理，超出入桶排队/丢弃。平滑但无法应对突发。
  • 令牌桶(Token Bucket)：恒定速率生成令牌，可应对一定突发。最常用(Sentinel/Guava RateLimiter)。

什么是服务雪崩？如何解决？
微服务高频

服务雪崩：一个服务故障→调用方阻塞等待→调用方资源耗尽→级联故障→整个系统崩溃。

解决方案（Hystrix/Sentinel/Resilience4j）：

  • 熔断（Circuit Breaker）：错误率达标→快速失败→定期探测恢复。
  • 降级（Fallback）：备用逻辑（返回默认值/缓存/提示）。
  • 限流（Rate Limiter）：控制请求速率，超过则拒绝。
  • 隔离：线程池隔离/信号量隔离，避免资源争抢。
  • 超时：设置合理超时，快速释放资源。

ZooKeeper 的选举机制（ZAB协议）？
ZK选举

ZAB（ZooKeeper Atomic Broadcast）实现一致性：

Leader选举：

  • 节点状态：LOOKING→LEADING/FOLLOWING。
  • 比较规则：先比Epoch（任期）→再比ZXID（事务ID）→最后比SID（节点ID）。
  • 超过半数投票即当选。

数据同步：Leader将提案Proposal发给Followers→过半ACK→提交。

💡 ZK集群建议奇数台（3/5/7）。

Kafka 如何保证消息不丢失？
Kafka消息队列

三端保证：

  • Producer：acks=all（所有副本确认）+ retries>0 + 幂等性enable.idempotence=true。
  • Broker：replication.factor≥3 + min.insync.replicas≥2 + unclean.leader.election.enable=false。
  • Consumer：手动提交offset（处理完再commit）+ 关闭自动提交enable.auto.commit=false。
20
Kafka 如何保证消息不重复消费？
Kafka幂等
  • 消费者幂等处理（核心）：业务层唯一键（订单号+业务类型）去重→Redis/DB记录已处理消息。
  • Producer幂等：enable.idempotence=true（PID+SequenceNumber去重）。
  • 事务消息：Kafka事务（但实际上不解决消费端重复）。

💡 重点：Kafka只能保证至少一次（at least once），消费端自己实现幂等！

Kafka ISR 是什么？min.insync.replicas的作用？
KafkaISR

ISR（In-Sync Replicas）：与Leader保持同步的副本集合。同步条件是replica.lag.time.max.ms内追上Leader。

min.insync.replicas：最少同步副本数。

  • 配合acks=all使用，确保消息至少写入ISR中这么多副本。
  • 设为≥2可保证Leader宕机不丢数据。
  • ISR数量 < min.insync.replicas时，生产者写入失败→不丢数据。

RabbitMQ 如何保证消息不丢失？
RabbitMQ
  • Producer→Exchange：Publisher Confirm机制（confirmCallback）。
  • Exchange→Queue：mandatory=true + returnCallback（消息退回处理）。
  • Queue→Broker持久化：Queue、Message都持久化（delivery_mode=2）。
  • Consumer：手动ACK（acknowledge-mode: manual），处理完再ack。
23
RabbitMQ 死信队列和延迟队列？
RabbitMQ

死信（DLX Dead Letter Exchange）：消息被拒绝+NACK+不重回队列、消息TTL过期、队列满时进入DLX。

延迟队列：设置消息TTL+死信队列实现。消息发到设置了TTL的队列→过期后→进入DLX→消费者监听DLX绑定的队列。

注意：不同TTL的消息可能不按预期顺序消费（队列头消息TTL最长会阻塞后面的）。可用插件rabbitmq_delayed_message_exchange精确延迟。

ES 写入数据和搜索数据的流程？
ES深入

写入流程：

  1. 请求到协调节点→路由到目标分片（hash(routing/doc_id) % num_primary_shards）。
  2. 写入主分片→主分片同步到副本分片→客户端确认。
  3. 先写translog→再写内存buffer→refresh(默认1s)后生成segment→可搜索。
  4. translog大到阈值→flush到磁盘→清空translog。

搜索流程（两阶段）：

  1. Query Phase：协调节点广播到所有分片→各分片返回(size+from)条文档ID+排序值。
  2. Fetch Phase：协调节点排序后，根据ID去对应分片获取完整文档。

ES 倒排索引原理？
ES高频

倒排索引：词项(Term)→文档列表的映射。

结构：

  • Term Dictionary：排序的词项目录（B-Tree/Trie，快速定位）。
  • Posting List：每个Term对应的文档ID列表（跳跃表Skip List加速交集/并集运算）。
  • Term Index：Term Dictionary的索引（FST有限状态转换器，压缩高效查找前缀）。

搜索"Java框架"→分词为Java+框架→分别查倒排索引→取文档ID交集→返回结果。

TCP 三次握手和四次挥手？
网络基础

三次握手：

  1. 客户端→SYN=1, seq=x →服务器（SYN_SENT）。
  2. 服务器→SYN=1, ACK=1, seq=y, ack=x+1 →客户端（SYN_RCVD）。
  3. 客户端→ACK=1, seq=x+1, ack=y+1 →服务器（ESTABLISHED）。

为什么是三次？防止已失效的连接请求到达服务器（历史SYN）。

四次挥手：

  1. 客户端→FIN→服务器（FIN_WAIT1）。
  2. 服务器→ACK→客户端（CLOSE_WAIT）。
  3. 服务器→FIN→客户端（LAST_ACK）。
  4. 客户端→ACK→服务器（TIME_WAIT, 2MSL后CLOSE）。

💡 TIME_WAIT=2MSL，确保最后的ACK能重传到对端。

HTTP 和 HTTPS 的区别？HTTPS 握手流程？
网络HTTPS

区别：HTTPS = HTTP + SSL/TLS，加密传输。端口443（HTTP为80）。需要CA证书。

TLS 1.2握手（简化）：

  1. Client Hello：支持的加密套件+随机数。
  2. Server Hello：选定的加密套件+随机数+证书。
  3. 客户端验证证书，生成PreMasterSecret（公钥加密）。
  4. 双方从3个随机数生成会话密钥（对称加密）。
  5. Finished确认握手完成。

💡 TLS 1.3只需1-RTT，比1.2少一轮。

Cookie、Session、Token（JWT）的区别？
认证高频
  • Cookie：存客户端浏览器，每次请求自动带上，有跨域限制，4KB限制。
  • Session：存服务端，Cookie存SessionID关联。分布式需共享存储。
  • Token（JWT）：无状态，客户端存储（localStorage/header），服务端无存储压力，适合分布式和移动端。

💡 JWT注意：Payload不加密（base64），敏感信息不存。设置合理过期时间+refreshToken机制。

设计模式六大原则（SOLID）是什么？
设计模式基础
  • S 单一职责：一个类只负责一件事。
  • O 开闭原则：对扩展开放，对修改关闭。
  • L 里氏替换：子类可以替换父类（子类不改变父类行为）。
  • I 接口隔离：接口尽量小，不强迫实现不需要的方法。
  • D 依赖倒置：依赖抽象而非具体实现（面向接口编程）。

💡 还有：迪米特法则（最少知识）、合成复用原则（组合优于继承）。

OAuth 2.0 和 SSO 单点登录原理？
认证OAuth2

OAuth 2.0四种授权模式：

  • 授权码模式（最安全）：第三方→授权服务器→获取授权码→换AccessToken。适用于有后端的应用。
  • 隐式模式：直接返回Token（已不推荐）。
  • 密码模式：用户直接把密码给第三方（内部系统登录）。
  • 客户端凭证：服务器间调用。

SSO原理：多个系统共用认证中心（CAS）。A系统登录→认证中心建Session+发Ticket→B系统校验Ticket→免登录。

DDD 领域驱动设计核心概念？
DDD架构

核心概念：

  • 实体(Entity)：有唯一标识，可变。
  • 值对象(Value Object)：无唯一标识，不可变（如地址、金额）。
  • 聚合(Aggregate)：一组相关对象的集合，聚合根是入口。
  • 仓储(Repository)：领域对象的持久化接口。
  • 领域服务：不适合放在实体/值对象中的业务逻辑。
  • 领域事件：领域内发生的有意义事件。
  • 限界上下文(Bounded Context)：领域模型的边界，微服务拆分的依据。

Maven 依赖传递和冲突解决？
Maven构建

依赖传递：引入A→A依赖B→B也被引入。scope影响传递（compile可传，provided/test不传）。

冲突解决：

  • 最短路径优先：A→B→C(1.0) > A→D→E→C(2.0) →选C(1.0)。
  • 第一声明优先：同路径深度，先声明的依赖优先。
  • 手动排除：<exclusions><exclusion>排除不需要的传递依赖。
  • 指定版本：<dependencyManagement>统一管理版本。
  • mvn dependency:tree查看依赖树，定位冲突。
